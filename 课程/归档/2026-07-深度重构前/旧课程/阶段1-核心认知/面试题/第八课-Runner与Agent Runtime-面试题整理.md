# 第八课面试题整理

## 题目 1

**问题：** 为什么 Agent 系统几乎一定要有循环，而不是一次模型调用加一次工具执行就结束？

**参考答案：** 因为在真实任务中，模型通常无法提前知道一次 Tool 调用是否足以完成任务。很多任务需要多轮观察、决策和执行，例如先下载项目、再读 README、再读配置、再搜索关键依赖，直到模型认为任务完成为止。因此 Agent 的本质是一个不预先确定轮数的闭环系统，而不是固定一次请求、一次执行就结束的流程。

**追问方向：** 这和 Workflow 的固定步骤机制有什么本质区别？

**易错点：** 以为 Tool Calling 只会发生一次，忽略多轮决策的必要性。

## 题目 2

**问题：** 为什么说现代 Agent 本质上是一个 State Machine？

**参考答案：** 因为 Agent 的运行过程可以抽象为一系列状态之间的流转，例如开始、调用模型、接收响应、判断是否存在 Tool Call、执行工具、回传结果、再次调用模型、最终结束。系统的核心不是单次函数调用，而是根据条件在这些状态之间不断切换。这种“状态 + 转移”的结构，本质上就是状态机，因此很多 Agent 框架最终都会走向显式状态管理或图结构表达。

**追问方向：** 状态机视角相比“循环视角”多带来了什么工程价值？

**易错点：** 只记住有个 `while True`，却没有意识到背后其实是状态流转。

## 题目 3

**问题：** 为什么可以把 Agent 类比为 Event Loop，而不只是多轮调用模型？

**参考答案：** 因为 Agent 在运行时会不断接收模型返回的事件，例如普通消息、Tool Call、后续动作指令等，然后根据事件类型执行对应处理，再等待下一轮事件。这种“收到事件 - 处理事件 - 等待下一事件”的模式，与操作系统事件循环、GUI 程序和 Node.js 的事件驱动模型高度相似。把 Agent 视为 Event Loop，有助于更准确理解它的运行机制和后续框架抽象。

**追问方向：** Event Loop 视角会如何影响 Agent 的代码组织方式？

**易错点：** 把 Agent 简化成“多次 API 调用”而忽略事件分派机制。

## 题目 4

**问题：** 为什么成熟 Agent 框架会把系统拆成 LLM、Tool Manager、Memory、Runner、Session 等模块？

**参考答案：** 因为这些部分承担的是完全不同的职责。LLM 负责推理与决策，Tool Manager 负责工具注册和执行，Memory 负责历史与长期信息，Runner 负责驱动整个 Loop，Session 负责组织某次运行的上下文状态。把它们拆开可以降低耦合、增强扩展性，也更符合真实运行时系统的复杂度。如果全部揉在一个类或文件里，系统会很快失去可维护性。

**追问方向：** 这些模块中，哪一层最容易在早期项目中被错误设计成“什么都管”？

**易错点：** 觉得模块拆分只是代码风格问题，而不是运行时职责划分。

## 题目 5

**问题：** 为什么很多现代框架倾向于设计 `Runner.run(agent)`，而不是简单的 `agent.run()`？

**参考答案：** 因为 Agent 和 Runner 的职责并不相同。Agent 更适合承载能力定义，例如 Prompt、Tool 集合、行为边界等；Runner 则负责实际运行，包括驱动循环、管理状态转移、处理工具调用和会话过程。把运行逻辑从 Agent 本体中拆出来，符合单一职责原则，也让同一个 Runner 能够运行不同 Agent，甚至支持 Multi-Agent 编排，因此更适合作为框架层抽象。

**追问方向：** 如果未来支持多个 Agent 协作，Runner 会承担哪些额外职责？

**易错点：** 以为 Runner 只是语法包装，没有看到它背后的运行时价值。

## 题目 6

**问题：** 为什么说 Agent 更准确地理解为 Runtime，而不是一个普通 Python 类？

**参考答案：** 因为真正运行中的 Agent 不只是一个类实例，它还包含当前 Prompt、Memory、Tool 集合、Session、State、Loop 和执行上下文等动态要素。类定义只是静态结构，而 Agent 真正体现能力的是运行时状态与状态流转过程。因此把 Agent 理解为 Runtime，能更准确地解释为什么现代框架需要 Session、Runner、Memory、Checkpoint 等组件。

**追问方向：** 如果把 Agent 错看成“只是一个类”，后续最容易在哪些设计问题上卡住？

**易错点：** 把实例化对象等同于完整 Agent 系统。
