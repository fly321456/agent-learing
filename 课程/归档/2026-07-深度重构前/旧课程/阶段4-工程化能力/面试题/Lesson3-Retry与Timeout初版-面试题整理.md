# 阶段4 - Lesson 3 面试题整理

## 题目 1

**问题：** 为什么 Retry 不能简单理解成“失败就再试几次”？

**参考答案：** 因为不是所有失败都属于暂时性失败。像网络抖动、短暂 provider 异常可能适合重试，但 Tool 不存在、参数错误、业务逻辑 Bug 这类问题即使重试也不会自己恢复。Retry 的本质不是无脑重复执行，而是对“可能自行恢复的失败”增加一次边界明确的恢复机会。因此 Retry 必须有分类前提，而不是全局默认行为。

**追问方向：** 在 Agent 项目里，哪些错误最典型地适合 Retry，哪些最典型地不适合？

**易错点：** 把 Retry 当成通用止损手段，而不是有限策略。

## 题目 2

**问题：** 为什么 Timeout 的第一价值不是“更快”，而是“不给系统无限等待的机会”？

**参考答案：** 因为在 Agent 系统里，某一层一旦挂住，例如 Tool 卡死或模型调用迟迟不返回，整个 Loop 就可能一直悬在那里，既没有结果也没有明确失败信号。Timeout 的作用首先是为这些不确定等待设置一个强制边界，让系统在超时后能进入可控状态，而不是无限挂起。它首先解决的是系统边界问题，然后才顺带改善响应效率。

**追问方向：** Agent 项目里最应该优先加 Timeout 的通常是哪几层？

**易错点：** 把 Timeout 单纯理解为性能优化策略。

## 题目 3

**问题：** 为什么当前阶段最适合先在 LLM 调用层加 Retry？

**参考答案：** 因为 LLM 调用层最容易遇到临时性失败，例如网络波动、provider 抽风或短暂请求错误，这些问题往往确实可能通过有限重试恢复。而 Tool 层的很多错误则更可能是逻辑错误或输入错误，不适合默认重试。因此从工程性价比上看，第一版 Retry 更适合先落在 `OpenAILLM.generate()` 这种 provider 交互边界上。

**追问方向：** 如果未来有多个 provider，Retry 策略会怎么进一步复杂化？

**易错点：** 不区分 provider 边界失败和业务逻辑失败。

## 题目 4

**问题：** 为什么说 Retry 必须有上限、有理由、有记录？

**参考答案：** 因为没有上限的 Retry 很容易变成死循环；没有理由的 Retry 会把根本不该重试的问题重复执行；没有记录的 Retry 会让排查者根本不知道系统到底失败了几次、最终为什么停下。Agent 工程中的 Retry 必须是可控的运行时策略，而不是遇错就盲重来。因此它必须同时满足“上限明确、适用范围明确、过程可观察”。

**追问方向：** 如果日志和 tracing 没跟上，Retry 会在哪些方面反而加大排障难度？

**易错点：** 觉得有 Retry 就等于系统更稳，而忽略失控重试反而更危险。

## 题目 5

**问题：** 为什么 Runner 是最小失败策略的最终执行者？

**参考答案：** 因为 Runner 负责驱动整个运行生命周期，它最适合决定“这次失败后还要不要继续”“达到上限后是否终止”“当前 Loop 是否应该结束”。虽然 ToolManager 和 LLM 层更接近具体错误来源，但真正把这些局部错误转换成整体运行策略的，是 Runner。它是运行时边界的最终控制层，因此应该承担最小失败策略的执行责任。

**追问方向：** 如果把所有 Retry / Timeout 逻辑都塞进 Runner，会有什么坏处？

**易错点：** 以为 Runner 既然负责运行，就应该理解所有底层错误细节。

## 题目 6

**问题：** 为什么说 Retry 不应该破坏错误边界，而应该建立在错误边界之上？

**参考答案：** 因为只有先在正确层级识别错误类型，系统才能知道这类错误到底值不值得重试。如果 ToolManager、LLM 层和 Runner 之间没有清晰边界，Retry 就只能变成“看到异常就重来”的盲策略，既不安全也不可解释。正确做法是先由各层识别错误语义，再由运行时根据语义决定是否重试，这样 Retry 才是分层控制能力，而不是全局补丁。

**追问方向：** 这个原则未来会如何影响 fallback、checkpoint 和恢复机制设计？

**易错点：** 把 Retry 当成可以替代错误建模的捷径。
