# Lesson7：Memory 分层设计初版 - 面试题整理

## 1. 为什么说 Session 不等于 Memory？

### 参考答案

因为两者解决的问题层级不同。

### Session

主要负责：

- 当前会话消息管理
- 当前上下文组织
- 当前 summary 和压缩状态

它服务的是：

> **这一次对话怎么继续**

### Memory

主要负责：

- 跨会话信息保存
- 长期可复用信息沉淀
- 稳定事实与偏好管理

它服务的是：

> **下次任务还能不能接着做**

所以 Session 更像短期工作记忆容器，Memory 更像长期信息保留机制。

---

## 2. 为什么 Agent 需要做 Memory 分层，而不是只维护一个大记忆池？

### 参考答案

因为不同信息的生命周期、访问频率和使用场景都不同。

例如：

- 当前轮上下文需要每轮都参与推理
- 当前会话 summary 需要维持任务连续性
- 长期记忆只在相关任务时注入

如果把这些信息全部混在一个大池子里，会带来两个主要问题：

1. 上下文膨胀
2. 高价值信息被低价值噪音淹没

所以分层设计的本质是：

> **让不同生命周期的信息走不同路径。**

---

## 3. 一个最小可用的 Agent 记忆分层模型可以怎么设计？

### 参考答案

当前阶段可以先采用三层模型：

### 第一层：当前轮上下文

包括：

- 当前输入
- 当前输出
- 最近几条即时消息

### 第二层：当前会话压缩记忆

包括：

- summary
- 阶段性结论
- 当前任务的压缩状态

### 第三层：长期记忆

包括：

- 用户偏好
- 项目稳定事实
- 已验证关键发现

这个模型足够简单，也足够支撑后续扩展。

---

## 4. 长期 Memory 第一版更适合存哪些内容？

### 参考答案

第一版更适合存：

1. 用户级稳定偏好
2. 项目级稳定事实
3. 已验证的关键结论

例如：

- 用户偏好中文回答
- 当前项目使用 SpringBoot + Redis + MySQL
- 订单主流程位于 `OrderService`

这些信息共同特点是：

> **稳定、高价值、后续高概率仍然有用。**

---

## 5. 为什么“什么都存进 Memory”通常不是好设计？

### 参考答案

因为长期记忆不是原始日志仓库，而是高价值信息层。

如果什么都存，会导致：

- 噪音越来越多
- 检索相关性下降
- 后续推理被低质量信息干扰
- Memory 自己变得不可维护

所以好的 Memory 系统不是存得越多越好，而是：

> **筛选出最稳定、最值得复用的信息。**

---

## 6. 哪些内容不适合直接进入长期 Memory？

### 参考答案

通常不适合直接进入长期 Memory 的包括：

- 临时推理过程
- 未验证猜测
- 大段原始日志
- 一次性 Tool 输出全文
- 很快就会过时的执行细节

这些内容更多适合留在当前 Session，或者在必要时做压缩处理，而不是直接沉淀为长期记忆。

---

## 7. Memory 应该什么时候写入比较合理？

### 参考答案

第一版比较合理的写入时机通常有三类：

1. 任务阶段结束时
2. 明确发现稳定事实时
3. 用户偏好被明确表达时

这些时机有一个共同点：

> **信息已经相对稳定，不是瞬时噪音。**

所以 Memory 写入不应该是每轮自动全量记录，而应该是“在稳定结论出现时写入”。

---

## 8. Memory 应该什么时候读出比较合理？

### 参考答案

Memory 读出应该按任务相关性触发，而不是每轮无脑全部注入。

例如：

- 用户再次分析同一个项目时，读出项目事实和关键模块结论
- 用户继续写同一代码库时，读出之前确认过的架构信息和风格偏好

这说明：

> **Memory 最好是选择性注入，而不是全量回灌。**

---

## 9. `MemoryStore`、`Session`、`Runner` 各自应该负责什么？

### 参考答案

### `Session`

负责：

- 当前会话消息
- 当前 summary
- 当前上下文构建

### `MemoryStore`

负责：

- 长期信息存储
- 长期信息读取
- 信息分类管理

### `Runner`

负责：

- 在合适时机触发写入 Memory
- 在新任务或新阶段开始时读取相关 Memory

这种划分的核心思想是：

> **Session 管当前会话，MemoryStore 管长期信息，Runner 管时机与流程。**

---

## 10. 为什么说 Memory 和 RAG 相关，但不是同一个概念？

### 参考答案

因为两者关注点不同。

### Memory

更偏向：

> Agent 自己应该记住什么

### RAG

更偏向：

> Agent 需要时如何从外部知识源检索信息

Memory 更像内部沉淀的长期信息层，RAG 更像外部知识获取机制。

它们后续可以配合，但不能简单画等号。

---

## 11. 为什么说 Memory 的本质不是“存更多”，而是“分层存储不同生命周期的信息”？

### 参考答案

因为真正的问题从来不是“有没有地方存”，而是：

> **不同信息应该活多久、放在哪一层、什么时候被再次使用。**

如果不做生命周期区分，那么：

- 当前即时上下文
- 当前会话中间状态
- 长期可复用知识

都会混在一起，系统很快变乱。

所以 Memory 的本质是信息生命周期管理，而不是单纯扩容。

---

## 12. 如果让你设计一个最小版 Memory 系统，你会怎么做？

### 参考答案

我会先做一个简单的 `MemoryStore`，只保存三类信息：

1. 用户偏好
2. 项目稳定事实
3. 已验证关键发现

然后让 `Runner` 只在稳定结论出现时写入，在新任务开始时按相关性读取。

这样先把长期记忆作为独立层引入系统，后面再逐步升级到更复杂的检索与召回机制。

---

## 13. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> Agent 里的 Session 和 Memory 不是一回事。Session 管的是当前会话上下文，Memory 管的是跨会话长期可复用信息。工程上更合理的设计是做记忆分层，把当前轮上下文、当前会话 summary 和长期记忆分开管理。长期 Memory 应优先保存稳定、高价值、可复用的信息，而不是把所有原始过程都塞进去。
