# Lesson6：上下文压缩与摘要策略初版 - 面试题整理

## 1. 为什么仅靠消息裁剪通常不足以支撑复杂 Agent？

### 参考答案

因为裁剪只能解决“长度太长”的问题，但不保证“关键信息还能保留下来”。

如果直接删除旧消息，可能会丢掉：

- 用户真实目标
- 已完成的重要结论
- 关键中间发现
- 后续步骤依赖的状态信息

结果就是 Agent 虽然没有超出窗口，但会出现失忆、重复分析、推理链断裂等问题。

所以复杂 Agent 往往不能只依赖裁剪，还需要压缩策略。

---

## 2. 什么是上下文压缩？

### 参考答案

上下文压缩的本质是：

> **把长历史变成短结论。**

它不是简单删除，而是将旧消息中的关键信息提炼出来，保留成更短但仍然可用的上下文表示。

例如把多个文件分析过程压缩成：

- 当前任务目标
- 已完成事项
- 关键发现
- 下一步建议

这样既能减小上下文长度，也能保留系统运行状态。

---

## 3. 为什么说“裁剪”和“压缩”不是一回事？

### 参考答案

因为两者解决的问题不同。

### 裁剪

核心目标是：

> 快速降低上下文体积

特点是实现简单，但可能直接丢信息。

### 压缩

核心目标是：

> 在缩短长度的同时尽量保住关键信息

特点是信息保留更好，但实现更复杂。

所以成熟的 Agent 系统通常不是二选一，而是把两者结合起来使用。

---

## 4. 在 Agent 场景里，哪些内容更适合被压缩？

### 参考答案

通常更适合压缩的是：

1. 已经结束的旧轮次多步分析过程
2. 超长 Tool Result
3. 阶段性结论和中间发现

这些内容原样保留会很长，但压缩成结构化结论后，仍然对后续任务有价值。

---

## 5. 哪些内容不应该轻易压缩？

### 参考答案

通常不应该轻易压缩的包括：

1. `system prompt`
2. 最近几轮正在使用的上下文
3. 精确格式要求或原始关键数据

例如：

- 文件路径
- 命令参数
- JSON 字段
- 错误日志原文

如果这些内容被过度压缩，可能影响后续推理和执行的准确性。

---

## 6. 一个好的 summary message 本质上是什么？

### 参考答案

summary message 不只是“写一段总结文字”，它更本质地是：

> **旧上下文的压缩状态表示。**

也就是说，它应该尽量保留：

- 当前任务目标
- 已完成事项
- 关键发现
- 后续待办

所以在 Agent 工程里，summary 更接近“运行状态摘要”，而不是普通文章摘要。

---

## 7. 为什么固定摘要模板在 Agent 初版里很有价值？

### 参考答案

因为固定模板虽然不复杂，但已经能很好地服务 Agent 运行状态保留。

例如模板：

```text
任务目标：
已完成：
关键发现：
下一步建议：
```

这种结构比随意写几句摘要更工程化，因为它直接围绕任务执行需要的信息组织。

对于初版系统来说，这是一种低成本但高价值的方案。

---

## 8. 上下文压缩应该放在哪一层实现比较合理？

### 参考答案

更合理的职责划分通常是：

### `Session`

负责：

- 保存原始消息
- 持有 summary
- 管理上下文替换关系

### `Runner`

负责：

- 驱动循环
- 在合适时机触发压缩

### `Summarizer` 或 LLM 辅助逻辑

负责：

- 生成摘要内容

因此更准确的说法是：

> **Session 管状态，Runner 管流程，摘要器管内容。**

---

## 9. 第一版摘要系统一定要用 LLM 吗？

### 参考答案

不一定。

工程上通常有三种方式：

1. 规则式摘要
2. LLM 生成摘要
3. 混合式摘要

在课程当前阶段，第一版完全可以先从规则式或半规则式摘要开始。

因为当前更重要的是先建立：

- 压缩触发机制
- summary 的结构
- Session / Runner 的职责边界

而不是一开始就追求最强摘要质量。

---

## 10. 为什么说上下文压缩和 Memory 相关，但不是一回事？

### 参考答案

因为它们解决的问题层级不同。

### 上下文压缩

主要解决：

> 当前会话消息太长怎么办

属于短期工作记忆整理。

### Memory

主要解决：

> 跨会话信息如何保存和复用

属于长期记忆系统。

所以压缩更偏向“当前 session 的上下文优化”，而 Memory 更偏向“长期知识保留”。

---

## 11. 为什么说压缩策略是在“成本”和“失忆”之间找平衡？

### 参考答案

因为如果什么都不删，系统会出现：

- 成本高
- 延迟高
- 爆上下文窗口

如果删得太狠，系统又会出现：

- 忘记目标
- 重复工作
- 上下文断裂

所以压缩策略的真正作用是：

> **在有限资源下尽量保留任务连续性。**

这就是它的工程价值。

---

## 12. 如果让你设计一个最小版上下文压缩方案，你会怎么做？

### 参考答案

我会这样设计：

1. 在 `Settings` 中定义压缩触发阈值，例如 `summary_trigger_messages`
2. 在 `Session` 中增加 `summary` 字段
3. 当历史消息超过阈值时，把较旧消息压缩成一条结构化 summary
4. 保留 summary + 最近几轮原始消息

这样就形成了一个“裁剪 + 压缩”的最小可用方案。

---

## 13. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 在多轮 Agent 里，单纯裁剪历史只能控制长度，但不能保证信息连续性，所以通常还需要上下文压缩。压缩的本质是把长历史提炼成短结论，例如保留任务目标、已完成事项、关键发现和下一步计划。工程上更合理的设计是由 Session 管理 summary，Runner 负责触发压缩流程，从而在成本和记忆连续性之间找到平衡。
