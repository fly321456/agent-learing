# Lesson4：Config 管理初版 - 面试题整理

## 1. 为什么 Agent 项目需要单独做配置管理？

### 参考答案

因为 Agent 项目里有大量“会变化但又会被多个模块共享”的运行参数，例如：

- 模型名
- API Key
- Base URL
- 最大循环次数
- 超时时间
- 重试次数
- tracing 开关

如果把这些内容直接写死在业务逻辑里，会带来几个问题：

1. 切换环境困难
2. 修改参数必须改源码
3. 测试和生产配置难以隔离
4. 变化点和稳定逻辑耦合在一起

所以配置管理的本质是：

> **把运行时变化点从核心逻辑中分离出来。**

---

## 2. 为什么说配置不是“边角料”，而是工程主干的一部分？

### 参考答案

因为在工程系统里，系统是否稳定、是否易扩展，很多时候不取决于核心逻辑是否存在，而取决于：

- 运行参数是否清晰
- 环境切换是否简单
- 配置入口是否统一
- 不同模块是否共享同一份配置语义

一个 Demo 可以没有配置层，但一个长期维护的 Agent 项目如果没有配置层，后续会非常难扩展。

所以配置管理并不是附属工作，而是工程化的一部分。

---

## 3. Agent 项目里哪些内容适合放入配置，而不是写死在代码里？

### 参考答案

适合放入配置的通常是“可能变化”的内容，例如：

- `model`
- `openai_api_key`
- `openai_base_url`
- `max_turns`
- `request_timeout`
- `max_retries`
- `enable_tracing`
- `log_level`

不适合放入配置的是系统稳定逻辑，比如：

- Runner 的主循环结构
- Tool 调度流程
- Session 的职责边界

也就是说，配置管理应该管理“参数”，而不是“架构逻辑”。

---

## 4. 为什么 Runner 不应该自己直接写死 `max_turns=10`？

### 参考答案

因为 `max_turns` 属于运行策略，不属于 Runner 的核心职责。

Runner 的职责是：

- 执行循环
- 判断是否结束
- 处理模型输出

它不应该决定默认策略值。

如果写死在 Runner 里，会导致：

- 测试不方便调整
- 不同 Agent 难以复用 Runner
- 参数变更必须改实现代码

更合理的设计是：

> **Runner 使用配置，但不拥有配置来源。**

---

## 5. 为什么 `OpenAILLM` 不应该把模型名写死在实现里？

### 参考答案

因为模型名本身是可变项。

例如：

- 开发环境可能用轻量模型
- 生产环境可能用高质量模型
- 不同客户可能要求不同供应商

如果模型名写死在实现里，LLM 抽象层就失去了复用价值。

正确做法是：

> **把模型名作为配置注入到 LLM 实现中。**

这样外层逻辑就不需要随模型变化而修改。

---

## 6. 配置管理和依赖注入（Dependency Injection）有什么关系？

### 参考答案

配置管理通常会和依赖注入一起出现。

例如：

- `Settings` 在 `app.py` 中统一创建
- `OpenAILLM(settings)` 显式接收配置
- `Runner(settings=settings)` 显式接收配置

这意味着模块不会自己偷偷去读取外部环境，而是：

> **由上层把依赖传进来。**

这正是依赖注入的体现。

它的好处是：

1. 模块更容易测试
2. 依赖更清晰
3. 更容易替换实现
4. 更符合工程化设计

---

## 7. 为什么说“配置管理本质上是在解决变化点管理问题”？

### 参考答案

因为配置本身就是系统中的变化点集合。

例如：

- 模型会变
- 超时会变
- 重试策略会变
- tracing 开关会变
- 环境地址会变

如果不把这些变化点集中管理，它们就会散落在业务逻辑中，导致系统越来越难维护。

所以配置管理的核心不是“读环境变量”，而是：

> **统一管理系统中高频变化但不属于核心逻辑的内容。**

---

## 8. 一个最小可用的 `Settings` 类通常至少要包含什么？

### 参考答案

对于当前这个 Agent 课程项目，一个最小可用的 `Settings` 类通常至少应包含：

- `openai_api_key`
- `openai_base_url`
- `model`
- `max_turns`
- `request_timeout`
- `max_retries`

如果再稍微完整一点，还可以加入：

- `enable_tracing`
- `log_level`

这已经足够支撑一个单 Agent 的工程化初版。

---

## 9. 为什么这一阶段不一定要立刻引入 Pydantic Settings？

### 参考答案

因为当前阶段的核心目标是：

> **先建立正确的工程边界和职责拆分。**

Pydantic Settings 很好，但它解决的是“配置定义更优雅、更严格”的问题。

而我们当前更重要的问题是：

- 有没有配置层
- 配置是不是独立对象
- 模块是不是通过配置解耦

所以现在先用原生 Python 实现一个清晰的 `Settings` 类，更符合渐进式学习路径。

---

## 10. 如果让你设计 Agent 项目的配置层，你会怎么划分职责？

### 参考答案

可以这样设计：

### `config.py`

负责：

- 定义 `Settings`
- 读取环境变量
- 提供默认值

### `app.py`

负责：

- 创建 `Settings`
- 组装 `Agent`、`Runner`、`LLM`

### `llm.py`

负责：

- 使用 `settings.model`
- 使用 `settings.request_timeout`

### `runner.py`

负责：

- 使用 `settings.max_turns`
- 使用 `settings.max_retries`

这种划分的核心思想是：

> **配置集中定义，运行模块按需消费。**

---

## 11. 面试时可以怎样简洁总结这一课？

### 参考答案

可以这样回答：

> 在 Agent 工程里，配置管理的本质不是读取环境变量，而是把模型、超时、重试、循环上限等运行时变化点从核心逻辑里抽离出来，形成统一的 Settings 层。这样可以降低耦合、方便测试、支持多环境切换，也让 Runner、LLM、Tracing 等模块的职责边界更清晰。
