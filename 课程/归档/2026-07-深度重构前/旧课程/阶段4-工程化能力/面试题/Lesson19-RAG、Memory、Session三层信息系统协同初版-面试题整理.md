# Lesson19：RAG、Memory、Session 三层信息系统协同初版 - 面试题整理

## 1. 为什么当 Session、Memory、RAG 同时存在时，系统复杂度会明显上升？

### 参考答案

因为这三层都可能向模型提供信息，但它们的信息来源、时间尺度和用途不同。

一旦同时存在，就容易出现：

- 信息重复
- 信息冲突
- 信息竞争模型注意力
- 主线被背景信息或外部知识淹没

所以问题不再只是“有没有信息”，而是“信息之间如何分工、排序和治理”。

---

## 2. 为什么说 Session、Memory、RAG 不是三个并列塞信息的模块？

### 参考答案

因为它们本质上属于不同层次的信息系统：

### Session

代表当前任务的即时运行状态。

### Memory

代表系统内部沉淀下来的长期高价值记忆。

### RAG

代表当前任务需要时临时取回的外部知识。

如果把它们都当作“往上下文里塞点信息的来源”，系统就很容易混乱。

所以必须先理解它们的层次差异。

---

## 3. 从时间尺度上看，Session、Memory、RAG 分别解决什么问题？

### 参考答案

可以这样理解：

### Session

解决“现在正在发生什么”。

### Memory

解决“过去沉淀下来的哪些经验和事实还值得带上”。

### RAG

解决“当前缺少哪些外部知识，需要临时取回什么”。

也就是说：

> **Session 解决现在，Memory 解决过去沉淀，RAG 解决当前按需外取。**

---

## 4. 为什么在三层信息系统里，Session 通常应当拥有最高优先级？

### 参考答案

因为 Session 最接近当前任务的即时现实。

它通常包含：

- 当前阶段
- 当前目标
- 当前已完成事项
- 当前待完成事项
- 最近观察结果

这些信息是最“新鲜”的。

而 Memory 和 RAG 都可能不是最新的，甚至可能与当前状态不完全一致。

所以在冲突处理上，当前 Session 状态通常应优先于旧 Memory 和外部 RAG 信息。

---

## 5. 为什么 Memory 不应该和 Session 争夺“当前状态解释权”？

### 参考答案

因为 Memory 更适合提供：

- 长期背景
- 稳定事实
- 用户偏好
- 已验证历史结论

它不适合覆盖当前任务刚刚发生的新状态。

如果旧 Memory 与当前 Session 冲突，而系统又无脑高权重注入 Memory，就会误导模型继续沿着过时前提推理。

所以更合理的原则是：

> **Memory 提供背景，但不替代当前实时状态。**

---

## 6. 为什么 RAG 更适合作为外部参考层，而不是当前任务主状态层？

### 参考答案

因为 RAG 取回的是：

> **当前任务需要时临时获得的外部知识。**

它的作用是补充，而不是接管任务主线。

如果把 RAG 当作主状态层，就容易出现：

- 外部一般知识淹没当前本地现实
- 外部文档覆盖当前代码真实情况
- 任务主线被资料牵着走

所以更合理的定位是：

> **RAG 是外部参考层，不是当前任务的主状态层。**

---

## 7. 为什么三层信息不能无差别全量注入模型？

### 参考答案

因为无差别全量注入会带来：

1. 上下文膨胀
2. 主次不分
3. 信息冲突更难定位
4. 当前任务真正关键的信息被淹没

所以三层协同的关键不是“每层都塞进去”，而是：

> **每层都只在合适的位置、以合适的量进入上下文。**

---

## 8. 第一版三层协同原则通常可以怎么总结？

### 参考答案

一个很实用的第一版原则是：

> **Session 主线，Memory 背景，RAG 外援。**

也就是说：

- Session 负责当前任务推进
- Memory 负责提供长期背景
- RAG 负责补充外部知识

这个分工足以支撑第一版信息系统协同设计。

---

## 9. 为什么信息注入顺序本身也是一个工程问题？

### 参考答案

因为模型不是同时“平等理解”所有信息的。

如果把外部知识或长期背景放得过重、过前，就容易稀释当前任务主线。

更合理的思路通常是：

1. 先明确系统规则
2. 再明确当前 Session 状态
3. 再补充 Memory 背景
4. 最后按需补充 RAG 外部知识

这样模型会先抓住当前任务，再吸收背景和外部材料。

---

## 10. 为什么冲突处理在三层信息系统里必须被显式考虑？

### 参考答案

因为冲突几乎一定会发生。

例如：

- Session 有新结论，Memory 里还是旧结论
- 当前本地实现与外部文档最佳实践不一致
- summary 和 recent context 发生更新冲突

如果不显式定义冲突处理原则，模型只能自己猜，结果会非常不稳定。

所以至少要有第一版规则，例如：

> 当前实时状态优先于旧 Memory，当前实际观察优先于外部一般知识。

---

## 11. 为什么说多层信息协同最终还是会上升到“上下文治理”问题？

### 参考答案

因为无论你有多少信息层，最终都要回答同一个问题：

> **当前这一轮到底该把什么信息放进上下文，放多少，按什么角色放。**

所以：

- Token 管理
- Summary 压缩
- Memory 注入
- RAG 检索
- Session 状态治理

这些能力到最后都会重新汇合到上下文治理上。

只是现在治理对象从单一消息流升级成了多来源信息流。

---

## 12. 为什么这一步是从“会做模块”走向“会做系统协同”的分水岭？

### 参考答案

因为理解单个模块只是第一步。

真正的工程难点是当多个模块同时存在时：

- 怎么避免重复
- 怎么避免冲突
- 怎么避免互相稀释
- 怎么给它们分工和优先级

这才是系统设计能力的核心。

所以三层信息协同能力，标志着开发者开始从模块思维进入系统思维。

---

## 13. 如果让你设计一个第一版三层协同策略，你会怎么做？

### 参考答案

我会先明确三层边界：

1. Session 负责当前任务主状态
2. Memory 负责长期背景
3. RAG 负责按需外部知识

然后定义一个最小注入顺序：

1. Prompt / 系统规则
2. Session 当前状态
3. 少量相关 Memory
4. 少量相关 RAG 知识

最后补一个冲突处理原则：

> 当前实时状态优先于旧记忆，当前实际观察优先于外部一般知识。

这已经是一个很好的第一版。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 当 Agent 同时拥有 Session、Memory 和 RAG 时，关键问题不再是信息够不够，而是多层信息如何协同。工程上通常应把 Session 作为当前任务主线，Memory 作为长期背景，RAG 作为按需外部知识，并通过信息优先级、注入顺序和冲突处理规则避免重复、冲突和主线被淹没。这本质上是上下文治理问题的升级版。
