# Lesson25：多 Agent 引入前的成本意识——通信、同步、冲突与治理代价 - 面试题整理

## 1. 为什么说多 Agent 不是免费午餐？

### 参考答案

因为多 Agent 虽然能带来：

- 职责分离
- 角色清晰
- 更独立的反馈视角

但同时也会引入真实而显著的系统成本，例如：

- 通信成本
- 状态同步成本
- 冲突处理成本
- 调度复杂度
- 可观测性复杂度
- 评估复杂度

所以多 Agent 不是白拿的更强，而是用更高复杂度换更清晰的任务结构表达。

---

## 2. 为什么多 Agent 看起来总是很诱人？

### 参考答案

因为它天然带有几个强吸引力：

1. 角色更清晰
2. 结构更像真实团队
3. 听起来能力更强
4. 看起来更先进

但这些吸引力主要是结构直觉上的优势，不等于在当前任务里它一定是更划算的方案。

所以成熟工程判断必须进一步问：

> **值不值得。**

---

## 3. 多 Agent 的第一类高成本是什么？为什么？

### 参考答案

第一类高成本通常是：

> **通信成本。**

因为在单 Agent 里很多信息流动是隐含发生的，而一旦拆成多个角色，系统就必须显式处理：

- 传什么
- 什么时候传
- 以什么格式传
- 传多少

例如 Planner 的计划要如何交给 Executor，Executor 的结果怎么交给 Reviewer。

这会把原本隐藏在单个上下文内部的信息流，变成显式工程问题。

---

## 4. 为什么通信一旦显式化，就容易出现信息损耗？

### 参考答案

因为角色之间的交接几乎总是伴随：

- 压缩
- 转述
- 摘要
- 筛选

Planner 不可能把全部推理过程都交给 Executor，Executor 也不可能把全部原始细节都交给 Reviewer。

所以在 handoff 过程中很容易发生：

- 信息丢失
- 语义偏差
- 上下文断裂

这就是多 Agent 相比单 Agent 的一个天然代价。

---

## 5. 为什么状态同步会成为多 Agent 系统的核心问题？

### 参考答案

因为多个角色会分别持有自己的局部状态。

例如：

- Planner 看到的阶段状态
- Executor 看到的执行状态
- Reviewer 看到的验收状态

如果这些状态不同步，就会出现：

- 每个角色都以为自己是对的
- 任务阶段判断不一致
- 收尾与返工判断混乱

所以状态同步不是可选项，而是多 Agent 系统的核心复杂度来源之一。

---

## 6. 为什么“谁拥有真相”会成为多 Agent 中的重要设计问题？

### 参考答案

因为多 Agent 中容易出现多个角色都持有局部状态解释权的情况。

例如：

- 当前阶段由谁说了算？
- 任务是否完成由谁说了算？
- 某个冲突应该听 Planner、Executor 还是 Reviewer？

这本质上是：

> **状态主权（state authority）问题。**

如果这一层不清楚，系统会非常容易混乱。

---

## 7. 为什么多 Agent 系统里的冲突成本会显著上升？

### 参考答案

因为多角色之间天然可能出现显式分歧，例如：

- Planner 想继续探索，Reviewer 认为已经够了
- Planner 设计的路线和 Executor 在现场发现的现实不一致
- Executor 觉得完成了，Reviewer 认为风险未清

在单 Agent 里，这些冲突被压缩在一个推理流里。

而在多 Agent 中，它们会变成显式角色冲突，必须被裁决。

所以冲突治理成本会显著增加。

---

## 8. 为什么调度复杂度会在多 Agent 系统里显著上升？

### 参考答案

因为现在不再只是“一个 Agent 什么时候继续”，而是：

- 什么时候从 Planner 切到 Executor
- 什么时候从 Executor 交给 Reviewer
- Reviewer 打回后回到谁
- 某个角色卡住后整个系统如何处理

这意味着系统从简单的单循环，升级成了：

> **多角色工作流调度系统。**

调度复杂度自然显著上升。

---

## 9. 为什么多 Agent 会增加 tracing 和调试复杂度？

### 参考答案

因为在单 Agent 中，你主要关注：

- 哪一轮出了问题

但在多 Agent 中，你还要额外关注：

- 哪个角色先偏了
- 偏差如何传给下一个角色
- 哪次 handoff 丢了关键信息
- 是 Planner、Executor 还是 Reviewer 的问题

所以 tracing 不再只是单链路，而是多角色交互链路，归因复杂度会明显上升。

---

## 10. 为什么多 Agent 也会带来评估成本上升？

### 参考答案

因为评估不再只看“最终任务成功没成功”，还要区分：

- 是规划质量提升了，还是执行偶然救回来了
- 是 Reviewer 帮系统挡住了风险，还是只是让流程更慢了
- 每个角色分别对结果贡献了什么

这意味着评估维度会更细，分析也会更复杂。

所以多 Agent 带来的不是“更容易评估”，而是“需要更精细的评估体系”。

---

## 11. 为什么多 Agent 决策的正确顺序不是“能不能拆”，而是“值不值得拆”？

### 参考答案

因为技术上很多事情都可以拆，但工程上更重要的是：

> **拆分带来的收益，是否足以覆盖新增复杂度。**

如果一个任务：

- 复杂度中等
- 单 Agent 已能稳定完成
- 只是需要更清晰的角色逻辑

那很可能没必要真正引入多 Agent。

所以成熟工程师关心的不是“能不能”，而是“值不值”。

---

## 12. 什么样的任务更值得引入真正多 Agent？

### 参考答案

通常更值得引入多 Agent 的任务有几个特征：

1. 职责边界已经很稳定
2. 单 Agent 角色过载明显
3. 任务链路长且阶段清晰
4. 预期收益明显覆盖通信和治理成本

也就是说，不是“任务复杂一点”就值得拆，而是要看到结构性收益足够大。

---

## 13. 为什么很多项目更适合“单 Agent + 角色化逻辑”而不是立刻上多 Agent？

### 参考答案

因为这是一种非常实用的中间态。

它的优点是：

- 保留角色分工带来的清晰度
- 暂时不引入过高通信成本
- 状态仍然集中，便于调试
- 更适合作为渐进式演化路径

所以不是所有项目都必须在“单 Agent”和“多 Agent”之间二选一，很多时候中间态反而最稳。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 多 Agent 并不是免费午餐，它虽然带来角色分工和结构清晰的收益，但同时也显著增加通信、状态同步、冲突处理、调度、可观测性和评估成本。所以在工程上更重要的问题不是“能不能拆”，而是“值不值得拆”。很多任务更适合先做单 Agent 的角色化逻辑，再根据收益是否足够大决定是否进入真正多 Agent 结构。
