# Lesson27：真正进入多 Agent 实现前，先做一次可拆分性审计 - 面试题整理

## 1. 为什么在真正进入多 Agent 实现前，必须先做一次“可拆分性审计”？

### 参考答案

因为多 Agent 并不是轻量调整，而是会显著提升系统复杂度的结构升级。

一旦拆分，就会引入：

- 通信链路
- 状态同步
- handoff 设计
- tracing 复杂度
- eval 复杂度

所以不能靠“感觉复杂了”就直接拆，而应该先判断：

> **当前任务和系统是否已经满足可拆分条件。**

这就是可拆分性审计的意义。

---

## 2. 什么叫“可拆分性”？

### 参考答案

可拆分性可以理解为：

> **一个任务或系统，是否已经具备足够清晰的职责边界、状态边界和协作边界，使得拆分后系统复杂度不会失控。**

也就是说，不是只看“能不能拆”，而是看：

- 拆完之后角色是否清楚
- 状态是否还能维持一致
- 协作是否能稳定进行

这比“任务看起来复杂”要更严格得多。

---

## 3. 为什么“感觉复杂了”不能作为拆多 Agent 的充分依据？

### 参考答案

因为“复杂”可能来自很多不同来源：

- Prompt 乱
- Tool 差
- Session 不清
- RAG 噪音大
- review 流程缺失

这些问题很多都可以先在单 Agent 内通过结构治理解决。

如果仅仅因为“感觉复杂了”就拆分，很容易把局部设计缺陷误判成必须多 Agent 的结构需求。

---

## 4. 可拆分性审计的第一类核心问题是什么？

### 参考答案

第一类核心问题是：

> **任务结构是否真的已经稳定分化。**

也就是说，是否真的存在长期稳定、可重复出现的不同职责。

例如：

- 规划与执行长期分离
- 执行与校验标准明显不同
- 阶段切换稳定存在

如果这些结构还不稳定，那很可能还不适合真正拆。

---

## 5. 为什么“单 Agent 是否真的已经过载”也是审计中的核心问题？

### 参考答案

因为不是所有复杂任务都意味着单 Agent 不行。

更重要的问题是：

> **当前单 Agent 的问题到底是结构性过载，还是局部设计还没理顺。**

如果问题主要仍然来自：

- Prompt
- Tool
- Session
- RAG
- Memory

这些局部层面，那就不能算真正意义上的“单 Agent 过载”。

只有当这些都治理过后，系统仍然明显因为职责混合而不稳，才更说明值得拆。

---

## 6. 为什么角色边界清晰度是可拆分性的关键指标？

### 参考答案

因为多 Agent 不是随便“拆几个角色名”就行。

真正拆之前，至少应当能明确：

- 每个角色负责什么
- 每个角色不负责什么
- 每个角色输入是什么
- 每个角色输出是什么
- 谁拥有最终裁决权

如果这些说不清，说明角色只是概念上的，尚未达到可工程化拆分的成熟度。

---

## 7. 为什么 handoff 清晰度是一个“硬指标”？

### 参考答案

因为多 Agent 系统的核心难点之一就在于角色之间怎么交接。

如果 handoff 定义不清，例如：

- 交什么
- 交多少
- 交什么格式
- 是否带上风险信息

那么拆分后就很容易发生：

- 信息丢失
- 理解偏差
- 角色间反复误解

所以 handoff 是否能结构化定义，是判断系统能否稳定拆分的重要硬条件。

---

## 8. 为什么“状态主权”在可拆分性审计里非常关键？

### 参考答案

因为一旦多个角色同时存在，就很容易出现多个局部状态解释者。

这时系统必须回答：

- 当前 phase 谁定义
- 是否完成谁裁定
- 冲突时谁说了算

如果这些拆之前就无法清楚回答，那拆之后状态系统通常会迅速失控。

所以状态主权清晰，是多 Agent 稳定运行的重要前置条件。

---

## 9. 为什么治理能力不足时，多 Agent 往往不是加分项，而是放大器？

### 参考答案

因为多 Agent 会把已有系统问题显著放大。

如果当前系统在单 Agent 阶段都还没有基本的：

- tracing
- eval
- checkpoint
- state 管理

那么拆分以后只会变成：

- 更难观察
- 更难调试
- 更难评估

所以治理能力是多 Agent 之前的重要托底条件。

---

## 10. 为什么收益 / 成本比是可拆分性审计的最终收束点？

### 参考答案

因为即使前面的边界都能划出来，最终仍然要回到一个现实问题：

> **拆分带来的收益，是否足以覆盖新增复杂度。**

如果收益只是“感觉更优雅”，但：

- 通信复杂度增加很大
- 调度复杂度增加很大
- tracing 和 eval 成本明显提高

那通常就不值。

所以最终判断不能只看“能不能拆”，而要看“拆了值不值”。

---

## 11. 为什么说“可拆分性审计”本质上是在做架构风险控制？

### 参考答案

因为它的本质不是增加一个流程，而是避免你在不成熟时机引入过高复杂度。

换句话说，它是在帮助你把：

- 冲动式架构升级

变成：

- 风险受控的结构化决策

所以这一步并不是拖慢开发，而是在降低架构演化失败的概率。

---

## 12. 一个第一版可拆分性审计至少应该覆盖哪些维度？

### 参考答案

当前阶段至少建议覆盖七类维度：

1. 任务结构
2. 单 Agent 是否真的过载
3. 角色边界清晰度
4. handoff 清晰度
5. 状态主权
6. 治理能力
7. 收益 / 成本比

这七类已经能构成一个相当实用的第一版工程审计框架。

---

## 13. 如果让你简洁总结“可拆分性审计”的工程意义，你会怎么说？

### 参考答案

我会这样总结：

> 可拆分性审计的意义，是在真正进入多 Agent 实现前，先系统检查这个任务和当前架构是否已经具备足够清晰的职责边界、状态边界、handoff 结构和治理能力。它本质上是在控制架构升级风险，避免系统在不成熟时过早进入高复杂度结构。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 多 Agent 不应该靠直觉决定，而应该先做可拆分性审计。工程上至少要检查任务结构是否稳定分化、单 Agent 是否真的结构性过载、角色边界和 handoff 是否清晰、状态主权是否明确，以及现有 tracing / eval / checkpoint 等治理能力是否足够支撑拆分。只有这些条件成熟，多 Agent 才更可能带来真实收益而不是系统性混乱。
