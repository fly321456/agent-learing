# Lesson15：长任务检查点与可恢复运行初版 - 面试题整理

## 1. 为什么长任务 Agent 一定会遇到恢复问题？

### 参考答案

因为长任务天然运行时间更长，链路更多，中断风险也更高。

常见中断来源包括：

- 模型请求失败
- 网络波动
- Tool 报错
- 进程退出
- 超时
- 用户暂停

短任务里“从头再来”还能忍受，但长任务里会带来高成本、重复工作和更强不稳定性。

所以对于长任务 Agent 来说，恢复能力不是极端需求，而是常态需求。

---

## 2. 为什么“从头重跑”不是一个工程化答案？

### 参考答案

因为从头重跑会带来至少三个问题：

1. 重复成本高
2. 可能重复触发有副作用的 Tool
3. 重跑路径不一定与上次相同，系统表现更不稳定

所以从头再来在 Demo 场景可以接受，但在长任务工程系统里并不是成熟方案。

---

## 3. Checkpoint 的本质是什么？

### 参考答案

Checkpoint 的本质不是简单保存聊天记录，而是：

> **保存某个时刻可继续执行的运行状态。**

这里关键词是“可继续执行”。

也就是说，恢复后系统不仅要能回忆过去发生了什么，还要知道：

- 现在处于哪个阶段
- 已经完成了什么
- 还剩什么没做
- 下一步该从哪里接着来

这才是真正的 Checkpoint。

---

## 4. 为什么“保存历史消息”不等于“具备恢复能力”？

### 参考答案

因为历史消息更多只是原始轨迹。

而恢复能力需要的是结构化运行状态，例如：

- 当前 goal
- 当前 phase
- completed steps
- pending steps
- summary
- 当前 turn

如果只有消息，没有这些状态，系统恢复后仍然很难稳定判断：

- 自己当前在哪
- 哪些工作不该重复
- 下一步应该从哪里继续

所以保存消息只是恢复的一部分，不是完整恢复能力。

---

## 5. 一个最小可恢复的 Checkpoint 第一版至少应包含哪些内容？

### 参考答案

第一版通常至少建议包含：

1. 任务标识，例如 `run_id`
2. 当前目标，例如 `goal`
3. 当前阶段，例如 `phase`
4. 进展状态，例如 `completed_steps` 和 `pending_steps`
5. 当前 summary
6. 一部分 recent messages
7. 当前轮次信息，例如 `turn_id`

这些内容足以支撑系统从某个稳定点继续，而不是盲目重启。

---

## 6. 为什么 Checkpoint 不一定需要每轮都存？

### 参考答案

因为每轮都存会增加：

- 存储频率
- 序列化成本
- 状态同步复杂度

第一版更合理的做法通常是在关键稳定点存，例如：

- 阶段切换时
- 完成重要子任务后
- 即将执行高风险步骤前

这样既能保留恢复能力，又不会把系统复杂度一下拉太高。

---

## 7. 为什么 Checkpoint 最好建在状态相对稳定的位置？

### 参考答案

因为如果在半完成状态上做 checkpoint，恢复时容易出现歧义。

例如：

- Tool 已执行但结果未完全回填
- summary 正在更新但没写完
- completed / pending 只更新了一半

这会导致恢复后系统不知道：

- 应该重做前一步还是后一步
- 当前状态是否可信

所以更好的原则是：

> **Checkpoint 建在阶段性稳定点，而不是任意时刻。**

---

## 8. 第一版可恢复运行流程通常该怎么设计？

### 参考答案

第一版可以先采用简单流程：

1. 读取最近一个成功 checkpoint
2. 恢复 Session 状态
3. 从下一个未完成步骤继续
4. 恢复前先做状态一致性检查

这个流程虽然简单，但已经能把系统从“只能重跑”升级到“可以续跑”。

---

## 9. 为什么恢复前要做状态一致性检查？

### 参考答案

因为能读出状态不代表状态一定健康。

常见风险包括：

- checkpoint 写入时正好处于半更新状态
- 某些字段同步成功，某些失败
- 已有状态之间本来就存在冲突

如果不先校验，系统可能会带着坏状态继续运行，让后续问题更难排查。

所以恢复前的一致性检查是非常关键的一步。

---

## 10. 为什么 Checkpoint 和 Tracing 最好配合使用？

### 参考答案

因为两者解决的问题不同但互补：

### Checkpoint

回答：

> 从哪里继续跑

### Tracing

回答：

> 上一次是怎么跑到这里的

有了 tracing，你可以知道：

- 中断发生前最后一个成功步骤是什么
- checkpoint 与失败点之间发生了什么
- 为什么会在这里停下

所以：

> **Checkpoint 负责恢复，Tracing 负责解释。**

---

## 11. 为什么设计 Checkpoint 会反过来促进 Session 状态治理？

### 参考答案

因为当你真正尝试做恢复时，会立刻发现：

- 哪些状态定义不清
- 哪些阶段没有显式表达
- 哪些完成进展无法恢复
- summary 和 recent messages 关系是否混乱

也就是说，如果 Session 状态本身定义不成熟，Checkpoint 根本做不好。

所以 Checkpoint 的引入会倒逼你把 Session 设计得更结构化、更可恢复。

---

## 12. 为什么可恢复运行是 Agent 走向长期运行系统的重要分水岭？

### 参考答案

因为 Demo 世界观通常是：

- 启动
- 跑完
- 结束

而真实长生命周期系统的世界观是：

- 启动
- 运行
- 中断
- 恢复
- 继续

只有当系统具备恢复能力时，它才真正开始接近长期运行系统，而不是一次性演示程序。

---

## 13. 如果让你设计一个最小版 Checkpoint 机制，你会怎么做？

### 参考答案

我会先做下面几件事：

1. 定义一个最小 checkpoint 结构，至少包含 goal、phase、completed/pending、summary、run_id
2. 选择两个稳定点作为保存点
3. 实现读取最近 checkpoint 并恢复 Session 的能力
4. 恢复前做基本一致性检查
5. 从未完成步骤继续，而不是从头重跑

这样就形成了一个最小可运行的续跑能力。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 长任务 Agent 默认会遇到中断，所以恢复能力不是高级特性，而是基本能力。Checkpoint 的核心不是保存聊天记录，而是保存可继续执行的运行状态，例如 goal、phase、completed/pending、summary 等。工程上第一版通常选择稳定状态点做 checkpoint，恢复时先还原 Session，再做一致性检查，最后从未完成步骤继续运行。
