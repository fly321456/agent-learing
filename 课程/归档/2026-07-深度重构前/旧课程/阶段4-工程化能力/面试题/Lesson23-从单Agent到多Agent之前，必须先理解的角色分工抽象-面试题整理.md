# Lesson23：从单 Agent 到多 Agent 之前，必须先理解的角色分工抽象 - 面试题整理

## 1. 为什么说多 Agent 的起点不是“多几个模型实例”，而是“角色职责开始可分离”？

### 参考答案

因为多 Agent 的根本动因，不是模型数量本身，而是复杂任务里开始出现不同类型的工作。

例如一个复杂任务往往同时包含：

- 规划
- 执行
- 审查
- 汇总

这些职责如果长期混在一个 Agent 里，就容易造成角色过载。

所以多 Agent 的真正起点是：

> **任务结构内部出现了稳定、可分离的职责边界。**

---

## 2. 为什么单 Agent 在简单任务下通常是正确起点？

### 参考答案

因为在简单任务里，任务链路短、职责少、局部决策成本低。

例如：

- 读一个文件
- 查一个时间
- 做一次简单总结

这类任务中，一个 Agent 同时承担理解、调用 Tool 和组织回答，通常不会明显过载。

所以单 Agent 并不是落后方案，而是很多问题的合理起点。

---

## 3. 为什么任务一复杂，单 Agent 就容易出现“角色过载”？

### 参考答案

因为复杂任务往往不只是一种工作，而是多种不同性质工作的组合。

例如：

- 先规划路线
- 再执行动作
- 再审查结果
- 再整理输出

如果全部塞给一个 Agent，它就需要在同一个上下文和同一个决策流里不断切换角色。

这会带来：

- 全局和局部互相污染
- 审查不够独立
- 上下文负担加重

所以复杂任务下，单 Agent 容易出现角色过载。

---

## 4. 什么是“角色分工抽象”？

### 参考答案

角色分工抽象可以理解为：

> **把复杂任务中不同类型的职责，从“全塞给一个 Agent”改成“明确由不同角色承担”。**

这里关注的重点不是线程数或实例数，而是：

> **职责边界。**

也就是说，角色分工首先是逻辑层抽象，其次才可能发展成真正的多 Agent 运行结构。

---

## 5. 为什么 Planner / Executor / Reviewer 会高频反复出现？

### 参考答案

因为复杂任务在结构上天然会出现三类高频工作：

1. 决定怎么做
2. 真正去做
3. 判断做得对不对

这三类工作分别自然对应：

- Planner
- Executor
- Reviewer

所以它们不是某个框架“发明”的，而是复杂任务结构本身逼出来的角色。

---

## 6. 为什么“一个 Agent 同时做规划、执行、审查”会越来越不稳？

### 参考答案

因为这三类工作本身目标不同：

- 规划要保持全局视角
- 执行要关注局部动作
- 审查要保持独立判断

如果全部混在一个 Agent 里，常见问题包括：

- 规划被局部执行细节打断
- 执行路径影响后续审查客观性
- 同一上下文负担过重

所以问题通常不是“做不到”，而是：

> **随着复杂度上升，会越来越不稳。**

---

## 7. 为什么角色分工不一定一开始就意味着必须上多 Agent 实例？

### 参考答案

因为角色分工首先是一种架构思维，而不是部署形态。

第一阶段完全可以先在单个系统内部做逻辑分层，例如：

- `plan_step()`
- `execute_step()`
- `review_step()`

虽然还没有真正启动多个 Agent，但职责边界已经开始清晰。

这说明：

> **先学会分工，再决定是否拆成多实例，是更稳的工程路径。**

---

## 8. 哪些任务更值得引入角色分工？

### 参考答案

通常更值得引入角色分工的任务包括：

1. 目标复杂、步骤多的任务
2. 执行和判断标准明显不同的任务
3. 需要降低自我确认偏差的任务
4. 天然可分阶段的任务

例如：

- 大型项目分析
- 复杂 bug 修复
- 代码修改后再审查
- 长链路报告生成

这些任务都很容易自然长出角色分工需求。

---

## 9. 为什么角色分工本质上是在做“职责解耦”？

### 参考答案

因为原本耦合在同一个 Agent 身上的多种工作：

- 规划
- 执行
- 审查

现在被显式拆开了。

这和你前面学过的很多设计原则是一致的，例如：

- Agent 和 Runner 解耦
- Session 和 Memory 解耦
- Tool 和调用协议解耦

所以多 Agent 前置认知的本质，并不是“更多实例”，而是：

> **任务层职责解耦。**

---

## 10. 为什么角色分工会反过来提升可观测性和可调试性？

### 参考答案

因为当所有事情混在一个 Agent 里时，你很难判断问题到底出在哪一类工作上。

例如结果错了时，你不容易判断：

- 是规划不合理
- 是执行出错
- 还是审查没发现问题

而一旦角色边界更清晰，问题归因就更容易：

- Planner 错
- Executor 偏
- Reviewer 漏

这会显著提升可观测性和调试效率。

---

## 11. 为什么角色分工也会带来新的复杂度成本？

### 参考答案

因为角色分工不是零成本的。

引入分工后，系统需要额外处理：

- 协调成本
- 状态传递成本
- 上下文同步成本
- 调度复杂度

所以并不是所有任务都值得立刻进入多角色结构。

这也是为什么要先做职责分析，再决定是否上真正的多 Agent 实例。

---

## 12. 如果让你简洁总结“角色分工抽象”的工程意义，你会怎么说？

### 参考答案

我会这样总结：

> 角色分工抽象的核心意义，是在复杂任务里识别出不同性质的职责，并把它们从一个 Agent 的混合工作中拆出来。这样做的目的不是为了堆更多模型实例，而是为了降低角色过载、提高清晰度、增强调试能力，并为后续真正的多 Agent 架构打下职责边界基础。

---

## 13. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 多 Agent 的起点不是增加模型实例数量，而是复杂任务里开始出现稳定、可分离的角色职责，例如规划、执行、审查。Planner、Executor、Reviewer 之所以高频出现，不是框架设计巧合，而是任务结构自然分化的结果。工程上更合理的路径是先做角色分工抽象，再决定是否真的拆成多 Agent 运行结构。
