# Lesson10：Agent 调试方法论与故障定位流程

## 1. 本课目标

到这一课为止，你已经不是在学一个“能跑的 Demo”了。

你已经逐步拥有了一个工程级 Agent 的多个核心部件：

- `Runner`
- `Session`
- `Memory`
- `Tool`
- `LLM` 抽象层
- `Retry / Timeout`
- `Config`
- `Token / Context` 管理
- `Tracing`

但这时一个真正的工程问题才会出现：

> **当 Agent 结果不对时，你到底该从哪里开始查？**

这是很多初学者会卡住的地方。

因为 Agent 出错，往往不像普通函数那样简单。

普通函数可能是：

```text
输入错了

或者代码 bug
```

但 Agent 的错误往往更复杂：

- Prompt 误导了模型
- Tool Schema 写得不清楚
- Tool 返回了噪音结果
- Session 裁剪丢掉了关键上下文
- Summary 压缩错了重点
- Memory 注入了不该注入的信息
- LLM 做了错误决策
- Retry 掩盖了真正故障

所以：

> **Agent 调试不是“看最后一句回答”，而是分层排查整条运行链路。**

这一课的目标，就是把这个调试思维建立起来。

---

## 2. 为什么 Agent 调试比普通程序更难

因为 Agent 是一个多因素联动系统。

你看到的一个错误结果，背后可能来自很多层：

### 输入层

用户问题本身是否清晰？

---

### Prompt 层

系统提示词是否给错了方向？

---

### Tool 层

Tool 有没有被错误描述？

---

### Context 层

关键信息是不是被裁掉了？

---

### Memory 层

是不是读入了错误、过时或不相关的长期记忆？

---

### Runtime 层

是不是某一轮 turn 顺序错了，或者重试逻辑改变了行为？

---

### Model 层

模型本身是不是在某一步判断失误？

所以在 Agent 里，错误结果通常不是单点问题，而是：

> **链路级问题。**

这就决定了调试方法不能靠猜，而要靠流程。

---

## 3. 这一课最重要的一句话

请你先记住这句话：

> **Agent 调试的核心不是“找代码报错”，而是“找决策在哪一层开始偏离”。**

这和传统开发非常不一样。

因为很多 Agent 的问题甚至不会抛异常。

它只是：

- 没有报错
- 能正常输出
- 但结果就是不对

这类问题如果没有方法论，最容易陷入两种坏状态：

### 第一种

盲改 Prompt。

---

### 第二种

盲改 Tool。

---

### 第三种

盲加更多上下文。

这些都可能暂时碰巧有效，但并不是稳定的工程排查方式。

---

## 4. 调试 Agent 时最常见的错误姿势

很多人看到 Agent 回答错了，第一反应是：

> 模型太笨。

这通常是错误的起点。

因为在真实工程里，模型只是系统的一部分。

更常见的问题其实是：

- Tool 定义不清
- Memory 注入污染
- Prompt 把目标说歪了
- 上下文被裁坏了
- Tool Result 太长把关键信息淹没了

所以第一条调试纪律就是：

> **先不要怪模型，先看链路。**

这会极大提高你的排查效率。

---

## 5. 第一版调试流程：先分五层排查

为了让你在项目里真正可用，我们先建立一个很实用的五层排查框架。

### 第一层：输入与目标层

先问：

- 用户到底想让 Agent 做什么？
- Prompt 是否清楚表达了任务目标？
- Runner 是否把正确输入传给了模型？

这一步解决的是：

> **问题是不是从一开始就定义歪了。**

---

### 第二层：上下文层

再问：

- 这轮给模型的上下文到底包含了什么？
- system prompt 还在吗？
- recent messages 是否完整？
- summary 是否正确？
- 有没有被错误裁剪？

这一步解决的是：

> **模型做决策时到底看到了什么。**

---

### 第三层：Tool / Memory 层

再问：

- Tool Schema 是否足够清晰？
- Tool Result 是否可靠？
- Memory 注入是否相关？
- 有没有旧记忆误导当前任务？

这一步解决的是：

> **模型依赖的外部能力和历史信息是否健康。**

---

### 第四层：运行时层

再问：

- 这是第几轮开始跑偏？
- retry 有没有改变行为？
- timeout 是否中断了某个关键步骤？
- turn 流程是否符合预期？

这一步解决的是：

> **系统运行控制流程是否稳定。**

---

### 第五层：模型决策层

最后才问：

- 在上下文、Tool、Memory 都正常的前提下，模型是否依然做了错误判断？

这一步才是：

> **真正意义上的模型决策问题。**

这套顺序很重要，因为它能避免你一开始就跑去乱调 Prompt 或乱换模型。

---

## 6. 为什么“先看上下文”几乎总是高收益动作

很多 Agent 问题，一旦把“真正发送给模型的内容”打印出来，问题就已经暴露了。

例如：

- system prompt 被裁掉了
- recent messages 顺序错了
- summary 把重点总结反了
- memory context 注入了无关项目事实
- tool result 太长，关键信息被淹没

所以调试 Agent 时，一个非常高收益的原则是：

> **不要先猜模型怎么想，先看模型到底看到了什么。**

这句话你以后会反复用到。

因为模型的错误判断，很多时候只是“输入不良”的结果。

---

## 7. 为什么 Tool 层是第二高发故障源

除了上下文之外，Tool 层也是最常出问题的地方。

常见问题包括：

### Schema 描述太弱

导致模型不知道什么时候该调用 Tool。

---

### Tool 参数设计不合理

导致模型即使想调用，也容易构造错参数。

---

### Tool Result 质量差

例如：

- 返回太长
- 返回太乱
- 返回没有关键结论

---

### Tool 本身成功了，但工程语义失败了

比如文件读到了，但读的是不相关文件。

所以调试 Tool 时，不能只看“函数有没有报错”，还要看：

> **这个 Tool 输出的结果，是否真的帮助了模型做下一步决策。**

---

## 8. Memory 调试为什么特别容易被忽略

很多人做了 Memory 以后，Agent 一旦回答不对，第一反应还是去查 Prompt 或 Tool。

但长期记忆其实是一个非常强的“隐形影响源”。

因为 Memory 一旦注入错了，不一定会直接报错。

它会更隐蔽地影响模型：

- 让模型带着错误前提继续推理
- 让模型把无关旧知识当成当前事实
- 让模型忽略当前任务的新变化

所以只要系统里引入了 Memory，你就必须把下面这个问题加入排查清单：

> **这次回答是不是被一条错误或过时的长期记忆带偏了？**

这在真实项目里非常常见。

---

## 9. Tracing 在调试里的真正价值

上一课我们讲了 tracing 的事件流价值。

这一课你要把它真正用起来。

Tracing 在调试时最重要的作用有三个：

### 第一，定位偏离从哪一轮开始

不是所有错误都从第一步开始。

很多时候前几轮都是对的，只是在某一轮开始跑偏。

---

### 第二，定位是哪类事件先异常

例如：

- 先异常的是 context
- 还是 tool
- 还是 memory
- 还是 llm request

---

### 第三，定位是内容问题还是流程问题

内容问题：

- prompt / context / memory / tool result 质量问题

流程问题：

- retry / timeout / turn 顺序 / tool 回填流程问题

所以 tracing 的意义不是“多一份记录”，而是：

> **让调试从猜测变成定位。**

---

## 10. 一个非常实用的排障顺序

如果你现在就要排查一个 Agent 结果错误，我推荐你按下面顺序走。

### 第一步：看最终输入给模型的上下文

先确认：

- system prompt
- recent messages
- summary
- memory context
- tool results

是不是都合理。

---

### 第二步：看这次 run 的事件流

确认：

- 一共跑了几轮
- 每轮发生了什么
- 第几轮开始异常

---

### 第三步：看 Tool 调用链

确认：

- Tool 是否被正确选择
- 参数是否正确
- 输出是否高质量

---

### 第四步：看 Memory 读写链

确认：

- 有没有读入不相关记忆
- 有没有写入错误事实
- 有没有 summary 和 memory 冲突

---

### 第五步：最后才考虑 Prompt / Model 调参

只有前四步基本健康了，才去判断：

- Prompt 是否需要优化
- 模型是否需要切换
- temperature / reasoning 策略是否要改

这会让调试顺序非常稳。

---

## 11. 为什么“复现问题”是调试 Agent 的第一原则之一

你后面会发现一个现实：

很多 Agent 问题不是“永远错”，而是：

- 有时错
- 有时对
- 某些输入下错
- 某些轮次下错

所以调试第一步最好先做：

> **把问题尽量复现成一个稳定场景。**

例如固定：

- 用户输入
- 模型版本
- Tools 集合
- Memory 状态
- Config 参数

这样你才能区分：

- 是系统本身不稳定
- 还是输入变化导致结果变化

没有复现，调试很容易变成“玄学修 bug”。

---

## 12. 为什么“看最终答案”不如“看中间决策”

这一点你一定要建立起来。

初学者经常做的事是：

```text
问一个问题

看最后回答对不对
```

这只能判断结果，不足以定位原因。

更有工程价值的做法是看中间链路：

- 模型为什么选这个 Tool
- Tool 为什么返回这个结果
- 这个结果为什么又触发了下一轮动作

因为 Agent 的行为本质上是一个决策序列。

所以调试 Agent，不是只看“答案错了”，而是要看：

> **哪一步决策开始偏离了正确路径。**

---

## 13. 第一版调试清单可以长什么样

你可以给自己的项目准备一个非常实用的 Debug Checklist：

### 输入层

- 用户目标是否明确
- Prompt 是否和任务一致

### 上下文层

- system prompt 是否存在
- summary 是否正确
- recent messages 是否完整
- memory context 是否相关

### Tool 层

- Tool Schema 是否清晰
- Tool 参数是否正确
- Tool 结果是否高质量

### Memory 层

- 读入的记忆是否相关
- 写入的记忆是否稳定
- 是否存在过时记忆污染

### Runtime 层

- 第几轮开始异常
- retry / timeout 是否影响行为
- tracing 事件顺序是否正常

这份清单在企业里非常实用。

---

## 14. 这一课背后的核心工程思想

这一课表面在讲调试。

但本质上是在训练你一个更深的能力：

> **把“结果错误”拆解成“哪一层产生了偏离”。**

这就是复杂系统工程师和普通调 API 开发者的分水岭。

普通使用者会说：

> 怎么又答错了？

Agent 工程师会问：

> 是输入歪了、上下文坏了、Tool 误导了、Memory 污染了，还是模型在健康输入下做错了决策？

这个差别非常大。

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

给项目写一份固定的 Agent Debug Checklist。

---

### 第二件

让 tracing 支持按 `run_id` 查看完整事件流。

---

### 第三件

在调试输出中增加“最终上下文快照”能力。

至少能看到：

- system
- summary
- memory context
- recent messages

---

### 第四件

挑一个错误案例，真的按这节课的方法走一遍排查流程。

只有走过一遍，你才会真正掌握它。

---

## 16. 本课小结

今天最重要的三句话：

### 第一

> **Agent 调试不是找最后一句话为什么错，而是找决策在哪一层开始偏离。**

### 第二

> **先看模型看到了什么，再看模型做了什么。**

### 第三

> **没有调试流程的 Agent 开发，最终很容易变成盲调 Prompt。**
