# Lesson27：真正进入多 Agent 实现前，先做一次可拆分性审计

## 1. 本课目标

前面几课，我们围绕多 Agent 已经做了几次非常关键的铺垫：

- 先讲了角色分工抽象
- 再讲了 `Planner / Executor / Reviewer` 为什么会成为经典三角
- 接着讲了多 Agent 的真实成本
- 然后又做了一次反向校准：很多问题其实根本不需要拆

到这里，一个成熟的工程路线不能再停留在“我理解了这些道理”。

它必须进一步收束成一个可执行动作：

> **当你真的准备把一个系统从单 Agent 拆向多 Agent 时，到底该先检查什么？**

这就是这一课要解决的问题。

我们把这个动作叫作：

> **可拆分性审计（Split Readiness Audit / Decomposability Audit）**

它的目标不是告诉你“多 Agent 好不好”，而是系统性回答：

> **当前这个任务、这个状态系统、这套工具链，到底适不适合拆。**

这一步很关键，因为它会把你前面学到的所有“多 Agent 判断力”真正落到工程决策流程里。

---

## 2. 为什么在真正拆之前必须先审计

很多人进入多 Agent 的方式通常是：

```text
感觉复杂了

那就拆
```

或者：

```text
看别人这么做了

我也拆
```

这类决策方式最大的问题是：

> **它不是基于系统现状的判断，而是基于直觉和想象。**

而架构拆分一旦发生，后续往往会带来：

- 额外通信链路
- 状态同步逻辑
- handoff 结构
- 更复杂的 tracing
- 更复杂的 eval

也就是说，它不是轻量试验，而是：

> **一次真正会改变系统复杂度曲线的动作。**

所以在拆之前先审计，不是保守，而是成熟。

---

## 3. 这一课最重要的一句话

请记住：

> **多 Agent 不应该靠“感觉复杂了”来决定，而应该靠“当前系统是否已经满足可拆分条件”来决定。**

这句话非常重要。

因为它直接把“多 Agent 决策”从灵感式判断，升级成了：

> **结构化判断。**

很多系统之所以拆了以后更乱，并不是因为多 Agent 这个方向本身错，而是因为：

> **它拆得太早、拆得太盲、拆在了错误的时机。**

所以你现在要学会问的，不是：

> 能不能拆？

而是：

> **现在是不是已经到了值得拆、适合拆、拆了能稳住的阶段？**

这才是审计的意义。

---

## 4. 什么叫“可拆分性”

你可以先把它理解成：

> **一个任务或系统，是否已经具备足够清晰的职责边界、状态边界和协作边界，使得拆分后系统复杂度不会失控。**

注意这里有三个关键词：

### 职责边界

角色是否已经天然稳定分化。

---

### 状态边界

不同角色之间需要共享哪些状态，谁说了算。

---

### 协作边界

角色之间的输入输出是否已经足够清楚，可以形成稳定 handoff。

如果这三层都还模糊，那你其实不是在拆分，而是在：

> **把一个本来还没理顺的问题复制到更多角色里。**

这通常不会带来好结果。

---

## 5. 第一类审计：任务结构是否真的已经分化

这是最先要看的。

不是所有复杂任务都值得拆。

你首先要问：

> **这个任务内部，是否已经存在稳定、重复出现、可以长期保持的不同职责结构？**

例如：

### 适合拆的信号

- 规划与执行长期明显分离
- 执行与审查标准明显不同
- 同一任务中反复出现稳定阶段切换

---

### 不适合拆的信号

- 任务虽然复杂，但本质上还是一个连续主线
- 角色界限只是临时看起来像不同工作
- 每次任务都换一套分工，没有稳定模式

所以第一条审计原则是：

> **只有当任务结构本身稳定分化，角色拆分才更可能成立。**

---

## 6. 第二类审计：单 Agent 是否真的已经过载

这也是一个很关键的判断点。

很多人会把“任务复杂”直接等同于“单 Agent 不行了”。

但工程上更应该看的是：

> **当前单 Agent 的问题，到底是结构性过载，还是局部设计还没整理好。**

典型的“结构性过载”信号包括：

- 规划经常被执行细节打断
- review 很难保持独立视角
- 任务阶段推进长期混乱
- 即使 Prompt、Tool、Session 治理后，系统仍明显不稳

而如果问题主要还是：

- Prompt 乱
- Tool 差
- RAG 噪音大
- Session 不清

那就不能算“单 Agent 过载”，而更像：

> **单 Agent 还没治理到位。**

这两者必须严格区分。

---

## 7. 第三类审计：角色边界是否已经足够清楚

就算你觉得需要拆，也要继续问：

> **到底拆成什么？**

这一点很多人会跳过。

例如大家会笼统地说：

> 做成 Planner + Executor + Reviewer

但如果你继续追问：

- Planner 具体输出什么？
- Executor 具体接什么？
- Reviewer 判断什么？
- 谁来决定结束？

却答不清楚，那说明：

> **角色边界还不够成熟。**

所以真正适合拆的时候，应该至少能明确：

- 每个角色的职责边界
- 每个角色的输入
- 每个角色的输出
- 谁拥有最终裁决权

这就是角色清晰度审计。

---

## 8. 第四类审计：handoff 是否可以被清晰定义

这一步特别关键，但很容易被忽略。

多 Agent 系统的核心难点之一，不是角色有没有，而是：

> **角色之间怎么交接。**

所以审计时必须问：

### Planner -> Executor

交的到底是：

- 自然语言计划
- 结构化步骤
- 任务状态 + 下一步动作

---

### Executor -> Reviewer

交的到底是：

- 原始执行日志
- 摘要结果
- 风险清单
- 结果证明材料

如果 handoff 定义不清，那么多 Agent 一上来就会：

- 信息丢失
- 理解偏差
- 角色之间反复误解

所以：

> **handoff 清晰度是判断能不能拆的硬指标。**

---

## 9. 第五类审计：状态主权是否能被定义

这是多 Agent 很容易翻车的一层。

在单 Agent 里，状态虽然复杂，但“真相”通常还是相对集中。

到了多 Agent，你必须回答：

> **谁拥有哪个状态的解释权？**

例如：

- 当前阶段由谁定义？
- 当前是否完成由谁裁定？
- 发生冲突时听谁的？

如果这些问题拆之前就答不出来，那拆之后很可能会陷入：

- 角色互相覆盖
- 状态彼此矛盾
- tracing 很难归因

所以：

> **状态主权清晰，是多 Agent 可拆分性的核心条件之一。**

---

## 10. 第六类审计：当前治理能力是否足够支撑拆分

这点特别重要。

很多人觉得多 Agent 是“结构升级”，但忽略了：

> **结构升级必须有治理能力托底。**

拆分前，你至少要看当前系统是否已经具备一定的：

- tracing 能力
- eval 能力
- checkpoint 能力
- state 管理能力
- review / debug 能力

为什么？

因为如果这些在单 Agent 阶段都还没有基本做起来，那多 Agent 只会把问题变得更难看见、更难调、更难评估。

所以：

> **治理能力不足时，多 Agent 往往不是加分项，而是放大器。**

---

## 11. 第七类审计：收益是否真的覆盖新增复杂度

这一步其实是前面所有审计的收束点。

最终你还是要回到一个非常现实的问题：

> **拆了以后，收益到底值不值这些成本？**

你可以从几个角度看：

### 潜在收益

- 任务成功率显著提升
- 规划更稳
- 审查更独立
- 长任务更可控

---

### 新增成本

- 通信
- 同步
- handoff
- 冲突治理
- tracing 复杂度
- eval 复杂度

如果收益只是“好像优雅一点”，那通常不够。

真正值得拆的时候，应该是：

> **拆分能带来明显工程收益，而不仅是结构美感。**

---

## 12. 为什么“可拆分性审计”本质上是在做架构风险控制

这一点非常值得你抓住。

很多人会把审计理解成：

> 多了一张检查表

但它更深层的意义其实是：

> **防止你在不成熟的时机引入过高复杂度。**

也就是说，审计的本质不是“慢”，而是：

> **用系统化判断替代架构冲动。**

这就是成熟工程决策的味道。

所以这一步并不是额外负担，而是：

> **一种架构风险控制机制。**

---

## 13. 第一版可拆分性审计表可以长什么样

你现在完全可以先用一个非常朴素但非常实用的审计表：

### 维度 1：任务结构

- 职责是否稳定分化
- 阶段是否清晰

### 维度 2：单 Agent 状态

- 当前问题是否真是结构性过载
- 是否已排除局部设计缺陷

### 维度 3：角色边界

- 每个角色职责是否清晰
- 输入输出是否明确

### 维度 4：handoff

- 交接内容能否结构化
- 交接后是否容易丢信息

### 维度 5：状态主权

- 谁决定 phase
- 谁决定完成
- 谁处理冲突

### 维度 6：治理能力

- tracing 是否足够
- eval 是否足够
- checkpoint 是否足够

### 维度 7：收益 / 成本比

- 收益是否明显覆盖复杂度成本

这已经是一个非常强的第一版工程审计框架。

---

## 14. 为什么这一步会让你真正具备“多 Agent 架构判断方法”

到前面为止，你已经有了很多零散判断力：

- 什么时候需要角色分工
- 为什么经典三角常见
- 多 Agent 会带来哪些成本
- 为什么很多问题根本不需要拆

而这一课做的事情，就是把这些判断力收束成一个系统方法。

也就是说，从这一课开始，你不再只是“有感觉”，而是开始拥有：

> **一套在真正架构决策前可执行的评估方法。**

这就是为什么这一课特别重要。

它标志着你开始从“概念理解”走向“工程判断方法化”。

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑一个你当前最复杂、最像“想拆多 Agent”的任务。

---

### 第二件

用本课的七个维度，给它做一遍“可拆分性审计”。

---

### 第三件

明确写出这次审计的结论：

- 现在不适合拆
- 适合先做单 Agent 角色化逻辑
- 已经具备拆分条件

---

### 第四件

如果结论还不适合拆，继续写出：

> 拆之前还缺哪些前置条件。

这一步会非常有价值。

## 16. 本课小结

今天最重要的三句话：

### 第一

> **多 Agent 不应该靠“感觉复杂了”来决定，而应该靠“当前系统是否已经满足可拆分条件”来决定。**

### 第二

> **可拆分性审计的核心，是检查职责边界、状态边界、handoff 边界和治理能力是否已经成熟。**

### 第三

> **这一步的本质不是拖慢架构升级，而是在控制架构升级风险。**
