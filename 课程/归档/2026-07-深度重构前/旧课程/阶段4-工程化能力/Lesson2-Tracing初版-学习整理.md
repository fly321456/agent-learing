# 阶段4 - Lesson 2 学习整理

## 本节定位

上一节我们已经给最小 Agent Framework 加上了第一层可观测性：

> Logging 初版

现在系统已经开始能回答这些问题：

- Runner 开始了吗
- LLM 被调用了吗
- Tool 执行了吗
- 哪一层报错了

但如果你真的开始排查一次完整运行，很快会发现另一个问题：

> 我知道发生了很多事，但我不确定这些事是不是同一次运行里的

这就是 Logging 的天然边界。

所以这一节要补上的，不是更多日志，而是：

> Tracing 初版

它的目标不是替代 Logging，而是把一次运行中的关键事件串起来。

---

## 本节目标

给当前 Agent 项目增加一个最小 Trace 机制，让一次运行具备：

1. 唯一标识
2. 关键步骤串联
3. 后续日志可归属于同一条运行链路

也就是说，这一节要让系统从：

```text
能看到很多分散日志
```

升级为：

```text
能看到“这一轮运行到底经历了什么”
```

这一步一旦做出来，后面调试：

- Tool 调度问题
- 多轮 Loop 问题
- Session 状态问题

都会容易很多。

---

## 本节核心知识点

### 1. Logging 和 Tracing 解决的不是同一个问题

这两个词经常被混着用，但在工程上它们关注点不同。

#### Logging 关注

```text
发生了什么
```

例如：

- 调用了 LLM
- 执行了 Tool
- 发生了错误

#### Tracing 关注

```text
这一连串事情是不是同一次运行里的，以及它们的先后关系是什么
```

例如：

- 这条 Tool 日志对应哪次用户请求
- 这次 LLM 调用前面是不是已经做过一次 Tool
- 这次错误属于哪条运行链路

所以可以简单理解成：

- Logging 让你看见点
- Tracing 让你看见线

---

### 2. 对 Agent 来说，Tracing 比很多普通项目更早变重要

普通 CRUD 系统里，一次请求往往执行路径相对稳定。

但 Agent 不一样，因为一次运行可能经历：

```text
用户输入
↓
LLM
↓
Tool 1
↓
LLM
↓
Tool 2
↓
LLM
↓
最终答案
```

如果没有 Trace，你虽然能看到很多日志，但很容易搞不清：

- 哪条日志属于哪轮运行
- 哪一步对应哪次 Tool Call
- 错误之前到底已经做到了哪一步

所以在 Agent 项目里，Tracing 往往会比很多普通小项目更早变得有价值。

---

### 3. 当前阶段的 Tracing 不需要复杂平台，只需要先把“运行链路身份”建立起来

很多人一听 Tracing，就会想到：

- OpenTelemetry
- Jaeger
- Span 树
- 复杂链路平台

这些以后都重要，但当前阶段不需要一步到位。

当前阶段最重要的是先建立：

> 一次运行要有 trace_id

也就是说，至少先做到：

- Runner 每次开始运行时生成一个 `trace_id`
- 这次运行中所有关键日志都带上这个 `trace_id`
- Tool 执行、LLM 调用、错误输出都能关联回这条 trace

这一版已经足够让 Tracing 从“概念”变成“有实际工程价值的机制”。

---

## 本节推荐的最小设计

这一节建议先不引入复杂库，先做一个最小版本。

### 方案：TraceContext 初版

例如增加一个非常小的对象：

```python
class TraceContext:
    def __init__(self, trace_id):
        self.trace_id = trace_id
```

或者更简单一点，先在 Runner 里生成：

```python
trace_id = ...
```

并把它传给：

- Runner 日志
- ToolManager
- LLM 层

这一版的关键不是对象形态多优雅，而是先把：

> 一次运行的身份

固定下来。

---

## 本节建议记录哪些 Trace 事件

当前阶段不需要把所有动作都做成复杂 span。

第一版建议至少记录这些关键节点：

### 1. Runner started

表示一轮运行开始。

### 2. LLM call started

表示开始调用模型。

### 3. Tool dispatched

表示开始执行某个 Tool。

### 4. Tool finished / failed

表示 Tool 成功或失败。

### 5. Run finished

表示本轮运行结束。

这样你就已经能看清：

> 一次运行从开始到结束的大致骨架

---

## 当前项目里最适合接 Trace 的位置

### `Runner`

最适合持有 `trace_id`，因为它是运行时入口。

Runner 天然知道：

- 一次运行什么时候开始
- 什么时候结束
- 中间有没有 Tool Call

所以第一版 Trace 最适合从 Runner 发起。

### `ToolManager`

适合继续沿用这条 `trace_id`，让 Tool 执行记录和本次运行绑定。

### `OpenAILLM`

适合把模型调用日志也挂到同一条 trace 上。

这意味着当前项目会第一次形成：

```text
trace_id
  ├── Runner start
  ├── LLM call
  ├── Tool dispatch
  ├── Tool result
  └── Run finish
```

这已经是非常有价值的初版 tracing 了。

---

## 本节一个非常关键的工程意识

Tracing 的第一版目标，不是“画出漂亮链路图”，而是：

> 让你以后定位问题时，知道一条日志属于哪次运行

这是一个非常务实的起点。

因为很多系统在没有 trace_id 之前，日志一多就会变成：

- 你看到很多信息
- 但根本串不起来

所以 tracing 的第一步不是“高级观测平台”，而是：

> 让链路有身份

---

## Code Review 视角

### 不推荐的做法

直接继续加更多日志，但每条日志都没有统一运行标识。

这样一开始可能觉得“信息更多了”，但很快你会发现：

- 不同运行混在一起
- 连续两次请求的日志难以区分
- Tool 日志和 LLM 日志无法串联

### 更推荐的做法

即使只是最小实现，也要先给每轮运行挂上：

```text
trace_id
```

然后让关键日志至少都能带上这个标识。

这样后续无论是排错还是升级到真正的 tracing 平台，都会顺畅很多。

---

## 官方框架怎么做

成熟 Agent Framework 往往不会把 Tracing 当成“最后补的高级功能”。

它们通常会很早就考虑：

- 一次运行的唯一标识
- 模型调用和 Tool 调用如何关联
- 错误如何挂到某条链路上

这是因为对于 Agent 这种多轮、动态、可调用外部能力的系统来说：

> 没有链路视角的观察，几乎不可能做稳定迭代

所以这一节做的，其实是把项目往“真正可调试的运行时系统”再推一步。

---

## 本节最重要的一句话

> Logging 让你看到发生了什么，Tracing 让你知道这些事情是不是属于同一次运行。

这句话就是这一节最核心的区分。
