# Lesson17：最小 RAG 接入与知识外置初版

## 1. 本课目标

到这一课为止，你已经把 Agent 的很多核心内部能力逐步搭起来了：

- `Runner`
- `Session`
- `Memory`
- `Tool`
- `Checkpoint`
- `Tracing`
- `Eval`
- 长任务调度与人工接管

这些能力解决的，大多还是：

> **Agent 自己怎么运行、怎么记、怎么恢复、怎么被治理。**

但真实项目很快会遇到另一个问题：

> **如果 Agent 需要用到大量外部知识，而这些知识既不适合长期塞进 Prompt，也不适合全部放进 Memory，该怎么办？**

这就是 RAG 真正要解决的问题。

所以这一课我们正式进入：

> **最小 RAG 接入与知识外置**

这一步很关键，因为它标志着你的 Agent 开始从“主要依赖内置上下文和内部状态”走向：

> **可以按需连接外部知识源。**

---

## 2. 为什么不是所有知识都应该塞进 Prompt

很多初学者遇到知识不足问题时，第一反应通常是：

> 那我把更多背景资料写进 Prompt 不就行了？

这在特别小的知识量下还能凑合。

但一旦知识变多，就会立刻出问题。

### 问题 1：Prompt 会变得过长

你会不断往 system prompt 里塞：

- 项目背景
- 业务规则
- 文档说明
- FAQ
- 历史总结

最后 Prompt 变成一个巨大的知识包。

---

### 问题 2：相关性很差

不是每次任务都需要全部知识。

如果你把所有东西都塞进去，模型会被大量无关信息干扰。

---

### 问题 3：知识更新很痛苦

一旦知识变化，你就得反复改 Prompt。

这会让系统越来越难维护。

所以你要先建立一个关键认知：

> **Prompt 适合表达规则和行为约束，不适合充当大规模知识仓库。**

---

## 3. 为什么不是所有知识都应该进长期 Memory

你前面已经学过 Memory。

很多人这时又会想：

> 那我把外部知识都存进 Memory 不就好了？

这同样不是一个好答案。

因为长期 Memory 更适合保存：

- 用户偏好
- 稳定项目事实
- 已验证关键结论
- 高价值可复用信息

而不适合无差别承载海量原始知识材料。

如果把外部知识全塞进 Memory，会出现：

### 问题 1：Memory 失去“高价值筛选”特性

它会从长期记忆层退化成知识堆。

---

### 问题 2：相关性变差

后续检索长期 Memory 时会越来越吵。

---

### 问题 3：更新和治理困难

外部知识变化频繁，不适合全部沉淀成内部长期状态。

所以你现在要区分三件事：

- Prompt：规则与行为约束
- Memory：长期高价值内生记忆
- RAG：按需接入的外部知识

这三者边界非常重要。

---

## 4. 这一课最重要的一句话

请记住：

> **RAG 的本质不是“接一个向量库”，而是“把知识从上下文里外置，并在需要时按相关性取回”。**

这句话非常关键。

很多人一提到 RAG，脑子里立刻想到：

- Embedding
- 向量数据库
- 相似度检索

这些当然重要，但它们都属于“实现方式”。

而从工程理解上，RAG 先要解决的是一个更根本的问题：

> **知识不应该一直背在模型身上，而应该在需要时再拿回来。**

这就是知识外置的意义。

---

## 5. 什么叫“知识外置”

你可以先把它理解成：

> **把本来可能塞进 Prompt / Memory / 长上下文里的知识，搬到 Agent 外部的独立知识源中。**

然后在任务需要时，Agent 再去取回与当前问题最相关的一小部分。

例如你有下面这些资料：

- 产品文档
- API 文档
- 项目架构说明
- 业务流程说明
- FAQ

它们不应该一直都在当前上下文里。

更合理的方式是：

1. 平时放在外部知识库中
2. 当前任务需要时检索相关片段
3. 只把相关片段注入到当前上下文

这就叫知识外置。

---

## 6. 为什么 RAG 在 Agent 里比在普通聊天里更重要

普通聊天里，RAG 的意义通常是：

> 让模型回答得更有知识依据

而在 Agent 里，它的意义更大。

因为 Agent 不只是“回答问题”，它还要：

- 做任务
- 调 Tool
- 分阶段推进
- 在长任务里持续决策

这意味着外部知识不仅影响答案内容，还会影响：

- 下一步怎么做
- 用哪个 Tool
- 哪个方向优先
- 是否需要继续探索

所以在 Agent 里，RAG 的角色更像：

> **外部知识驱动的决策辅助层**

而不只是“补几段参考资料”。

---

## 7. 最小 RAG 第一版先解决什么问题

当前阶段我们不追求复杂检索平台。

第一版先只解决一个核心问题：

> **让 Agent 能在需要时，从外部知识源中取回少量相关文本。**

也就是说，第一版你只需要先具备：

1. 有一批知识材料
2. 能根据当前问题找到相关内容
3. 能把这些内容注入当前上下文

这已经足够让你真正进入 RAG 主线。

---

## 8. 第一版知识源可以非常简单

很多人一学 RAG 就想着：

- 上向量数据库
- 上检索服务
- 做分块、索引、重排

这些都会学，但不是第一步。

第一步完全可以很朴素。

例如你的知识源先只是：

- 一个文档目录
- 若干 Markdown 文件
- 一些项目说明文本

甚至第一版你都不一定需要真正的向量检索。

你可以先从：

> **最小文档集合 + 最简单检索逻辑**

开始。

因为当前阶段的重点是：

> **先把“外部知识按需接回上下文”这条链打通。**

---

## 9. 为什么第一版 RAG 更适合从“检索流程”而不是“向量技术”开始学

这是一个很重要的学习顺序问题。

如果一上来就沉迷向量库细节，你很容易错过真正主干：

> **RAG 是一条知识流转链。**

这条链至少包括：

1. 知识如何被存放
2. 当前问题如何形成检索请求
3. 如何召回相关内容
4. 如何把召回内容整理成可用上下文
5. 如何和 Session / Memory / Prompt 结合

这条链才是 RAG 的主干。

至于用 BM25、embedding、rerank，属于后续优化手段。

所以当前阶段更应该先掌握：

> **RAG 的运行流程，而不是先陷进实现细节。**

---

## 10. 第一版 RAG 流程应该长什么样

你可以先把第一版最小 RAG 流程理解成：

```text
用户问题

↓

判断是否需要外部知识

↓

生成检索查询

↓

从知识源找相关片段

↓

整理成 knowledge context

↓

与 prompt / session / memory 一起送给模型
```

这就是最小 RAG 闭环。

你会发现它和 Memory 很像，但又不一样：

- Memory 更偏内部沉淀
- RAG 更偏外部取回

这两条线会在后面逐渐融合成更完整的信息系统。

---

## 11. 为什么“是否需要检索”本身就是一个决策点

这一点非常关键。

RAG 不是每轮都必须触发。

很多时候当前任务根本不需要外部知识，例如：

- 只是查当前时间
- 只是读取本地文件
- 只是继续当前会话里的已知任务

如果每轮都去检索，通常会带来：

- 额外耗时
- 更多噪音
- 更高成本

所以第一版 RAG 也要建立一个意识：

> **检索不是默认动作，而是按需动作。**

这和 Tool 调用、Memory 注入其实是同一种工程逻辑。

---

## 12. 为什么检索出的知识不能原样全塞进上下文

这是很多 RAG 初学者的高频坑。

觉得只要召回了相关内容，就应该一股脑都塞进去。

这样做通常会出问题：

### 问题 1：上下文又变长了

你刚刚才学会做上下文治理，现在又把大块文本灌回去。

---

### 问题 2：重点不突出

召回内容可能只是“相关”，不代表全部都重要。

---

### 问题 3：和当前 Session 目标脱节

当前任务真正需要的可能只是其中 2 段，而不是整个文档片段。

所以：

> **RAG 不是“检索出来就结束”，而是“检索后还要组织成可消费上下文”。**

这和 Tool 结果设计、Memory 注入设计，其实是一脉相承的。

---

## 13. 第一版 knowledge context 应该怎么组织

当前阶段，你完全可以先用一个非常简单的结构：

```text
Relevant knowledge:

- 文档A中的相关结论
- 文档B中的关键片段
- FAQ 中与当前问题最相关的一条
```

而不是把原始文本整块塞进去。

更工程化一点，你甚至可以开始区分：

- 来源
- 片段
- 为什么相关

例如：

```text
Relevant knowledge:

1. Source: architecture.md
   Key point: 订单流程集中在 OrderService。

2. Source: cache-design.md
   Key point: Redis 只用于缓存，不承载主业务数据。
```

这种结构比简单拼接原文更利于模型消费。

---

## 14. RAG 和 Memory 到底怎么分工

这一点你现在必须建立清楚。

### Memory

更偏：

> Agent 自己运行中沉淀下来的高价值内部信息

例如：

- 用户偏好
- 已验证项目事实
- 之前任务得到的重要结论

---

### RAG

更偏：

> 当前任务需要时，从外部知识库中临时取回的信息

例如：

- 外部文档内容
- 产品说明
- API 规范
- 项目知识库

所以你可以这样记：

> **Memory 是内生记忆，RAG 是外取知识。**

这两者都会进入上下文，但来源和治理逻辑不同。

---

## 15. 为什么第一版 RAG 要先做“知识接入”，而不是先做“知识正确”

这句话可能有点反直觉，但很重要。

当前阶段，你先要解决的是：

> **系统有没有能力从外部知识源取回相关内容并参与推理。**

如果这条链都没打通，谈更高阶问题没有意义。

后面当然还会继续优化：

- 检索准确率
- 片段切分质量
- 去噪
- 重排
- 知识新鲜度

但这些属于第二阶段优化。

第一阶段先把链路打通，才是正确节奏。

---

## 16. 这一课背后的核心工程思想

这一课真正训练的是：

> **把 Agent 的知识来源，从“全靠上下文硬背”升级成“可按需连接外部知识系统”。**

这是一个非常关键的架构升级。

因为一旦你具备了知识外置能力，很多前面难以解决的问题就会开始变得可解：

- Prompt 不再需要塞满背景资料
- Memory 不再被迫承担海量知识存储
- 上下文可以更聚焦
- 知识更新不必总靠改 Prompt

这说明：

> **RAG 不是锦上添花，而是 Agent 规模化获取知识的基础设施。**

---

## 17. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

先准备一个最小知识源。

例如：

- 3 到 5 篇 Markdown 文档
- 1 个小型 FAQ 集

---

### 第二件

为 Agent 增加一个最小检索步骤：

- 判断是否需要知识检索
- 从知识源找相关内容

---

### 第三件

把检索结果整理成一段结构化 `knowledge context`，

而不是原样拼文档。

---

### 第四件

思考并写出：

哪些知识适合放 Prompt，

哪些适合放 Memory，

哪些更适合走 RAG。

---

## 18. 本课小结

今天最重要的三句话：

### 第一

> **RAG 的本质不是接一个向量库，而是把知识从上下文里外置，并在需要时按相关性取回。**

### 第二

> **Prompt 适合规则，Memory 适合长期高价值内生记忆，RAG 适合外部按需知识。**

### 第三

> **第一版 RAG 的核心不是检索技术有多高级，而是把外部知识接入链路打通。**
