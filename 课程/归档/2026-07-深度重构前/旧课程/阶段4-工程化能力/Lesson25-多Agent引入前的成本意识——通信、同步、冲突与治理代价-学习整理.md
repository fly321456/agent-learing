# Lesson25：多 Agent 引入前的成本意识——通信、同步、冲突与治理代价

## 1. 本课目标

上一课我们已经把多 Agent 前置主线推进到了一个很关键的认知：

> **Planner / Executor / Reviewer 之所以会成为经典三角，不是框架巧合，而是复杂任务天然会稳定分化出规划、执行、校验这三类工作。**

到这里，很多人会自然产生一个冲动：

> 那我是不是应该赶紧把系统拆成多个 Agent？

这就是这一课要专门纠偏的地方。

因为多 Agent 虽然很强，但它绝不是：

> **拆了就一定更高级，拆了就一定更好。**

恰恰相反。

很多系统一旦过早进入多 Agent，常见结果不是更强，而是：

- 更慢
- 更乱
- 更难调
- 更难评估
- 更难治理

所以这一课的目标非常明确：

> **在真正进入多 Agent 实现之前，先建立足够强的“成本意识”。**

这一步非常关键，因为它决定你以后是在做成熟架构决策，还是在做“为了多 Agent 而多 Agent”的堆叠。

---

## 2. 为什么多 Agent 看起来总是很诱人

这件事很正常。

多 Agent 之所以让人兴奋，是因为它天然带有几个非常强的直觉吸引力：

### 吸引力 1：角色更清晰

听起来比“一个 Agent 什么都干”更优雅。

---

### 吸引力 2：能力看起来更强

感觉像一个小团队在协作，而不是一个人在硬扛。

---

### 吸引力 3：结构更像真实组织

Planner、Executor、Reviewer 很像现实团队分工。

---

### 吸引力 4：听起来更先进

很多文章、Demo、框架宣传都会强调多 Agent。

所以很多人天然会觉得：

> 多 Agent = 更高级架构

这种直觉并不奇怪。

但工程上更重要的问题是：

> **它值不值得。**

---

## 3. 这一课最重要的一句话

请记住：

> **多 Agent 不是免费午餐，它用“角色清晰”换来了“系统复杂度显著上升”。**

这句话非常重要。

因为它会帮助你建立一个成熟工程师该有的平衡感。

多 Agent 带来的收益通常包括：

- 职责分离
- 路径更清晰
- 质量反馈更独立

但它带来的代价同样真实：

- 通信成本
- 状态同步成本
- 冲突处理成本
- 调度复杂度
- 可观测性复杂度
- 评估复杂度

所以多 Agent 不是“白拿的更强”，而是：

> **用更高系统复杂度换取更好的任务结构表达。**

---

## 4. 多 Agent 的第一类成本：通信成本

这是最直观也最容易低估的一类。

单 Agent 里很多信息流动是隐含发生的：

- 想法在一个上下文里
- 状态在一个 Session 里
- 决策在一个循环里

但一旦拆成多个 Agent，就会立刻出现一个问题：

> **它们之间怎么传信息？**

例如：

- Planner 产出的计划怎么交给 Executor？
- Executor 的执行结果怎么交给 Reviewer？
- Reviewer 的反馈又怎么回到 Planner？

这时你必须显式处理：

- 传什么
- 传多少
- 什么格式传
- 什么时候传

原来单 Agent 隐含解决的问题，现在都会变成显式工程问题。

这就是通信成本。

---

## 5. 为什么通信一旦变显式，信息损耗就会出现

当一个 Agent 自己在一个上下文里推理时，信息在内部是连续的。

但一旦角色分开，系统就必须面对一个现实：

> **信息在角色交接时会被压缩、转述、筛选。**

例如：

- Planner 不可能把全部思考细节都交给 Executor
- Executor 也不可能把全部原始执行轨迹都交给 Reviewer

所以交接天然会带来：

- 信息丢失
- 语义偏差
- 上下文断裂

这意味着多 Agent 不是简单“复制一个上下文给另一个角色”，而是：

> **每一次角色交接都在重新设计信息边界。**

这是很多系统后期不稳的根源之一。

---

## 6. 第二类成本：状态同步成本

前面你已经学过 Session、Memory、RAG、Checkpoint。

在单 Agent 里，这些状态虽然复杂，但至少还在一个系统内统一维护。

可一旦变成多 Agent，问题就变成：

> **多个角色看到的状态是不是一致？**

例如：

- Planner 认为当前阶段是“执行中”
- Executor 已经认为自己完成了
- Reviewer 还以为处于“待验证”

这类问题在多 Agent 里非常高频。

因为状态不再只是“要不要保存”，而是：

> **要不要同步、同步到什么粒度、谁拥有最终状态解释权。**

这就是状态同步成本。

---

## 7. 为什么“谁拥有真相”会成为多 Agent 的核心问题

这一点特别重要。

在单 Agent 里，当前状态的“真相”通常比较集中。

但多 Agent 一旦引入后，很容易出现：

- 每个角色都持有自己的局部状态
- 每个角色都觉得自己看到的是真的

于是系统就必须回答：

> **到底谁说了算？**

例如：

- 当前阶段到底由 Planner 决定，还是由 Executor 的执行进度决定？
- 任务是否完成，到底由 Reviewer 定义，还是由 Planner 的原计划定义？

这说明多 Agent 不是只多了角色，还多了一个新的系统设计问题：

> **状态主权（state authority）**

如果这一层没设计清楚，多 Agent 系统会非常容易乱。

---

## 8. 第三类成本：冲突成本

一旦有多个角色，冲突就几乎不可避免。

例如：

### 冲突 1：规划冲突

Planner 觉得应该继续探索，Reviewer 觉得已经足够输出。

---

### 冲突 2：执行冲突

Planner 指向 A 路线，Executor 在执行中发现 B 路线更实际。

---

### 冲突 3：质量冲突

Executor 觉得任务完成了，Reviewer 认为还有明显风险。

这些冲突在单 Agent 里通常被压在一个推理流中，不那么显式。

而在多 Agent 里，冲突会被放大成：

> **角色之间的显式不一致。**

这时候系统必须进一步回答：

> **冲突如何裁决？谁有最终仲裁权？**

这就是冲突治理成本。

---

## 9. 第四类成本：调度成本

前面你已经学过 Runner、Checkpoint、waiting_for_human、任务状态机。

多 Agent 会把这层复杂度再往上抬。

因为现在不仅要调度：

- 一个 Agent 什么时候继续

而是还要调度：

- 什么时候从 Planner 切到 Executor
- 什么时候从 Executor 交给 Reviewer
- Reviewer 打回后是回到 Executor 还是 Planner
- 某个角色卡住时整个系统怎么办

这实际上已经开始接近：

> **多角色工作流引擎**

所以多 Agent 的代价不只是多几个模型，而是：

> **运行时调度复杂度显著增加。**

---

## 10. 第五类成本：可观测性成本

在单 Agent 里，tracing 已经不简单了。

到了多 Agent，复杂度会进一步上升。

你需要知道的不再只是：

- 第几轮出了问题

而是：

- 哪个角色先偏了
- 偏差是如何传染到下一个角色的
- Planner 的问题，还是 Executor 的问题，还是 Reviewer 的问题
- 某次 handoff 丢了什么信息

所以多 Agent 的 tracing 不再只是单链路 tracing，而开始变成：

> **多角色交互链路 tracing。**

这意味着：

- 事件更多
- 关联键更多
- 归因更复杂

所以可观测性成本会大幅提升。

---

## 11. 第六类成本：评估成本

前面你已经建立了最小评测体系。

单 Agent 评估至少还能相对清楚地看：

- 任务成功率
- Tool 正确率
- 轮数

到了多 Agent，问题就会变得更细：

- 是 Planner 的计划质量变好了，还是 Executor 偶然补救了？
- 是 Reviewer 提升了稳定性，还是只是让流程更慢了？
- 多 Agent 比单 Agent 强，究竟强在哪个环节？

这意味着评估维度会显著增加。

你可能需要分别观察：

- 规划质量
- 执行质量
- 审查拦截率
- 角色 handoff 成功率

所以：

> **多 Agent 带来的不是“评估更简单”，而是“评估要更精细”。**

---

## 12. 为什么多 Agent 不是先问“能不能做”，而是先问“值不值得做”

这是这一课最想帮你建立的架构判断力。

技术上，很多事情都能做。

但成熟工程师更在意：

> **为了解决当前问题，是否值得引入这一级复杂度。**

如果一个任务其实只是：

- 中等复杂
- 步骤不多
- 风险不高
- 单 Agent 通过一些角色逻辑分层就能稳定搞定

那你很可能根本不需要真正多 Agent 化。

所以多 Agent 决策的正确顺序不是：

> 能不能拆？

而是：

> **当前复杂度是否已经高到足以覆盖多 Agent 的成本？**

这才是成熟判断。

---

## 13. 什么情况下才更值得引入真正多 Agent

当前阶段，你可以先用一个很实用的判断框架。

更值得引入多 Agent 的场景通常有这些特征：

### 特征 1：职责边界已经很稳定

例如 Planner / Executor / Reviewer 的边界已经很清楚。

---

### 特征 2：单 Agent 角色过载明显

例如：

- 规划经常被局部执行打断
- 审查明显不独立
- 任务越来越不稳

---

### 特征 3：任务链路长且阶段明确

长任务更容易从分工中获益。

---

### 特征 4：收益足以覆盖通信和调度成本

也就是说，多 Agent 不是“理论上优雅”，而是：

> **工程收益显著。**

这时才是真正值得拆的时候。

---

## 14. 为什么很多项目更适合“单 Agent + 角色化逻辑”，而不是立刻上多 Agent

这是一个非常重要、也非常实用的中间态。

很多项目并不需要立刻进入真正多实例、多角色互发消息。

它们更适合先做：

> **单 Agent 内部角色化逻辑**

例如：

- 先 plan
- 再 execute
- 再 review

虽然底层还是一个 Agent 运行时，但职责已经被拆清楚了。

这种做法的好处是：

- 保留角色分工收益
- 暂时不支付过高的通信与同步成本
- 更容易调试和演进

所以你要知道：

> **多 Agent 不是只有“0”和“1”两种状态，中间有很长的渐进演化带。**

这点非常关键。

---

## 15. 这一课背后的核心工程思想

这一课真正训练的是：

> **不要因为一个架构在理论上更优雅，就忽略它在运行时的真实成本。**

这是一种非常重要的工程成熟度。

很多架构文章只讲：

- 多 Agent 可以分工
- 多 Agent 可以协作
- 多 Agent 可以更强

这些都没错。

但真正决定你是不是成熟工程师的，是你会不会同时追问：

- 代价是什么
- 复杂度上升在哪里
- 谁来支付同步成本
- 谁来承担治理成本

这就是为什么“成本意识”是多 Agent 之前必须补的一课。

---

## 16. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑一个你觉得“可能适合多 Agent”的任务，列出如果真拆开，至少会新增哪些成本：

- 通信
- 同步
- 冲突
- 调度
- tracing
- eval

---

### 第二件

思考并回答：

> 当前这个任务，拆多 Agent 的收益，是否真的覆盖这些成本？

---

### 第三件

尝试写一个判断：

这个任务更适合：

- 单 Agent
- 单 Agent + 角色化逻辑
- 真正多 Agent

并说明原因。

---

### 第四件

找一个你以前直觉上觉得“应该上多 Agent”的场景，重新用成本视角再评估一次。

今天最重要的三句话：

### 第一

> **多 Agent 不是免费午餐，它用角色清晰换来了系统复杂度显著上升。**

### 第二

> **多 Agent 决策的正确顺序不是“能不能拆”，而是“值不值得拆”。**

> **很多项目更适合先做单 Agent 的角色化逻辑，而不是立刻进入真正多 Agent。**
