# Lesson13：Tool 设计质量评估与接口重构初版

## 1. 本课目标

上一课我们已经把 Prompt 迭代拉回到了工程轨道上：

- 有问题定义
- 有实验假设
- 有固定评测集
- 有版本对照

这很好，但如果你继续做 Agent，很快会遇到一个非常现实的问题：

> **有些 Agent 看起来“不够聪明”，其实不是 Prompt 没写好，而是 Tool 根本不适合给模型用。**

这是很多初学者最容易忽略的一层。

因为表面上看，Tool 好像只是一个 Python 函数：

```python
def read_file(path): ...
```

但从 Agent 工程视角看，Tool 不是“给人写的函数”，而是：

> **给模型做决策和调用的接口。**

所以这一课我们正式进入一个很关键的工程主题：

> **Tool 也要评估质量，也要重构接口。**

---

## 2. 为什么 Tool 常常是 Agent 的真实瓶颈

很多人一看到 Agent 行为不理想，第一反应是：

- 模型不够强
- Prompt 不够好
- Memory 不够聪明

这些当然都可能有问题。

但真实工程里，另一个高频问题源是：

> **Tool 本身设计得不适合模型调用。**

常见表现包括：

### 表现 1：模型明明该调 Tool，却不调

原因可能不是模型不想调，而是：

- Tool 名字不清晰
- Description 太弱
- 参数语义太模糊

---

### 表现 2：模型调用了 Tool，但参数老传错

原因可能是：

- 参数名不直观
- 参数设计过于复杂
- 单个 Tool 承担了太多职责

---

### 表现 3：Tool 明明执行成功了，但对任务没有帮助

原因可能是：

- 返回结果太乱
- 返回结果太长
- 返回结果不具备下一步决策价值

所以你要先建立一个新认知：

> **Tool 成功执行，不等于 Tool 设计是成功的。**

---

## 3. 这一课最重要的一句话

请记住：

> **Tool 不是“能调用就行”，而是“要让模型容易理解、容易选择、容易正确使用”。**

这句话非常重要。

因为很多工程师写 Tool 时，还是站在人类程序员视角：

- 这个函数我自己看懂了
- 这个参数我自己会传
- 这个返回值我自己能解析

但 Agent 不是你自己在调用这些函数。

而是：

> **模型在根据名字、描述、参数结构、返回结果来做决策。**

所以 Tool 的设计质量，直接决定了模型的可用性上限。

---

## 4. 为什么 Tool 设计本质上是接口设计问题

这一点你一定要吃透。

很多人把 Tool 理解成“Agent 的外挂能力”。

这没错，但还不够深。

更工程化的理解是：

> **Tool 是 LLM 与外部世界之间的接口层。**

既然是接口层，那么它自然就要面对所有经典接口设计问题：

- 命名是否清晰
- 边界是否明确
- 参数是否稳定
- 返回值是否结构化
- 职责是否单一

所以 Tool 设计不是“小细节”，而是典型的 API / Interface Design 问题。

这也意味着：

> **很多 Agent 问题，本质上是接口设计问题，不是模型问题。**

---

## 5. 一个差 Tool 往往长什么样

我们先看反面例子。

一个质量不高的 Tool 常见会有这些特征：

### 特征 1：名字抽象

例如：

```text
process_data
handle_file
run_task
```

这些名字对模型几乎没有决策帮助。

---

### 特征 2：Description 太空

例如：

```text
处理文件
```

问题是：

- 处理什么文件
- 做什么处理
- 什么时候该用

模型看不出来。

---

### 特征 3：参数过多、过杂

例如：

```json
{
  "path": "...",
  "mode": "...",
  "options": "...",
  "extra": "...",
  "config": "..."
}
```

参数一复杂，模型构造正确调用的概率就会下降。

---

### 特征 4：返回值不面向下一步决策

比如返回一大段无结构原始文本，但没有关键字段，没有简洁结果，没有可继续推理的信号。

这会让 Tool 虽然“返回了很多”，但没有真正帮助 Agent。

---

## 6. 一个好 Tool 往往长什么样

反过来，一个高质量 Tool 通常具备这些特点：

### 第一，名字直接表达能力

例如：

- `read_file`
- `list_directory`
- `search_code`
- `get_current_time`

模型一眼就能理解用途。

---

### 第二，Description 直接回答“什么时候用”

例如：

```text
读取指定路径的文本文件内容。
当需要查看文件原文时使用。
不要用于列目录；列目录请使用 list_directory。
```

这就比“读取文件”强很多。

---

### 第三，参数尽量少且语义明确

例如：

```json
{
  "path": "string"
}
```

比混合一堆可选字段更适合模型。

---

### 第四，返回值对下一步有用

例如：

- 内容本体
- 状态字段
- 错误原因
- 必要的结构信息

而不是一坨难以继续使用的原始输出。

所以：

> **好 Tool 的目标不是暴露最多能力，而是暴露最容易被正确使用的能力。**

---

## 7. 为什么“单一职责”对 Tool 特别重要

Tool 和普通函数一样，也非常需要单一职责原则。

很多人为了“省事”，喜欢做这种 Tool：

```text
file_manager
```

它既能：

- 读文件
- 写文件
- 列目录
- 删除文件
- 搜索内容

看起来很强大。

但对模型来说，这通常是灾难。

因为：

- 什么时候该调用它不清楚
- 调用时参数结构复杂
- 失败模式复杂

所以对于 Agent 来说，很多时候更好的方式不是“一个超级 Tool”，而是：

> **多个职责清晰、边界明确的小 Tool。**

这和可维护 API 设计是同一套逻辑。

---

## 8. 为什么 Tool 参数设计会直接影响调用正确率

这点非常重要。

很多 Agent 调错 Tool 参数，不一定是模型笨，而是参数本身不好用。

典型坏设计包括：

### 参数名不直观

例如：

- `target`
- `input`
- `data`

模型很难知道这里真正要填什么。

---

### 参数语义重叠

例如同时有：

- `path`
- `file_path`
- `target_path`

模型容易混淆。

---

### 参数结构过深

嵌套对象太多，会显著增加调用出错概率。

所以一个很重要的工程经验是：

> **参数不是给人类 API 使用者设计的，而是给模型生成调用时设计的。**

这会直接改变你的设计标准。

---

## 9. 为什么返回值设计同样重要

很多人花很多心思写 Tool 名字和参数，却忽略了返回值。

但返回值其实直接决定了：

> **模型下一轮是否容易做出正确决策。**

例如一个 `read_file` Tool，如果返回：

```text
success
```

那几乎没用。

如果返回：

```json
{
  "path": "...",
  "content": "...",
  "truncated": false
}
```

就好很多。

再进一步，如果超长时还能明确告诉模型：

```json
{
  "path": "...",
  "content_preview": "...",
  "truncated": true,
  "suggestion": "If more detail is needed, read a smaller target file."
}
```

那模型的后续决策会更稳定。

所以：

> **Tool 返回值不是“把结果吐回去”就完了，而是下一步决策输入的一部分。**

---

## 10. 第一版 Tool 质量评估应该看什么

这一课我们不只讲设计，还要讲评估。

当前阶段，你完全可以先用下面几个维度评估 Tool 质量：

### 维度 1：可发现性

问题：

> 模型看到名字和描述后，是否容易知道什么时候该用它？

---

### 维度 2：可调用性

问题：

> 模型是否容易构造出正确参数？

---

### 维度 3：可消费性

问题：

> 返回结果是否容易被模型继续利用？

---

### 维度 4：边界清晰度

问题：

> 这个 Tool 和其他 Tool 的职责是否清晰分离？

---

### 维度 5：稳定性

问题：

> 同类任务下，它的调用行为和结果是否稳定？

这五个维度已经很适合作为第一版 Tool 评估框架。

---

## 11. Tool 重构通常从哪几类动作开始

如果你发现某个 Tool 质量不高，不一定要全部推倒重写。

很多时候重构可以从下面几个动作开始：

### 动作 1：改名字

让用途更直接。

---

### 动作 2：重写 Description

尤其要明确：

- 什么时候该用
- 什么时候不该用
- 它和其他 Tool 的区别

---

### 动作 3：简化参数

删除低价值可选项，减少模型出错面。

---

### 动作 4：拆分职责

把一个超级 Tool 拆成多个小 Tool。

---

### 动作 5：改返回值结构

让结果更结构化，更适合作为下一轮输入。

这五类动作通常就足够让 Tool 质量明显提升。

---

## 12. 为什么 Tool 重构也应该走“评估 -> 改动 -> 回归”流程

这点和 Prompt 迭代是同样的工程逻辑。

不能因为 Tool 是“代码”就默认改动一定是进步。

例如你把 Tool 拆小以后，可能：

- 参数更简单了
- 但模型开始在多个相似 Tool 之间犹豫

或者你加强了 Description，可能：

- 某类调用成功率提升
- 但另一类边界任务开始保守不用 Tool

所以 Tool 重构也必须走完整闭环：

> **先识别问题，再做小改动，再用固定样例集回归。**

这说明 Agent 工程里，Tool 不是一次性写完就结束，而是持续优化对象。

---

## 13. 为什么很多“模型不聪明”的问题，本质是接口不友好

这一点很值得你反复理解。

很多人会说：

> 为什么模型连这么简单的 Tool 都不会调？

但真实情况常常是：

- 名字不清楚
- 描述太模糊
- 参数太复杂
- 返回结果不好用

也就是说，模型失败不是因为它不聪明，而是因为：

> **你给它的接口设计得不利于它成功。**

这和人类程序员面对糟糕 API 时也会容易用错，是同一个道理。

所以高质量 Agent 开发，不能只训练 Prompt，还要训练接口设计能力。

---

## 14. 这一课背后的核心工程思想

这一课真正训练的是：

> **把 Tool 从“功能函数”升级成“面向模型的接口产品”。**

这句话很重要。

因为一旦你有了这个视角，很多设计标准都会变：

- 不是“我自己会不会用”
- 而是“模型会不会稳定地用”

这会让你真正进入 Agent Engineer 的设计视角。

从这里开始，你写 Tool 时关注的不只是业务逻辑正确性，还包括：

- 决策友好性
- 调用友好性
- 消费友好性

这就是 Agent 工程和普通脚本封装的分水岭。

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑 1 到 2 个你当前项目里的 Tool，按下面五个维度做一次体检：

- 可发现性
- 可调用性
- 可消费性
- 边界清晰度
- 稳定性

---

### 第二件

找出一个最明显的问题。

例如：

- 名字不清晰
- 参数太复杂
- 返回值太乱

---

### 第三件

只做一轮小重构。

例如：

- 改 Description
- 简化参数
- 调整返回值结构

---

### 第四件

用固定评测集回归，比较重构前后的 Tool 使用效果。

---

今天最重要的三句话：

### 第二

### 第三
