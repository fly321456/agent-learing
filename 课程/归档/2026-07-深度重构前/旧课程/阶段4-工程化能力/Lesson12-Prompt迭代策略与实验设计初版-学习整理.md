# Lesson12：Prompt 迭代策略与实验设计初版

## 1. 本课目标

上一课我们正式把课程推进到了评估体系：

- 有固定样例集
- 有最小评测指标
- 有回归评测意识

这意味着从现在开始，你终于可以不再凭感觉优化 Agent。

接下来最自然的问题就是：

> **当你准备改 Prompt 时，应该怎么改，才能让优化是可验证的，而不是越改越乱？**

这就是这一课的核心。

很多人做 Agent 优化时，最容易陷入的状态是：

```text
觉得不够好

就改 Prompt

改完再问几个问题

感觉好像强了一点
```

这不是工程化迭代，这只是试错。

所以这一课要建立的核心能力是：

> **把 Prompt 优化从“拍脑袋微调”，变成“带假设、带评估、带对照的实验过程”。**

---

## 2. 为什么 Prompt 优化最容易失控

因为 Prompt 是最容易改、也最容易“看起来有效”的东西。

比如你看到 Agent 有问题，第一反应常常是：

- 补一句规则
- 多写一段说明
- 加几个示例
- 强调“不允许……”

短期看这很自然。

但如果没有方法，很快就会进入下面的状态：

### 状态 1：Prompt 越来越长

每次发现一个问题，就加一条规则。

最后变成：

```text
补丁式 Prompt
```

---

### 状态 2：修一个问题，带来两个副作用

例如：

- Tool 调用更积极了
- 但误调用也变多了

或者：

- 回答更保守了
- 但任务完成率下降了

---

### 状态 3：不知道是哪句话起了作用

一次改了很多地方，最后即使结果变好了，也不知道真正有效的是哪部分。

所以 Prompt 优化最大的问题不是“难写”，而是：

> **太容易在没有实验纪律的情况下越改越乱。**

---

## 3. 这一课最重要的一句话

请记住：

> **Prompt 迭代不是写作活动，而是实验活动。**

这句话非常关键。

因为很多人把 Prompt 优化理解成：

> 文案写得更漂亮一点

这不准确。

在工程里，Prompt 更像系统行为控制接口的一部分。

你每改一句 Prompt，本质上都在改变：

- 模型决策倾向
- Tool 使用习惯
- 风险偏好
- 输出结构

所以每一次 Prompt 改动，本质上都应该被看成：

> **一次会影响系统行为的实验。**

---

## 4. 为什么不能一次改很多 Prompt 内容

这是最常见的错误之一。

很多人会这样做：

```text
重写 system prompt

补 5 条工具规则

加 3 个示例

改输出格式
```

然后再跑一遍，觉得“好像更好了”。

问题是：

> **你已经失去了归因能力。**

因为结果变化到底来自：

- 新规则
- 新示例
- 新语气
- 新格式约束

你完全不知道。

所以第一条实验纪律是：

> **一次只改一个明确变量。**

这就是最基础的对照实验思想。

---

## 5. Prompt 迭代前，先写清楚“要解决什么问题”

Prompt 优化最忌讳的一种状态是：

> 感觉不够好，所以改一改

这太模糊了。

更工程化的做法是先明确：

### 现象是什么

例如：

- 在时间查询任务里，Agent 不调用时间 Tool
- 在简单解释任务里，Agent 误调用文件 Tool
- 在多轮分析任务里，Agent 回答太早结束

---

### 你怀疑的原因是什么

例如：

- Tool 使用规则表达不够明确
- Prompt 没强调“优先使用已有 Tool”
- Prompt 过于鼓励保守回答

---

### 你准备改哪一处

例如：

- 只调整 Tool 使用规则那一段

这样你做的就不再是“盲改 Prompt”，而是：

> **带问题定义的 Prompt 实验。**

---

## 6. 一个最小 Prompt 实验模板

当前阶段，你完全可以给自己固定一个很简单的实验模板：

### 1. 问题描述

当前 Agent 在什么任务上表现不好？

---

### 2. 假设

我怀疑问题来自 Prompt 的哪一部分？

---

### 3. 改动内容

这次只改哪一段、哪一句、哪一个示例？

---

### 4. 验证样例

用哪几个固定 case 来验证？

---

### 5. 观察指标

看什么：

- 任务成功率
- Tool 调用正确率
- 平均轮数
- 明显失败数

---

### 6. 结果

改动后：

- 提升了什么
- 退化了什么
- 是否值得保留

这个模板非常简单，但非常有工程价值。

---

## 7. Prompt 优化通常有哪几类目标

这一点你也要建立起来。

不是所有 Prompt 改动都在解决同一类问题。

当前阶段，你可以先把 Prompt 目标分成四类：

### 第一类：任务目标澄清

例如：

- 明确 Agent 的职责
- 明确什么时候该继续分析
- 明确什么时候可以结束

---

### 第二类：Tool 使用约束

例如：

- 遇到时间问题优先调用时间 Tool
- 不要在无关问题里乱调 Tool
- 有文件读取需求时使用文件 Tool

---

### 第三类：输出行为约束

例如：

- 回答结构更清晰
- 先给结论再展开
- 尽量简洁但不遗漏关键点

---

### 第四类：风险控制约束

例如：

- 不确定时先说明假设
- 不要编造 Tool 结果
- 缺少信息时先继续观察

当你知道自己是在优化哪一类目标时，Prompt 改动就会更聚焦。

---

## 8. 为什么“补规则”不是唯一的 Prompt 优化方式

很多初学者一遇到问题，就只会：

> 再补一条规则

但 Prompt 优化不只有这一种方式。

常见手段至少有这些：

### 方式 1：重写角色与目标描述

让 Agent 更清楚自己是谁、应该优先做什么。

---

### 方式 2：重写 Tool 使用规则

让模型更清楚什么时候该调用 Tool。

---

### 方式 3：增加少量示例

让模型看到期望行为模式。

---

### 方式 4：减少冲突信息

有时问题不是规则太少，而是 Prompt 里有互相冲突的要求。

---

### 方式 5：删掉过度约束

有时 Prompt 太重，模型反而不敢行动。

所以：

> **Prompt 优化不一定是加法，也可能是减法和重构。**

这一点非常关键。

---

## 9. 为什么 Prompt 越长不一定越好

这是很多人会踩的坑。

看起来加更多规则似乎更安全，但现实里经常出现两个问题：

### 第一，模型注意力被稀释

重点规则不再突出。

---

### 第二，规则之间开始冲突

例如：

- 既要求积极使用 Tool
- 又要求尽量少调用 Tool

如果表达不好，模型会摇摆。

所以 Prompt 质量很多时候不取决于“写了多少”，而取决于：

> **是否清晰、是否一致、是否突出关键决策。**

这就是为什么 Prompt 也需要重构思维。

---

## 10. 为什么评测集是 Prompt 迭代的护栏

上一课我们建立评测体系，这一课它终于派上真正用场了。

如果没有固定样例集，你每次改 Prompt 都只能靠临时问几个问题。

而有了评测集，你就能做最关键的一件事：

> **同样一组任务，比较 Prompt 版本 A 和版本 B。**

这会让 Prompt 迭代从：

```text
我感觉 B 更好
```

变成：

```text
B 在 12 个样例里：

任务成功率从 67% 提升到 83%

但误调用 Tool 率从 8% 升到了 17%
```

这就是工程判断。

---

## 11. 第一版 Prompt 对照实验应该怎么做

你现在不需要复杂 A/B 平台。

第一版完全可以用一个非常朴素的方法：

### Step 1

保留旧 Prompt 版本 A。

---

### Step 2

创建只改一处的版本 B。

---

### Step 3

对同一组固定样例分别跑 A 和 B。

---

### Step 4

比较：

- 成功率
- Tool 正确率
- 平均轮数
- 明显失败案例

---

### Step 5

决定：

- 保留 B
- 回滚到 A
- 基于结果再做下一轮小改动

这就是一个最小可运行的 Prompt 实验闭环。

---

## 12. 为什么要保留 Prompt 版本历史

这一点非常重要，但很多人会忽略。

如果你每次都直接改掉原 Prompt，而不保留版本，那么后面会出现一个很现实的问题：

> **你不知道系统是从哪次改动开始变好或变坏的。**

所以 Prompt 也应该像代码一样有版本意识。

例如：

- `prompt_v1`
- `prompt_v2_tool_rule`
- `prompt_v3_finish_rule`

哪怕只是本地保存一份变更记录，也比“直接覆盖”强很多。

因为：

> **没有版本历史，就没有真正的实验对照。**

---

## 13. 什么时候该停止继续补 Prompt

这也是一个很成熟的判断点。

不是所有问题都应该继续通过 Prompt 解决。

如果你发现问题本质上是下面这些：

- Tool 结果质量太差
- Memory 注入噪音过高
- 上下文裁剪策略有问题
- Runtime 顺序有 bug

那么继续补 Prompt 往往只是在“掩盖系统问题”。

所以 Prompt 优化前要先问：

> **这是 Prompt 问题，还是系统其他层的问题？**

如果不是 Prompt 问题，就不要拿 Prompt 当万能补丁。

---

## 14. 这一课背后的核心工程思想

这一课真正训练的是：

> **把 Prompt 从“魔法文本”变成“可实验、可比较、可回滚的系统配置”。**

这非常重要。

因为很多团队做 Prompt，方式仍然像手工调参：

- 想到就改
- 感觉有效就留
- 说不清为什么有效

而真正成熟的做法应该是：

> **有问题定义、有改动边界、有评测样例、有结果记录。**

这才是 Prompt 工程，而不是 Prompt 灵感管理。

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑一个真实存在的问题场景。

例如：

- 时间查询不调用 Tool
- 回答太早结束
- 文件任务误调用无关 Tool

---

### 第二件

写一个最小实验单：

- 问题
- 假设
- 改动点
- 验证样例
- 指标

---

### 第三件

只改 Prompt 的一个局部，然后用固定样例集跑一遍对照。

---

### 第四件

记录结果，明确回答：

- 这次改动值不值得保留
- 它改善了什么
- 它又带来了什么副作用

---

## 16. 本课小结

今天最重要的三句话：

### 第一

> **Prompt 迭代不是写作活动，而是实验活动。**

### 第二

> **一次只改一个明确变量，才能保住归因能力。**

### 第三

> **评测集是 Prompt 优化的护栏，没有评测就很容易越改越乱。**
