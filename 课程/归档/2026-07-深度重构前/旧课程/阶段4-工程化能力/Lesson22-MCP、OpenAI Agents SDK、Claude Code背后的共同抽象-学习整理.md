# Lesson22：MCP、OpenAI Agents SDK、Claude Code 背后的共同抽象

## 1. 本课目标

上一课我们已经把 MCP 从“为什么需要”推进到了“它到底在标准化什么”。

你现在已经理解了几个关键点：

- MCP 不只是统一 Tool 的 JSON 字段
- 它在统一能力声明、能力发现、调用协议、结果理解
- 它的核心关键词是：**可互操作**

但如果课程只停在这里，你很容易把 MCP 单独看成一个孤立主题。

而真正成熟的工程视角应该进一步看到：

> **MCP、OpenAI Agents SDK、Claude Code 这些看起来不同的系统，背后其实在收敛一些相似的抽象。**

这就是这一课要做的事。

我们不是来比较“谁 API 更好看”，而是要回答：

> **为什么不同 Agent 系统最后都会长出类似的结构？**

这一步非常关键，因为它会让你从“学一个框架”升级到：

> **开始看懂框架背后的设计共性。**

---

## 2. 为什么这一步对成为 Agent 工程师很重要

很多人学习框架时会停留在这样的层面：

- 这个框架怎么用
- 那个 SDK 怎么调
- 这个类怎么实例化

这种学习方式的问题在于：

> **一旦换框架，就容易重新归零。**

因为你学到的是表层 API，而不是底层结构。

如果你能看到更深的共性，你会发现：

- MCP 在解决什么
- Agents SDK 在解决什么
- Claude Code 这类系统在解决什么

虽然实现形态不同，但它们往往都在围绕几件核心事情展开：

- 能力声明
- 运行时状态
- 工具调用
- 生命周期控制
- 可观测性
- 信息组织

所以这一课真正的重要性在于：

> **帮你建立跨框架的抽象理解能力。**

---

## 3. 这一课最重要的一句话

请记住：

> **成熟 Agent 系统表面上长得不一样，但底层都在围绕“能力、状态、调度、信息、治理”这几个共同抽象收敛。**

这句话非常重要。

它意味着你以后看任何 Agent 系统时，不应该先问：

> 这个 API 怎么写？

而应该先问：

> 它把哪些核心问题抽象成了哪些组件？

这就是从“使用者视角”走向“设计者视角”的关键一步。

---

## 4. 先看第一个共同抽象：能力（Capability）

不管是 MCP、OpenAI Agents SDK，还是 Claude Code，这类系统都必须回答一个根问题：

> **系统到底能做什么？**

这其实就是能力抽象。

在不同系统里，它的表现形式不同：

### 在你自己的 Agent 里

可能是：

- `tools`
- `read_file`
- `search_code`

---

### 在 OpenAI Agents SDK 里

会体现为：

- tool
- function tool
- agent 可用能力集合

---

### 在 MCP 里

会体现为：

- 外部能力声明
- 可发现能力
- 可调用能力接口

---

### 在 Claude Code 这类系统里

则更像：

- 文件能力
- 命令能力
- 编辑能力
- 搜索能力

所以虽然名字不同，但本质上都在回答：

> **有哪些能力被暴露给 Agent Runtime 使用。**

这就是第一个共同抽象。

---

## 5. 第二个共同抽象：状态（State）

前面课程你已经学了很多关于 `Session`、`summary`、`completed_steps`、`pending_steps`、`checkpoint` 的内容。

为什么这些在几乎所有成熟系统里都会出现？

因为 Agent 不是一次函数调用，而是：

> **有运行过程的系统。**

只要有运行过程，就一定会有状态。

不同系统里，它可能叫不同名字：

- session
- context
- memory
- run state
- task state

但本质上都在解决：

> **系统当前处于什么位置，已经做了什么，还剩什么没做。**

所以你要开始形成一个稳定判断：

> **凡是成熟 Agent 框架，必然会有一层状态抽象。**

只不过有的显式，有的隐式。

---

## 6. 第三个共同抽象：调度（Orchestration / Scheduling）

这是很多初学者最容易忽略，但成熟系统一定会有的一层。

Agent 不只是“有能力”和“有状态”，它还必须回答：

> **下一步该做什么？什么时候继续？什么时候结束？什么时候暂停？**

这就是调度抽象。

在不同系统里，它的表现可能不同：

### 在你自己实现的最小 Agent 里

可能是：

```python
while True:
    ...
```

---

### 在 OpenAI Agents SDK 里

可能体现为：

- Runner
- run lifecycle
- tool execution orchestration

---

### 在长生命周期 Agent 系统里

会进一步体现为：

- pause / resume
- waiting_for_human
- checkpoint recovery

所以：

> **调度抽象的本质，就是控制能力与状态如何在时间上推进。**

这也是为什么几乎所有成熟 Agent 系统，最终都会从“调用模型”长成“运行时调度器”。

---

## 7. 第四个共同抽象：信息系统（Information System）

这也是你最近几课一直在学的东西。

Agent 不只是执行，还要处理信息。

而信息来源会越来越复杂：

- 当前消息
- summary
- completed/pending
- Memory
- RAG
- 外部 Tool 结果

所以成熟系统都会逐步形成某种信息系统抽象，用来回答：

> **当前决策需要哪些信息，这些信息来自哪里，优先级如何，怎么注入上下文。**

不同系统里，这层可能没有一个统一类名，但一定会以各种方式存在。

所以你以后看框架时，要注意找的不是某个叫 `InformationManager` 的类，而是：

> **它如何组织多来源信息进入模型上下文。**

这才是信息抽象的真正位置。

---

## 8. 第五个共同抽象：治理（Governance / Control）

到这一阶段，你前面已经学了很多治理相关能力：

- tracing
- eval
- retry
- timeout
- checkpoint
- human handoff

这些能力看起来分散，但其实它们背后对应的是同一个更高层问题：

> **如何让 Agent 系统可控、可观测、可恢复、可评估。**

这就是治理抽象。

为什么成熟系统一定会长出这层？

因为只要 Agent 从 Demo 走向真实系统，就不可能只靠：

- 模型能不能答对

还必须关心：

- 怎么查错
- 怎么限权
- 怎么回滚
- 怎么恢复
- 怎么审计
- 怎么评估

所以：

> **治理不是附加组件，而是成熟 Agent 系统的必要组成部分。**

---

## 9. 为什么这五个抽象会在不同系统中反复出现

到这里你应该开始发现规律了。

无论是：

- 你自己从零写的 Agent
- OpenAI Agents SDK
- Claude Code 这种产品级系统
- MCP 这类工具生态协议

它们虽然长相不同，但都逃不开这些根问题：

1. 系统有哪些能力
2. 当前系统处于什么状态
3. 下一步怎么推进
4. 当前决策需要哪些信息
5. 这个系统怎么被治理

只要问题空间相似，抽象就会逐渐收敛。

所以这不是巧合，而是：

> **工程问题相似，抽象结构自然相似。**

这就是你现在要学会的“框架共性识别能力”。

---

## 10. MCP、Agents SDK、Claude Code 各自更偏重哪一层

虽然它们有共同抽象，但侧重点并不一样。

这一点也非常值得你理解。

### MCP

更偏重：

> **能力层和互操作层**

它非常关心：

- 外部能力如何声明
- 如何发现
- 如何调用
- 如何在不同客户端之间共享

---

### OpenAI Agents SDK

更偏重：

> **单 Agent 运行时抽象**

它更像在帮你组织：

- Agent 定义
- Runner
- Tool 调用
- 会话运行

---

### Claude Code 这类系统

更偏重：

> **复杂真实任务下的调度、状态和治理整合**

例如：

- 任务分解
- 文件操作
- 长链路运行
- 可观测性
- 安全与接管

所以：

> **它们不是互相替代关系，而更像是在不同层面回答 Agent 系统的不同核心问题。**

---

## 11. 为什么这会帮助你以后看懂框架源码

如果你不掌握共同抽象，打开源码时很容易只看到：

- 一堆类
- 一堆方法
- 一堆事件

然后感觉很乱。

但如果你先有这套抽象框架，你再去看源码就会自然开始做映射：

- 这里是在定义能力
- 这里是在维护状态
- 这里是在做调度
- 这里是在组织信息
- 这里是在做治理

一旦能这样看，框架就不再神秘。

所以这一课真正是在帮你获得一种能力：

> **看框架时，不是从 API 细节看，而是从抽象分层看。**

这对后面读源码非常重要。

---

## 12. 为什么这一步也是你从“会用 Agent”到“能设计 Agent”的分水岭

很多人长期停留在：

> 我会调用一个 Agent 框架。

但只有当你开始识别这些共同抽象时，你才会逐渐具备：

> **自己做架构决策的能力。**

因为这意味着你不再依赖：

- 这个框架有没有这个类

而开始能主动问：

- 我这里缺的是能力层抽象，还是状态层抽象？
- 我的问题是调度不清，还是治理没跟上？
- 我现在该重构 Tool，还是该重构信息系统？

这才是真正的工程设计能力。

## 13. 第一版你应该怎么练这种“共同抽象识别能力”

这一课不是只用来“理解”的，还要开始练习。

当前阶段非常适合做下面几件事：

### 练习 1

回头看你自己的 Agent 项目，问自己：

- 能力层在哪里
- 状态层在哪里
- 调度层在哪里
- 信息层在哪里
- 治理层在哪里

---

### 练习 2

看到一个新框架时，不先研究 API，而先尝试画出它的五层抽象。

---

### 练习 3

对比两个系统，不问“语法差异”，而问：

> 它们在能力、状态、调度、信息、治理这五层分别怎么处理？

这个练习非常有效。

## 14. 这一课背后的核心工程思想

这一课真正训练的是：

> **从具体实现中抽离出稳定结构。**

这是一种很关键的高级工程能力。

初级学习者通常关注：

- 这个方法怎么调用
- 那个字段是什么意思

而成熟工程师会进一步关注：

> **这些具体实现背后，哪些结构是稳定反复出现的。**

这也是为什么我一直强调：

> **不要只学 API，要学抽象。**

因为最终让你跨系统迁移、跨框架理解、自己做设计的，不是记住了多少函数名，而是识别出了多少稳定结构。
