# Lesson23：从单 Agent 到多 Agent 之前，必须先理解的角色分工抽象

## 1. 本课目标

到这一课为止，你已经逐步搭起了一个相当完整的单 Agent 工程认知：

- Tool 系统
- Runner / Session / Memory
- RAG
- Checkpoint
- 调度与人工接管
- MCP 前置认知
- 多个框架背后的共同抽象

这时候很多人会自然进入下一个话题：

> **多 Agent。**

但一提到多 Agent，初学者很容易直接跳到：

- 两个 Agent 怎么互相发消息
- 多个 Agent 怎么并行
- AutoGen / CrewAI / LangGraph 怎么配

这其实太快了。

因为在真正理解多 Agent 之前，你必须先搞清楚一个更底层的问题：

> **为什么单 Agent 系统在复杂任务下，会自然长出角色分工需求？**

这就是这一课要解决的核心。

也就是说，这一课不是先讲“多 Agent 编排”，而是先讲：

> **角色分工抽象（Role Decomposition）**

因为很多看起来是“多 Agent 技术”的问题，本质上首先是：

> **任务结构和职责结构的问题。**

---

## 2. 为什么单 Agent 一开始看起来什么都能做

在任务还比较简单时，单 Agent 往往足够。

例如：

- 读取一个文件
- 调一个 Tool
- 回答一个问题
- 做一个简单总结

这时你会感觉：

> 一个 Agent 就够了。

而且这种感觉确实是对的。

因为任务规模还没到必须拆分的程度。

此时一个 Agent 同时承担：

- 理解需求
- 决定步骤
- 调用 Tool
- 组织答案

并不会显得很吃力。

所以：

> **单 Agent 不是落后方案，它是很多问题的正确起点。**

这一点要先认清。

---

## 3. 为什么任务一复杂，单 Agent 就会开始“角色过载”

问题通常不是出在第一个任务，而是出在复杂任务逐步增大之后。

例如一个复杂 Coding Agent 任务可能同时要求系统：

- 先理解用户目标
- 再规划任务步骤
- 再搜索代码
- 再修改实现
- 再运行验证
- 再审查结果
- 最后输出报告

你会发现，这里面其实混合了多种完全不同性质的工作：

### 工作 1：规划

决定先做什么、后做什么。

---

### 工作 2：执行

真的去读文件、搜代码、改代码、跑命令。

---

### 工作 3：校验

判断结果靠不靠谱，有没有遗漏或风险。

---

### 工作 4：汇报

把结论清晰交给用户。

如果全部塞进一个 Agent，常见结果就是：

> **它不是做不到，而是会越来越像“一个人同时扮演太多角色”。**

这就会带来角色过载问题。

---

## 4. 这一课最重要的一句话

请记住：

> **多 Agent 的起点不是“多几个模型实例”，而是“一个复杂任务里开始出现稳定、可分离的角色职责”。**

这句话非常关键。

因为很多人误以为：

> 多 Agent = 多个模型一起跑

这只是表面。

更深层地看，多 Agent 背后的真正动因是：

> **复杂任务内部开始出现不同类型的工作，它们更适合被不同角色承担。**

所以在你真正进入多 Agent 编排之前，先学会识别：

- 哪些职责本来就不同
- 哪些步骤应该被分工
- 哪些工作混在一起会让一个 Agent 过载

这才是多 Agent 的根。

---

## 5. 什么叫“角色分工抽象”

你可以先把它理解成：

> **把一个复杂任务中不同类型的职责，从“全塞给一个 Agent”改成“明确由不同角色承担”。**

注意，这里关键词是：

> **职责（Responsibility）**

不是：

> **线程数** 或 **实例数**

角色分工首先是逻辑层抽象。

例如在一个复杂任务里，天然可能出现这样的角色：

- Planner：负责任务分解与路线制定
- Executor：负责实际调用 Tool 与执行动作
- Reviewer：负责审查结果是否可靠

你看，角色分工最先发生在：

> **思考结构**

而不是部署结构。

---

## 6. 为什么 Planner / Executor / Reviewer 会反复出现

你后面看很多系统时，会发现这几个名字出现频率很高。

这不是巧合。

而是因为复杂任务在工程上天然就会出现这三类工作：

### 第一类：决定怎么做

这是 Planner。

它关注：

- 目标拆解
- 步骤排序
- 风险预判

---

### 第二类：真的去做

这是 Executor。

它关注：

- Tool 调用
- 文件操作
- 搜索分析
- 具体动作落地

---

### 第三类：判断做得对不对

这是 Reviewer。

它关注：

- 结果质量
- 风险遗漏
- 回归问题
- 是否满足原始目标

所以你现在要理解：

> **这些角色不是框架发明出来的，它们是任务结构自然逼出来的。**

---

## 7. 为什么“一个 Agent 同时做规划、执行、审查”会越来越不稳

在简单任务里，混合这三件事问题不大。

但任务一复杂，常见问题会越来越明显：

### 问题 1：规划和执行互相污染

Agent 一边想路线，一边陷入局部细节执行，很容易失去全局。

---

### 问题 2：执行和审查互相放水

同一个 Agent 做完了事情，再自己审核，很容易沿着原来的思路继续自洽，而不是严格发现问题。

---

### 问题 3：上下文负担过重

同一个上下文里同时承载：

- 目标规划
- 执行细节
- 审查标准

很容易让主线混乱。

所以角色不拆分时，问题往往不是“完全做不了”，而是：

> **越来越不稳、越来越难控、越来越难调。**

---

## 8. 为什么角色分工不一定一开始就意味着“多实例”

这点非常重要。

很多人会把“角色分工”直接等同于：

> 启动多个 Agent 实例

其实不是。

角色分工首先是架构设计思维。

第一阶段你完全可以先在单 Agent 项目里做“逻辑角色分层”，例如：

- 先有一个 `plan_step()`
- 再有一个 `execute_step()`
- 再有一个 `review_step()`

虽然最终还是一个系统在跑，但角色已经开始被分开建模。

这一步非常重要，因为它意味着：

> **你先学会分工，再决定是否真的拆成多 Agent。**

这比一上来就上多实例框架稳得多。

---

## 9. 什么样的任务更值得引入角色分工

不是所有任务都需要角色拆分。

当前阶段，你可以先识别几类高价值场景：

### 第一类：目标复杂、步骤多

例如：

- 分析整个项目
- 调试一个跨模块问题
- 生成完整报告

---

### 第二类：执行与判断标准明显不同

例如：

- 先修改代码
- 再按不同标准做审查

---

### 第三类：需要减少自我确认偏差

例如同一个 Agent 写完代码再自己说“看起来没问题”，风险通常较高。

如果有独立审查角色，会更稳。

---

### 第四类：任务可自然分阶段

例如：

- 规划
- 执行
- 复核

这类任务就非常适合角色化。

所以：

> **多 Agent 不是为了炫技，而是为了应对复杂任务中的天然职责差异。**

---

## 10. 为什么角色分工本质上是在做“职责解耦”

这和前面你学过的很多软件工程原则是一脉相承的。

我们前面一直在做的事情其实都是解耦：

- Agent 和 Runner 解耦
- LLM 接口与具体实现解耦
- Session 和 Memory 解耦
- Tool 和调用协议解耦

现在来到多 Agent 前置阶段，本质上还是同一件事：

> **把本来耦合在一个 Agent 身上的多种职责拆开。**

也就是说，多 Agent 不是突然开始的全新话题，而是：

> **前面解耦思维在任务层的一次延伸。**

这会帮助你把知识体系连起来。

---

## 11. 为什么角色分工会反过来提升可观测性和可调试性

这点非常重要，但很多人开始时感受不到。

当所有事情都由一个 Agent 混着做时，你看到一个错误结果，很难判断：

- 是规划错了
- 还是执行错了
- 还是审查没发现

但如果角色清晰后，调试会容易很多。

例如：

- Planner 规划就不合理
- Executor 明明拿到了好计划却执行偏了
- Reviewer 没识别出明显问题

这样一来，问题归因会更清楚。

所以：

> **角色分工不仅是为了做得更强，也是为了查得更清。**

这和前面学的治理、tracing、eval 主线是完全一致的。

---

## 12. 为什么角色分工会带来新的成本

这一点也要平衡看。

不能把多角色想成只有好处没有代价。

角色分工一旦引入，也会带来新的复杂度：

### 成本 1：协调成本

角色之间需要传递状态和结果。

---

### 成本 2：上下文同步成本

不同角色需要知道哪些共同事实、哪些局部事实，要设计清楚。

---

### 成本 3：系统复杂度上升

调度、handoff、恢复都会更复杂。

所以这也是为什么我一直强调：

> **先理解角色分工抽象，再决定是否真的上多 Agent。**

因为不是所有问题都值得立刻支付这些复杂度。

---

## 13. 第一版角色分工应该先做到什么程度

当前阶段，不要一上来就追求：

- 多个进程
- 多个模型
- 并行多角色对话

第一版更合理的目标是：

> **先学会在任务结构上清楚区分角色职责。**

也就是说，你至少先能回答：

- 哪部分是规划职责
- 哪部分是执行职责
- 哪部分是审查职责
- 哪些职责不应该混在一起

只要这一步做到了，后面你再进入真正多 Agent 编排就会顺得多。

这也是为什么这一课是“前置认知课”，而不是“框架实现课”。

---

## 14. 这一课背后的核心工程思想

这一课真正训练的是：

> **当复杂度上升时，不要只想着加更多能力，而要先考虑重新划分职责。**

这是一条非常核心的系统设计原则。

很多人一看到复杂任务做不好，第一反应是：

- 换更强模型
- 加更多 Tool
- 加更多 Prompt 规则

但很多时候更本质的办法是：

> **把不同性质的工作拆成不同角色。**

这就是为什么角色分工是多 Agent 之前必须理解的核心抽象。

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑一个你当前课程项目里最复杂的任务，写出它实际上混合了哪些不同职责。

例如：

- 规划
- 执行
- 审查
- 汇总

---

### 第二件

尝试把这个任务用“角色视角”重写一遍。

例如：

- Planner 负责什么
- Executor 负责什么
- Reviewer 负责什么

---

### 第三件

思考并回答：

> 当前这个任务如果仍然全塞给一个 Agent，最容易出现哪一类过载问题？

---

### 第四件

先不要真的拆多实例，只在逻辑设计上做一次角色分工练习。

---

### 第二
