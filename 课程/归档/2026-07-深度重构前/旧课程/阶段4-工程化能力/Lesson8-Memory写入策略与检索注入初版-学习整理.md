# Lesson8：Memory 写入策略与检索注入初版

## 1. 本课目标

上一课我们已经把一个非常重要的结构拆开了：

- `Session` 负责当前会话
- `Memory` 负责长期信息

并且建立了一个初步分层模型：

- 当前轮上下文
- 当前会话压缩信息
- 跨会话长期记忆

但是到这里，其实还只是“有了一个 Memory 容器”。

真正的工程问题现在才开始：

> **Memory 什么时候写？什么时候读？读多少？怎么避免把模型喂成噪音？**

这就是这一课要解决的核心问题。

一句话概括：

> **Memory 系统难的不是“存”，而是“写入策略”和“注入策略”。**

---

## 2. 为什么很多 Memory 系统看起来有，实际上没用

很多初学者做 Memory，第一版通常是这样：

```text
有信息就存

每次都全读
```

看起来像是“Agent 终于有记忆了”。

但很快就会出问题：

### 问题 1：什么都存

导致：

- Memory 很快膨胀
- 有价值信息被噪音淹没
- 后续检索效果变差

---

### 问题 2：什么都读

导致：

- 上下文再次变长
- 模型注意力被分散
- 本轮真正相关的信息反而不突出

---

### 问题 3：存了但不用

导致：

- 系统看起来复杂了
- 实际运行效果没有变好

所以 Memory 不应该理解成“开一个数据库”。

真正的重点是：

> **让 Memory 只吸收高价值信息，并且只在相关时机参与推理。**

---

## 3. 这一课最重要的一句话

请记住下面这句话：

> **一个好的 Memory 系统，不是记得最多，而是记得准、取得准、喂得准。**

这句话可以拆成三层：

### 记得准

写入前要筛选，不是所有信息都值得沉淀。

---

### 取得准

读取时要考虑相关性，不是所有记忆都应该被取出。

---

### 喂得准

注入模型时要控制量和格式，不是把取出来的内容原样全塞给模型。

这三步，缺哪一步都不行。

---

## 4. Memory 的第一版写入策略要解决什么问题

先看“写入”。

如果没有写入策略，Memory 最后会变成：

> **长期垃圾桶**

所以第一版写入策略要回答的其实不是技术问题，而是判断问题：

> **这条信息值不值得活到未来？**

在你当前阶段，第一版非常适合先用下面三个判断标准：

### 第一，是否稳定

例如：

- 用户长期偏好中文回答
- 项目是 SpringBoot + Redis + MySQL

这种信息不太容易一轮后就失效。

---

### 第二，是否高价值

例如：

- 订单流程核心在 `OrderService`
- 权限逻辑集中在 `AuthService`

这些信息能显著减少后续重复分析。

---

### 第三，是否可复用

例如：

- 下次继续分析这个项目时还会用到
- 之后写代码时仍然有参考价值

只有同时满足这些条件的信息，才值得进入第一版长期记忆。

---

## 5. 第一版写入触发时机

上一课我们提过一些写入时机，这一课把它收敛成更明确的工程规则。

第一版你可以只保留三类触发点：

### 触发点 1：阶段性任务完成后

例如：

- 一个模块分析完成
- 一轮代码审查完成
- 一次架构总结完成

这时候最适合沉淀“结论”，而不是中间过程。

---

### 触发点 2：明确稳定事实被确认时

例如：

- 技术栈确定
- 项目结构确定
- 核心模块归属确定

这类信息一旦确认，后续复用价值通常很高。

---

### 触发点 3：用户偏好被反复表达时

例如：

- 总是希望中文回答
- 希望代码示例简洁
- 喜欢先结论后展开

这种偏好属于高价值长期信息。

---

## 6. 为什么“每轮自动写 Memory”通常是坏主意

因为每一轮都有很多临时噪音。

例如：

- 模型的试探性推理
- 未验证的判断
- 过渡性步骤
- 一次性 Tool 输出

如果你每轮都自动写入 Memory，最后得到的通常不是“长期记忆”，而是：

> **长期污染**

所以第一版经验规则非常重要：

> **Memory 写入应该稀疏，而不是高频。**

这和日志系统不一样。

日志可以多，长期记忆不应该多。

---

## 7. 读取策略为什么和写入策略同样重要

很多人花很多时间研究“怎么存”，却忽略“怎么读”。

但从模型效果上看，读的策略往往更直接影响回答质量。

因为就算你存得很好，如果读取时：

- 不分任务类型
- 不分相关性
- 不控数量

那么这些 Memory 最终仍然会变成新的上下文噪音。

所以读取策略的核心问题是：

> **这次任务真正需要哪部分记忆？**

---

## 8. 第一版读取策略：按任务相关性注入

在当前阶段，你不需要一开始就做复杂召回算法。

第一版先建立一个非常实用的原则：

> **只有当 Memory 和当前任务相关时，才注入。**

例如：

### 场景 1：继续分析同一个项目

适合注入：

- 项目级事实
- 已确认模块归属
- 关键架构结论

---

### 场景 2：继续给这个项目写代码

适合注入：

- 项目结构
- 用户编码偏好
- 已确认的约束条件

---

### 场景 3：一个全新无关任务

这时很多旧 Memory 就不应该强行注入。

所以第一版即使没有复杂检索，也要先建立一个判断：

> **不是所有长期记忆都要参与每一次推理。**

---

## 9. 为什么“全量回灌”会让 Agent 变笨

这点很重要。

很多人以为：

```text
喂更多信息 = 更聪明
```

实际上常常相反。

当你把太多不相关记忆回灌给模型时，会出现：

1. 当前任务重点被稀释
2. 模型注意力分散
3. prompt 结构变混乱
4. token 成本进一步升高

所以一个成熟 Agent 的原则不是：

> **能注入多少就注入多少**

而是：

> **只注入对当前决策真正有帮助的少量信息**

这和搜索系统、推荐系统、本质上是同一种“相关性优先”思维。

---

## 10. 第一版注入方式应该长什么样

第一版最简单的方式，不是把 Memory 原样拼回消息流，而是：

> **把读出的相关记忆整理成一段结构化 memory context，再注入到 prompt 中。**

例如：

```text
Relevant memory:

- 用户偏好中文回答
- 当前项目使用 SpringBoot + Redis + MySQL
- 订单主流程位于 OrderService
```

这种方式有三个优点：

1. 对模型更友好
2. 比原始散乱记录更容易控制长度
3. 容易和 system / session summary 分开组织

所以在第一版里，你可以把 Memory 注入理解成：

> **先检索，再整理，再喂给模型。**

---

## 11. Memory 注入应该放在哪一层处理

这里也有一个很重要的职责问题。

### `MemoryStore`

负责：

- 存储记忆
- 提供查询接口

它不应该直接知道 prompt 怎么拼。

---

### `Runner`

负责：

- 在运行时决定是否查询 Memory
- 决定当前任务需要哪些记忆

---

### `Prompt Builder` 或上下文组装逻辑

负责：

- 把检索出的记忆整理成模型可消费的上下文片段

所以更清晰的理解是：

> **MemoryStore 管数据，Runner 管时机，Prompt 组装层管注入格式。**

这比让 `MemoryStore` 直接输出大段 prompt 更可维护。

---

## 12. 第一版可以不用复杂检索，也能做出正确结构

这一点很关键。

你现在不需要被下面这些词绑住：

- embedding
- similarity search
- rerank
- recall pipeline

这些后面会学。

当前阶段更重要的是先把结构搭对：

1. 有明确 Memory 分类
2. 有明确写入标准
3. 有明确读取时机
4. 有明确注入格式

如果这四点都没有，就算你接了向量库，效果也不会稳定。

所以第一版的目标不是“召回最聪明”，而是：

> **先让 Memory 真正以工程化方式参与 Agent 运行。**

---

## 13. 一个很实用的第一版流程

你可以把第一版 Memory 运行流程理解成下面这样：

```text
任务开始

↓

判断是否需要读取 Memory

↓

取出少量相关记忆

↓

整理成 memory context

↓

与 system prompt、session summary、recent messages 一起构造输入

↓

Agent 运行

↓

任务阶段结束

↓

判断是否有新的稳定高价值信息

↓

写入 Memory
```

这就是一个真正开始跑起来的最小 Memory 闭环。

---

## 14. 这一课背后的核心工程思想

这一课真正训练的不是“多会存数据”，而是：

> **如何把记忆从静态仓库变成动态运行机制。**

很多系统的问题是：

- 有数据库
- 有存储
- 有历史

但是没有真正的“记忆使用策略”。

结果就是：

> **看起来有 Memory，实际上对推理几乎没有帮助。**

所以 Agent 的 Memory 系统，关键不在于“有没有”，而在于：

> **有没有被正确写入、正确取出、正确注入。**

---

## 15. 和后面的 RAG 会怎么衔接

这一课其实已经在为后面的 RAG 铺路了。

因为后面你会发现：

- Memory 写入策略，和知识沉淀策略很像
- Memory 读取策略，和检索召回思路很像
- Memory 注入策略，和 RAG 的上下文组装很像

区别只是：

### 当前这一课

更偏：

> Agent 自己沉淀下来的长期记忆

### 后面的 RAG

更偏：

> 从外部知识源拿回相关知识

所以你现在学的其实已经不是“单纯记忆”，而是在学习：

> **信息什么时候进入模型上下文，为什么进入，以及怎么进入。**

---

## 16. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

为 `MemoryStore` 增加基本分类读取能力，例如：

- `get_preferences()`
- `get_project_facts()`
- `get_findings()`

---

### 第二件

在 `Runner` 中增加“任务开始前读取 Memory”的步骤。

哪怕先用简单规则判断相关性也可以。

---

### 第三件

把读取出的内容整理成一段独立的 memory context，而不是原样塞消息列表。

---

### 第四件

在阶段性任务结束时，只把稳定、高价值、可复用的信息写入 Memory。

---

## 17. 本课小结

今天最重要的三句话：

### 第一

> **Memory 的核心难点不是存储，而是写入策略和注入策略。**

### 第二

> **长期记忆不应该全量回灌，而应该按任务相关性选择性注入。**

### 第三

> **一个好的 Memory 系统，不是记得最多，而是记得准、取得准、喂得准。**
