## 本节目标

给当前最小 Agent Framework 增加第一层可观测性。

这一节不追求一上来做复杂日志系统，只做最小但正确的事情：

1. 让关键运行节点有日志
2. 让错误日志和普通流程日志分开
3. 让你在不打开调试器的情况下，也能知道一次运行大致经历了什么

也就是说，这一节的目标不是“把日志写满”，而是：

> 让系统第一次具备最小可观察运行轨迹

---

## 本节核心知识点

### 1. Logging 不是“多打印几行”

很多初学者第一次做日志，会直接写：

```python
print("calling llm")
print("tool result", result)
print("done")
```

这当然比没有强，但它不是工程意义上的 Logging。

因为真正的日志至少要解决这些问题：

- 这条信息属于哪一层
- 这是正常流程还是错误
- 这条信息以后还能不能被过滤、检索、追踪

所以 Logging 的第一层升级，不是“打印更多”，而是：

> 把输出从随手 print 变成结构化运行信息

---

### 2. Agent 项目最先应该打日志的地方不是 everywhere，而是关键边界

日志不是越多越好。

在当前阶段，最值得优先打日志的地方通常只有这些：

#### 1. Runner 入口

例如：

- 收到用户输入
- 开始一次运行

#### 2. LLM 调用前后

例如：

- 准备调用模型
- 模型返回了什么类型的响应

#### 3. Tool 调度前后

例如：

- 准备执行哪个 Tool
- Tool 执行是否成功

#### 4. 错误边界

例如：

- ToolManager 失败
- LLM 调用失败
- Runner 终止运行

也就是说：

> 第一版日志应该打在“系统边界”上，而不是打满每一行代码

---

### 3. Logging 的本质是给未来的你留线索

很多人一开始写日志时，容易陷入一个误区：

> 我现在都知道代码在干什么，为什么还要写日志？

但日志真正服务的，不是“你现在写代码这一刻”，而是：

- 你三天后回来排查问题的时候
- 你加了 Memory 之后系统行为变复杂的时候
- 你接入 MCP 之后出现异常调用链的时候

日志本质上是在做一件事：

> 给未来的你留下足够的运行线索

这也是为什么 Logging 属于工程化能力，而不是语法层面的补充。

---

## 本节推荐的最小做法

当前阶段不需要上复杂日志平台，也不需要一上来做 JSON logging。

最小正确做法就够了：

### 第一步

统一用 `logging` 模块，而不是继续散落 `print()`

例如：

```python
import logging

logger = logging.getLogger(__name__)
```

### 第二步

至少区分日志级别：

- `info`
- `warning`
- `error`

### 第三步

在关键节点补日志：

- Runner 开始
- LLM 调用前后
- Tool 执行前后
- 错误发生时

这一版已经足够让系统从“黑盒跑一下”升级到“能看到大致路径”。

---

## 当前项目里最适合先补日志的模块

### `runner.py`

因为 Runner 是主流程中枢，最适合记录：

- 本轮开始
- 当前是否进入 Tool Call 分支
- 本轮结束

### `tool_manager.py`

最适合记录：

- 执行了哪个 Tool
- 参数是什么
- 是否成功

### `llm.py`

最适合记录：

- 调用了哪个 provider
- 请求是否成功
- 返回了哪类输出

### 不建议现在就重点打的地方

- 每一条 message 的完整大段内容
- 每一层内部很细碎的函数细节

因为第一版日志应该先解决“看清主路径”，而不是制造大量噪音。

---

## 本节一个非常重要的工程意识

日志不是越多越专业。

如果现在把所有地方都打满日志，很快会出现两个问题：

- 重要信息被淹没
- 后续一出问题，根本不知道该看哪条

所以第一版最重要的原则是：

> 少，但打在边界上

这和前面一直强调的系统设计方法是一致的：

- 边界清晰
- 职责清晰
- 可观察点也要清晰

## Code Review 视角

### 不推荐的写法

```python
print("start")
print("messages", messages)
print("response", response)
print("tool", tool_name)
print("done")
```

问题在于：

- 没有级别
- 没有模块边界
- 后续难以控制输出量

### 更推荐的写法

```python
logger.info("Runner started")
logger.info("Calling LLM")
logger.info("Dispatching tool: %s", tool_name)
logger.error("Tool execution failed: %s", exc)
```

重点不在于形式多高级，而在于：

> 让日志语义化，并且围绕边界组织

---

## 官方框架怎么做

成熟框架通常不会把日志当成“调试时临时加的 print”。

它们一般会把日志作为运行时的一部分来设计：

- 运行开始日志
- 模型调用日志
- Tool 调度日志
- 错误日志
- Trace / Span 关联

也就是说，在成熟框架里：

> Logging 不是附属能力，而是运行时观察系统的一部分

所以这一节其实是在给后面的 Tracing 铺路。
