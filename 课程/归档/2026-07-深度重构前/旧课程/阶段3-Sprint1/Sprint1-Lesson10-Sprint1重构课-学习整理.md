## 本节目标

把 `Sprint 1` 前 9 节里逐步搭起来的最小 Agent，做一次系统性整理。

这一节的目标不是大改架构，而是完成三件事：

> 把前面已经做出来的东西，整理成一个真正像项目的版本

## 本节核心知识点

### 1. 为什么阶段性重构是必须的

很多初学者最容易犯的错误就是：

> 每一节都只加新东西，从来不回头整理

短期看，这样好像进度更快。

但长期一定会出现几个问题：

- lesson 临时写法越来越多
- 命名开始不统一
- 某些逻辑重复出现
- 模块职责重新变模糊
- 明明代码能跑，但越来越难改

所以 Sprint 式学习里，重构课不是“锦上添花”，而是：

> 防止项目在学习过程中逐步腐化的必要动作

---

### 2. 重构不等于推翻重写

很多人一听到“重构”，会本能地觉得：

- 是不是要大改
- 是不是要重写很多代码
- 是不是前面都白做了

这其实是误解。

Sprint 1 的重构课更准确地说是：

> 收敛（Consolidation）

它的重点是：

- 合并临时实现
- 统一命名
- 固定边界
- 去掉明显重复

而不是推翻前面做的内容。

所以这节课不是“重新开始”，而是：

> 把前面已经做对的东西正式定型

---

### 3. 当前阶段最容易出现的技术债是什么

经过前面 9 节的持续推进，当前最可能出现的技术债通常包括：

#### 1. 临时文件或临时版本痕迹

例如：

- `lesson` 版实现
- 早期占位代码
- 旧结构残留

#### 2. 命名不一致

例如：

- 有的地方叫 `tool_registry`
- 有的地方叫 `tools`
- 有的地方叫 `tool_manager`

#### 3. 消息组织逻辑重复

例如：

- Runner 里还有一些消息构造残留
- Session 里已经开始有上下文能力
- 两边职责可能有重叠

#### 4. 错误边界不完全统一

例如：

- 有的地方直接 `raise`
- 有的地方直接 `return error`
- 有的地方只是打印

这些问题单看都不致命，但如果不在这个节点清理，后面加 Memory、MCP、RAG 时就会越来越痛苦。

## 本节推荐的重构范围

这一节不要贪大，建议只做 Sprint 1 范围内最关键的收敛。

### 1. 模块边界收敛

确认以下职责边界是否稳定：

- `Agent`：只负责配置
- `Runner`：只负责流程调度
- `Session`：只负责上下文状态
- `ToolManager`：只负责工具注册与执行
- `OpenAILLM`：只负责模型调用

如果某个类开始“顺手多管一点”，这一节就要及时收回来。

### 2. 命名收敛

统一：

- 方法名
- 变量名
- 文件命名方式
- session / message / tool 相关术语

这一步比很多人想象中更重要，因为后面项目一大，命名不统一会显著拉高理解成本。

### 3. 错误处理收敛

统一明确：

- 哪些层负责抛错
- 哪些层负责转换错误
- 哪些层负责终止运行

不要让错误风格一半在 ToolManager，一半在 Runner，一半在 LLM 层乱飘。

### 4. 测试收敛

检查：

- 现有测试是否覆盖了当前稳定边界
- 是否有一两个最关键路径还没测
- 测试命名是否清晰

这一节不要求测试变多很多，但要求它们和当前模块边界对齐。

## 本节一个非常重要的工程意识

很多人在学习项目里会产生一个误区：

> 只要代码还能跑，就先别动

这其实是非常危险的。

因为对于成长中的框架项目来说，更重要的不是“现在勉强还能跑”，而是：

> 下一个 Sprint 开始时，你还能不能放心往上继续搭

重构课的价值就在这里：

它不是为了“今天更优雅”，而是为了：

> 给下一个阶段腾出干净地基

## Code Review 视角

### 不推荐的推进方式

```text
Lesson 1 加一点
Lesson 2 加一点
Lesson 3 加一点
...
Lesson 10 继续加一点
```

一直只加不收敛。

这种方式的典型后果是：

- 项目越学越像教程拼接物
- 文件边界越来越虚
- 测试越来越跟不上
- 后续重构成本突然暴涨

### 更推荐的推进方式

每完成一个小阶段，就做一次：

- 收敛
- 去重
- 命名统一
- 边界确认

这才是接近真实团队节奏的做法。

---

## 官方框架怎么做

成熟框架并不是一开始就长成最终形态的。

它们也会经历很多轮：

- 增加能力
- 发现边界问题
- 重构收敛
- 再继续扩展

只不过这些过程在你看到它的公开版本时，已经被“整理干净”了。

所以自己做 Agent Framework 时，一定要主动加入这种节奏：

> 每几个迭代就安排一次结构整理

这不是拖慢开发，而是让后续开发变快。

---

## 本节最重要的一句话

> Sprint 的价值不只是做出功能，更是周期性把功能收敛成稳定结构。

这句话非常值得记住。

因为很多学习项目最后失败，不是功能做不出来，而是：

> 没有重构课，导致项目长期处在“能跑但越来越乱”的状态

## Sprint 1 完成标准

到这一节结束时，Sprint 1 应该形成一个最小但稳定的 Agent 基础版本，至少具备：

- 配置层：Agent
- 运行层：Runner
- 模型层：BaseLLM / OpenAILLM
- 工具层：ToolManager + 多 Tool
- 上下文层：Session + Prompt / Message 组织
- 验证层：最小测试
- 边界层：错误处理初版

如果这些都已经形成，那么你就已经真正完成了：

> 第一个“不是 demo，而是可以继续进化的最小 Agent Framework”

## 下一步

Sprint 1 完成之后，下一阶段最自然的方向不再是继续往单 Agent 里堆功能，而是进入：

> 工程化能力阶段

建议优先顺序是：

1. Logging
2. Tracing
3. Retry / Timeout
4. Config management
5. Token / Context 管理

也就是说，从下一阶段开始，课程会正式从：

> 做出一个 Agent

> 做出一个能持续演进的 Agent 工程项目
