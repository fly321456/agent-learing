# Sprint 1 - Lesson 6 面试题整理

## 题目 1

**问题：** 为什么在 Agent 项目里，Prompt 不能只当作一段临时字符串处理？

**参考答案：** 因为 Prompt 不只是提示词，它实际上决定了模型的角色边界、任务目标和行为约束，属于系统配置的一部分。如果把它当作临时字符串散落在代码里，后续会很难维护、复用和调试，也不利于判断问题究竟来自 Prompt 设计还是运行逻辑。因此从工程角度看，Prompt 应该被稳定管理，而不是随手拼接。

**追问方向：** Prompt 从字符串升级为正式模块后，最先带来的工程收益是什么？

**易错点：** 认为 Prompt 只是文案，不属于架构设计范畴。

## 题目 2

**问题：** 为什么说 `messages` 在 Agent 里不是普通数组，而是运行时上下文？

**参考答案：** 因为 `messages` 不只是保存聊天记录，它实际上是模型在当前轮次中能看到的全部上下文。模型是否理解任务、是否正确选择 Tool、是否能基于 Tool Result 继续推理，都直接依赖这份上下文的组织方式。所以在 Agent 系统里，messages 更接近运行时状态的一部分，而不是简单的数据列表。

**追问方向：** 如果 `messages` 组织混乱，会具体表现为哪些问题？

**易错点：** 把消息列表仅仅看成调用 API 所需的参数格式。

## 题目 3

**问题：** 为什么 Tool Result 不应该简单伪装成一条普通 user message？

**参考答案：** 因为 Tool Result 本质上不是新的用户输入，而是系统在当前运行时阶段获得的外部执行结果。如果把它伪装成普通 user message，会模糊用户意图和系统观察结果的边界，导致模型更难稳定理解当前状态。更合理的做法是以明确的结构或至少清晰标注的方式回填 Tool Result，让模型知道这是一条工具执行反馈。

**追问方向：** 如果继续把 Tool Result 当作 user message，后面最容易出现什么错误行为？

**易错点：** 觉得“只要模型看得到结果就行”，忽略上下文语义边界。

## 题目 4

**问题：** 为什么在这一节建议把消息组织逻辑从 `Runner.run()` 里抽成辅助方法？

**参考答案：** 因为随着系统演进，消息构造、Tool Result 回填和多轮上下文维护会变得越来越复杂。如果所有这些逻辑都堆在 `run()` 里，主流程会迅速变得难读难改。先把消息组织逻辑提炼成像 `_build_initial_messages`、`_append_tool_result` 这样的辅助方法，可以让主循环保持清晰，也为后续正式引入 Session 抽象创造条件。

**追问方向：** 什么信号说明某段消息组织逻辑已经值得被抽成单独方法？

**易错点：** 觉得现在逻辑少，全部写在 `run()` 里也无所谓。

## 题目 5

**问题：** 为什么这一节虽然没有新增 Tool 或 Memory，却依然是架构上重要的一节？

**参考答案：** 因为它解决的是 Agent 运行时最核心但最容易被忽略的问题：上下文如何组织。哪怕 Tool、Loop、LLM 都有了，如果消息组织混乱，系统仍然会表现不稳定。通过明确 system prompt、user input 和 tool result 的进入方式，这一节实际上是在为后续 Session、Memory、多轮对话和更复杂运行时状态管理打基础。

**追问方向：** 如果跳过这一节，直接进入 Session 或 Memory，后续最可能出现什么混乱？

**易错点：** 只把“新增功能”看成进度，把“整理运行时上下文”看成可有可无。

## 题目 6

**问题：** 为什么说“Agent 的上下文不是拼接出来的文本，而是组织起来的运行时状态”？

**参考答案：** 因为对于 Agent 来说，Prompt、用户输入、Tool Call、Tool Result 和多轮消息并不是彼此独立的文本片段，而是共同构成模型当前决策基础的运行时状态。如果只是把它们当作字符串拼接，系统很快会失去边界感，难以维护和扩展。把上下文看成运行时状态，才会自然引出 Session、Message Store、Conversation State 这些更成熟的抽象。

**追问方向：** 这种“状态化的上下文观”会如何影响后续 Memory 设计？

**易错点：** 把上下文管理简化成字符串拼接技巧，而不是运行时设计问题。
