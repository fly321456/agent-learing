# Sprint 1 - Lesson 7 面试题整理

## 题目 1

**问题：** 为什么在 Agent 项目里，`messages` 不能长期只是 Runner 里的局部变量？

**参考答案：** 因为一旦系统开始支持多轮交互、Tool Result 回填、上下文延续和后续的 Memory 接入，消息列表就不再只是临时数据，而是运行时状态的一部分。如果它继续裸露在 Runner 主流程里，Runner 就会同时承担流程控制和上下文管理职责，导致边界混乱、难以扩展。把它提升为 Session，才能让上下文管理成为独立能力。

**追问方向：** 如果继续把上下文裸放在 Runner 里，后续最容易在哪些地方失控？

**易错点：** 觉得 list 已经够用了，不需要额外抽象。

## 题目 2

**问题：** Session 在 Agent 系统里更准确的定位是什么？

**参考答案：** Session 不是简单的聊天记录，而是当前 Agent 运行过程中的上下文容器。它负责保存消息历史、提供追加接口、暴露完整上下文给 LLM，并成为后续接入多轮对话、Memory、上下文裁剪和恢复能力的落点。因此 Session 更接近运行时状态对象，而不是普通的数据结构包装。

**追问方向：** Session 和未来的 Memory 在职责上应该如何区分？

**易错点：** 把 Session 理解成“只是一个 messages 数组”。

## 题目 3

**问题：** 为什么 Session 应该属于运行时层，而不是放回 Agent 里？

**参考答案：** 因为 Agent 保存的是静态配置，例如 LLM、Prompt 和 Tools，而 Session 保存的是动态状态，例如当前消息、当前轮次和 Tool Result 回填位置。前者回答“我是谁”，后者回答“我现在运行到了哪里”。把 Session 塞回 Agent，会重新混淆配置层和运行时层的边界，破坏前面建立起来的架构分层。

**追问方向：** 如果未来要同时运行多个会话，Agent 和 Session 的关系应该怎样理解？

**易错点：** 认为和 Agent 有关的东西都应该放进 Agent 类里。

## 题目 4

**问题：** 为什么从这一节开始，Runner 应该更多像“调度器”而不是“消息管理器”？

**参考答案：** 因为 Runner 的核心职责是驱动流程：调模型、判断 Tool Call、调用 ToolManager、控制循环结束。消息历史和上下文追加属于运行时状态管理，应该由 Session 负责。只有当 Session 管状态、Runner 管流程时，系统边界才会清晰，后续扩展多轮对话、Memory 和恢复能力时也不会让 Runner 膨胀成上帝对象。

**追问方向：** 如果 Runner 继续同时负责流程和上下文，会对后续测试造成什么影响？

**易错点：** 把“能跑”当作架构合理的证明。

## 题目 5

**问题：** 为什么 Session 的第一版虽然简单，但仍然是一个关键架构节点？

**参考答案：** 因为它决定了后续几乎所有运行时增强能力的接入位置。无论是多轮对话、上下文裁剪、Token 管理、Memory 注入还是 Checkpoint 恢复，最终都需要依赖一个稳定的上下文容器。如果这一层迟迟不建立，后面的每一种能力都会被迫直接塞进 Runner，造成结构失控。因此 Session 初版虽然简单，但它是一个关键边界对象。

**追问方向：** 如果跳过 Session，直接去做 Memory，会在哪些地方卡住？

**易错点：** 觉得 Session 只是工程整洁性问题，而不是运行时设计问题。

## 题目 6

**问题：** 为什么说“当上下文开始影响系统行为时，它就不应该继续只是局部变量”？

**参考答案：** 因为一旦上下文开始决定模型能看到什么、能调用什么 Tool、能否继续推理以及最终如何回答用户，它就已经成为系统行为的一部分，而不再只是临时数据。继续把它当作局部变量，会导致行为依赖关系隐藏在实现细节里，难以调试和扩展。把它升级为 Session，意味着正式承认上下文是运行时状态的一等公民。

**追问方向：** 这种“上下文对象化”的思路，后续会如何影响 Token 管理和恢复机制设计？

**易错点：** 把上下文管理看成消息拼接技巧，而不是系统状态管理。
