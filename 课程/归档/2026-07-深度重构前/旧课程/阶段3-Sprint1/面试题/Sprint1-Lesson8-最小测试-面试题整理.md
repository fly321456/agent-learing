# Sprint 1 - Lesson 8 面试题整理

## 题目 1

**问题：** 为什么 Agent 项目通常要比很多普通脚本更早引入测试？

**参考答案：** 因为 Agent 项目即使代码量不大，也很快会出现循环、Tool 调用、消息上下文、运行时对象和多层抽象等结构。一旦这些组合起来，系统就不再是“一眼能看出有没有坏”的简单脚本，而是具有多条执行路径和多种状态变化的运行时系统。因此 Agent 项目往往比普通脚本更早需要测试，不是因为它更长，而是因为它更容易在演进中悄悄出错。

**追问方向：** 哪些信号说明一个项目已经过了“可以先不测”的阶段？

**易错点：** 认为“代码还少”就等于“暂时不需要测试”。

## 题目 2

**问题：** 为什么当前阶段测试重点应该放在 ToolManager、Session 和 Tool，而不是模型回答质量？

**参考答案：** 因为当前阶段最需要验证的是我们自己系统的边界是否正确，例如工具注册和执行是否正常、Session 是否能正确保存上下文、纯函数 Tool 是否返回预期结果。这些部分稳定、可控、可重复。而模型回答质量会受到 API、模型版本、Prompt 微调等多种因素影响，暂时不适合作为第一层主测试目标。工程上应先测自己能稳定控制的部分，再逐步扩展到更复杂的集成行为。

**追问方向：** 哪些测试属于“测系统边界”，哪些已经开始进入“测模型效果”？

**易错点：** 一上来就把“模型答得好不好”当成唯一测试指标。

## 题目 3

**问题：** 为什么 Runner 在当前阶段更适合做最小行为测试，而不是完整真实接口测试？

**参考答案：** 因为 Runner 同时连接了 Session、ToolManager、LLM 和 Loop，是当前系统里耦合最多的一层。如果一开始就对它做很重的真实接口测试，测试会变得脆弱、昂贵，而且一旦失败很难定位到底是哪一层出了问题。当前阶段更适合通过假的 LLM 或可控响应对象来验证 Runner 是否按预期调用依赖、处理 Tool Call、回填 Tool Result 和结束循环。

**追问方向：** 什么情况下 Runner 的测试可以逐步从行为测试升级为更完整的集成测试？

**易错点：** 觉得最核心的模块就必须最先做重测试。

## 题目 4

**问题：** 为什么假 LLM（FakeLLM）在测试 Runner 时很有价值？

**参考答案：** 因为 FakeLLM 可以返回完全可预测的响应，从而把测试重点从“模型会不会随机变化”转移到“Runner 是否正确处理响应”。这让测试更稳定、更可控，也更适合定位问题。通过 FakeLLM，开发者可以专注验证运行时逻辑，例如是否正确进入 Tool 分支、是否追加 Tool Result、是否在无 Tool Call 时结束。

**追问方向：** FakeLLM 和 Mock 的区别在这个场景下怎么理解？

**易错点：** 认为测试 LLM 相关逻辑就必须真的连 API。

## 题目 5

**问题：** 为什么这一节虽然没有新增用户功能，却仍然是工程上的关键升级？

**参考答案：** 因为它补的是“系统可验证性”这一层能力。没有测试，前面做出来的 Agent 只是“暂时能跑”的代码，后续每次新增 Tool、调整 Session、重构 Runner 都会变得越来越危险。增加最小测试意味着项目第一次进入“改完知道有没有坏”的状态，这对后续工程演进的价值远高于继续堆一个新功能。

**追问方向：** 从“功能新增”视角和“工程升级”视角看，这一节的价值分别是什么？

**易错点：** 觉得只有用户可见能力增加才算课程推进。

## 题目 6

**问题：** 为什么说“当系统开始出现运行时对象时，测试就必须尽快补上”？

**参考答案：** 因为运行时对象一旦出现，例如 Runner、Session、ToolManager，它们之间的依赖和状态流转就会迅速增加。此时系统错误不再只表现为函数返回错值，而可能体现在消息追加顺序、循环终止条件、工具调度路径等更隐蔽的问题上。如果没有测试，这些问题会在后续功能扩展中不断累积，最终让项目变得难以安全重构。因此测试必须跟着运行时抽象一起出现，而不是留到系统复杂后再补。

**追问方向：** 运行时对象比纯函数对象更需要测试的核心原因是什么？

**易错点：** 把测试只理解为“对纯函数做断言”，没有意识到运行时状态更需要验证。
