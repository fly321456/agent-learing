# Sprint 1 - Lesson 8 学习整理

## 本节定位

到上一节为止，我们已经把最小 Agent 的运行时骨架基本搭出来了：

- `Agent`
- `Runner`
- `BaseLLM / OpenAILLM`
- `ToolManager`
- `Prompt / Message` 组织
- `Session`

这时大多数初学者会本能地做一件事：

> 继续加功能

但真正的工程训练在这里应该先踩一下刹车。

因为如果系统开始有多个运行时对象，却还没有最基本的测试，后面每增加一点功能，都会让你越来越不敢改代码。

所以这一节的重点不是新增能力，而是：

> 给当前最小 Agent Framework 补上第一层工程验证能力

也就是：

> 最小测试

---

## 本节目标

这一节不追求测试覆盖率漂亮，也不追求一口气把所有东西都测全。

本节真正目标只有一个：

> 建立最小可用的测试习惯，让当前 Agent 项目进入“可验证状态”

这一节建议优先测试三类东西：

1. `ToolManager`
2. `Session`
3. `Runner` 的最小主流程

也就是说，我们要从“代码能跑”升级到：

> 代码改完之后，知道它有没有坏

---

## 本节核心知识点

### 1. 为什么 Agent 项目比普通脚本更早需要测试

很多人会觉得：

> 现在代码还不多，先别急着写测试

这在普通一次性脚本里有时成立，但在 Agent 项目里，这个判断通常是错的。

因为 Agent 项目很快会出现这些东西：

- 循环
- Tool 调用
- 多轮消息
- 运行时上下文
- 分层抽象

一旦这些元素叠加起来，你就很难再单靠“肉眼运行一次看看”确认系统有没有坏。

所以 Agent 项目比很多普通小脚本更早需要测试。

不是因为它代码量大，而是因为：

> 它的运行路径多、状态多、组合多

---

### 2. 这一节不测“大模型聪不聪明”，而测“我们的系统边界”

测试 Agent 项目有一个很容易走偏的地方：

很多人一上来就想测：

```text
模型回答得好不好
```

这其实不是当前阶段最值得测的东西。

当前最应该测的是：

- ToolManager 能不能按名字正确找到 Tool
- ToolManager 能不能正确执行有参 / 无参 Tool
- Session 能不能正确保存消息
- Runner 遇到最小输入时是否按预期调用依赖

也就是说：

> 当前阶段测试的是我们自己的系统边界，而不是模型输出质量

这是非常重要的测试观念。

---

### 3. 测试要优先覆盖“最稳定的部分”

现在项目里，不是所有层都适合同样方式测试。

#### 适合先测的

- 纯函数 Tool
- ToolManager
- Session

因为这些部分：

- 输入输出清晰
- 外部依赖少
- 结果稳定

#### 暂时不适合重测的

- 真实联网 LLM 输出内容

因为这类测试在当前阶段会受到：

- API 波动
- 模型版本变化
- 提示词差异

影响，不适合作为第一层主测试。

所以测试策略应该是：

> 先测我们能稳定控制的边界

---

## 本节推荐的最小测试拆分

这一节建议至少新增一个 `tests/` 目录，并从下面三个文件开始：

### 1. `test_tools.py`

测试纯 Tool 行为，例如：

- `get_current_time()` 是否返回字符串
- `calculator("18*29")` 是否得到 `522`

### 2. `test_tool_manager.py`

测试：

- Tool 是否注册成功
- `get_schemas()` 是否返回预期 schema
- `execute()` 是否能按名字调用正确 Tool

### 3. `test_session.py`

测试：

- 初始化时是否包含 system instructions
- `add_user_message()` 是否正确追加
- `add_tool_result()` 是否正确追加
- `get_messages()` 是否返回完整历史

这三类测试一旦有了，项目就会第一次真正具备“改完能验证”的基础。

---

## Runner 为什么这节不建议先做重集成测试

很多人会问：

> Runner 不是最核心吗？为什么不先把它完整测透？

原因是：

Runner 现在牵涉到太多层：

- Session
- ToolManager
- LLM
- Loop

如果一上来就写很重的集成测试，会很容易：

- 测试写得很脆弱
- 出问题时很难定位
- 变成“模型没答对，到底是哪个模块错了”

所以更合理的顺序是：

1. 先把 ToolManager / Session 这类稳定边界测住
2. 再给 Runner 补少量最小流程测试

这才是可持续的工程推进方式。

---

## 本节建议的 Runner 测试方式

Runner 在当前阶段更适合做：

> 最小行为测试

而不是做“大而全”的真实接口测试。

例如你可以用一个假的 LLM：

```python
class FakeLLM(BaseLLM):
    def generate(self, messages, tools=None):
        ...
```

让它返回一个可预测的最小响应。

这样测试的重点就会变成：

- Runner 有没有调用 LLM
- Runner 有没有把 Tool Result 回填
- Runner 有没有在没有 Tool Call 时结束

这类测试更稳定，也更能说明你自己的代码边界是否正确。

## Code Review 视角

### 不推荐的写法

```python
先什么都不测，继续写 Memory、MCP、Multi-Agent
```

这样做短期看起来进度很快，长期几乎一定会出问题。

因为你会越来越怕改已有逻辑，最后项目会进入一种状态：

> 代码越多，信心越少

### 更推荐的做法

现在就给最稳定的层补最小测试：

- Tool
- ToolManager
- Session

等这些边界稳了，再继续长功能。

这就是典型的工程节奏控制。

---

## 官方框架怎么做

成熟框架通常不会等“功能全做完”才加测试。

它们会非常早就开始测试这些边界：

- schema 生成是否正确
- tool dispatch 是否正确
- session / context 行为是否正确
- runner 的核心状态流转是否正确

因为真正的框架开发者很清楚：

> 没有测试的运行时抽象，很快就会变成无法安全演进的代码堆

所以这一节其实是在补：

> Framework 开发的最低工程纪律

---

## 本节最重要的一句话

> 当系统开始出现运行时对象时，测试就不再是“以后再说”，而是当前就必须补上的能力。

这句话对 Agent 项目尤其重要。
