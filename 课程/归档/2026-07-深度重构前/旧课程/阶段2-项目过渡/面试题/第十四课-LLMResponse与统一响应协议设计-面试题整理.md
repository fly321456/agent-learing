# 第十四课面试题整理

## 题目 1

**问题：** 第十三课讲“为什么要结构化输出”，第十四课为什么还要单独讲 `LLMResponse` 与统一响应协议设计？

**参考答案：** 因为“知道要结构化”只是方向，而工程落地真正困难的地方在于：到底要设计一个什么样的响应对象来承接 Agent 输出。第十三课解决的是意识升级，第十四课解决的是接口落地。如果没有统一响应协议，后续很容易变成在代码里零散地塞 `content`、日志、工具结果和前端字段，最后虽然表面上在做结构化输出，实际上只是把临时信息拼在一起，缺少稳定语义和系统边界。

**追问方向：** 如果不先设计协议，直接在 `llm.py` 里加字段，最容易出现什么问题？

**易错点：** 觉得“结构化输出”和“统一响应协议设计”是重复内容。

## 题目 2

**问题：** 统一响应协议真正“统一”的是什么？

**参考答案：** 它统一的不是不同 SDK 的字段名，而是上层系统真正关心的结果语义。系统关心的不是 OpenAI、Claude、Qwen 各自原始返回层级怎么命名，而是：最终答案是什么、是否发生了工具调用、有哪些过程事件、有没有适合前端消费的 blocks、为什么这次响应结束。统一响应协议的本质，就是用系统自己的语言重新描述模型输出。

**追问方向：** 为什么说这是“语义统一”而不是“字段格式统一”？

**易错点：** 以为只要把各家 SDK 的字段改成同名就算完成抽象。

## 题目 3

**问题：** 一个最小可用的 `LLMResponse` 为什么至少需要 `content / tool_calls / events / blocks / finish_reason / raw_response` 这些字段？

**参考答案：** 因为它们分别承接了系统中的稳定结果语义：`content` 提供最易读的最终文本；`tool_calls` 显式记录工具调用；`events` 记录过程事件；`blocks` 承载更适合前端组件渲染的结构化内容；`finish_reason` 解释这次响应为什么结束；`raw_response` 保留底层原始对象作为调试和迁移逃生口。这组字段已经足以支撑 CLI、调试、工作台、协议演进和未来工程化扩展，是一个最小但完整的系统响应雏形。

**追问方向：** 如果只能保留 2 到 3 个字段，你会优先保留哪些，为什么？

**易错点：** 把这些字段看成“为了完整性凑出来的集合”，而不是每个都有独立职责。

## 题目 4

**问题：** 为什么 `tool_calls` 不能省，或者直接塞进 `content` 里描述？

**参考答案：** 因为 Tool Calling 是 Agent 核心能力之一，不应该作为隐含文本留在自然语言里。只放进 `content` 的结果是：调试时无法稳定知道工具是否被调用、调用参数是什么、执行成功还是失败，也很难在前端工作台展示执行过程。单独抽象 `tool_calls` 能让工具执行从“隐藏行为”变成“显式协议数据”，从而支持调试、展示、统计、回放和治理。

**追问方向：** 一个最小可用的 `ToolCall` 子结构最少应该有哪些字段？

**易错点：** 觉得工具结果只是“补充说明”，不属于核心输出。

## 题目 5

**问题：** 为什么 `events` 不能简单等同于日志？

**参考答案：** 因为日志主要是给开发者阅读的自由文本，而事件流是给系统消费的结构化协议。日志可以很随意，但事件需要让前端、Runner、Tracing、测试等系统稳定理解。例如 `tool_call`、`tool_result`、`planning`、`analysis` 这些事件类型都应该有明确结构。只有把过程信息提升为正式事件，Agent 系统的“过程可见”才真正成立。

**追问方向：** `events` 最适合被哪些系统或模块消费？

**易错点：** 觉得有日志就不需要单独的事件流。

## 题目 6

**问题：** 为什么 `blocks` 和 `content` 不是互相替代，而是互补关系？

**参考答案：** 因为两者承担的职责不同。`content` 提供最简单、最稳定、最易调试的自然语言结果；`blocks` 提供更适合前端工作台和结构化组件渲染的内容组织形式。一个成熟系统里，`content` 常常作为兜底文本保留，而 `blocks` 作为产品化展示协议存在。只保留 `content` 会失去结构化渲染能力，只保留 `blocks` 又会失去很多调试和简单展示场景的便利。

**追问方向：** 什么场景下最适合优先读取 `content`，什么场景更适合优先读取 `blocks`？

**易错点：** 认为有了 `blocks` 就不再需要 `content`。

## 题目 7

**问题：** 为什么 `finish_reason` 是一个容易被忽略但非常关键的字段？

**参考答案：** 因为一次 Agent 响应结束的原因并不总是“正常完成”。它可能是模型主动停止、达到终止条件、工具失败后中止、命中 guardrails、外部超时等。没有 `finish_reason`，调用方只能猜测系统为什么停在这里。这个字段的价值在于给“为什么结束”提供显式解释，使调用方、调试系统和未来治理逻辑能更稳定地理解响应行为。

**追问方向：** 如果没有 `finish_reason`，最容易在哪些场景造成误判？

**易错点：** 把响应结束简单理解成“模型已经回答完了”。

## 题目 8

**问题：** 为什么保留 `raw_response` 不等于封装失败？

**参考答案：** 因为 `raw_response` 的作用不是让业务逻辑依赖底层 SDK，而是为调试、兼容、迁移保留逃生通道。真正成熟的封装不是盲目把底层完全藏死，而是在正常路径上依赖统一协议，在异常排查和过渡阶段仍然能查看原始响应。如果业务逻辑依赖 `raw_response`，那是封装失败；但如果它只是调试与兼容保底机制，那反而是成熟设计。

**追问方向：** 怎样判断一个系统是不是“实际上依赖了 raw_response”？

**易错点：** 认为抽象层必须把底层细节 100% 抹掉才算成功。

## 题目 9

**问题：** 设计协议时，怎样判断一个字段是“稳定语义”还是“临时便利”？

**参考答案：** 一个实用判断方式是看这个字段是否表达了系统长期稳定关心的结果语义，而不是某个阶段的展示方便。例如 `content`、`events`、`tool_calls`、`finish_reason` 都属于稳定语义，因为无论前端怎么换、模型怎么换，这些信息都长期有意义。而像 `display_mode`、`panel_style` 这类字段，往往更像某个界面阶段的临时便利，不适合轻易进入核心响应协议。好的协议设计不是字段越多越好，而是核心语义越稳定越好。

**追问方向：** 如果一个字段暂时有用，但还不确定是否稳定，最稳妥的处理方式是什么？

**易错点：** 为了当前方便，把很多展示层细节直接塞进核心响应对象。
