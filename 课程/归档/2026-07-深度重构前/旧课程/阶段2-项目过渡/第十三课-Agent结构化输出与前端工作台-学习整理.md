# 第十三课学习整理：Agent 结构化输出与前端工作台

## 本课定位

阶段 2 到这里，课程主线已经很明确：

- 第九课：从“学概念”切到“做自己的 Agent 项目”
- 第十课：建立 `LLM Interface` 抽象，先把模型边界立住
- 第十一课：理解 OpenAI Agents SDK 为什么这样设计
- 第十二课：亲手写出 100 行以内的最小 Agent，真正跑通一次闭环

那么第十三课要补上的，不是再学一个新 API，也不是直接进入复杂前端实现，而是解决一个只要你开始做产品就绕不过去的问题：

> Agent 跑完以后，结果该以什么协议交给上层系统消费？

所以这一课真正讨论的，不是“页面怎么画”，而是：

> Agent 的输出为什么不能长期停留在纯文本，以及它为什么必须逐步走向结构化协议

---

## 为什么这节课应该接在第十二课后面

如果没有前面几课，这节课很容易被误解成一节偏 UI 的内容。

但放在第十三课，它的意义就完全不同了。

因为到现在为止，我们已经知道：

- Agent 不是神秘对象，而是一套有边界的系统
- `LLM Interface` 的作用是隔离模型提供商差异
- 官方 Agent Framework 本质上也在做分层与协议封装
- 最小 Agent 的核心闭环，本质上就是：`LLM -> Tool -> LLM -> Finish`

当你已经理解这些，再回头看“输出怎么设计”，就会发现这根本不是展示层的小事，而是整个系统边界的继续延伸。

也就是说：

### 第九课解决的是

> Agent 内部如何分层

### 第十课解决的是

> 模型调用如何抽象

### 第十一课解决的是

> 官方框架为什么这样分层

### 第十二课解决的是

> 最小 Agent 闭环如何自己实现

### 第十三课解决的是

> 这个闭环产出的结果，应该如何以稳定协议交给外部系统

这才是这节课最合理的位置。

---

## 从“能跑”到“能接入系统”，缺的不是前端，而是协议

很多同学把 Agent 跑通之后，会自然认为下一步就是做一个聊天界面。

但真实情况通常不是这样。

一旦 Agent 开始承担真实任务，比如：

- 读项目文件
- 搜索信息
- 执行命令
- 汇总结论
- 生成报告
- 分步骤给建议

你很快就会发现，真正卡住系统演进的，往往不是页面，而是：

> 你根本不知道 Agent 的结果该以什么格式稳定传出去

如果输出只是：

```text
"我已经分析完项目了，下面是结论……"
```

那么短期可以展示，长期一定会越来越难维护。

因为系统并不知道这段文本里到底包含了什么：

- 哪部分是最终结论
- 哪部分是中间过程
- 哪部分来自工具结果
- 哪部分是代码片段
- 哪部分其实更适合渲染成卡片、步骤流、表格

所以问题的本质不是“前端强不强”，而是：

> 后端有没有给出可消费的输出结构

---

## 为什么纯文本输出在 Agent 系统里很快会失效

纯文本输出在普通问答里很自然，但在 Agent 系统里会快速暴露三个问题。

### 1. 上层无法理解结果结构

如果 Agent 返回一整段自然语言，那么调用方只能把它当作文案处理。

但真实产品经常需要区分：

- 标题
- 摘要
- 步骤
- 风险
- 表格
- 代码块
- 工具执行记录
- 最终结论

如果这些全混在一段文本里，上层系统就无法精确消费。

### 2. 中间过程丢失

最小 Agent 一旦跑起来，它其实已经不是单轮聊天，而是一个过程系统。

例如：

```text
读取目录
-> 定位关键文件
-> 读取文件
-> 分析代码
-> 调用更多工具
-> 汇总结论
```

如果最后只剩下一段结果，那么系统在用户眼里仍然像黑盒。

而真正的 Agent 产品，往往需要让用户知道：

- 现在卡在哪
- 已经做了什么
- 下一步要做什么
- 结论是怎么来的

### 3. 无法支持稳定扩展

今天你可能只想展示文字。

但以后你很可能想加：

- 报告卡片
- 文件列表
- 错误清单
- 代码 diff
- 执行时间线
- 工具调用明细

如果前期没有定义输出协议，后面所有扩展都会变成“从自然语言里猜结构”，这会非常脆弱。

---

## 这节课真正想建立的认知：Agent 也是一个“协议系统”

前面我们已经在输入侧建立过这个意识。

例如：

- Tool 不是普通函数，而是带 Schema 的能力描述
- `LLM Interface` 不是 SDK 调用，而是统一模型协议边界
- Runner 不是函数调用，而是运行时闭环

这一课其实是在输出侧建立同样的意识：

> Agent 的结果也不该只是“模型说了一段话”，而应该是“系统输出了一份协议对象”

也就是说，未来你看 Agent 输出时，脑子里应该逐步从：

```text
response.output_text
```

升级到：

```text
result = {
  final_text: ...,
  tool_calls: ...,
  events: ...,
  blocks: ...,
  metadata: ...
}
```

这就是这节课最核心的架构升级。

---

## 一个更合理的 Agent 输出应该包含什么

在阶段 2，这里不需要一开始就设计得非常复杂，但至少要有“分层结果”的意识。

一个更合理的输出，通常至少可以拆成四层。

### 1. 最终答案层

这是最容易理解的一层，也就是最终给用户看的自然语言结果。

例如：

```text
这个项目的核心问题在于 llm.py 只封装了调用，但还没有统一响应对象。
```

这一层对应的是：

> 给人读的最终答案

### 2. 工具调用层

Agent 做过哪些工具调用、用了什么参数、返回了什么摘要，这些应该能被记录下来。

例如：

```json
{
  "name": "read_file",
  "arguments": { "path": "agent-from-scratch/llm.py" },
  "summary": "读取成功，共 120 行"
}
```

这一层对应的是：

> 给系统调试、前端工作台、用户过程感知使用

### 3. 事件流层

除了最终答案，系统还应该能表达运行过程中的阶段变化。

例如：

```json
[
  { "type": "planning", "text": "先看项目结构，再分析 llm.py" },
  { "type": "tool_call", "name": "list_files" },
  { "type": "tool_result", "summary": "发现 18 个文件" },
  { "type": "tool_call", "name": "read_file" },
  { "type": "analysis", "text": "当前实现已初步解耦模型调用" },
  { "type": "final" }
]
```

这一层对应的是：

> 给 Runner、日志、Tracing、前端实时展示使用

### 4. 结构化内容层

最终结果除了自然语言，还可能有更适合组件渲染的结构化块。

例如：

```json
{
  "blocks": [
    { "type": "heading", "text": "分析结论" },
    { "type": "list", "items": ["缺少统一响应对象", "Tool 结果未标准化"] },
    { "type": "steps", "items": ["抽象 LLMResponse", "统一 ToolCall", "补事件流"] }
  ]
}
```

这一层对应的是：

> 给前端组件直接消费

## 结构化输出不只是一种格式，而是一条演进路线

很多同学容易把结构化输出理解成一个二选一问题：

- 要么纯文本
- 要么复杂 JSON

但真实工程里更常见的路径不是跳跃式切换，而是逐步演进。

一个很合理的演进过程通常是：

```text
纯文本
-> Markdown
-> JSON blocks
-> blocks + events + metadata
```

### 第一阶段：纯文本

最适合最早期验证闭环。

优点是：

- 最快
- 实现成本最低
- 适合验证最小 Agent 是否能工作

问题是：

- 上层无法稳定消费
- 很难拆分过程与结果
- 几乎无法支撑工作台

### 第二阶段：Markdown

这是非常实用的中间阶段。

优点是：

- 保持人可读
- 模型容易生成
- 可以快速支持标题、列表、表格、代码块

它适合：

> 先把“结果有结构”这件事做出来

但它依然有边界：

- 对程序来说语义不够强
- 很难稳定表达“这是风险卡片”“这是步骤流”“这是工具记录”

### 第三阶段：JSON blocks

这是更偏产品化的阶段。

例如系统开始明确区分：

- `heading`
- `paragraph`
- `list`
- `code`
- `table`
- `card`
- `steps`

这意味着输出的已经不再只是文案，而是：

> 明确的渲染意图

### 第四阶段：blocks + events + metadata

这是更接近成熟 Agent 系统的阶段。

也就是说，最终系统不仅有：

- 给用户看的结果块 `blocks`

还会有：

- 给过程展示的 `events`
- 给调试与治理的 `metadata`
- 给系统调用的 `tool_calls`

这才是真正完整的“系统响应”。

---

## 为什么 Markdown 和 Blocks 应该同时存在

这里很容易走向另一个误区：

> 既然 JSON blocks 更高级，那是不是 Markdown 就没用了？

其实不是。

更合理的理解是：

- Markdown 更适合快速交付和文档型结果
- Blocks 更适合产品化渲染和稳定协议消费

在很多真实系统里，它们完全可以共存。

### 方案一：模型先输出 Markdown，后处理成 blocks

这种方式更适合：

- 快速原型
- 结果类型相对有限
- 团队先要跑通链路

### 方案二：模型直接输出结构化 blocks

这种方式更适合：

- 结果协议已经比较稳定
- 前端组件系统已经成型
- 需要更强的一致性与可控性

### 方案三：同时保留多份结果

例如：

```json
{
  "content": "自然语言总结",
  "markdown": "## 分析结论 ...",
  "blocks": [...],
  "events": [...]
}
```

这种方案的价值在于：

- `content` 给简单展示或回退使用
- `markdown` 给文档型渲染使用
- `blocks` 给工作台组件使用
- `events` 给过程面板使用

它让系统在不同阶段都有退路，也更方便平滑升级。

## 为什么这节课和 `LLM Interface` 强相关

很多人会把“结构化输出”理解成前端问题。

但从架构角度看，它更应该被理解成：

> `LLM Interface` 的职责继续向输出侧延伸

第十课我们已经讲过，`LLM Interface` 的意义是：

- 对外暴露统一能力
- 对内屏蔽供应商差异

那么同样的逻辑也适用于输出。

不管底层是 OpenAI、Claude 还是 Qwen，上层系统都不应该直接依赖它们原始返回格式。

上层更应该看到的是统一结果对象，例如：

```python
class LLMResponse:
    content: str
    tool_calls: list
    events: list
    blocks: list
    finish_reason: str | None
    raw_response: object
```

这样做的价值非常大：

- Agent 不依赖某一家模型的原始字段
- Runner 不依赖某一家模型的原始字段
- 前端不依赖某一家模型的原始字段
- 后续换模型时，不会把上层一起带崩

所以这节课其实是在告诉你：

> `LLM Interface` 不是封装结束了，而是边界继续向输出侧生长了

---

## 为什么这节课和 Responses API 也强相关

如果你前面已经理解了 Responses API，这节课会更容易吃透。

因为 Responses API 一个很重要的启发就是：

> 模型输出不该只被看成“最终文本”，而应该被看成“由多个事件组成的响应”

这和传统的 Chat Completions 思维很不一样。

传统理解往往是：

```text
输入消息 -> 返回一段文本
```

但 Agent 更接近：

```text
输入上下文
-> 模型产生事件
-> 可能触发工具
-> 工具结果回流
-> 再继续生成
-> 最终完成
```

所以从课程衔接上说，这节课其实是在把：

- 第十一课对官方框架的理解
- 第十二课对最小 Agent 闭环的理解

继续推进为：

> 对输出事件与结果协议的理解

## 为什么成熟的 Agent 前端更像“工作台”

当输出开始结构化之后，前端形态自然就会发生变化。

它不再只是一个简单聊天框，而更像一个工作台。

因为前端现在可以分别展示：

- 用户输入
- Agent 当前计划
- 工具调用状态
- 中间分析事件
- 最终自然语言结论
- 结构化结果块

也就是说，界面从：

```text
消息列表
```

升级成：

```text
对话区 + 过程区 + 结果区
```

这不是因为前端“设计得更花哨”，而是因为：

> 后端终于给出了可以支撑这种界面的输出协议

因此，“前端工作台”不是这节课最底层的主题，它只是：

> 结构化输出成熟后自然推导出来的一种产品形态

---

## 工作台形态为什么比“聊天框升级版”更合理

很多人第一次做 Agent 前端时，容易把目标理解成：

> 在聊天框旁边多加几个面板

这其实还不够准确。

更成熟的理解应该是：

> Agent 前端不是“聊天框加挂件”，而是围绕任务执行过程组织出来的 Workspace

一个合理的 Agent Workspace，通常会自然分成三层：

### 1. 对话层

负责承载：

- 用户问题
- Agent 的最终自然语言答复
- 追问与继续协作

这一层解决的是：

> 人和 Agent 怎么交流

### 2. 过程层

负责承载：

- 当前计划
- 正在执行的步骤
- 工具调用记录
- 中间状态变化
- 错误与重试信息

这一层解决的是：

> Agent 在做什么，为什么现在还没结束

### 3. 结果层

负责承载：

- 结构化摘要
- 报告卡片
- 文件列表
- 表格
- 代码块
- 建议步骤

这一层解决的是：

> 这次执行最终产出了什么，可以如何继续消费

所以“工作台”这个词比“展示页”更准确，是因为它强调的不是视觉布局，而是：

> 把对话、过程、结果三种不同性质的信息拆开承载

---

## 前端真正需要的不是“大模型结果”，而是“渲染契约”

当前端开始承接结构化输出后，一个非常重要的工程观念也会跟着出现：

> 前端并不关心模型是怎么想出来的，它关心的是自己能不能稳定渲染

也就是说，前端最需要的不是某家模型的原始响应，而是明确的渲染契约。

前端希望拿到的不是：

```json
{
  "provider_output": { "...": "..." }
}
```

而是：

```json
{
  "blocks": [
    { "type": "heading", "text": "分析结论" },
    { "type": "list", "items": ["问题 1", "问题 2"] }
  ]
}
```

这背后的本质是：

> 前端消费的是协议，不是模型厂商

这也再次呼应了前面课程一直在训练的能力：

- 输入侧做抽象
- 运行时做抽象
- 输出侧也做抽象

---

## StructuredRenderer 思维：协议到组件的映射层

当系统开始有 `blocks` 之后，前端实际上也会出现一个新的核心角色：

> StructuredRenderer

它的职责不是“生成内容”，而是：

> 把结构化协议稳定映射成组件

例如：

```ts
const rendererMap = {
  heading: HeadingBlock,
  paragraph: ParagraphBlock,
  list: ListBlock,
  code: CodeBlock,
  table: TableBlock,
  card: CardBlock,
  steps: StepsBlock,
}
```

然后统一渲染：

```ts
blocks.map(block => {
  const Component = rendererMap[block.type]
  return <Component block={block} />
})
```

这一层非常重要，因为它意味着：

- 前端不会把一堆 `if/else` 写散在各处
- 新 block 类型只需要注册，不需要重写整套界面
- 展示能力可以像插件一样增长

所以从架构上说，后端会逐步长出：

- `LLMResponse`
- `Event`
- `ToolCall`
- `Block`

而前端也会逐步长出：

- `StructuredRenderer`
- `BlockRegistry`
- 各类 `BlockComponent`

这两边其实是在围绕同一份协议协同演化。

---

## 为什么 Block Registry 是一个很自然的后续抽象

一旦前端开始支持多个 block 类型，很快就会遇到一个工程问题：

> 这些 block 应该怎么统一注册和扩展？

如果没有注册表，代码很容易变成：

- 到处判断 `block.type`
- 到处手写分支逻辑
- 新增一种展示类型就改很多地方

更自然的做法是引入：

> Block Registry

也就是把：

- block 类型
- 对应组件
- 可选的校验逻辑
- 可选的降级策略

统一收口到一个地方。

这意味着系统后续甚至可以做到：

- 某些 block 只在桌面端启用
- 某些 block 在移动端自动降级
- 某些未知 block 自动回退成 Markdown 或纯文本

也就是说，结构化输出一旦成熟，前端就不再只是“渲染页面”，而是开始拥有：

> 自己的协议适配层

---

## 对 `agent-from-scratch` 来说，这节课意味着什么

这节课最有价值的地方，不是让我们立刻去写前端，而是明确项目下一步应该怎么演进。

对当前 `agent-from-scratch` 而言，可以把后续升级路线理解成下面这样：

### 第一步：先有统一的文本生成入口

例如：

```python
llm.generate(messages, tools)
```

### 第二步：把工具调用结果也纳入统一结果

也就是说，不只是拿最终文本，还要能拿到：

- 触发了哪些 Tool
- 参数是什么
- 返回结果是什么

### 第三步：抽象 `LLMResponse`

把当前零散结果统一收敛成标准对象。

### 第四步：加入事件流

让 Runner 不只是“跑完给答案”，而是能暴露过程状态。

### 第五步：加入结构化 blocks

让最终结果不只是 `content`，还支持更适合前端渲染的内容块。

### 第六步：为前端预留 StructuredRenderer 接口

即便当前仓库还没有前端，也应该在后端协议设计时提前想清楚：

- block 的最小字段是什么
- event 的最小字段是什么
- 是否需要 Markdown 回退
- 未知 block 如何降级

这会让后续真的接前端时，不需要推倒重来。

这一整条路线的本质是：

> 把一个能跑的最小 Agent，逐步升级成一个可接入产品系统的 Agent

## 这节课最容易踩的误区

### 误区 1：把这节课当作纯前端课

这节课不是在教你“如何设计更好看的页面”，而是在建立：

> 输出协议属于系统架构的一部分

### 误区 2：以为先把文本跑通就够了

纯文本只能支撑最初的 Demo。

一旦要做：

- 调试
- 观测
- 工作台
- 流式过程展示
- 报告型结果

你迟早都要回头补协议。

### 误区 3：一上来设计过于复杂的大协议

这节课真正推荐的不是过度设计，而是：

> 先建立“输出分层”的意识，再逐步把协议长出来

也就是说，不是一下子设计几十种 block，而是先让系统知道：

- 最终文本是什么
- 工具记录是什么
- 事件是什么
- 结构化块是什么

先把边界分清，再慢慢演进。

---

## 本课核心结论

### 1. Agent 的输出不应该长期停留在纯文本层

纯文本适合演示，不适合长期系统化演进。

### 2. 结构化输出不是前端小技巧，而是系统协议设计

它决定了结果能否被上层程序稳定消费。

### 3. `LLM Interface` 的职责应该继续向输出侧延伸

不仅统一调用，也要逐步统一结果对象。

### 4. Responses API 和 Agent Loop 的事件思维，是这节课的重要前置基础

因为 Agent 的输出本来就不只是一段最终文本。

### 5. “前端工作台”是结构化输出成熟后的自然形态

不是先有界面创意，而是先有可消费协议。

### 6. `StructuredRenderer` 和 `BlockRegistry` 是前端侧非常自然的后续抽象

因为协议一旦存在，前端就会需要稳定的映射层与扩展机制。
