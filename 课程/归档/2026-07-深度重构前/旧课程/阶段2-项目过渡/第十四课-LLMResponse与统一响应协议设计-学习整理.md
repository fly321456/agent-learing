# 第十四课学习整理：LLMResponse 与统一响应协议设计

## 本课定位

第十三课我们已经把一个关键问题讲清楚了：

> Agent 的输出不能长期停留在“纯文本回复”，而应该逐步升级成系统可消费的结构化结果

但到这里其实还差最后一步。

因为“知道要结构化”只是方向，真正落地时我们马上会遇到一个更具体的问题：

> 到底应该设计一个什么样的统一响应对象，来承接 Agent 的输出？

所以这一课的任务非常明确：

> 把上一课的“结构化输出意识”，正式收敛成一个可实现的响应协议设计

换句话说，第十三课解决的是：

> 为什么要有结构化输出

而第十四课解决的是：

> 结构化输出在代码里到底长什么样

---

## 为什么第十四课必须先讲协议，而不是直接改代码

很多同学学到这里，会很自然地产生一个冲动：

> 直接去 `llm.py` 里加几个字段不就行了？

这其实是最容易踩的坑。

因为如果没有先把协议想清楚，后面很容易变成这样：

- `content` 先放一份
- tool 调用结果临时放一份
- 中间状态随手打日志
- 前端需要什么再多塞几个字段

最后就会出现一个非常常见的问题：

> 系统看起来在输出结构化结果，其实只是把很多零散信息临时拼在一起

这类设计的问题不在于“不能跑”，而在于：

- 字段语义不稳定
- 不同调用方理解不一致
- 后续扩展越来越难
- 前后端会逐渐失去共同语言

所以在真正改代码之前，先设计响应协议，不是文档主义，而是：

> 先把系统边界立清楚

## 统一响应协议到底在统一什么

很多人第一次听到“统一响应协议”，会下意识理解成：

> 把不同模型的返回字段改成一样

这只说对了一半。

更完整的理解应该是：

> 它统一的不是 SDK 字段名，而是上层系统真正关心的结果语义

也就是说，系统真正关心的不是：

- OpenAI 返回字段叫这个
- Claude 返回字段叫那个
- Qwen 的 Tool Call 嵌套层级不同

系统真正关心的是：

- 最终答案是什么
- 是否发生了工具调用
- 工具调用有哪些
- 过程里出现了哪些事件
- 是否有适合前端消费的结构化块
- 本次调用为什么结束

所以统一响应协议的本质是：

> 用系统自己的语言，重新描述模型输出

这也是“抽象”这件事最典型的工程体现。

---

## 一个最小可用的 `LLMResponse` 应该包含什么

在阶段 2，我们不追求一次性设计出终极协议，而是先设计一个：

> 最小可用、语义稳定、未来可扩展

的响应对象。

一个很合理的最小版本，可以从下面这些字段开始：

```python
class LLMResponse:
    content: str
    tool_calls: list
    events: list
    blocks: list
    finish_reason: str | None
    raw_response: object | None
```

这个设计看起来不复杂，但每个字段其实都在承接前面课程里一个明确的问题。

---

## 字段一：`content`

`content` 是最终自然语言结果。

例如：

```text
这个项目当前已经具备基础的 LLM 抽象，但还缺少统一响应对象和事件流设计。
```

为什么这个字段仍然必须保留？

因为不管系统怎么演进，最终都几乎一定还需要一份：

> 最容易直接展示、最容易直接调试、最容易直接阅读的文本总结

也就是说，即便未来已经有：

- `blocks`
- `events`
- `tool_calls`

你仍然会经常需要 `content` 来作为：

- CLI 输出
- 调试输出
- 降级展示
- 简易日志摘要

所以这不是“旧世界残留”，而是：

> 一个非常稳定的基础字段

---

## 字段二：`tool_calls`

`tool_calls` 负责承接模型触发的工具调用结果。

例如：

```json
[
  {
    "name": "read_file",
    "arguments": { "path": "agent-from-scratch/llm.py" },
    "status": "success",
    "summary": "读取成功，共 120 行"
  }
]
```

为什么这个字段不能省？

因为对 Agent 系统来说，工具调用不是偶发现象，而是能力核心。

如果没有这层统一字段，后续你几乎做不了这些事：

- 调试为什么工具没被正确调用
- 在前端展示工具执行过程
- 统计哪些工具最常被使用
- 为失败调用加重试或回放

也就是说：

> `tool_calls` 让“模型调用了工具”从隐含过程变成显式数据

---

## 字段三：`events`

`events` 承接的是运行过程中的阶段性事件。

例如：

```json
[
  { "type": "planning", "text": "先查看项目结构" },
  { "type": "tool_call", "name": "list_files" },
  { "type": "tool_result", "summary": "发现 18 个文件" },
  { "type": "analysis", "text": "当前工程分层已经基本成型" },
  { "type": "final" }
]
```

为什么要单独有 `events`，而不是把这些东西写进日志？

因为日志是给开发者看的，而事件流是给系统消费的。

两者最大的差异在于：

- 日志偏自由文本
- 事件偏结构化协议

日志可以写成：

```text
[Runner] start tool read_file...
```

但事件更像：

```json
{ "type": "tool_call", "name": "read_file" }
```

这意味着 `events` 可以被：

- 前端实时展示
- Runner 进一步处理
- Tracing 系统消费
- 测试断言使用

所以 `events` 的价值是：

> 让“过程”第一次成为正式的一等输出

---

## 字段四：`blocks`

`blocks` 承接的是更适合前端组件消费的结构化内容。

例如：

```json
[
  { "type": "heading", "text": "分析结论" },
  { "type": "list", "items": ["缺少统一响应对象", "缺少事件流"] },
  { "type": "steps", "items": ["抽象 LLMResponse", "统一 ToolCall", "让 runner 输出 events"] }
]
```

为什么 `blocks` 不能直接等价于 `content`？

因为它们解决的是两类完全不同的问题：

- `content` 解决“怎么最快把结果读出来”
- `blocks` 解决“怎么把结果稳定渲染成结构化界面”

所以在一个成熟系统里，常见的情况是：

- `content` 作为兜底文本存在
- `blocks` 作为产品化渲染协议存在

这两者不是替代关系，而是互补关系。

---

## 字段五：`finish_reason`

`finish_reason` 很容易被忽略，但其实非常关键。

因为一次 Agent 响应之所以结束，可能有很多原因：

- 正常完成
- 达到某个终止条件
- 模型停止生成
- 工具执行失败后中止
- 命中 guardrails

如果没有 `finish_reason`，系统外部常常只能靠猜。

例如调用方会问：

> 为什么这次没有继续调用工具？  
> 为什么这次只返回了一半？  
> 为什么响应结束了但没有最终答案？

这时如果协议里有：

```python
finish_reason: str | None
```

很多行为就能被更稳定地解释。

所以这个字段的意义是：

> 给“为什么结束”一个显式解释

---

## 字段六：`raw_response`

`raw_response` 代表底层模型供应商的原始响应对象。

很多人第一次会觉得这个字段不够优雅，似乎应该完全隐藏底层细节。

但从工程实践看，保留这个字段通常是值得的。

因为它能解决很多现实问题：

- 排查 SDK 差异
- 临时查看底层字段
- 做兼容迁移
- 调试协议映射错误

也就是说，`raw_response` 的作用不是让上层依赖它，而是：

> 给系统保留一条调试逃生通道

真正成熟的用法应该是：

- 正常业务逻辑不要依赖 `raw_response`
- 调试、兼容、迁移时可以查看 `raw_response`

这是一种很典型的“封装但不盲化”的设计。

---

## 为什么这个协议不应该一开始就设计成“大而全”

到这里很容易出现另一个风险：

> 既然都设计协议了，那是不是应该一次性把几十种字段都补齐？

这其实也是一个常见误区。

阶段 2 更合理的策略应该是：

> 先设计最小稳定协议，而不是设计终极协议

原因很简单：

- 现在系统还在快速演化
- 你对真实使用场景的理解还在增长
- 过早设计过大的协议，很多字段最后会成为噪音

所以当前最合适的是先把下面这些立住：

- `content`
- `tool_calls`
- `events`
- `blocks`
- `finish_reason`
- `raw_response`

这已经足够支撑：

- CLI 结果展示
- 基础工作台
- 协议向前演进
- 后续第十五课以后继续细化

---

## `ToolCall` 这个子结构应该怎么想

`LLMResponse` 不是孤立对象，它一定会引出几个配套子结构。

其中第一个最自然的，就是 `ToolCall`。

一个最小可用版本可以长这样：

```python
class ToolCall:
    name: str
    arguments: dict
    status: str
    summary: str | None
```

这里最重要的不是字段多少，而是语义清晰：

- `name`：调用了哪个工具
- `arguments`：传了什么参数
- `status`：成功、失败、跳过等
- `summary`：给人读的简短说明

这样上层系统就不需要再自己理解底层 SDK 的 Tool Call 结构。

---

## `Event` 这个子结构应该怎么想

第二个最自然的配套结构，是 `Event`。

一个很实用的最小版本可以是：

```python
class Event:
    type: str
    text: str | None
    name: str | None
    data: dict | None
```

例如：

- `type="planning"`
- `type="tool_call"`
- `type="tool_result"`
- `type="analysis"`
- `type="final"`

这里不要急着把所有事件类型都设计完。

更重要的是先建立一个原则：

> 事件是过程协议，不是日志文本

这会直接影响你后续能不能把 Runner、Tracing、前端过程展示真正串起来。

---

## `Block` 这个子结构应该怎么想

第三个自然出现的结构，就是 `Block`。

一个最小版本甚至不需要先做成很多类，先用统一对象也完全够用：

```python
class Block:
    type: str
    data: dict
```

例如：

```json
{ "type": "heading", "data": { "text": "分析结论" } }
```

这种设计有两个好处：

- 初期实现简单
- 后期可以再逐步细分成更强类型结构

也就是说，阶段 2 的重点不是一上来把 Block 类型系统做复杂，而是先回答：

> 我们有没有一个稳定的位置来放“可渲染结果块”？

只要这个位置先有了，后面细化是自然的。

---

## 一个很重要的判断标准：这个字段是“系统语义”还是“临时便利”

设计协议时，一个非常有用的判断方法是反复问自己：

> 这个字段是在表达系统真正稳定的语义，还是只是为了当前方便临时塞进去？

例如：

- `content` 是稳定语义
- `tool_calls` 是稳定语义
- `events` 是稳定语义
- `finish_reason` 是稳定语义

但像这种字段就要警惕：

- `display_mode`
- `panel_style`
- `is_frontend_card_mode`

因为这类字段很可能只是某个阶段的临时便利，不应该轻易进入核心响应协议。

这也是为什么好的接口设计，不是字段越多越强，而是：

> 核心语义越稳定越强

---

## 对 `agent-from-scratch` 来说，这节课意味着什么

这节课最直接的意义，就是后续我们终于可以不再停留在：

```python
return response.output_text
```

这种最薄输出层了。

更合理的方向会变成：

```python
return LLMResponse(
    content=...,
    tool_calls=...,
    events=...,
    blocks=...,
    finish_reason=...,
    raw_response=...,
)
```

一旦这个对象建立起来，很多之前分散的问题都会自然收口：

- Runner 不再只处理文本
- ToolManager 的执行结果可以进入统一结构
- 前端未来不需要理解底层供应商差异
- 测试可以直接断言结构化结果

所以第十四课真正推动的，是：

> 从“模型返回文本”走向“系统返回协议对象”

---

## 这节课最容易踩的误区

### 误区 1：把 `LLMResponse` 理解成单纯的数据容器

它当然是数据容器，但更重要的是：

> 它是系统边界的一部分

也就是说，这不是“顺手建个类”，而是在定义上层如何理解 Agent 输出。

### 误区 2：一开始就做成极其复杂的强类型体系

阶段 2 更适合的是：

- 先把核心结构立住
- 再逐步增强类型约束

而不是一下子写出几十个 dataclass / schema。

### 误区 3：保留 `raw_response` 就等于封装失败

不是。

关键不在于有没有 `raw_response`，而在于：

> 正常业务逻辑是否依赖 `raw_response`

保留调试逃生口是成熟设计，不是失败设计。

---

## 本课核心结论

### 1. 第十三课解决的是“为什么要结构化”，第十四课解决的是“结构化对象怎么设计”

这两节课是连续的，不是重复的。

### 2. 统一响应协议统一的不是字段名，而是系统真正关心的结果语义

这才是抽象层真正的价值。

### 3. 一个最小可用的 `LLMResponse`，至少应该包含 `content / tool_calls / events / blocks / finish_reason / raw_response`

这已经足够支撑下一阶段工程演进。

### 4. `ToolCall / Event / Block` 会自然成为 `LLMResponse` 的配套子结构

这不是额外设计，而是协议落地后的自然拆分。

### 5. 好的协议设计不是字段越多越好，而是核心语义越稳定越好

这会直接决定系统后续是否容易扩展。

## 下一步

这节课之后，最自然的后续内容已经很明确了。

下一步最适合继续推进的是：

- 在 `agent-from-scratch` 里引入 `LLMResponse`
- 给 Tool 执行结果抽象 `ToolCall`
- 给 Runner 过程输出抽象 `Event`
- 给最终结构化渲染结果预留 `Block`
- 再回头看 `llm.py` 应该如何从“返回文本”升级成“返回协议对象”

也就是说，接下来真正要做的是：

> 让 Agent 不再只“回答问题”，而是开始“返回系统级结果”
