# M07 测试与评测

## 里程碑目标

建立从函数级正确性到 Coding Agent 任务级效果的验证体系，让每次改动都能回答“协议是否仍正确”和“任务表现是否退化”。

## 必须交付

- 单元测试覆盖纯逻辑、边界和错误路径。
- 契约测试覆盖 `LLMResponse`、`ToolResult`、`Event`、`RunResult`。
- 集成测试覆盖 Runner 与 ToolManager。
- 端到端测试在临时仓库完成读取、搜索、补丁、运行验证。
- `evals/cases.json` 恰好包含至少 20 个固定 Coding Agent 任务。
- 评测汇总成功率、工具调用数、步骤数、延迟和失败分类。

## 代码入口

- `tests/`
- `evals/cases.json`
- `src/agent_from_scratch/evaluation.py`
- `tests/test_evaluation.py`
- `tests/test_e2e_coding_tools.py`

## 测试分层

| 层级 | 主要问题 | 是否依赖真实 API |
| --- | --- | --- |
| 单元 | 一个函数或类型是否正确 | 否 |
| 契约 | 模块间协议是否稳定 | 否 |
| 集成 | Runner、LLM 替身、Tool 是否闭环 | 否 |
| E2E | 临时仓库任务是否完成 | 否 |
| 在线烟雾 | 当前供应商集成是否仍兼容 | 可选 |

## 评测原则

测试验证确定性行为，评测衡量任务效果，两者不能互相替代。当前 `coding-agent-eval` 是离线协议回归：脚本化 LLM 驱动真实 Runner 重放 20 条工具序列，但不会执行有副作用的真实工具。它验证协议与指标管线，不代表在线模型任务成功率；真实工具由 E2E 测试验证，在线模型必须另建带版本的实验记录。

## 实作任务

1. 为非法 JSON、未知 Tool、审批拒绝、越界路径和超时补测试。
2. 阅读 20 个评测任务，确认覆盖读取、搜索、编辑、执行和安全。
3. 为一个任务设计确定性验收器，而不是让另一个 LLM 主观打分。
4. 比较两次评测的成功率、平均步骤和工具调用数。

## 自动验证

```powershell
cd agent-from-scratch
python -m pytest -q
coding-agent-eval
python -m compileall -q src tests examples
```

## 常见失败

- 只测 happy path，未覆盖终止和错误语义。
- 在线 API 是默认测试依赖，导致昂贵且不稳定。
- 任务描述很多，但没有机器可执行的验收器。
- 只统计成功率，忽略步骤、延迟和失败类型。
- 修改任务集同时宣称模型表现提升。

## 完成定义

默认测试稳定离线通过；20 个任务可被校验加载并完成协议回放；一次协议或工具回归能被测试定位；评测输出明确区分离线协议与在线模型效果。
