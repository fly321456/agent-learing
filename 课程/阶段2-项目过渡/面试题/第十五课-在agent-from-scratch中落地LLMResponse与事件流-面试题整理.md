# 第十五课面试题整理：在 agent-from-scratch 中落地 LLMResponse 与事件流

## 题目 1

**问题：** 为什么第十五课要把 `LLMResponse` 真正落到 `agent-from-scratch` 代码里，而不是只停留在课程设计层？

**参考答案：** 因为只有真正改进运行链路，统一响应协议才算成立。前面的课程是在讲接口设计思想，但如果 `Runner` 仍然直接依赖底层 SDK 原始对象，那么所谓的 `LLMResponse` 只是概念层包装，并没有改变系统边界。把它落到代码里，核心价值在于让上层运行时开始依赖系统自己的响应语义，而不是继续被 OpenAI SDK 的字段结构牵着走。

**追问方向：** 如何判断一个项目是真的完成了抽象，而不是只新增了一个“看起来很规范”的类？

**易错点：** 以为“定义了 `LLMResponse` 类”就等于完成了统一响应协议改造。

## 题目 2

**问题：** 在最小 Agent 项目里，为什么优先改 `llm.py` 和 `runner.py`，而不是先做前端展示层？

**参考答案：** 因为 `llm.py` 负责把模型原始输出转换成系统语义，`runner.py` 负责消费这些语义并驱动后续执行，这两个位置正好构成响应协议落地的核心链路。前端展示只是消费者之一，如果运行时内部还没有统一对象，前端层拿到的数据也只能继续拼装和猜测。先改 `llm.py` 和 `runner.py`，等于先把协议的生产者和第一消费者打通。

**追问方向：** 为什么说前端工作台只是 `LLMResponse` 的“下游消费者”？

**易错点：** 一上来就把重心放在 UI 字段设计，而忽略运行时边界的统一。

## 题目 3

**问题：** 为什么 `OpenAILLM.generate()` 不应该继续直接返回 SDK 原始响应对象？

**参考答案：** 因为那会让调用方直接绑定到底层供应商实现上。只要 `Runner`、日志系统、工作台或者后续测试代码都依赖 `response.output`、`response.output_text` 这类供应商字段，系统就没有形成自己的稳定协议。`generate()` 返回 `LLMResponse`，本质上是在模型适配层完成一次“协议翻译”，让运行时使用统一语义字段，比如 `content`、`tool_calls`、`events`。

**追问方向：** 如果未来接入别的模型供应商，这种做法会带来什么直接收益？

**易错点：** 觉得“反正现在只接 OpenAI”，所以没必要做这层转换。

## 题目 4

**问题：** 在这类最小实现里，为什么 `raw_response` 还要暂时保留？

**参考答案：** 因为最小重构阶段的目标不是一步到位彻底切断底层，而是先把主路径改成统一协议，同时保留一个调试和兼容逃生口。比如当前 `Runner` 可能还需要把底层的原始 `output` 重新挂回 `input_items` 作为下一轮上下文，这时候直接删掉 `raw_response` 反而会让改造成本暴涨。保留 `raw_response` 是为了平滑迁移，但业务主逻辑不应长期依赖它。

**追问方向：** 什么情况下说明系统已经可以继续推进到“弱化甚至移除 `raw_response` 依赖”？

**易错点：** 把保留 `raw_response` 理解成抽象失败，而不是阶段性迁移策略。

## 题目 5

**问题：** 为什么工具调用应该先被解析成 `tool_calls`，再由 `Runner` 执行？

**参考答案：** 因为这体现了清晰的职责分层。`llm.py` 的职责是把模型输出翻译成统一协议，所以它负责识别“模型打算调用什么工具、参数是什么”；`runner.py` 的职责是消费协议并执行系统动作，所以它负责真正调度工具。如果 `Runner` 还要自己去遍历原始响应、判断 `item.type == "function_call"`、再手动解析参数，那说明适配层职责没有收口干净。

**追问方向：** 为什么说工具调用信息属于“响应语义”，而不只是“执行细节”？

**易错点：** 认为 `tool_calls` 只是为了写得好看，实际上它是运行时控制流的重要输入。

## 题目 6

**问题：** 第十五课里引入 `events` 的工程意义是什么？

**参考答案：** `events` 的意义是把运行过程中的关键动作正式化。以前工具调用、工具结果、思考阶段这些信息往往散落在日志、print 输出或者自然语言描述里，系统很难稳定消费。引入事件流之后，前端工作台、调试面板、Tracing、测试断言都可以围绕统一事件结构来工作。它让“过程可见”从经验层变成协议层。

**追问方向：** `tool_call` 和 `tool_result` 这类事件，分别更适合被哪些模块消费？

**易错点：** 把事件流简单理解为“更规范的日志”。

## 题目 7

**问题：** 如果这次只做最小落地，`LLMResponse` 最值得优先跑通的是哪几项字段？

**参考答案：** 通常优先是 `content`、`tool_calls`、`raw_response`，然后再逐步补 `events`、`blocks`、`finish_reason`。原因是这三项已经足以支撑“文本回答 + 工具调用 + 与现有运行链路兼容”这一条最小闭环。工程改造讲究薄切片落地，先把最关键的主路径跑通，再扩展更丰富的协议能力，风险更低。

**追问方向：** 为什么 `blocks` 很重要，但在最小实现阶段可以先不做重投入？

**易错点：** 一开始就想把所有协议能力一次性做满，导致改造面过大。

## 题目 8

**问题：** 为什么说第十五课是“从接口抽象走向运行时抽象”的关键一课？

**参考答案：** 因为前几课更多是在定义“应该有什么接口”，而第十五课开始真正决定运行时依赖谁。系统一旦让 `Runner`、工具执行链路、后续事件流都依赖 `LLMResponse`，就意味着统一协议不再只是文档层约定，而是成为运行时事实。这一步完成后，后面的工作台、Tracing、回放、测试、模型切换都会更好做。

**追问方向：** 为什么很多项目“看起来有抽象”，但一改供应商就露馅？

**易错点：** 把接口设计和运行时依赖边界混为一谈。

## 题目 9

**问题：** 如果你来继续演进这套最小实现，下一步会优先补什么？

**参考答案：** 比较合理的顺序是先补 `finish_reason` 和更完整的 `events`，然后让 `Runner` 逐步减少对 `raw_response` 的依赖，最后再补 `blocks` 供前端工作台消费。这个顺序遵循的是“先增强运行时可解释性，再增强展示层能力”。也就是说，先让系统更容易调试、观测和迁移，再去做更丰富的 UI 协议。

**追问方向：** 如果要做课程里的前端工作台，为什么 `blocks` 会变成下一阶段重点？

**易错点：** 直接跳去做前端渲染，而没有先把运行时解释能力补齐。
