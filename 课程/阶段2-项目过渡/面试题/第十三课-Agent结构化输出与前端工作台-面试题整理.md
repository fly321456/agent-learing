# 第十三课面试题整理

## 题目 1

**问题：** 为什么说 Agent 的输出不能长期停留在纯文本，而必须逐步走向结构化结果？

**参考答案：** 因为纯文本只适合最早期 Demo 展示，不适合长期系统演进。对 Agent 系统来说，上层往往不仅关心“最后说了什么”，还关心“调用了哪些工具”“过程里发生了什么”“哪些内容适合渲染成卡片、表格、步骤流”。如果输出只有一段自然语言，那么前端、日志、Tracing、调试系统和后续自动化流程都很难稳定消费这些信息。结构化结果的价值在于，它把最终答案、工具调用、过程事件和可渲染内容块从隐含信息变成显式协议。

**追问方向：** 如果一个系统当前只能返回纯文本，后续最容易在哪些场景暴露问题？

**易错点：** 把“纯文本可以展示”误认为“纯文本足够支撑产品化”。

## 题目 2

**问题：** 为什么成熟的 Agent 前端更像“工作台”，而不只是“聊天框升级版”？

**参考答案：** 因为 Agent 和普通问答机器人不同，它不仅输出答案，还会经历计划、工具调用、分析、重试、汇总等过程。成熟的 Agent 产品需要把对话、过程、结果拆开承载：对话层负责人与 Agent 的交流，过程层负责展示当前计划、工具调用和中间状态，结果层负责展示结构化产物。只有这样，用户才能理解 Agent 在做什么、为什么还没结束、结果是怎么来的。因此“工作台”强调的是围绕任务执行组织信息，而不是简单在聊天框旁边多加几个面板。

**追问方向：** 对话层、过程层、结果层分别最适合承载哪些信息？

**易错点：** 把工作台理解成视觉设计升级，而忽略它背后是输出协议变化。

## 题目 3

**问题：** 结构化输出为什么和 `LLM Interface` 强相关，而不只是前端问题？

**参考答案：** 因为 `LLM Interface` 的核心职责是对上提供稳定接口、对下屏蔽不同模型供应商差异。这个逻辑不仅适用于调用侧，也适用于输出侧。上层系统不应该直接依赖 OpenAI、Claude、Qwen 各自原始返回格式，而应该看到统一的结果对象，例如 `content`、`tool_calls`、`events`、`blocks` 等系统语义。这样 Agent、Runner、前端和后续治理能力都不需要直接理解供应商细节，系统边界才真正稳定。

**追问方向：** 如果没有这层统一输出抽象，后续换模型时最容易在哪些地方出问题？

**易错点：** 认为 `LLM Interface` 只负责“封装请求”，不负责“统一结果”。

## 题目 4

**问题：** 为什么说结构化输出是一条演进路线，而不是“纯文本”和“JSON”之间的二选一？

**参考答案：** 因为真实工程里通常不会一步跳到终极协议，而是逐步演进。常见路径是：纯文本用于最早期闭环验证，Markdown 用于快速获得结果结构，JSON blocks 用于产品化组件渲染，最后再演进到 `blocks + events + metadata + tool_calls` 的完整系统响应。每一步都对应不同阶段的成本、稳定性和产品需求。把它看成演进路线，比一上来就追求复杂协议更符合工程实际。

**追问方向：** Markdown 和 JSON blocks 各自更适合什么阶段？

**易错点：** 要么只信纯文本，要么一开始就想把协议设计成极其复杂的大系统。

## 题目 5

**问题：** 为什么 Markdown 和 Blocks 在很多系统里应该共存，而不是互相替代？

**参考答案：** 因为它们解决的问题不同。Markdown 更适合快速交付、文档型结果和人可读场景；Blocks 更适合稳定渲染、组件映射和产品化工作台。很多系统会同时保留 `content`、`markdown`、`blocks` 和 `events`：`content` 负责简单展示与回退，`markdown` 负责文档型渲染，`blocks` 负责结构化前端组件，`events` 负责过程面板。这种共存设计更有利于平滑演进，也能降低协议升级风险。

**追问方向：** 什么情况下适合让模型先输出 Markdown，再后处理成 blocks？

**易错点：** 把 Markdown 和 Blocks 看成只能二选一的关系。

## 题目 6

**问题：** 前端真正消费的为什么不是“大模型结果”，而是“渲染契约”？

**参考答案：** 因为前端并不关心模型底层是怎么生成内容的，它真正关心的是自己能不能稳定渲染。前端最需要的不是某家模型的原始输出对象，而是一份明确的渲染契约，例如 `blocks` 数组里每个 `type` 分别对应什么组件、字段结构是什么、未知类型如何降级。只有当前端消费的是稳定协议，它才不会被供应商差异绑死，也不会因为后端字段波动而大量重写展示逻辑。

**追问方向：** 如果前端直接消费供应商原始响应，会带来哪些维护问题？

**易错点：** 误以为前端只需要拿到一份文本就算“完成接入”。

## 题目 7

**问题：** `StructuredRenderer` 和 `BlockRegistry` 为什么会自然出现？

**参考答案：** 因为一旦系统开始支持多种 block 类型，前端就需要一层稳定的“协议到组件映射层”。`StructuredRenderer` 负责根据 block 类型统一选择组件并渲染；`BlockRegistry` 负责把 block 类型、对应组件、校验规则、降级策略统一注册管理。这样可以避免把大量 `if/else` 分散写在页面各处，也让新增一种 block 类型时不需要重写整套界面。这种抽象说明前后端其实是在围绕同一份协议协同演进。

**追问方向：** 如果没有 `BlockRegistry`，新增 block 类型时最容易出现哪些工程问题？

**易错点：** 把 `StructuredRenderer` 理解成单纯的前端实现细节，而忽略它对应的是协议成熟度。
