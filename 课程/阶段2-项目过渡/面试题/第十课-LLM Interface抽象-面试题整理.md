# 第十课面试题整理

## 题目 1

**问题：** 为什么一个成熟的 Agent 项目通常不会在业务代码里到处直接写 `client.responses.create(...)`？

**参考答案：** 因为这样会让业务层直接依赖某个具体模型供应商的 SDK 实现，导致代码高度耦合。一旦后续需要从 OpenAI 切换到 Claude、Qwen、DeepSeek 或 Gemini，就需要在大量业务文件中修改调用方式。成熟项目通常会把模型调用封装到统一的 LLM 抽象层后面，让上层系统只依赖稳定接口，而不是依赖具体厂商实现，从而降低变更成本并提升可扩展性。

**追问方向：** 如果未来需要做多模型路由或 A/B 测试，这种抽象会带来哪些额外好处？

**易错点：** 觉得“先直接调用，后面再封装”总是低成本，忽略了耦合扩散问题。

## 题目 2

**问题：** 为什么要单独设计 `llm.py` 或 `LLM Interface` 这一层？

**参考答案：** 因为上层 Agent 系统真正需要的是“生成一次响应”的能力，而不是某家 SDK 的具体调用细节。通过单独设计 `llm.py` 或 `LLM Interface`，可以把不同模型提供方的实现细节隐藏在统一接口后面，让业务层统一调用 `generate()` 之类的方法。这样既方便替换底层模型，也有利于测试、Mock、多模型扩展和整体架构稳定。

**追问方向：** 一个好的 LLM Interface 最少应该暴露哪些能力？

**易错点：** 把封装理解成“只是少写几行代码”，没有看到它的架构意义。

## 题目 3

**问题：** 什么叫 `Agent -> LLM Interface -> Provider` 这种分层，为什么它重要？

**参考答案：** 这种分层表示 Agent 不直接依赖 OpenAI、Claude 或其他供应商，而是依赖一个中间抽象接口；具体供应商实现则放在接口下层。这样高层系统只面对统一能力，底层可以自由替换和扩展不同 Provider。这种设计非常重要，因为它把系统从单一厂商绑定中解耦出来，让 Agent 核心逻辑更稳定，也更符合大规模工程中的可维护性要求。

**追问方向：** 如果没有这一层抽象，后续最容易在哪些地方出现架构问题？

**易错点：** 只从“换模型方便”理解价值，没有看到它对整个系统边界的影响。

## 题目 4

**问题：** 为什么说这一课真正学到的不是 OpenAI，而是软件架构？

**参考答案：** 因为这一课虽然以模型调用为切入点，但重点并不是某个 API 的用法，而是如何为 Agent 系统建立稳定的抽象边界。通过引入 `LLM Interface`，课程实际上在训练依赖倒置、接口统一、供应商解耦和面向抽象编程这些工程能力。这些能力不只适用于 OpenAI，也适用于任何模型、任何工具层和任何大规模系统设计。

**追问方向：** 除了 LLM 层，Agent 系统中还有哪些地方也适合用类似的抽象方式？

**易错点：** 把这节课当成“模型调用封装技巧”，而不是架构课。

## 题目 5

**问题：** 依赖倒置原则在 Agent 系统里的一个典型体现是什么？

**参考答案：** 一个典型体现就是让 `Agent`、`Runner` 等高层模块依赖抽象的 `LLM Interface`，而不是直接依赖 OpenAI SDK、Claude SDK 或其他具体 Provider。这样高层系统依赖的是稳定能力接口，底层供应商实现反而变成可替换细节。这正符合依赖倒置原则的核心思想：高层不依赖低层细节，而是双方共同依赖抽象。

**追问方向：** 如果继续推广这个原则，Tool Manager、Memory、Session 层分别可以怎样抽象？

**易错点：** 只会背“依赖倒置原则”定义，但说不出在 Agent 项目中的真实落点。

## 题目 6

**问题：** 为什么课程从这一课开始强调“每节课一个 Git Commit”的项目式推进？

**参考答案：** 因为项目式推进能把学习从“听懂知识点”变成“持续交付工程产物”。每节课一个 Commit，意味着每次学习都有明确边界、可回溯结果和真实代码演进过程，这既更接近企业内培养工程师的方式，也能最终沉淀出完整的 GitHub 项目和作品集。相比零散练习，这种方式更有助于形成真正的 Agent 工程能力。

**追问方向：** 这种推进方式对代码质量、复盘和面试准备分别有什么帮助？

**易错点：** 把 Git Commit 只看成版本记录，而没有看到它对学习节奏和工程习惯的塑造作用。
