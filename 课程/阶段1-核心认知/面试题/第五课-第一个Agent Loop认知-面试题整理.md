# 第五课面试题整理

## 题目 1

**问题：** 为什么说 Agent 的核心其实是一个 `while` 循环？

**参考答案：** 因为 Agent 的本质不是调用一次模型就结束，而是不断重复“请求 LLM - 判断是否产生 Tool Call - 执行 Tool - 回传 Tool Result - 再次请求 LLM”这一循环，直到模型输出最终答案为止。这个过程天然对应一个持续迭代的控制流，因此在工程实现上通常会表现为一个 `while` 循环或等价的状态机。

**追问方向：** 当 Agent 规模变大时，`while` 循环一般会扩展出哪些能力？

**易错点：** 只把 Agent 理解成“一次模型调用 + 一个工具函数”。

## 题目 2

**问题：** 为什么 Tool 本身往往不复杂，但 Tool Schema 很重要？

**参考答案：** 因为 Tool 的执行逻辑通常只是一个普通函数，例如计算、读文件、获取时间，这些代码本身并不神秘。真正影响 Agent 是否能正确使用这个 Tool 的，是模型是否知道这个工具的名字、用途、参数要求和适用场景，而这些信息都来自 Tool Schema。也就是说，函数负责执行，Schema 负责让模型理解这个函数何时该被调用。

**追问方向：** 如果一个 Tool 函数写得很好，但 Schema 很差，会出现什么问题？

**易错点：** 把注意力全部放在函数实现上，忽略模型可理解性。

## 题目 3

**问题：** 为什么一个带 Tool Calling 的最小 Agent，通常至少包含两轮交互？

**参考答案：** 因为第一轮通常是用户输入发送给模型，模型根据工具定义返回 Tool Call；第二轮是宿主程序执行完 Tool 后，把 Tool Result 再发回模型，让模型基于真实结果组织最终自然语言回答。也就是说，模型先做“决策”，再根据执行结果做“总结”，这至少需要两段消息往返。

**追问方向：** 在什么情况下，Agent 会超过两轮而进入多轮循环？

**易错点：** 以为模型第一次返回时就一定是最终答案。

## 题目 4

**问题：** 为什么说第一次返回的 `function_call` 不是最终答案？

**参考答案：** 因为 `function_call` 本质上只是模型生成的一段结构化调用意图，表示“我建议调用某个工具，并传入这些参数”。它不是工具的执行结果，也不是自然语言回答。只有当外部程序真正执行工具、拿到结果并回传给模型后，模型才能基于真实执行结果生成面向用户的最终答案。

**追问方向：** 如果工具执行失败，下一步应该如何处理？

**易错点：** 把 Tool Call 当成 Tool Result，混淆决策和执行两个阶段。

## 题目 5

**问题：** 为什么 Agent 不应该主要靠 `if question contains ...` 这类规则来决定用哪个 Tool？

**参考答案：** 因为这种写法本质上仍然是传统规则驱动程序，属于 Workflow 思维，而不是 Agent 思维。Agent 的关键价值在于把“下一步该做什么”交给模型基于上下文动态判断。如果开发者把所有路由逻辑都提前写死，系统虽然接了 LLM，但本质上仍然是 if-else 编排，失去了 Agent 的动态决策能力。

**追问方向：** 有没有场景仍然适合保留一部分显式路由规则？

**易错点：** 把“让 LLM 决策”误解为完全不需要程序控制或安全边界。

## 题目 6

**问题：** 一个最小 Agent 中，LLM 与 Tool 的职责边界是什么？

**参考答案：** LLM 的职责是理解用户意图、结合 Prompt 和 Tool Schema 做出决策，并在拿到工具结果后生成自然语言回答；Tool 的职责是执行具体动作，例如计算、读文件、查询数据等。LLM 负责决定“做什么”，Tool 负责真正“去做”。宿主程序则负责把二者连接起来，形成闭环。

**追问方向：** 宿主程序在这个闭环里扮演的角色更像什么？

**易错点：** 认为模型既负责决策也负责执行。
