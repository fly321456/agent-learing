# 阶段4 - Lesson 3 学习整理

## 本节定位

到上一节为止，工程化能力阶段已经完成了两件很关键的事情：

- `Logging`：让系统可见
- `Tracing`：让一次运行可串起来看

现在系统已经开始具备：

- 能看到发生了什么
- 能知道这些事属于哪次运行

但还有一个非常现实的问题没有解决：

> 如果某一层卡住了，或者某次调用失败了，系统应该怎么办？

这就是这一节要解决的问题：

> Retry 与 Timeout 初版

从这一步开始，项目会第一次从“知道失败了”升级到“对失败开始有最小控制能力”。

---

## 本节目标

这一节不追求一上来做完整的容错系统，也不做复杂的重试策略矩阵。

当前阶段的目标非常务实：

1. 让明显可能失败的地方具备最小重试能力
2. 让可能卡住的地方具备最小超时边界
3. 让 Runner 在失败时不至于无限等待或盲目继续

也就是说，这一节真正要建立的是：

> 失败可控，而不是失败随机蔓延

---

## 本节核心知识点

### 1. Retry 解决的是“偶发失败”，不是“所有失败都重来一遍”

很多人第一次加 Retry 时，容易写出一种非常危险的逻辑：

> 只要失败，就重试

这其实是不对的。

因为不同失败类型含义完全不一样：

#### 适合重试的

- 网络临时波动
- provider 短暂异常
- 偶发性请求失败

#### 不适合重试的

- Tool 根本不存在
- 参数结构错误
- 逻辑 Bug
- Prompt 配置错误

所以 Retry 不是“默认多跑几次”，而是：

> 对可能是临时性失败的问题，增加一次恢复机会

这点必须非常清楚。

---

### 2. Timeout 的目标不是“让程序更快”，而是“防止无限等待”

Timeout 经常也会被误解。

很多人会把它理解成：

> 超时是不是为了优化性能？

部分是，但在当前阶段更重要的意义其实是：

> 给运行加边界

例如：

- 某个 Tool 卡住了
- 某次模型调用长时间没返回
- 某个外部依赖一直挂起

如果没有 Timeout，系统就可能：

- 卡死
- 一直占着运行资源
- 让上层看起来“什么都没发生”

所以 Timeout 的第一价值不是快，而是：

> 不让系统无限悬挂

---

### 3. 当前阶段要先做“最小控制”，不要急着做复杂策略

很多人学到 Retry / Timeout 时会很兴奋，马上想做：

- 指数退避
- provider fallback
- 多级超时策略
- 任务恢复

这些以后都可以做，但现在最需要的是：

> 先把最小边界立住

当前阶段建议先做到：

- LLM 调用失败时，最多重试固定次数
- Tool 执行卡住时，有最小 timeout 边界
- 超过边界后，Runner 明确结束当前运行

这已经足够让项目进入一个更稳的状态。

---

## 当前项目里最适合先加 Retry / Timeout 的地方

### 1. LLM 调用层

最适合先加 Retry 的位置通常是：

```text
OpenAILLM.generate()
```

因为这里最可能面对的是：

- provider 请求失败
- 短暂网络问题
- 临时 API 异常

这种失败有一定概率是“再试一次就恢复”的。

所以：

> 第一个 Retry，最适合先放在 LLM 调用层

---

### 2. Tool 执行层

最适合先考虑 Timeout 的位置通常是：

```text
ToolManager.execute()
```

特别是后续一旦 Tool 扩展到：

- shell
- python
- file system
- browser

卡住的概率会越来越高。

所以这一节虽然是“初版”，也应该从现在开始建立这个意识：

> Tool 执行不能默认无限等待

---

### 3. Runner 终止层

Runner 当前不一定直接做复杂 retry，但它必须知道：

- 这次失败后还要不要继续
- 超时后当前运行要不要终止
- 如果连续失败，是不是应该停止 Loop

这意味着：

> Runner 是最小失败策略的最终执行者

---

## 本节推荐的最小策略

当前阶段不做复杂容错，只做最小正确版本。

### 策略 1：LLM 固定次数重试

例如：

- 最多重试 2 到 3 次
- 每次失败后记录 warning / error

### 策略 2：Tool 执行加最小超时边界

即使当前 Tool 还比较简单，也要先把“超时是一个正式概念”立住。

### 策略 3：达到上限后停止运行

不要无限 retry，也不要在未知状态下继续 Loop。

也就是说，当前第一版策略重点是：

> 有边界、有上限、可解释

---

## Retry 与错误边界的关系

上一节我们讲了：

> 错误要在正确边界上被看见

这一节则是在这个基础上再往前迈一步：

> 在正确边界上，决定要不要再试一次

所以 Retry 不应该破坏错误边界，反而应该建立在它之上。

例如：

- ToolManager 先识别 Tool 错误是不是逻辑错误
- OpenAILLM 先识别 LLM 错误是不是暂时性失败
- Runner 再根据这些信息决定运行策略

这说明一个很重要的工程原则：

> Retry 不应该是全局盲重试，而应该是分层策略

## Code Review 视角

### 不推荐的做法

```python
while True:
    try:
        ...
    except:
        continue
```

这类写法最大的问题是：

- 没有上限
- 没有分类
- 没有失败边界

最后系统很可能会：

- 死循环
- 重试真正不该重试的错误
- 把问题越试越模糊

### 更推荐的做法

```python
for attempt in range(max_retries):
    try:
        ...
        return result
    except TemporaryError:
        ...
raise FinalError(...)
```

重点不在代码形式，而在原则：

> Retry 必须有上限、有理由、有记录

---

## 官方框架怎么做

成熟框架一般不会把 Retry / Timeout 写成临时补丁。

它们通常会系统化考虑：

- 哪些错误可以重试
- 哪些错误必须快速失败
- 哪些操作要有 timeout
- 超时和重试的日志 / trace 如何打通

这说明 Retry / Timeout 在 Agent 工程里不是“小优化”，而是：

> 运行时控制能力的一部分

所以这节课本质上是在给 Agent Runtime 补第一层调度韧性。

---

## 本节最重要的一句话

> Retry 的意义不是“多试几次”，而是“把临时性失败控制在明确边界内”。

这句话就是这节课最重要的工程理解。
