# Lesson11：Agent 评估指标与最小评测体系初版

## 1. 本课目标

到这一课，你的课程主线已经从“理解 Agent”走到了“开发 Agent、调试 Agent、维护 Agent”。

但是工程里还有一个非常关键的问题，如果不解决，整个项目很容易停在“感觉还行”的阶段：

> **你怎么证明这个 Agent 真的在变好？**

很多初学者做 Agent，评价方式通常只有两种：

### 第一种

自己问几个问题，感觉结果还不错。

---

### 第二种

改完 Prompt 或架构后，直觉上觉得“这次更聪明了”。

这两种方式都不可靠。

因为它们最大的问题是：

> **不可重复、不可比较、不可量化。**

所以这一课我们正式进入一个 Agent 工程师必须掌握的能力：

> **评估（Evaluation）**

更准确地说，是：

> **为你的 Agent 建立一个最小可运行的评测体系。**

---

## 2. 为什么 Agent 开发一定要有评估体系

如果没有评估体系，Agent 项目通常会很快进入一种非常危险的状态：

```text
改了很多

看起来有进步

但不确定是不是真的更好了
```

这会带来几个很现实的问题：

### 问题 1：无法判断优化是否有效

比如你做了这些改动：

- 改了 Prompt
- 改了 Tool Schema
- 增加了 Memory 注入
- 增加了 Summary

但到底哪一项真的提升了效果？

如果没有评估，你只能靠感觉。

---

### 问题 2：无法发现回归

你可能修好了一个问题，却不知不觉引入了新问题。

例如：

- Tool 调用更积极了
- 但误调用率也变高了

或者：

- Memory 让回答更完整了
- 但也引入了更多无关信息

没有评估体系，这些“回归”很难及时看见。

---

### 问题 3：无法做持续迭代

一个项目如果不能稳定评估，就很难做工程化演进。

因为你没法回答：

- 这周比上周强在哪
- 哪些能力在提升
- 哪些能力在退化

所以评估不是“可选项”，而是 Agent 迭代能力的前提。

---

## 3. 这一课最重要的一句话

请记住：

> **没有评估，Agent 优化很容易退化成主观感受管理。**

这句话非常重要。

因为很多人会在 Agent 项目里投入很多精力：

- 调 Prompt
- 调 Memory
- 调 Tool
- 调模型

但如果最后只能说：

> 我感觉这次好像更好了

那这还不是成熟工程。

成熟工程需要的是：

> **你能拿出一组任务和结果，说明系统在哪些维度变好了、变差了，或者没有变化。**

---

## 4. Agent 评估和普通函数测试有什么不同

这一点一定要先建立起来。

普通函数测试通常更接近：

```python
input -> expected output
```

例如：

```python
add(1, 2) == 3
```

它的判断非常确定。

但 Agent 不是这样。

Agent 的输出通常有更强的不确定性：

- 同一问题可能有多种合理表达
- 中间 Tool 路径可能不同
- 结果对不对不总是能靠字符串完全匹配判断

所以 Agent 评估通常不会只看：

> **文本完全一致**

而会更关注：

- 任务有没有完成
- 关键步骤是否合理
- Tool 是否调用正确
- 最终答案是否满足目标

所以：

> **Agent 评估更像任务级评估，而不是字符串级断言。**

---

## 5. 第一版评估体系先评什么

很多人一上来就想做很复杂的评测平台。

其实没有必要。

当前阶段我们先建立一个最小可用体系，只关注最关键的几类指标。

第一版你完全可以先评下面四个维度：

### 第一类：任务完成率

问题：

> 用户交给 Agent 的任务，最终完成了没有？

例如：

- 能不能正确读取文件
- 能不能正确调用时间工具
- 能不能完成项目分析

这是最基础、最重要的指标。

---

### 第二类：Tool 调用正确率

问题：

> 该调 Tool 的时候有没有调对，不该调的时候有没有乱调？

例如：

- 问时间时是否调用 `get_current_time`
- 问文件时是否调用 `read_file`
- 普通解释问题时是否没有多余 Tool 调用

这对 Agent 非常关键。

---

### 第三类：输出质量

问题：

> 最终回答是否正确、完整、符合任务目标？

这类指标可以先用人工判断，也可以后面再逐步结构化。

---

### 第四类：运行效率

问题：

> 完成同样任务，花了多少轮、多少时间、多少成本？

例如：

- 平均 turn 数
- 平均 Tool 调用次数
- 平均耗时

这能帮助你避免系统虽然“能做”，但越来越重、越来越慢。

---

## 6. 为什么任务完成率永远是第一指标

很多工程师一开始会被各种“高级指标”吸引，比如：

- reasoning 漂不漂亮
- 总结是不是更详细
- 表达是不是更自然

这些都可以看，但不是第一优先级。

第一优先级永远是：

> **任务到底有没有完成。**

因为如果 Agent 说得再漂亮，但任务没完成，系统核心价值就是不成立的。

所以第一版评估体系一定要先保住这个原则：

> **先看任务完成，再看完成质量。**

---

## 7. 为什么“样例集”比单次演示更重要

很多 Demo 最大的问题是：

```text
展示一个成功案例
```

这在演示时没问题，但对工程毫无说服力。

因为你永远可以挑一个容易成功的案例。

真正工程评估需要的是：

> **一组固定样例集（eval set）**

例如你可以先做一个最小集合：

- 5 个单 Tool 任务
- 5 个多轮任务
- 5 个容易出错的边界任务

只要你后面每次改动都跑这组样例，你就开始拥有最小可比较能力了。

这就是评估体系的起点。

---

## 8. 第一版评测集应该怎么设计

当前阶段，建议你不要追求大而全。

先做一个小而稳的评测集。

例如按任务类型分成三组：

### A 组：基础能力任务

例如：

- 查询当前时间
- 读取指定文件
- 做简单计算

这类任务主要验证：

- 基础 Tool Calling 是否稳定

---

### B 组：多轮任务

例如：

- 先读文件，再总结内容
- 先看目录，再找核心文件

这类任务主要验证：

- Agent Loop 是否稳定
- Tool 链路是否健康

---

### C 组：易错任务

例如：

- 不该调用 Tool 的问题
- 容易被无关 Memory 干扰的问题
- 容易被长上下文带偏的问题

这类任务主要验证：

- 系统边界是否清晰
- 错误控制是否变好

这个分组非常适合你当前课程项目。

---

## 9. 第一版评估不必一开始全自动

这一点很重要。

很多人一听“评估”，立刻想到：

- 自动评分平台
- judge model
- 可视化 dashboard
- 回归报告系统

这些很好，但不是第一步。

第一步更重要的是：

> **先建立固定样例 + 固定观察维度。**

哪怕第一版评分方式还是人工表格，也完全有价值。

例如对每个样例先记录：

- 是否完成任务
- Tool 是否调用正确
- 回答是否基本正确
- 是否出现明显跑偏

这已经比“凭感觉”强很多了。

所以第一版要先追求：

> **稳定可比较**

而不是一开始就追求：

> **全自动豪华评测平台**

---

## 10. 为什么评估指标不能只看“回答对不对”

因为 Agent 和普通问答模型不一样。

一个 Agent 的问题很多时候不是“答错”，而是：

- 路径低效
- Tool 调错
- 成本过高
- 轮次过多
- Memory 使用混乱

例如两个 Agent 最终答案都对：

### Agent A

1 轮完成，1 次 Tool 调用。

### Agent B

8 轮完成，调用了 5 个不必要 Tool。

如果你只看最终答案，它们都“通过”了。

但从工程角度看，质量完全不同。

所以 Agent 评估必须至少包含：

> **结果正确性 + 路径合理性 + 运行效率**

---

## 11. 第一版可以定义哪些最小指标

下面给你一组非常适合当前阶段的最小指标。

### 指标 1：Task Success Rate

任务成功率。

定义：

> 完成任务的样例数 / 总样例数

---

### 指标 2：Tool Selection Accuracy

Tool 选择正确率。

定义：

> Tool 调用是否符合任务需要

---

### 指标 3：Unnecessary Tool Call Rate

多余 Tool 调用率。

定义：

> 不该调 Tool 时却调了的比例

---

### 指标 4：Average Turns

平均完成轮数。

---

### 指标 5：Average Runtime

平均耗时。

---

### 指标 6：Obvious Failure Count

明显失败数。

例如：

- 跑偏
- 死循环
- 错误工具调用
- 没完成任务

这 6 个指标已经足够支撑第一版迭代。

---

## 12. 为什么“回归评测”是 Agent 工程的核心动作

真正的工程迭代不是：

```text
改一下

感觉好像行
```

而是：

```text
改一下

重新跑固定评测集

看哪些指标变好

看哪些指标变差
```

这就叫回归评测。

它的价值非常大：

- 防止你修一处坏三处
- 帮你验证优化是否真实有效
- 帮你建立稳定迭代节奏

所以从今天开始，你要有一个工程习惯：

> **任何重要改动，都应该尽量回归一遍固定评测集。**

---

## 13. 第一版评测结果应该怎么记录

你现在不需要复杂平台。

第一版可以非常朴素。

例如用一个表格记录：

| Case ID | 任务类型 | 是否成功 | Tool 是否正确 | 轮数 | 耗时 | 备注 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| A1 | 查时间 | 是 | 是 | 1 | 0.8s | 正常 |
| B2 | 读文件并总结 | 是 | 是 | 3 | 2.1s | 总结偏长 |
| C3 | 不该调 Tool 的问题 | 否 | 否 | 2 | 1.5s | 误调用 read_file |

你会发现：

> **只要开始结构化记录，评估体系就已经启动了。**

它不一定要高级，但必须可比较。

---

## 14. 这一课背后的核心工程思想

这一课真正训练的是一个非常关键的能力：

> **把“优化”从主观感受变成可比较实验。**

这和科研、推荐系统、搜索系统、传统软件工程，其实是共通的。

如果没有评估，你就无法真正回答：

- 这次优化值不值
- 这次重构有没有副作用
- 这套 Memory 策略到底有没有帮助

所以：

> **评估不是项目后期锦上添花，而是从一开始就应该存在的反馈闭环。**

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

手动整理一个最小评测集。

建议先做 10 到 15 个样例就够了。

---

### 第二件

为每个样例定义至少 4 个观察字段：

- 是否成功
- Tool 是否正确
- 轮数
- 备注

---

### 第三件

挑一个最近做过的改动，拿这组样例重新跑一遍。

---

### 第四件

把结果记录下来，哪怕先是 Markdown 表格也可以。

---

## 16. 本课小结

今天最重要的三句话：

### 第一

> **没有评估，Agent 优化很容易退化成主观感受管理。**

### 第二

> **Agent 评估首先要看任务是否完成，其次才是回答质量和运行效率。**

### 第三

> **固定样例集 + 固定观察维度，是最小评测体系的起点。**
