# Lesson5：Token 与上下文窗口管理初版

## 1. 本课目标

前面几课我们已经把 Agent 做成了一个逐渐工程化的系统：

- 有 `Runner`
- 有 `Session`
- 有日志
- 有 tracing
- 有 retry 和 timeout
- 也开始有配置层

但是这还不够。

因为只要你的 Agent 进入多轮任务，它一定会遇到一个非常现实的问题：

> **上下文窗口不是无限的。**

所以这一课我们要正式进入一个 Agent 工程师必须掌握的主题：

> **Token 管理与上下文窗口管理**

这一课的目标不是一次性把“上下文压缩系统”做完，而是先建立第一版工程意识：

1. 为什么上下文会爆
2. 为什么多轮 Agent 比普通聊天更容易爆
3. 第一版应该怎么做 message 裁剪
4. 为什么这件事必须放进 Runner / Session 的工程设计里

---

## 2. 为什么这是 Agent 的核心问题

很多普通聊天场景下，你可能感觉不到上下文窗口的问题。

例如：

```text
用户：你好
助手：你好
用户：帮我翻译一句话
助手：……
```

这类交互通常很短。

但是 Agent 不一样。

一个真正运行中的 Agent 会不断积累上下文：

```text
用户请求

system prompt

历史消息

tool call

tool result

新的 reasoning

新的 tool call

新的 tool result
```

而且这些内容不是一轮结束，而是会持续叠加。

所以 Agent 的上下文增长速度，远快于普通聊天机器人。

---

## 3. 一个最典型的爆炸场景

假设用户说：

> 帮我分析这个 SpringBoot 项目

Agent 很可能会经历下面这些步骤：

1. 读取目录结构
2. 读取 `README`
3. 读取 `pom.xml`
4. 搜索 `Controller`
5. 搜索 `Service`
6. 读取多个核心文件
7. 总结项目架构

如果你把每一步的原始输入输出都无脑塞回上下文，很快就会变成：

```text
消息越来越长

Tool 结果越来越多

请求成本越来越高

模型可用上下文越来越少
```

最后出现三种常见问题：

1. 请求太贵
2. 响应变慢
3. 超出上下文窗口限制

这就是为什么现代 Agent 框架一定会做上下文管理。

---

## 4. 这一课最重要的一句话

请你把下面这句话牢牢记住：

> **Agent 不是只会“思考”，Agent 还必须学会“遗忘”。**

很多初学者只关注：

- Tool 怎么调用
- Loop 怎么写
- Runner 怎么设计

但真正的工程问题是：

> **什么该保留，什么该裁掉。**

因为如果 Agent 永远不丢上下文，它迟早会把自己撑爆。

---

## 5. 什么是 Token 管理

你可以先把它理解成：

> **控制每次发给模型的上下文体积。**

在工程里，Token 管理通常会涉及：

- 历史消息保留策略
- Tool 结果裁剪策略
- 超长文件摘要策略
- 会话压缩策略
- 成本控制策略

但在当前课程阶段，我们先只做第一版：

> **历史消息裁剪（history truncation）**

---

## 6. 第一版先解决什么问题

这一课我们不追求复杂算法。

我们先解决最基础、也是最有价值的问题：

> **Session 里的消息不能无限增长。**

例如当前 `session.messages` 可能是这样：

```python
[
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "tool", "content": "..."},
    ...
]
```

如果每一轮都继续 append，而从不裁剪，那么这个列表只会越来越大。

所以第一版策略可以非常朴素：

> **只保留最近 N 轮消息。**

这虽然不完美，但已经是一个非常重要的工程进步。

---

## 7. 为什么“只保留最近 N 轮”是一个合理起点

因为它有三个优点：

### 第一，足够容易实现

不需要复杂 Token 计算器，也不需要额外依赖。

---

### 第二，能立刻防止无上限增长

哪怕策略不够聪明，它至少能让系统先稳定下来。

---

### 第三，便于后续升级

你后面可以逐步升级成：

- 按 Token 数裁剪
- 保留 system prompt + 最近 K 轮
- 大 tool result 自动摘要
- 长期记忆与短期记忆分层

所以“最近 N 轮”不是最终方案，但它是很好的第一版方案。

---

## 8. 一个非常容易犯的错误

很多人第一次做上下文控制，会直接在 `Runner.run()` 里写：

```python
if len(messages) > 20:
    messages = messages[-20:]
```

这看起来能用，但有两个问题：

1. `Runner` 开始直接操纵底层消息结构
2. `Session` 的职责被削弱了

更合理的设计是：

> **消息如何保存、如何裁剪，应该优先由 Session 负责。**

为什么？

因为 `Session` 的职责本来就是管理会话状态。

而 `Runner` 的职责是驱动循环，不是亲自做所有数据整理。

---

## 9. 这一课推荐的职责划分

### `Session`

负责：

- 保存消息
- 添加消息
- 根据策略裁剪消息

---

### `Runner`

负责：

- 每轮向 `Session` 追加新消息
- 从 `Session` 读取当前上下文
- 驱动 Agent Loop

---

### `Settings`

负责：

- 提供上下文管理相关参数

例如：

- `max_history_messages`
- `max_tool_result_chars`

这样职责就很清晰：

```text
Settings 定策略参数

Session 做消息管理

Runner 负责运行流程
```

---

## 10. 第一版可以长什么样

例如我们给 `Session` 增加这样的方法：

```python
class Session:
    def __init__(self, max_history_messages: int = 20):
        self.messages = []
        self.max_history_messages = max_history_messages

    def add_message(self, message: dict):
        self.messages.append(message)
        self._truncate_if_needed()

    def _truncate_if_needed(self):
        if len(self.messages) > self.max_history_messages:
            self.messages = self.messages[-self.max_history_messages:]
```

这就是一个最小可运行的第一版。

但是这里还有一个细节要注意：

> **system prompt 最好不要被裁掉。**

所以真正更合理一点的版本应该是：

- 固定保留 system message
- 裁剪其余历史消息

---

## 11. 更合理一点的第一版策略

假设消息结构里第一条是 system prompt，那么可以这样理解：

```text
system message 永远保留

剩余消息只保留最近 N 条
```

这样做的原因很简单：

system prompt 通常定义了 Agent 的身份和规则。

如果你把它裁掉，后面模型的行为就可能漂移。

所以第一版经验规则是：

> **宁可裁剪历史轮次，也尽量保留 system prompt。**

---

## 12. 为什么 Tool Result 是最危险的膨胀点

在多轮 Agent 中，最容易把上下文撑爆的通常不是用户问题，而是：

> **Tool 的返回结果**

例如：

- 读取整份源码文件
- 读取很长的日志
- 抓到很长的网页文本
- 搜索结果太多

所以真正的 Token 管理不仅是“消息条数管理”，还包括：

> **大块内容管理**

在第一版里，你可以先建立一个非常实用的规则：

> **Tool Result 超过一定长度，就先截断。**

例如只保留前 2000 个字符，再附加一条提示：

```text
[truncated]
```

这虽然简单，但非常有工程价值。

---

## 13. 为什么现在先做“字符级截断”也可以

严格来说，最好按 Token 来管理。

但在当前阶段，先做字符级截断也是合理的。

原因是：

1. 实现简单
2. 先解决 80% 的失控增长问题
3. 后续很容易升级成真正的 token-aware 裁剪

所以这一阶段不要被“必须精确算 token”卡住。

先把系统做成：

> **不会无限膨胀**

比一开始就追求完美更重要。

---

## 14. 这一课背后的工程思想

这一课表面在讲 Token。

但底层真正训练的是一个更深的能力：

> **资源约束下的系统设计**

因为 Agent 从来不是“想做什么都能做什么”的系统。

它始终受限于：

- 上下文窗口
- 延迟
- 成本
- API 限制

所以一个成熟的 Agent 工程师，不能只会写功能，还必须具备这种意识：

> **任何能力都要考虑资源边界。**

这和传统后端工程、分布式系统、操作系统设计，其实是同一种思维。

---

## 15. 和官方框架怎么对照理解

你以后看 OpenAI Agents SDK、LangGraph、Claude Code、OpenHands 这类系统时，会发现它们都在处理类似问题：

- 历史消息如何组织
- Tool 输出如何回填
- 超长上下文如何压缩
- 多轮任务如何避免成本失控

也就是说：

> **上下文管理不是高级优化，而是 Agent 主干能力。**

如果一个 Agent 只能在 2 轮以内工作，它更像 Demo。

如果一个 Agent 能稳定完成 20 轮、50 轮任务，它背后一定有上下文管理机制。

---

## 16. 这一课建议你在项目里落地什么

这一课落地时，建议你只做三件事：

### 第一件

在 `Settings` 中增加：

- `max_history_messages`
- `max_tool_result_chars`

---

### 第二件

在 `Session` 中增加：

- `add_message()`
- `_truncate_if_needed()`
- `get_messages()`

---

### 第三件

在 Tool Result 回填到上下文之前，先做一次长度裁剪。

这样你就已经把“上下文失控”这个问题，从无防护状态推进到了第一版可控状态。

---

## 17. 本课小结

今天最重要的不是某个具体实现，而是下面这两个认知：

### 第一

> **多轮 Agent 的核心难题之一，就是上下文会不断膨胀。**

### 第二

> **一个能长期运行的 Agent，必须有“保留什么、裁掉什么”的策略。**

这就是为什么 Token 管理是工程主线，而不是补充话题。
