# Lesson6：上下文压缩与摘要策略初版

## 1. 本课目标

上一课我们已经解决了一个基础但关键的问题：

> **上下文不能无限增长。**

我们给出的第一版方案是：

- 保留最近 N 条消息
- 对超长 Tool Result 做截断

这已经能让系统从“完全失控”进入“初步可控”。

但是很快你会发现一个新问题：

> **有些历史不能直接删。**

例如：

- 用户前面明确说过的目标
- Agent 已经完成过的重要结论
- 某次 Tool 分析得到的核心判断
- 后续步骤依赖的中间结果

如果你直接把这些内容裁掉，Agent 可能会“失忆”，然后：

- 重复做同样的事
- 忘记任务目标
- 推理链断裂
- 输出前后矛盾

所以这一课我们进入下一步：

> **如果不能原样保留全部历史，那就把历史压缩成更短但仍然有用的信息。**

这就是上下文压缩与摘要策略的起点。

---

## 2. 为什么“裁剪”还不够

裁剪的逻辑很简单：

```text
太长了

删掉旧的
```

它的优点是直接、便宜、实现容易。

但它的问题也很明显：

> **裁剪保住了长度，却不一定保住了信息。**

举个例子。

假设 Agent 已经做过这些事情：

1. 读了 `README`
2. 知道这是一个 SpringBoot + Redis + MySQL 项目
3. 发现认证逻辑在 `AuthService`
4. 发现订单流程在 `OrderService`

如果这些内容全都被直接裁掉，那么后面的 Agent 可能又会重新去做一遍相同分析。

所以仅靠删除历史，通常只能解决“长度问题”，不能解决“记忆问题”。

---

## 3. 什么是上下文压缩

你可以先把它理解成一句很朴素的话：

> **把长历史变成短结论。**

例如原始历史可能是这样：

```text
读了 5 个文件

做了 3 次搜索

执行了 2 次工具

得到很多原始输出
```

压缩后变成：

```text
已确认这是一个 SpringBoot 项目。
核心模块包括认证、订单、库存。
Redis 用于缓存，MySQL 用于主存储。
后续应重点分析 OrderService 和 InventoryService。
```

你会发现：

- 长度变短了
- 关键信息还在
- 后续推理还能继续

这就是压缩的价值。

---

## 4. 这一课最重要的一句话

请记住：

> **裁剪是在丢信息，压缩是在提炼信息。**

这两个动作都很重要，但它们不是一回事。

### 裁剪

目标：

> 快速控制体积

代价：

> 可能丢掉重要上下文

---

### 压缩

目标：

> 在减少长度的同时保住关键信息

代价：

> 实现更复杂，也更依赖策略质量

所以真正成熟的 Agent 系统，通常不是“只裁剪”或“只压缩”，而是：

> **裁剪 + 压缩结合使用**

---

## 5. 哪些内容适合被压缩

不是所有上下文都值得压缩。

在 Agent 系统里，通常更适合压缩的是下面这些内容：

### 第一类：旧轮次的多步分析过程

比如：

- 已经完成的一段子任务
- 多个中间推理步骤
- 一连串已经结束的 Tool 调用

这些内容原样保留很长，但压缩成结论后仍然有价值。

---

### 第二类：超长 Tool Result

例如：

- 读取大文件
- 搜索返回很多文本
- 日志输出太长

很多时候，真正有价值的不是原始全文，而是：

> **从中提取出的关键结论**

---

### 第三类：阶段性工作总结

例如：

- “已经确认项目使用 Redis 做缓存”
- “订单主流程在 OrderService”
- “Controller 层比较薄，主要逻辑在 Service”

这类内容非常适合作为压缩后的结构化记忆。

---

## 6. 哪些内容不应该轻易压缩

同样重要的是，你也要知道什么不该轻易压缩。

### system prompt

通常不要压缩。

因为它定义了 Agent 的行为边界。

---

### 当前正在进行中的最近几轮消息

通常不要过早压缩。

因为当前局部上下文对模型的即时推理最关键。

---

### 精确格式要求或原始关键数据

例如：

- 文件路径
- 命令参数
- JSON 结构
- 报错原文

如果压缩得过头，可能会损失后续执行所需的精确性。

所以压缩不是“把一切都概括掉”，而是有边界地压缩。

---

## 7. 第一版摘要策略应该长什么样

在你当前课程阶段，不需要一上来就做复杂的自动摘要系统。

我们先做一个最小有用版本：

> **当历史消息超过阈值时，把较旧的一段消息总结成一条 summary message。**

例如原本有 30 条消息：

```text
system
msg1
msg2
msg3
...
msg30
```

第一版可以变成：

```text
system
summary_of_msg1_to_msg20
msg21
msg22
...
msg30
```

这就是“压缩后保留”的基本模型。

---

## 8. 这个 summary message 本质上是什么

很多初学者会把 summary 理解成“写一段总结文字”。

这不算错，但还不够工程化。

更准确地说，它应该是：

> **对旧上下文的结构化浓缩表示。**

也就是说，一个好的 summary 不是随便写几句，而应该尽量保留：

- 当前目标
- 已完成事项
- 关键发现
- 后续待办

所以比起“摘要”，你更可以把它理解成：

> **压缩后的工作状态**

---

## 9. 一个很实用的摘要模板

在当前阶段，你完全可以先用固定模板。

例如：

```text
任务目标：
...

已完成：
...

关键发现：
...

下一步建议：
...
```

这个模板非常适合 Agent 场景。

因为它不是单纯做文章摘要，而是在保留运行状态。

这也是 Agent 摘要和普通“内容摘要”的一个关键区别。

---

## 10. 摘要应该放在哪一层

这一点很重要。

很多人第一反应是：

```python
Runner 里直接做 summary
```

这通常不是最好的第一选择。

更合理的职责划分是：

### `Session`

负责：

- 判断历史是否需要压缩
- 持有 summary message
- 管理“原始消息”和“压缩消息”的替换关系

---

### `Runner`

负责：

- 驱动循环
- 在合适时机触发压缩流程

---

### `LLM` 或 `Summarizer`

负责：

- 真正生成摘要内容

也就是说：

> **Session 管状态，Runner 管流程，摘要器管压缩内容。**

这比把一切塞进 Runner 更清晰。

---

## 11. 第一版到底要不要单独做 Summarizer

如果按长期架构看，最好有独立的摘要模块。

例如：

```text
Summarizer

CompressionPolicy

ContextManager
```

但在你当前阶段，不必一上来就拆这么细。

我们可以先采用一个更轻量的设计：

> **先把“摘要生成”当成一个辅助能力，由 Session 或 Runner 调用。**

等后面进入更复杂的长生命周期 Agent，再把它独立成模块。

这是很典型的渐进式架构演进思路。

---

## 12. 第一版可以怎么实现

第一版完全可以非常朴素。

例如触发条件：

```text
如果历史消息超过 20 条
```

那么：

1. 取较旧的前 12 条
2. 把它们压缩成一条 summary
3. 用这条 summary 替换原来的 12 条消息
4. 保留后面的新消息不动

这样做以后，消息长度就会明显下降，但又不会像纯裁剪那样把信息完全抹掉。

---

## 13. 摘要可以由谁生成

在工程上通常有三种路径：

### 方案 A：规则式摘要

例如：

- 只截取每条消息前 100 字
- 按固定模板拼接

优点：

- 成本低
- 稳定

缺点：

- 质量有限

---

### 方案 B：LLM 生成摘要

把旧消息交给模型，让模型总结。

优点：

- 质量高
- 更聪明

缺点：

- 额外成本
- 增加延迟

---

### 方案 C：混合式

先规则式压缩，再在必要时用 LLM 做高质量总结。

在当前课程阶段，最推荐你先理解：

> **第一版可以先从规则式或半规则式摘要开始。**

因为我们的目标是先建立架构，不是先追求最强效果。

---

## 14. 这一课背后的核心工程思想

这一课表面上在讲“摘要”。

但底层真正训练的是：

> **如何在有限资源下保留系统连续性。**

因为多轮 Agent 的难点从来不只是“当前怎么回答”，而是：

> **多轮之后，它还能不能持续保持任务状态。**

如果没有压缩机制，系统会出现两种坏结果：

### 第一种

全部保留。

问题：

- 太贵
- 太慢
- 爆窗口

### 第二种

全部删除。

问题：

- 失忆
- 重复工作
- 上下文断裂

所以压缩策略本质上是在这两者之间找平衡。

---

## 15. 和“Memory”有什么关系

这一点你现在要先建立一个初步感觉。

很多人把“上下文压缩”和“Memory”混在一起。

它们相关，但不是同一层东西。

### 上下文压缩

解决的是：

> **当前会话上下文太长怎么办**

---

### Memory

解决的是：

> **跨会话、长期信息怎么保存**

所以压缩更偏向：

> **短期工作记忆整理**

而 Memory 更偏向：

> **长期记忆系统**

这两个后面会逐渐衔接起来。

---

## 16. 这一课建议你在项目里怎么落地

这节课不要贪多，建议只做下面三件事：

### 第一件

在 `Settings` 中增加压缩相关参数，例如：

- `summary_trigger_messages`
- `summary_keep_recent_messages`

---

### 第二件

在 `Session` 中引入一个 summary message 的概念。

例如：

- `self.summary`
- `build_context_messages()`

---

### 第三件

定义一个最小版摘要函数。

哪怕先不是 LLM 版，也没关系。

例如先做：

- 提取旧消息中的关键信息
- 拼成固定模板

这样你就已经从“裁剪系统”升级到了“裁剪 + 压缩系统”。

---

## 17. 本课小结

今天真正要记住的有三句话：

### 第一

> **裁剪解决长度问题，压缩解决信息保留问题。**

### 第二

> **summary 不是装饰文本，而是旧上下文的压缩状态表示。**

### 第三

> **长生命周期 Agent 一定需要压缩策略，否则不是太贵，就是太健忘。**
