# Lesson26：从多 Agent 协作回看单 Agent——为什么很多问题其实根本不需要拆

## 1. 本课目标

前面几课，我们已经把多 Agent 主线推进得比较完整了：

- 先讲了角色分工抽象
- 再讲了经典三角 `Planner / Executor / Reviewer`
- 又补上了多 Agent 的真实成本：通信、同步、冲突、调度、治理

到这里，一个成熟课程必须做一件非常重要的事：

> **反向校准。**

因为如果只讲“为什么多 Agent 很强”，你很容易产生一种偏差：

> 复杂一点的问题，就应该拆成多 Agent。

这其实是危险的。

所以这一课我们要专门回答一个非常关键的问题：

> **为什么很多看起来像“该上多 Agent”的问题，最后其实根本不需要拆？**

这一步非常重要，因为真正成熟的 Agent 工程师，不是看到复杂度就拆，而是：

> **先判断复杂度到底属于“角色问题”，还是只是“单 Agent 结构还没整理好”。**

---

## 2. 为什么很多人会过早进入多 Agent

这件事很常见，而且完全可以理解。

因为当单 Agent 出现问题时，表面现象通常很像：

- 想不清
- 做不稳
- 容易跑偏
- 审查不严

这时候多 Agent 方案看起来特别诱人：

- 想不清？加 Planner
- 做不稳？加 Executor
- 审查不严？加 Reviewer

从结构直觉上看，这很顺。

但问题在于：

> **很多时候，问题并不是“缺角色”，而是“单 Agent 内部结构还没治理好”。**

如果这一层没分清，你就会很容易把：

- Prompt 问题
- Tool 问题
- Session 问题
- Memory 问题
- 调度问题

误诊成：

> 需要多 Agent。

这就是典型的“用结构升级掩盖局部设计缺陷”。

---

## 3. 这一课最重要的一句话

请记住：

> **很多问题之所以看起来像“需要多 Agent”，其实只是因为单 Agent 还没有完成角色化、状态化、治理化。**

这句话非常关键。

它会帮你建立一种很重要的诊断能力：

看到系统不稳时，不要第一反应就是：

> 再加一个 Agent。

而要先追问：

> 这是职责真的不可同处，还是当前单 Agent 只是还没被设计清楚？

这两者差别非常大。

---

## 4. 哪些问题经常被误诊成“要上多 Agent”

这一课最实用的部分，就是帮你识别常见误诊。

### 误诊 1：任务流程不清

表面上看像：

> 需要 Planner。

但很多时候本质上只是：

- 没有明确阶段
- 没有 `completed_steps`
- 没有 `pending_steps`
- 没有结束条件

这其实首先是：

> **Session 和调度设计问题。**

---

### 误诊 2：结果质量不稳

表面上看像：

> 需要 Reviewer。

但很多时候本质上只是：

- 没有评测集
- 没有 review checklist
- 没有显式校验步骤

这其实首先是：

> **治理和评估流程问题。**

---

### 误诊 3：执行容易跑偏

表面上看像：

> 需要独立 Executor。

但很多时候本质上只是：

- Tool 设计太差
- 上下文组织太乱
- RAG 注入太吵
- Memory 污染当前判断

这其实首先是：

> **能力层和信息层问题。**

---

### 误诊 4：系统一长任务就乱

表面上看像：

> 单 Agent 不行，得拆。

但很多时候本质上只是：

- Session 状态失控
- summary 质量差
- checkpoint 不合理
- 恢复机制不清

这其实首先是：

> **运行时状态治理问题。**

所以你要开始学会：

> **先做误诊排除，再做结构升级。**

---

## 5. 为什么“单 Agent + 角色化逻辑”常常已经足够强

这是前几课一直在铺垫的一个关键中间态。

很多问题并不需要立刻走到真正多 Agent。

更合适的第一步往往是：

> **在单 Agent 内部显式引入角色化逻辑。**

例如：

### 先规划

```text
先明确目标和阶段
```

### 再执行

```text
按阶段去调用 Tool
```

### 再复核

```text
按 checklist 检查结果
```

注意，这时候：

- 角色已经拆了
- 逻辑已经清了
- 运行时仍然集中

这通常会比“直接拆多 Agent”更稳，也更容易调。

所以：

> **很多系统真正缺的不是更多 Agent，而是更清楚的内部步骤。**

---

## 6. 为什么“拆角色”和“拆实例”必须分开看

这一点非常非常重要。

很多人脑子里会默认：

```text
角色分工 = 多实例
```

其实不是。

这两个层次必须分开：

### 第一层：逻辑分工

回答的是：

> 哪些职责应该被拆开表达

---

### 第二层：运行时拆分

回答的是：

> 这些职责是否值得交给不同实例、不同上下文、不同运行单元

你会发现：

第一层经常是必须的，

但第二层未必。

这就是为什么很多项目更适合先停留在：

> **单 Agent + 明确角色步骤**

而不是马上变成真正多 Agent。

---

## 7. 什么情况下，单 Agent 继续优化通常比拆多 Agent 更划算

这是你以后做架构判断时非常重要的一条经验线。

当前阶段，更适合继续优化单 Agent 的情况通常包括：

### 情况 1：任务主线其实还比较集中

虽然复杂一点，但仍然围绕一个主目标推进。

---

### 情况 2：状态还可以集中维护

Session、Memory、RAG 仍然能在一个运行时里比较清楚地协同。

---

### 情况 3：最大问题来自局部设计不清

例如：

- Prompt 乱
- Tool 差
- RAG 噪音大
- 评测没建立

这些都更适合先在单 Agent 内修好。

---

### 情况 4：当前收益不足以覆盖多 Agent 成本

也就是：

拆了角色虽然更“像团队”，但并没有带来足够显著的质量提升。

这时候就不值得拆。

所以：

> **只要单 Agent 的问题还能通过结构治理解决，就应该优先治理，而不是优先拆分。**

---

## 8. 为什么很多“多 Agent 成功案例”背后，核心其实是流程显式化

这点特别值得你理解。

很多案例看起来像是：

> 上了多 Agent，所以变强了。

但你仔细拆，会发现它真正带来的提升常常不是“多了几个实例”，而是：

- 规划步骤被显式化了
- 校验步骤被显式化了
- 状态边界被显式化了
- handoff 信息被结构化了

换句话说：

> **真正产生价值的，很多时候是“显式化流程”，而不是“实例数量增加”。**

这意味着：

很多收益，其实在单 Agent 里通过结构化步骤就能先拿到一大半。

这会极大提升你的架构判断力。

---

## 9. 为什么“先把单 Agent 做干净”是一条非常强的工程路径

很多成熟系统最后即使真的走向多 Agent，它们前面通常也经历过一个过程：

> **先把单 Agent 做得尽可能清楚、稳定、可治理。**

为什么这条路径强？

因为如果你连单 Agent 都还没做干净，就直接拆成多 Agent，通常只是把问题复制和放大。

例如：

- Prompt 本来就乱
- 拆成多 Agent 后，每个 Prompt 都乱

或者：

- Tool 接口本来就差
- 拆成多 Agent 后，更多角色一起调差 Tool

所以一个非常成熟的判断原则是：

> **单 Agent 没做干净时，多 Agent 很容易只是把局部混乱升级成系统性混乱。**

---

## 10. 为什么单 Agent 的“可治理性”是是否值得拆分的重要前置条件

你前面已经学了很多治理能力：

- tracing
- eval
- retry
- summary
- checkpoint
- waiting_for_human

这些能力如果在单 Agent 里都还不成熟，你就很难在多 Agent 里稳定地复制它们。

所以你可以把它理解成一个前置条件：

> **只有当单 Agent 已经具备一定的可治理性，拆分才更有可能是收益，而不是灾难。**

这和软件里“先把单体理顺，再考虑分布式化”是同一个道理。

---

## 11. 一个很实用的判断问题：你到底是在拆职责，还是在逃避重构

这句话很尖锐，但特别有用。

当你下一次想上多 Agent 时，建议先问自己：

> **我是因为职责确实天然分化了，还是因为我不想继续重构当前单 Agent？**

这是两个完全不同的动机。

### 前者

说明你在做结构演进。

### 后者

说明你可能只是想用更复杂的架构逃避当前的设计债务。

这个自检非常重要。

因为很多过早多 Agent 化，背后其实是第二种情况。

---

## 12. 第一版“先不拆”的策略应该长什么样

这一课不是反对多 Agent，而是反对过早拆分。

所以当前阶段更成熟的默认策略通常是：

### Step 1

先把当前任务改造成显式阶段结构。

---

### Step 2

在单 Agent 内引入角色化步骤：

- plan
- execute
- review

---

### Step 3

建立 tracing 和 eval，验证结构化后是否已经明显变稳。

---

### Step 4

只有当：

- 角色边界已稳定
- 单 Agent 仍然明显过载
- 复杂度收益足够大

再考虑真正多 Agent。

这是一条非常成熟的工程路径。

---

## 13. 这一课背后的核心工程思想

这一课真正训练的是：

> **不要把“架构升级”当成“设计问题的默认答案”。**

有时候最成熟的工程判断，不是加一层，而是：

> **先把当前这一层做对。**

这是很多人容易忽略，但又极其重要的能力。

因为架构的价值不在于复杂，而在于：

> **用恰当复杂度解决恰当问题。**

如果一个问题本来可以通过：

- 角色化逻辑
- 状态治理
- Prompt 重构
- Tool 重构
- 信息系统整理

解决，那直接上多 Agent 就很可能是过度设计。

---

## 14. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

挑一个你之前直觉觉得“应该拆多 Agent”的任务。

---

### 第二件

重新做一次诊断，问自己：

- 真的是职责天然分化了吗？
- 还是当前单 Agent 只是结构还不清楚？

---

### 第三件

尝试先用“单 Agent + 显式角色步骤”重构一次。

---

### 第四件

对比重构前后，看看问题是否已经明显缓解。

如果缓解了，就说明这类问题原本并不需要真正多 Agent。
