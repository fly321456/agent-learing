# Lesson19：RAG、Memory、Session 三层信息系统协同初版

## 1. 本课目标

到这一课为止，你已经分别学习并建立了三类非常重要的信息层：

### 第一层：Session

负责：

- 当前任务的即时上下文
- 当前阶段状态
- `summary`
- `completed_steps`
- `pending_steps`

---

### 第二层：Memory

负责：

- 用户偏好
- 稳定项目事实
- 已验证关键结论
- 跨会话可复用信息

---

### 第三层：RAG

负责：

- 外部知识源接入
- 按需检索相关知识
- 将外部材料动态注入当前任务

你现在已经分别理解了它们。

但真正开始做系统时，新的问题很快就会出现：

> **当 Session、Memory、RAG 同时存在时，这三层信息到底怎么协同，才不会互相冲突、互相污染、互相淹没？**

这就是这一课的核心。

因为模块“单独成立”不等于系统“整体协同”。

所以这一课我们正式进入：

> **三层信息系统协同设计**

这会把你的课程从“理解单个模块”推进到“理解信息系统整体结构”。

---

## 2. 为什么三层信息系统一旦同时存在，就很容易打架

如果你只有一种信息来源，事情反而简单。

例如：

- 只有当前消息
- 或只有长期记忆
- 或只有外部知识检索

但一旦三层同时存在，系统复杂度会明显上升。

因为它们都可能向模型提供“看起来有用的信息”。

于是就会出现：

### 情况 1：信息重复

同一个事实同时出现在：

- Session summary
- Memory
- RAG 检索片段

模型会看到三遍。

---

### 情况 2：信息冲突

例如：

- Session 里是刚刚分析出来的新结论
- Memory 里还是旧结论
- RAG 里又是文档里的历史说法

模型会面临多个版本。

---

### 情况 3：信息竞争注意力

当前任务真正需要的是：

- 最近上下文里的一个局部细节

但大量 Memory 和 RAG 信息一起灌进去后，真正关键的内容反而不显眼了。

所以你要建立一个关键认知：

> **信息层越多，问题越不只是“有没有信息”，而是“信息之间怎么分工、怎么排序、怎么治理”。**

---

## 3. 这一课最重要的一句话

请记住：

> **Session、Memory、RAG 不是三个并列的“都往上下文里塞点东西”的模块，而是三种不同时间尺度、不同来源、不同用途的信息层。**

这句话非常重要。

因为一旦你只是把它们理解成：

> 三个都能给模型喂信息的模块

那系统迟早会乱。

更正确的理解是：

### Session

代表：

> 当前这次任务正在发生什么

---

### Memory

代表：

> 系统过去沉淀下来的高价值内部经验

---

### RAG

代表：

> 当前任务需要时临时取回的外部知识

这三者不是一个层次的东西。

一旦层次感清楚，协同逻辑就会清楚很多。

---

## 4. 先从“时间尺度”理解三层分工

这是最容易帮助你建立直觉的一种方式。

### Session：最短时间尺度

它关注的是：

- 这一次任务
- 这一轮上下文
- 当前阶段推进

它最“近”，也最“实时”。

---

### Memory：中长期时间尺度

它关注的是：

- 跨会话
- 跨任务
- 长期仍有价值的经验与事实

它不是当前轮最实时的信息，但通常更稳定。

---

### RAG：按需外部时间尺度

它关注的是：

- 当前任务临时需要的外部知识

这些知识可能既不是当前 Session 自己产生的，也不是 Memory 已经沉淀下来的，而是：

> **现在需要才去拿。**

所以如果按时间尺度理解：

> **Session 解决“现在”，Memory 解决“过去沉淀”，RAG 解决“当前临时外取”。**

这个理解非常有帮助。

---

## 5. 为什么 Session 通常应当拥有最高优先级

这一点很关键。

如果三层信息同时存在，第一版工程上通常更应该优先相信：

> **当前 Session 的状态。**

为什么？

因为 Session 最接近当前任务现实。

例如：

- 当前刚刚读了哪个文件
- 当前阶段是什么
- 当前已经完成了什么
- 当前待办是什么

这些信息具有最强的“当前性”。

而 Memory 和 RAG 都有一个共同问题：

- 它们可能不是最新的
- 它们未必和当前任务局部状态完全一致

所以在冲突处理上，一个非常重要的第一版原则是：

> **当前 Session 的即时状态，通常优先于长期 Memory 和外部 RAG。**

---

## 6. 为什么 Memory 不应该和 Session 争夺“当前状态解释权”

这也是高频混乱来源。

Memory 的价值在于：

- 提供背景
- 提供稳定事实
- 提供长期偏好

它不应该强行覆盖当前任务里刚刚发生的更新状态。

例如：

- Session 刚分析出“当前项目新版已经改了缓存策略”
- Memory 里还是旧版缓存设计

这时如果 Memory 被无脑高权重注入，就会误导模型。

所以工程上你要建立一个原则：

> **Memory 更适合提供背景，不适合替代当前 Session 的实时状态判断。**

这和数据库里“缓存数据不能覆盖实时事务状态”很像。

---

## 7. 为什么 RAG 也不应该和 Session 抢“当前任务控制权”

很多人接入 RAG 后，容易出现一种新问题：

> 只要查到了外部知识，模型就开始被外部知识牵着走。

这其实很危险。

因为 RAG 的作用是：

> **补充当前任务所需的外部知识。**

而不是：

> **接管当前任务主线。**

例如当前任务是：

- 分析本地项目当前实现

这时 RAG 可能只应该补充：

- 某个框架规范
- 某个 API 文档说明

但如果把大量外部文档塞进来，模型就可能忽视：

- 当前代码真实状态
- 当前 Session 已确认的结论

所以：

> **RAG 是当前任务的外部参考层，不是主状态层。**

---

## 8. 第一版协同原则：Session 主线，Memory 背景，RAG 外援

为了让你现在就能在脑子里形成稳定结构，我们先给出一个很实用的第一版协同原则：

> **Session 负责主线推进，Memory 负责长期背景，RAG 负责按需外援。**

你可以这样记：

### Session

回答：

> 这次任务当前做到哪了？

---

### Memory

回答：

> 过去有哪些稳定经验和事实值得带上？

---

### RAG

回答：

> 当前任务缺什么外部知识，需要临时查什么？

这三个问题一旦分清，信息协同就会清楚很多。

---

## 9. 为什么三层信息不能无差别全量注入

这是第一版系统最容易翻车的地方。

很多人一旦把三层都做好了，就容易兴奋地想：

> 那就全都塞进去，信息越多越好。

现实通常正好相反。

如果你同时灌入：

- 大量 recent messages
- 大段 summary
- 很多 Memory
- 很多 RAG 片段

结果通常会是：

### 问题 1：上下文膨胀

你前面辛苦做的上下文治理又被冲垮。

---

### 问题 2：主次不分

模型很难判断哪部分最该优先相信。

---

### 问题 3：信息冲突更难发现

同一事实多个版本一起出现，调试会变得很难。

所以：

> **三层信息系统协同的第一原则，不是“都要有”，而是“都要克制”。**

---

## 10. 第一版协同应该先解决哪些问题

这一课我们不追求一步到位的统一信息总线。

第一版先解决三个最关键的问题：

### 第一，谁是主状态层

答案通常是：

> Session

---

### 第二，谁提供长期背景

答案通常是：

> Memory

---

### 第三，谁按需补外部知识

答案通常是：

> RAG

只要把这三件事先分清，你的系统就已经比很多混乱的 Agent 项目更成熟了。

---

## 11. 为什么需要“信息注入顺序”这个概念

当三层信息都可能参与上下文构造时，顺序本身就会变得重要。

当前阶段，你可以先建立一个很朴素但很有用的顺序意识：

### 第一层：系统规则 / Prompt

定义行为边界。

---

### 第二层：Session 当前状态

定义当前任务主线。

---

### 第三层：Memory 背景

补充长期稳定信息。

---

### 第四层：RAG 外部知识

补充当前任务缺少的外部材料。

这个顺序的意义不是绝对死规则，而是：

> **让模型先理解当前任务，再补背景，再补外部知识。**

如果顺序颠倒，很容易让主线被外部材料淹没。

---

## 12. 为什么“冲突处理”必须被显式考虑

一旦三层并存，冲突几乎一定会发生。

例如：

### 冲突 1

Session 刚确认的事实 vs Memory 中的旧事实

---

### 冲突 2

当前项目现实实现 vs 外部文档最佳实践

---

### 冲突 3

summary 中的阶段结论 vs 新一轮 recent context 中的更新信息

如果没有冲突处理原则，模型就只能自己“猜”。

而这通常会带来不稳定行为。

所以你至少要给系统一个第一版规则：

> **当前运行状态优先于旧 Memory，当前实际观察优先于外部一般知识。**

这就是非常关键的协同原则。

---

## 13. 第一版信息系统协同流程可以怎么理解

你现在可以把整体流程理解成下面这样：

```text
用户任务进入

↓

构建 Session 当前状态

↓

按需读取少量相关 Memory

↓

判断是否需要外部知识检索

↓

按需取回少量 RAG 片段

↓

统一整理为上下文

↓

送给模型决策
```

这条链的重点不在于“模块越多越强”，而在于：

> **每一层信息都只在合适的位置、以合适的角色进入系统。**

这才是协同。

---

## 14. 为什么三层协同最终还是会回到“上下文治理”

这一点很值得你注意。

你学到现在会发现，前面很多主线其实在这里重新汇合了：

- Token 管理
- Summary 压缩
- Memory 注入
- RAG 检索
- Session 状态治理

最后它们都会回到同一个核心问题：

> **当前这一轮，到底该把什么信息放进上下文，放多少，按什么角色放。**

这说明：

> **多层信息系统协同，本质上还是上下文治理问题的升级版。**

只是现在你管理的已经不是单一消息流，而是多来源、多时间尺度的信息流。

---

## 15. 为什么这一步是 Agent 工程能力的重要分水岭

很多初学者做到前面时，还是模块化理解：

- 学了 Session
- 学了 Memory
- 学了 RAG

但真正的工程难点从来不只是“知道每个模块是什么”，而是：

> **知道它们放到一起以后怎么不互相伤害。**

这正是系统设计能力的核心。

所以这一课其实标志着你开始进入一个更成熟的阶段：

> **从会做模块，走向会做协同。**

这是成为 Agent 工程师非常关键的一步。

## 16. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

写出你当前项目里：

- Session 管什么
- Memory 管什么
- RAG 管什么

的边界定义。

---

### 第二件

给系统写一个第一版信息优先级原则。

例如：

- Session 当前状态优先
- Memory 提供背景
- RAG 提供外部临时知识

---

### 第三件

找一个具体问题场景，检查是否存在：

- 信息重复注入
- 信息冲突
- 外部知识淹没主线

---

### 第四件

尝试把上下文构造分成几段：

- 当前任务状态
- 长期背景
- 外部知识

而不是全部混成一坨。

---

## 17. 本课小结

今天最重要的三句话：

### 第一

> **Session、Memory、RAG 不是三个并列塞信息的模块，而是三种不同时间尺度、不同来源、不同用途的信息层。**

### 第二

> **第一版协同原则是：Session 主线，Memory 背景，RAG 外援。**

### 第三

> **多层信息系统协同，最终本质上还是上下文治理问题的升级版。**
