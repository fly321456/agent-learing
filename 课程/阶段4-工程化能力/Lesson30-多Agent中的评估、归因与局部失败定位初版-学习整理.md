# Lesson30：多 Agent 中的评估、归因与局部失败定位初版

## 1. 本课目标

到这一课为止，你已经把多 Agent 实现前后最核心的结构问题基本串起来了：

- 为什么要先做角色分工抽象
- 为什么经典三角高频出现
- 为什么多 Agent 不是免费午餐
- 为什么很多问题其实不需要拆
- 为什么拆之前要做可拆分性审计
- 为什么第一版实现要先做协作协议
- 为什么共享状态、局部状态和状态主权必须讲清楚

现在系统终于进入一个非常现实的问题：

> **如果多 Agent 系统结果不好，到底是谁的问题？**

这不是一个小问题。

因为在单 Agent 里，问题通常已经够难查了。

到了多 Agent，问题会进一步复杂化：

- 是 Planner 的规划就错了？
- 还是 Executor 执行偏了？
- 还是 Reviewer 没拦住问题？
- 还是 handoff 过程丢了关键信息？
- 还是共享状态同步错了？

这就是这一课要解决的核心。

所以这一课的目标是：

> **建立多 Agent 系统的评估、归因与局部失败定位框架。**

也就是说，你要开始学会：

- 怎么评估多 Agent 不只是“最后结果对不对”
- 怎么定位到底是哪一个角色或哪一次交接出了问题
- 怎么避免多 Agent 系统变成“出了问题谁都说不清”的黑盒

---

## 2. 为什么多 Agent 的“最终答案评估”远远不够

很多系统评估第一反应还是：

> 最后答对了吗？

这在单 Agent 里都已经不够，在多 Agent 里就更不够了。

为什么？

因为多 Agent 系统的失败，可能发生在很多不同层：

### 层 1：规划失败

一开始路线就不合理。

---

### 层 2：执行失败

规划合理，但动作落偏了。

---

### 层 3：审查失败

前两步都还行，但质量门槛没守住。

---

### 层 4：协作失败

角色各自能力都不差，但 handoff 丢信息、误解信息，导致系统整体失效。

如果你只看最终答案，那这些层次全都会被压扁成一句：

> 结果不对。

这在工程上几乎没有足够诊断价值。

所以你现在要先建立一个核心认知：

> **多 Agent 评估不只是结果评估，还必须是过程评估和角色级评估。**

---

## 3. 这一课最重要的一句话

请记住：

> **多 Agent 系统最怕的不是失败，而是失败以后无法归因。**

这句话非常关键。

因为多 Agent 一旦没有归因能力，就会快速滑向一种很糟糕的状态：

- 结果不好
- 每个角色都“看起来”做了点事
- tracing 一大堆
- 但没人能说清第一个错误到底发生在哪

这时候系统会变成：

> **表面上结构更先进，实际上更难维护。**

所以多 Agent 真正要成熟，不只是角色更多，而是：

> **失败后能拆得开、看得清、定位得到。**

这就是归因能力的意义。

---

## 4. 什么叫“局部失败定位”

你可以先把它理解成：

> **把一次系统整体失败，拆解成具体哪个角色、哪次交接、哪类状态先偏了。**

这很重要，因为多 Agent 的失败通常不是“一瞬间全错”，而是：

1. 某个局部先偏
2. 偏差通过 handoff 继续扩散
3. 后续角色在错误前提上继续工作
4. 最终变成整体错误

也就是说：

> **整体失败，通常是局部失败传染出来的。**

所以多 Agent 调试的关键不是盯着最后一句话，而是：

> **找到第一个局部失败发生的位置。**

这就叫局部失败定位。

---

## 5. 为什么多 Agent 系统更像“链路系统”而不是“单点系统”

单 Agent 的问题，很多时候至少还可以近似理解成：

> 这个 Agent 在某一步判断错了。

但多 Agent 系统更像什么？

> **一条角色协作链。**

例如：

```text
Planner
  ↓
plan handoff
  ↓
Executor
  ↓
execution result handoff
  ↓
Reviewer
  ↓
pass / revise
```

只要链路里某一段出了问题，后面就可能全部受影响。

所以多 Agent 评估和调试的核心视角应该从：

> 单点判断

升级成：

> **链路归因**

这会非常影响你后续怎么设计 tracing 和 eval。

---

## 6. 第一类评估：角色输出质量评估

这是最直观、也最应该先建立的一层。

你要开始把“角色本身的输出”作为独立评估对象。

例如：

### Planner

评什么？

- 目标拆解是否合理
- 阶段划分是否清楚
- 下一步动作是否可执行

---

### Executor

评什么？

- 是否按目标正确执行
- Tool 使用是否合理
- 结果物是否完整

---

### Reviewer

评什么？

- 是否能发现明显问题
- 是否能提出有效打回意见
- 是否能正确判断是否收尾

所以第一版你要先建立一个意识：

> **多 Agent 系统里，每个角色本身都是可单独评估的。**

这和单 Agent 只看总结果完全不同。

---

## 7. 第二类评估：handoff 质量评估

很多系统的问题并不在角色内部，而在角色之间。

这就是为什么多 Agent 里 handoff 需要被单独评估。

你至少要开始看：

### handoff 是否完整

关键信息有没有带过去。

---

### handoff 是否清晰

接收方能不能稳定知道下一步该做什么。

---

### handoff 是否有噪音

有没有带太多无关信息，稀释主线。

---

### handoff 是否有责任边界

接收后谁拥有下一步动作权，是否明确。

所以：

> **多 Agent 里，handoff 本身必须从“连接动作”升级成“可评估对象”。**

这非常关键。

---

## 8. 第三类评估：状态一致性评估

前一课你已经学了共享状态、局部状态和状态主权。

这一课开始把它真正纳入评估。

要看的问题包括：

### 当前共享状态是否一致

例如：

- Planner、Executor、Reviewer 对当前 phase 的理解是否一致

---

### completed / pending 是否冲突

有没有出现一个角色认为完成了，另一个角色仍当作未完成。

---

### review 结论与执行结果是否对齐

是不是 Reviewer 在审一个其实并非当前最新版本的结果。

这说明多 Agent 评估不能只看“结果内容”，还要看：

> **状态协同是否健康。**

---

## 9. 第四类评估：链路传染评估

这是多 Agent 非常有代表性的一层。

很多时候真正的问题不是某个角色绝对差，而是：

> **上游小偏差被下游不断放大。**

例如：

- Planner 只把下一步写得稍微模糊
- Executor 就执行歪了一点
- Reviewer 又因为看到的是不完整结果，放过了它

最后用户看到的是：

> 完全失败

这就是典型的链路传染问题。

所以多 Agent 评估里，你还要学会看：

> **局部偏差是如何在角色链中被放大的。**

这会帮助你做更有价值的归因，而不是只盯着最后失败点。

---

## 10. 为什么“第一个错误发生点”比“最后失败表现”更有价值

很多调试都会有一个直觉错误：

> 哪里爆了，就去修哪里。

但在多 Agent 系统里，最后爆的地方往往只是症状，不一定是根因。

例如：

- Reviewer 最后放过了错误结果

这看起来像 Reviewer 的问题。

但继续看链路，可能会发现：

- 它收到的 execution result 就已经不完整

那问题可能更早发生在 Executor 或 handoff。

所以一个非常重要的原则是：

> **最终失败表现不一定等于第一错误发生点。**

多 Agent 的成熟归因，必须尽量往前找：

> **第一个把系统带偏的局部节点。**

---

## 11. 第一版 tracing 应该如何支持多 Agent 归因

前面你已经学过 tracing。

在多 Agent 里，tracing 需要更进一步。

至少要开始记录：

### 角色维度

例如：

- 当前事件属于哪个角色

---

### handoff 维度

例如：

- 从谁交给谁
- 交了哪些关键字段

---

### 状态维度

例如：

- 当前 phase
- 当前 completed/pending snapshot

---

### 决策维度

例如：

- 这一步是继续、通过、打回，还是升级人工接管

这样一来，你就能真正追踪：

> **错误是在角色内部产生，还是在角色之间传染。**

这就是多 Agent tracing 和单 Agent tracing 的关键区别。

---

## 12. 第一版评估表应该怎么从“单 Agent 指标”升级

前面你已经有了：

- task success rate
- tool accuracy
- average turns

到了多 Agent，第一版至少还应该增加下面几类观察：

### 角色输出质量

- Planner 输出是否可执行
- Executor 输出是否完整
- Reviewer 结论是否有效

---

### handoff 质量

- 是否漏关键信息
- 是否责任不清

---

### 状态一致性

- phase 是否一致
- completed/pending 是否一致

---

### 返工效率

- 打回后系统是否能清楚回到正确节点

这些都属于多 Agent 里非常有价值的第一版指标。

---

## 13. 为什么多 Agent 归因能力本质上是一种治理能力

很多人会把“归因”理解成调试技巧。

其实从更高层看，它是一种治理能力。

因为只要系统变复杂，你就必须能回答：

- 问题在哪里出现
- 谁应该负责修
- 是局部缺陷还是结构缺陷
- 是角色问题还是协议问题

如果没有这种能力，多 Agent 很容易从“结构优雅”滑向“维护噩梦”。

所以：

> **归因能力不是锦上添花，而是多 Agent 系统是否可持续演进的前提。**

---

## 14. 为什么这一步会决定你能不能真正做多 Agent

很多人能把多 Agent 跑起来，但真正难的是：

> **跑歪了以后，能不能修。**

如果修不了，那系统其实还不算成熟。

所以你可以把这一课看成一个非常现实的分水岭：

- 会做 Demo 多 Agent
- 和能维护多 Agent 系统

之间差的，往往就是：

> **有没有角色级评估、handoff 评估、状态一致性评估和局部失败定位能力。**

这也是为什么这一课必须接在状态主权之后讲。

---

## 15. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

给你设想中的每个角色各写一条“角色输出质量标准”。

---

### 第二件

给每一种 handoff 各写一条“handoff 质量标准”。

例如：

- Planner -> Executor
- Executor -> Reviewer

---

### 第三件

定义一个最小“状态一致性检查表”。

例如检查：

- phase 是否一致
- completed_steps 是否一致
- review target 是否是最新版本

---

### 第四件

找一个你过去的复杂失败案例，尝试按本课方法反推：

> 第一个局部失败点最可能在哪。

---

## 16. 本课小结

今天最重要的三句话：

### 第一

> **多 Agent 系统最怕的不是失败，而是失败以后无法归因。**

### 第二

> **多 Agent 评估不只是结果评估，还必须包括角色输出、handoff 质量、状态一致性和链路传染评估。**

### 第三

> **最终失败表现不一定等于第一错误发生点，成熟归因要尽量往前找第一个把系统带偏的局部节点。**
