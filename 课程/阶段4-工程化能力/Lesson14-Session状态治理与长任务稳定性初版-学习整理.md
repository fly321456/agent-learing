# Lesson14：Session 状态治理与长任务稳定性初版

## 1. 本课目标

前面几课我们已经把很多关键模块一一补上了：

- Prompt 迭代策略
- Tool 设计质量评估
- Memory 分层与注入
- Tracing 与调试方法
- Eval 与回归评测

这时如果你继续让 Agent 执行更长的任务，很快会遇到一个几乎必然出现的问题：

> **为什么 Agent 前几轮还很正常，跑到后面就开始重复、混乱、跑偏，甚至忘了自己在做什么？**

很多人第一反应会怪：

- 模型不稳定
- 上下文太长
- Prompt 不够强

这些都可能有影响。

但从工程视角看，这类问题背后还有一个非常核心的层：

> **Session 状态没有被很好治理。**

所以这一课的目标不是再讲“消息怎么存”，而是正式进入：

> **如何把 Session 从消息容器，升级成受控运行状态容器。**

---

## 2. 为什么“有 Session”不等于“Session 治理得好”

很多项目做到这里时，已经有一个 `Session` 类了。

例如它可能保存：

- `messages`
- `summary`
- 一些上下文数据

这当然是好的开始。

但这还不等于 Session 已经具备治理能力。

因为“保存状态”和“治理状态”是两回事。

### 保存状态

更像是：

> 有地方放东西

---

### 治理状态

更像是：

> 知道哪些状态该保留、该压缩、该清理、该校验、该阻止失控

长任务 Agent 真正需要的是后者。

所以这一课你要建立一个关键认知：

> **Session 不只是记录运行过程，更要约束运行过程。**

---

## 3. 这一课最重要的一句话

请记住：

> **长任务 Agent 的很多“变笨”现象，本质上不是智能退化，而是状态失控。**

这句话非常重要。

很多人看到后期表现变差，会自然认为：

> 模型累了

当然不是。

更常见的原因是：

- 状态堆积太多
- 状态结构混乱
- 旧状态和新状态冲突
- 任务阶段没有显式推进
- Agent 没有清晰知道“我已经做到了哪一步”

所以从工程角度看，这不是玄学问题，而是：

> **运行状态管理问题。**

---

## 4. 长任务 Agent 最常见的几类状态失控现象

你后面做长任务时，几乎一定会见到下面这些现象。

### 现象 1：重复做已经做过的事

例如：

- 已经读过 `README`，后面又重新读
- 已经分析过 `OrderService`，后面又重复分析

这通常说明：

> **已完成状态没有被清晰记录和利用。**

---

### 现象 2：任务进行到后期开始跑偏

例如前面都在分析 SpringBoot 项目，后面突然把注意力转到不重要的文件或细枝末节。

这通常说明：

> **当前目标状态被弱化了，局部噪音开始主导决策。**

---

### 现象 3：反复在几个 Tool 之间打转

例如：

- 读文件
- 搜索
- 再读文件
- 再搜索

但一直没有推进任务阶段。

这通常说明：

> **Session 里缺少阶段性进展状态。**

---

### 现象 4：Summary 和最近上下文开始互相冲突

例如 summary 说“认证逻辑已确认”，但 recent context 又像还没确认一样继续查。

这通常说明：

> **Session 内不同状态层之间没有一致性治理。**

---

## 5. 为什么 Session 本质上更像“运行时状态机快照”

如果你还把 Session 理解成：

> 消息列表

那它很快就会不够用。

更准确的理解应该是：

> **Session 是当前 Agent Runtime 的状态快照。**

这个状态快照里，至少应该能表达：

- 当前任务目标
- 当前阶段
- 已完成事项
- 待完成事项
- 当前上下文
- 当前 summary
- 当前注入的 memory
- 当前轮次编号
- 是否接近结束

这时你会发现，Session 已经不只是聊天记录容器，而更像：

> **一个任务执行中的控制面板。**

这就是 Session 状态治理的起点。

---

## 6. 为什么“任务阶段”对长任务特别重要

很多短任务不明显，但一旦任务超过 5 轮、10 轮，阶段感就会变得非常重要。

例如一个“分析代码仓库”的任务，很自然就可以分成：

1. 目录感知阶段
2. 核心文件识别阶段
3. 关键模块分析阶段
4. 汇总结论阶段

如果 Session 完全没有阶段意识，Agent 很容易出现：

- 永远停留在搜集阶段
- 一直不进入总结阶段
- 中途又回去重复前面阶段

所以长任务 Agent 里，一个非常关键的治理动作是：

> **让 Session 显式表达当前任务处于哪个阶段。**

这会极大提升运行稳定性。

---

## 7. 第一版 Session 状态治理先治理什么

这一课我们不追求一步做到复杂工作流系统。

先治理三个最关键的东西：

### 第一，任务目标状态

Session 里要明确：

- 当前总目标是什么
- 当前子目标是什么

这样后续每轮决策才有锚点。

---

### 第二，任务进展状态

Session 里要明确：

- 已完成哪些关键步骤
- 还有哪些关键步骤未完成

这能减少重复劳动。

---

### 第三，阶段状态

Session 里要明确：

- 当前处于信息收集
- 分析判断
- 生成输出

哪一个阶段

这能减少中后期跑偏。

这三个治理点已经足够支撑第一版长任务稳定性升级。

---

## 8. 为什么“已完成事项列表”很有价值

很多 Agent 重复劳动，本质上是因为：

> **做过的事没有被压缩成显式状态。**

如果你只是保留原始消息，模型当然“理论上”可以回看。

但工程上，这通常不够稳。

更好的方式是把关键进展显式化，例如：

```text
completed_steps:
- read README
- identified pom.xml
- confirmed project uses Redis
```

这样做的价值是：

1. 让已完成事项不再埋在长上下文里
2. 让模型更容易避免重复执行
3. 让后续总结阶段更容易聚焦

所以：

> **原始消息是历史，已完成事项是状态。**

这两者都需要，但作用不同。

---

## 9. 为什么“待完成事项列表”同样重要

很多人会想到记录“做过什么”，但忘了记录：

> **还剩什么没做。**

结果就是 Agent 容易：

- 收集了很多信息
- 但不知道什么时候该停
- 也不知道下一步优先级是什么

如果 Session 里有一个轻量的待办状态，例如：

```text
pending_steps:
- inspect OrderService
- inspect InventoryService
- draft final summary
```

那对模型来说，任务路径会更清晰。

这也是为什么高质量 Agent 通常不只是“有上下文”，而是：

> **有被组织过的上下文状态。**

---

## 10. 为什么 Session 需要“一致性治理”

一旦 Session 里开始出现多个状态层：

- recent messages
- summary
- completed steps
- pending steps
- memory context

新的问题就来了：

> **这些状态之间可能彼此矛盾。**

例如：

- summary 说“项目结构已确认”
- pending steps 还写着“确认项目结构”

或者：

- completed 说“已经读取 README”
- recent context 又在重新找 README

所以 Session 治理不仅仅是“多存几个字段”，还包括：

> **保证这些字段之间尽量一致。**

第一版哪怕先靠简单规则同步，也已经很重要。

---

## 11. 为什么长任务稳定性本质上是在做“局部状态收敛”

这个概念很重要。

长任务 Agent 最大的问题之一是状态会不断发散：

- 信息越来越多
- 目标越来越模糊
- 中间结论越来越分散
- 决策开始受局部噪音影响

Session 状态治理做的事情，本质上就是不断把这些发散信息收回来，形成更稳的局部状态。

例如：

- 用 summary 收敛历史
- 用 completed / pending 收敛进展
- 用 phase 收敛当前关注点

所以：

> **长任务稳定性不是靠“记住更多”，而是靠“把状态收敛得更清楚”。**

这非常关键。

---

## 12. 第一版 Session 治理结构可以怎么设计

你现在不需要一上来做复杂状态机框架。

第一版完全可以先用一个很朴素的结构：

```python
class SessionState:
    goal: str
    phase: str
    completed_steps: list[str]
    pending_steps: list[str]
    summary: str
    recent_messages: list[dict]
```

这已经足够让 Session 从“消息仓库”升级成“运行状态容器”。

重点不在字段多，而在：

> **这些字段是不是能帮助 Agent 知道自己现在在哪、做到了哪、下一步该做什么。**

---

## 13. 为什么 Session 治理和 Memory 治理不是一回事

很多人到这一步又会混淆：

> 这些状态是不是都可以放到 Memory？

不建议这样理解。

### Session 治理

核心解决：

> **当前这次长任务怎么稳定推进**

---

### Memory 治理

核心解决：

> **哪些高价值信息值得跨会话保留**

所以：

- `completed_steps`
- `pending_steps`
- `phase`

这些通常更偏 Session

而：

- 用户偏好
- 稳定项目事实
- 已验证长期结论

这些才更偏 Memory

这两层边界清楚以后，系统会稳定很多。

---

## 14. Session 治理为什么会直接影响结束判断

很多 Agent 结束得不好，常见有两种：

### 结束太早

实际上任务还没完成，但模型已经开始总结。

---

### 结束太晚

其实已经够了，但模型还在继续搜索、继续读文件。

这类问题很多时候并不只是 Prompt 问题，而是：

> **Session 没有足够清楚地表达“还差什么”和“已经完成什么”。**

如果 Session 里显式有：

- `completed_steps`
- `pending_steps`
- `phase`

那结束判断会更稳。

因为模型不再只是“凭感觉结束”，而是：

> **根据状态来结束。**

---

## 15. 这一课背后的核心工程思想

这一课真正训练的是：

> **把 Agent 的长任务运行，从“靠上下文漂流”升级成“靠状态收敛推进”。**

这就是很多 Demo Agent 和工程级 Agent 的巨大区别。

Demo Agent 通常依赖：

- 临时上下文
- 一时判断
- 局部消息

而工程级 Agent 开始引入：

- 任务阶段
- 已完成状态
- 待完成状态
- 结构化 summary

这意味着系统开始拥有：

> **更强的运行自我组织能力。**

这正是长任务稳定性的基础。

---

## 16. 当前阶段建议怎么落地

这节课建议你只做下面 4 件事：

### 第一件

给当前 Session 增加三个最小字段：

- `phase`
- `completed_steps`
- `pending_steps`

---

### 第二件

选一个长任务案例，观察当前 Agent 是否有：

- 重复劳动
- 中途跑偏
- 不知道何时结束

---

### 第三件

尝试把这个任务的中间过程显式压缩成：

- 已完成事项
- 待完成事项

再观察行为是否更稳定。

---

### 第四件

用 tracing 看看：

- 第几轮开始重复
- 第几轮开始跑偏

并把它和 Session 状态变化对照起来。
