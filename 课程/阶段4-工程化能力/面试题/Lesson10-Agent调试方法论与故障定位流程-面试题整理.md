# Lesson10：Agent 调试方法论与故障定位流程 - 面试题整理

## 1. 为什么 Agent 调试通常比普通程序调试更难？

### 参考答案

因为 Agent 是一个多层联动系统，错误结果可能来自很多不同层：

- Prompt
- Context
- Tool
- Memory
- Runtime 控制流程
- Model 决策

而且很多 Agent 错误不会直接抛异常，而是“能正常输出，但结果不对”。

这意味着调试不能只靠看报错栈，而要靠分层排查整条运行链路。

---

## 2. 为什么说 Agent 调试的核心不是“找代码报错”，而是“找决策在哪一层开始偏离”？

### 参考答案

因为很多 Agent 问题本质上不是程序崩溃，而是决策质量出了问题。

例如：

- 选错 Tool
- 读错 Memory
- 上下文被错误裁剪
- summary 总结错误
- prompt 把目标说歪

这些问题未必会产生异常，但会让最终答案偏离正确路径。

所以 Agent 调试的关键不是只盯着代码错误，而是定位：

> **哪一层输入或决策开始走偏。**

---

## 3. 调试 Agent 时为什么不应该第一时间就怪模型？

### 参考答案

因为模型只是整个系统的一部分。

真实工程里更常见的问题其实是：

- Tool Schema 不清
- Tool Result 质量差
- Memory 注入污染
- Context 丢失关键信息
- Prompt 目标定义有偏差

如果一开始就把问题归因于“模型太笨”，很容易走向盲目换模型或乱调 Prompt，而错过真正的系统问题。

所以更成熟的调试顺序是：

> **先看链路，再看模型。**

---

## 4. 一个实用的 Agent 调试分层框架通常可以怎么设计？

### 参考答案

可以先按五层排查：

1. 输入与目标层
2. 上下文层
3. Tool / Memory 层
4. Runtime 层
5. Model 决策层

这种顺序的价值在于：

- 先排查外部输入和上下文质量
- 再排查外部能力和运行流程
- 最后才判断是不是模型本身决策失误

这样能避免一开始就陷入盲调。

---

## 5. 为什么“先看模型到底看到了什么”通常是高收益调试动作？

### 参考答案

因为很多 Agent 的错误并不是模型本身“想错了”，而是输入给模型的上下文就已经有问题。

例如：

- system prompt 被裁掉
- summary 总结反了
- memory context 注入了无关内容
- tool result 太长稀释了重点

所以在调试时，先查看最终送给模型的完整上下文，往往能很快定位问题源头。

这比直接猜测模型内部想法更有效。

---

## 6. 为什么 Tool 层是 Agent 调试中的高发故障区？

### 参考答案

因为 Tool 是模型与外部世界交互的关键桥梁，常见问题很多：

- Tool Schema 不清晰
- 参数设计不合理
- Tool 结果太长或太乱
- Tool 虽然执行成功，但结果对当前任务无帮助

所以调试 Tool 层时，不能只看函数有没有报错，还要看：

> **这个 Tool 输出有没有真正帮助模型做下一步决策。**

---

## 7. 为什么引入 Memory 后，调试复杂度会明显上升？

### 参考答案

因为 Memory 是一个隐形影响源。

它不像函数异常那样直接报错，而是会悄悄改变模型的前提条件。

例如：

- 读入了错误的旧结论
- 读入了过时的项目事实
- 把不相关记忆注入到当前任务

这些都会让模型“逻辑上看起来合理，但前提已经错了”。

所以引入 Memory 后，调试必须新增一类检查：

> **当前结果是否被错误记忆污染。**

---

## 8. tracing 在 Agent 调试中的最大价值是什么？

### 参考答案

tracing 的最大价值是把多轮运行过程变成结构化事件流，从而帮助你：

1. 找到第几轮开始异常
2. 找到先异常的是哪类事件
3. 区分内容问题和流程问题
4. 回放一次完整运行链路

所以 tracing 不只是“记录更多”，而是让调试从猜测变成定位。

---

## 9. 为什么调试 Agent 时应该尽量先复现问题？

### 参考答案

因为很多 Agent 问题并不是稳定复现的，而是：

- 有时对，有时错
- 某些输入下错
- 某些状态下错

如果不能尽量固定：

- 输入
- 模型版本
- Tools 集合
- Memory 状态
- 配置参数

调试就很容易变成玄学。

所以复现问题是调试的第一原则之一。

---

## 10. 为什么“看最终答案”不如“看中间决策链”？

### 参考答案

最终答案只能告诉你“结果错了”，但不能告诉你：

- 为什么选了这个 Tool
- 哪一轮开始跑偏
- 哪条记忆影响了判断
- 哪个 Tool Result 误导了模型

而 Agent 本质上是一个多轮决策序列。

所以调试真正有价值的是看：

> **哪一步中间决策开始偏离了正确路径。**

---

## 11. 一个实用的 Agent Debug Checklist 通常应包含哪些检查项？

### 参考答案

通常至少应包含：

### 输入层

- 用户目标是否明确
- Prompt 是否一致

### 上下文层

- system prompt 是否在
- summary 是否正确
- recent messages 是否完整
- memory context 是否相关

### Tool 层

- Schema 是否清晰
- 参数是否合理
- 结果是否高质量

### Memory 层

- 读入记忆是否相关
- 写入记忆是否稳定
- 是否有过时记忆污染

### Runtime 层

- 第几轮开始异常
- retry / timeout 是否影响行为
- tracing 事件顺序是否正常

这会让调试过程更系统，而不是靠感觉。

---

## 12. 为什么没有调试流程的 Agent 开发很容易退化成“盲调 Prompt”？

### 参考答案

因为如果缺少分层排查框架，开发者很容易看到结果不对就直接改 Prompt。

但很多问题其实并不在 Prompt，而是在：

- Context
- Tool
- Memory
- Runtime

盲调 Prompt 有时能暂时缓解问题，但并没有真正定位根因。

所以成熟的 Agent 开发必须先建立调试流程，再做针对性优化。

---

## 13. 如果让你设计一个最小版 Agent 调试流程，你会怎么做？

### 参考答案

我会按这个顺序：

1. 固定输入和环境，尽量复现问题
2. 查看最终送给模型的上下文快照
3. 查看 tracing 事件流，定位从哪一轮开始异常
4. 检查 Tool 选择、参数和结果质量
5. 检查 Memory 的读写和注入是否合理
6. 最后再考虑 Prompt 或模型层面的优化

这个流程能显著降低盲目排查成本。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> Agent 调试和普通程序不同，它的核心不是找哪里报错，而是定位哪一层决策开始偏离。工程上通常需要分层排查输入、上下文、Tool、Memory、Runtime 和模型决策，同时结合 tracing 查看 run 级和 turn 级事件流。这样才能避免把调试退化成盲改 Prompt。
