# Lesson14：Session 状态治理与长任务稳定性初版 - 面试题整理

## 1. 为什么很多长任务 Agent 前几轮正常，后几轮却开始重复、混乱、跑偏？

### 参考答案

因为这类问题很多时候不是模型“突然变笨”，而是运行状态逐渐失控。

常见原因包括：

- 上下文不断堆积但没有收敛
- 已完成事项没有显式状态表达
- 当前目标被局部噪音稀释
- 不同状态层之间开始冲突
- Agent 不知道自己现在处于哪个任务阶段

所以从工程角度看，这类现象本质上属于 Session 状态治理问题。

---

## 2. 为什么说“有 Session”不等于“Session 治理得好”？

### 参考答案

因为有 Session 只说明系统有地方保存：

- messages
- summary
- 一些上下文信息

但治理 Session 还意味着：

- 知道哪些状态该保留
- 哪些状态该压缩
- 哪些状态该清理
- 哪些状态字段应该彼此一致
- 如何用这些状态约束后续行为

所以“保存状态”和“治理状态”是两回事。

---

## 3. 为什么说长任务 Agent 的很多“变笨”现象，本质上是状态失控？

### 参考答案

因为随着任务轮数增加，系统状态会不断膨胀和发散。

如果没有治理机制，就容易出现：

- 重复读取同一信息
- 重复做已经完成的事
- 目标逐渐模糊
- 中间结论彼此冲突
- 结束时机不稳定

这些都不是模型“智商下降”，而是状态没有被有效组织和收敛。

因此长任务稳定性问题，本质上更像状态管理问题。

---

## 4. 为什么单靠历史消息列表不足以支撑长任务稳定运行？

### 参考答案

因为历史消息只是原始轨迹，不等于结构化状态。

虽然理论上模型可以从消息中回看历史，但工程上这通常不够稳定：

- 历史太长，重点被淹没
- 做过的事没有被明确标记
- 剩下的事没有被显式表达
- 当前任务阶段不清楚

所以仅有消息列表，并不能保证 Agent 真正“知道自己已经做到哪一步”。

---

## 5. 为什么任务阶段（phase）对长任务 Agent 特别重要？

### 参考答案

因为长任务往往天然具有阶段性，例如：

1. 信息收集
2. 关键对象识别
3. 深入分析
4. 生成结论

如果 Session 没有阶段意识，Agent 就容易：

- 长时间停留在搜集阶段
- 迟迟不进入总结阶段
- 中途回退去重复前面步骤

所以 phase 的作用是：

> **让 Agent 知道当前应该优先推进哪类动作。**

---

## 6. 为什么显式记录 `completed_steps` 很有工程价值？

### 参考答案

因为很多重复劳动，本质上是做过的事没有被压缩成显式状态。

如果仅靠原始消息，已完成信息容易被埋没在长上下文中。

而显式记录：

- 已读取哪些文件
- 已确认哪些事实
- 已完成哪些分析步骤

可以显著降低：

- 重复执行
- 状态遗忘
- 总结阶段遗漏关键进展

所以 `completed_steps` 的价值在于：

> **把历史轨迹提升成可直接利用的运行状态。**

---

## 7. 为什么 `pending_steps` 对结束判断和任务推进同样重要？

### 参考答案

因为很多 Agent 的问题不是“不知道做过什么”，而是“不知道还剩什么要做”。

没有待办状态时，常见问题包括：

- 提前结束
- 无限制继续搜索
- 在多个 Tool 间来回打转

而有了 `pending_steps` 之后，模型会更清楚：

- 还差哪些关键动作
- 是否已经具备收尾条件
- 当前下一步优先级是什么

所以 `pending_steps` 对长任务推进和结束判断都非常关键。

---

## 8. 为什么 Session 状态之间还需要做一致性治理？

### 参考答案

因为随着 Session 变复杂，里面会同时存在：

- recent messages
- summary
- completed steps
- pending steps
- memory context

这些状态如果彼此冲突，就会误导模型。

例如：

- summary 说已经确认项目结构
- pending steps 却还写着确认项目结构

或者：

- completed steps 说读过 README
- recent context 还在重复找 README

所以 Session 治理不只是存更多字段，更重要的是保证它们尽量一致。

---

## 9. 为什么说 Session 更像“运行时状态快照”，而不只是“聊天记录”？

### 参考答案

因为在长任务 Agent 中，Session 不仅要保存对话，还要表达当前运行状态，例如：

- 当前总目标
- 当前阶段
- 已完成事项
- 待完成事项
- 当前 summary
- 当前近期上下文

这些内容组合起来，才构成 Agent 此刻的运行状态。

所以更准确地说，Session 是当前 Agent Runtime 的状态快照，而不是单纯聊天记录容器。

---

## 10. 为什么长任务稳定性本质上是在做“状态收敛”？

### 参考答案

因为长任务随着时间推进，信息会不断发散：

- 消息越来越多
- 中间结果越来越杂
- 局部细节越来越多
- 当前目标越来越容易被稀释

Session 治理要做的，就是不断把发散状态重新收敛回来，例如：

- 用 summary 收敛历史
- 用 completed / pending 收敛进展
- 用 phase 收敛当前关注点

所以长任务稳定性并不等于保留更多信息，而是更清楚地组织当前有效状态。

---

## 11. Session 治理和 Memory 治理有什么本质区别？

### 参考答案

两者解决的问题层次不同。

### Session 治理

解决的是：

> 当前这次长任务如何稳定推进

它更关注：

- 当前阶段
- 当前进展
- 当前待办
- 当前上下文组织

### Memory 治理

解决的是：

> 哪些高价值信息值得跨会话保留和复用

它更关注：

- 用户偏好
- 稳定事实
- 长期可复用结论

所以 Session 更偏短期运行控制，Memory 更偏长期沉淀。

---

## 12. 为什么 Session 治理会直接影响“何时结束”这个问题？

### 参考答案

因为结束判断本质上需要知道：

- 已经完成了什么
- 还剩什么没做
- 当前是否进入收尾阶段

如果这些状态不清楚，Agent 就容易：

- 提前结束
- 无限继续
- 重复检查

所以 Session 中显式的：

- `completed_steps`
- `pending_steps`
- `phase`

会直接提升结束判断的稳定性。

---

## 13. 如果让你设计一个最小版 Session 状态治理结构，你会怎么做？

### 参考答案

我会先设计如下几个字段：

- `goal`
- `phase`
- `completed_steps`
- `pending_steps`
- `summary`
- `recent_messages`

这个结构已经能让 Session 从消息仓库升级成运行状态容器。

第一版不追求复杂，但要确保这些字段能帮助 Agent 明确：

- 我在做什么
- 我做到了哪一步
- 我下一步该做什么

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 长任务 Agent 的很多重复、跑偏和结束不稳问题，本质上是 Session 状态失控，而不是模型突然变差。工程上需要把 Session 从消息容器升级成运行状态容器，至少显式管理当前阶段、已完成事项和待完成事项，并通过状态收敛减少重复劳动和任务漂移。这样才能真正提升长任务稳定性。
