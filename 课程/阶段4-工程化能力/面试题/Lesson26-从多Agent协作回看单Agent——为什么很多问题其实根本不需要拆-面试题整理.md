# Lesson26：从多 Agent 协作回看单 Agent——为什么很多问题其实根本不需要拆 - 面试题整理

## 1. 为什么很多看起来像“需要多 Agent”的问题，实际上并不一定真的要拆？

### 参考答案

因为很多问题的根因并不是“缺少多个角色实例”，而是单 Agent 本身还没有被设计清楚。

常见真实根因包括：

- 没有显式阶段
- 没有 completed / pending 状态
- Prompt 不清
- Tool 设计差
- Memory 或 RAG 注入混乱
- 缺少 review 步骤

这些问题首先更像：

> **单 Agent 的结构治理问题。**

如果不先排除这些问题，就直接上多 Agent，很容易把局部混乱升级成系统性混乱。

---

## 2. 为什么说“很多问题之所以像需要多 Agent，只是因为单 Agent 还没有完成角色化、状态化、治理化”？

### 参考答案

因为在很多项目里，单 Agent 本来就承担了多种职责，但这些职责没有被显式表达出来。

例如：

- 没有 plan step
- 没有 review step
- 没有清晰状态推进
- 没有显式阶段结构

这时系统表现出来的症状，表面上很像“需要多个 Agent”。

但实际上，很多收益只要通过：

- 角色化逻辑
- 状态治理
- 显式 review

就能在单 Agent 内先拿到。

---

## 3. 哪些问题最容易被误诊成“应该上多 Agent”？

### 参考答案

典型误诊包括：

1. 任务流程不清
2. 结果质量不稳
3. 执行容易跑偏
4. 长任务后期混乱

这些问题表面上很像：

- 缺 Planner
- 缺 Reviewer
- 缺 Executor

但很多时候本质上是：

- Session 设计问题
- Tool / 信息系统问题
- 治理和评测问题

所以要先做误诊排除，再做结构升级。

---

## 4. 为什么“单 Agent + 角色化逻辑”经常已经足够强？

### 参考答案

因为很多收益并不来自“多个实例”，而来自：

- 规划步骤被显式化
- 执行步骤被显式化
- 审查步骤被显式化

当这些逻辑在单 Agent 内被结构化以后，系统通常已经能获得：

- 更清晰的任务推进
- 更稳定的状态演化
- 更明确的质量检查

这意味着很多时候根本不必立刻支付多 Agent 的通信和同步成本。

---

## 5. 为什么“拆角色”和“拆实例”必须分开看？

### 参考答案

因为它们是两个不同层次的问题。

### 拆角色

解决的是：

> 哪些职责应该被显式分开

### 拆实例

解决的是：

> 这些职责是否值得交给不同运行单元来承担

第一层很多时候是必要的，但第二层未必。

所以更成熟的路径通常是：

> **先角色分工，再决定是否多实例化。**

---

## 6. 为什么很多“多 Agent 成功案例”真正带来收益的，其实是流程显式化？

### 参考答案

因为很多系统变强，不一定是因为模型数量增加，而是因为：

- 规划被显式化
- 校验被显式化
- handoff 被结构化
- 状态边界更清楚

这些收益其实很多都可以在单 Agent 里先获得。

所以不少所谓“多 Agent 带来的提升”，本质上首先是：

> **流程被设计清楚了。**

---

## 7. 为什么“先把单 Agent 做干净”是一条更成熟的工程路径？

### 参考答案

因为如果单 Agent 里本来就存在：

- Prompt 混乱
- Tool 设计差
- 状态治理弱
- tracing 不清
- eval 不稳定

那直接拆成多 Agent，通常只会把这些问题复制和放大。

相反，先把单 Agent 的：

- 角色逻辑
- 状态治理
- 信息组织
- 调试评估

做清楚，后面再决定是否拆，风险会低很多。

所以这是一条更稳、更成熟的工程路径。

---

## 8. 为什么说“架构升级”不应该成为设计问题的默认答案？

### 参考答案

因为更复杂的架构并不天然意味着更好的系统。

如果问题本来可以通过：

- Prompt 重构
- Tool 重构
- Session 治理
- 角色化步骤
- review 机制

解决，那直接上多 Agent 就可能是过度设计。

成熟的工程师会优先问：

> **当前问题是否真的需要这一级复杂度。**

---

## 9. 什么情况下更适合继续优化单 Agent，而不是进入多 Agent？

### 参考答案

当前阶段，更适合继续优化单 Agent 的场景通常包括：

1. 任务主线仍然相对集中
2. 状态仍可集中维护
3. 核心问题主要来自局部设计不清
4. 多 Agent 收益还不足以覆盖成本

这时优先做：

- 角色化逻辑
- 状态治理
- review step
- 信息系统整理

通常更划算。

---

## 10. 为什么说“我是不是在拆职责，还是在逃避重构”是一个很重要的自检问题？

### 参考答案

因为很多过早多 Agent 化，背后的真实动机不是职责天然分化，而是：

> **不想继续修当前单 Agent 的设计债务。**

例如：

- Prompt 乱了，不想重构，就想换多 Agent
- Session 混了，不想治理，就想拆模块

这类情况下，多 Agent 往往不是解决问题，而是在放大问题。

所以这个自检能帮助你区分：

- 是在做结构演进
- 还是在逃避当前设计清理

---

## 11. 为什么单 Agent 的可治理性是是否值得拆分的重要前置条件？

### 参考答案

因为如果单 Agent 里：

- tracing 不清
- eval 不稳
- 状态不清
- review 不明

那这些问题进入多 Agent 后通常只会更严重。

所以在真正拆之前，单 Agent 至少应当具备基本治理能力。

否则拆分往往不是收益，而是把问题从单点混乱升级成系统混乱。

---

## 12. 如果让你总结这一课的工程意义，你会怎么说？

### 参考答案

我会这样总结：

> 这一课的核心意义，是帮我们建立“不要过早多 Agent 化”的判断力。很多问题表面上像缺少更多角色，实际上只是单 Agent 还没有完成角色化、状态化和治理化。工程上更成熟的路径通常是先把单 Agent 的流程、状态和 review 做清楚，再判断是否真的值得为进一步收益支付多 Agent 的复杂度成本。
