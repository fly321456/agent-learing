# 阶段4 - Lesson 2 面试题整理

## 题目 1

**问题：** Logging 和 Tracing 在 Agent 工程里分别解决什么问题？

**参考答案：** Logging 主要回答“发生了什么”，例如某次调用开始了、某个 Tool 被执行了、某个错误出现了；Tracing 则回答“这些事情是不是属于同一次运行，以及它们之间的顺序关系是什么”。换句话说，Logging 更像是离散事件记录，Tracing 更像是把这些事件串成一条运行链路。在 Agent 这种多轮循环系统里，这种区分尤其重要。

**追问方向：** 为什么在 Agent 项目里，只有 Logging 往往还不够？

**易错点：** 把 Tracing 理解成“更多日志”。

## 题目 2

**问题：** 为什么 Agent 项目往往比很多普通系统更早需要 Tracing？

**参考答案：** 因为 Agent 的一次运行通常不是单步完成，而是会经历多次 LLM 调用、多个 Tool 执行、上下文回填和多轮循环。随着这些步骤叠加，如果没有链路标识，很快就会搞不清哪些日志属于哪次运行、哪次 Tool Call 接在哪次模型响应后面。因此在 Agent 系统里，Tracing 的价值会比很多执行路径固定的普通系统更早显现出来。

**追问方向：** 哪类 Agent 场景最容易在没有 Tracing 的情况下迅速失去可观察性？

**易错点：** 认为 Tracing 只适合超大规模分布式系统。

## 题目 3

**问题：** 当前阶段为什么不必一上来就引入复杂 Tracing 平台，而是先做最小 trace_id？

**参考答案：** 因为当前阶段最关键的问题还不是“如何做漂亮的链路平台可视化”，而是“如何让一次运行有唯一身份，并让相关日志能归到同一条链路下”。先建立 trace_id，就已经能够解决大部分当前阶段的排查问题，例如区分不同运行、串联 Tool 和 LLM 日志、定位错误属于哪次请求。这是一个投入小但收益很高的第一步。

**追问方向：** trace_id 建立之后，后续升级到真正的 span / trace 平台会更容易在哪些方面？

**易错点：** 觉得不接 OpenTelemetry 就不算做 Tracing。

## 题目 4

**问题：** 为什么 Runner 最适合作为当前阶段 trace_id 的发起位置？

**参考答案：** 因为 Runner 是一次运行的入口和主流程控制中心，它天然知道什么时候开始、什么时候结束，以及中间经历了哪些主要分支。由 Runner 生成 trace_id 并向下游传递，可以让 ToolManager 和 LLM 层都挂到同一条链路上。这样一来，trace 的生命周期和 Agent 运行生命周期是对齐的，设计上最自然。

**追问方向：** 如果以后引入 Session，trace_id 和 session 的关系应该如何理解？

**易错点：** 随便在任意层生成 trace_id，导致链路边界混乱。

## 题目 5

**问题：** 当前阶段最值得优先记录的 Trace 事件有哪些？

**参考答案：** 当前阶段最值得优先记录的是：Runner started、LLM call started、Tool dispatched、Tool finished 或 failed、Run finished。这些事件刚好构成一次最小 Agent 运行的主骨架，足够帮助开发者看清一轮执行的大致路径。第一版 tracing 的重点不是细，而是能把关键节点串起来。

**追问方向：** 为什么第一版不应该过早追求把所有 message 细节都纳入 trace？

**易错点：** 把 tracing 的目标理解成“记录得越多越好”。

## 题目 6

**问题：** 为什么说“Logging 让你看到发生了什么，Tracing 让你知道这些事情是不是属于同一次运行”？

**参考答案：** 因为没有 trace_id 时，你看到的只是很多分散的日志点，它们各自都可能是有意义的，但未必能被串成完整故事；而有了 tracing 之后，这些日志就能归属于某一条运行链路，从而帮助开发者判断一次请求从开始到结束到底经历了哪些步骤。这个差异在 Agent 系统里尤其重要，因为单次运行往往包含多次循环和多次外部调用。

**追问方向：** 如果未来再加上 Retry 和 Timeout，Tracing 的价值会如何进一步放大？

**易错点：** 以为 Tracing 只是更换日志格式，而不是建立链路视角。
