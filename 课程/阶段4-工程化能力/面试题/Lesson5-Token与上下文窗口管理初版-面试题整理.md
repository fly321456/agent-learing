# Lesson5：Token 与上下文窗口管理初版 - 面试题整理

## 1. 为什么 Token 管理在 Agent 系统里比在普通聊天机器人里更重要？

### 参考答案

因为普通聊天通常轮次较少、上下文较短，而 Agent 是多轮循环系统，会不断累积：

- 用户输入
- system prompt
- assistant 输出
- tool call
- tool result
- 新一轮 reasoning

所以 Agent 的上下文增长速度远快于普通聊天。

如果不做管理，就会出现：

1. 请求成本快速上升
2. 响应变慢
3. 超出上下文窗口限制

因此 Token 管理在 Agent 中不是优化项，而是稳定运行的前提条件。

---

## 2. 为什么说“Agent 必须学会遗忘”？

### 参考答案

因为上下文窗口是有限的，Agent 不可能无限保留所有历史信息。

如果每一轮都把全部历史、全部 tool result、全部中间过程都保留下来，最终会导致：

- 上下文膨胀
- 成本失控
- 模型无法继续处理新任务

所以 Agent 不仅要会收集信息，还要会选择性保留和删除信息。

这就是“Agent 必须学会遗忘”的含义。

---

## 3. Token 管理在工程上通常管理哪些内容？

### 参考答案

Token 管理通常不只是“统计 token 数量”，而是管理整个上下文体积。常见内容包括：

- 历史消息保留策略
- tool result 长度限制
- 长文件读取后的摘要策略
- 会话压缩策略
- token 成本控制

在课程当前阶段，最先落地的通常是：

> **历史消息裁剪 + tool result 截断**

---

## 4. 为什么多轮 Agent 特别容易把上下文撑爆？

### 参考答案

因为多轮 Agent 每一轮都可能新增多种上下文：

- 用户新请求
- 模型新输出
- tool call
- tool 执行结果

而且 Tool 返回内容往往很长，例如：

- 代码文件
- 搜索结果
- 页面文本
- 日志内容

这些内容累积起来，比普通问答场景更容易快速逼近上下文窗口上限。

---

## 5. 第一版上下文管理为什么可以先采用“只保留最近 N 条消息”？

### 参考答案

因为这是一个很适合初版系统的策略：

1. 实现简单
2. 可以立刻防止消息无限增长
3. 容易继续升级

虽然它不够智能，但已经能解决“完全无上限增长”的核心问题。

对于 Sprint 阶段来说，这是一种很好的渐进式工程方案。

---

## 6. 为什么不建议直接在 `Runner.run()` 里手动裁剪消息列表？

### 参考答案

因为消息管理本来就属于 Session 的职责范围。

如果 `Runner` 直接操作底层消息结构，会导致：

- `Runner` 过度膨胀
- `Session` 职责被弱化
- 消息管理逻辑难以复用

更合理的设计是：

> **Runner 负责驱动流程，Session 负责保存和裁剪消息。**

这符合单一职责原则。

---

## 7. 为什么 system prompt 一般要尽量保留？

### 参考答案

因为 system prompt 往往定义了 Agent 的核心行为约束，例如：

- 身份
- 目标
- 工具使用规则
- 输出风格
- 安全边界

如果 system prompt 被裁掉，模型后续行为可能出现漂移，导致：

- 工具选择变差
- 回答风格不稳定
- 任务目标偏离

所以上下文裁剪时，通常优先保留 system prompt，再裁剪普通历史消息。

---

## 8. 在 Agent 场景里，最危险的上下文膨胀点通常是什么？

### 参考答案

最危险的膨胀点通常是：

> **Tool Result**

因为 Tool 返回的内容往往比用户输入长得多。

例如：

- 整个源码文件
- 大段网页内容
- 多条搜索结果
- 很长的日志

所以很多时候，不是聊天历史本身把上下文撑爆，而是工具返回结果把上下文撑爆。

---

## 9. 为什么第一版可以先做“字符级截断”，而不是一开始就精确按 Token 截断？

### 参考答案

因为当前阶段的首要目标是：

> **先让系统停止无上限膨胀。**

字符级截断虽然不精确，但有几个优点：

1. 实现简单
2. 不依赖额外库
3. 足以解决多数明显超长问题

等系统主干稳定后，再升级为真正的 token-aware 裁剪会更合适。

这符合渐进式工程设计思路。

---

## 10. Token 管理和 Session、Runner、Settings 分别是什么关系？

### 参考答案

可以这样理解：

### `Settings`

负责提供参数，例如：

- `max_history_messages`
- `max_tool_result_chars`

### `Session`

负责：

- 保存消息
- 添加消息
- 根据策略裁剪消息

### `Runner`

负责：

- 在每轮运行中把消息写入 Session
- 从 Session 取出当前可发送的上下文

也就是说：

> **Settings 定策略参数，Session 管上下文状态，Runner 驱动流程。**

---

## 11. 为什么说上下文管理是 Agent 主干能力，而不是高级优化？

### 参考答案

因为只要 Agent 是多轮系统，它就一定要面对上下文增长问题。

如果没有上下文管理，Agent 只能处理非常短的小任务。

而一个真正有工程价值的 Agent，通常需要：

- 多轮分析
- 多次调用工具
- 长任务执行
- 复杂上下文跟踪

这就意味着上下文管理不是锦上添花，而是系统能否稳定运行的基础能力。

---

## 12. 如果让你设计一个最小版上下文管理方案，你会怎么做？

### 参考答案

我会分三步做：

1. 在 `Settings` 中增加上下文相关配置，例如 `max_history_messages` 和 `max_tool_result_chars`
2. 在 `Session` 中实现消息追加和自动裁剪能力
3. 在 Tool 结果写回上下文前先做长度截断

这是一个最小可用、职责清晰、后续可升级的第一版方案。

---

## 13. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 在 Agent 系统中，Token 管理的本质是控制上下文体积，因为 Agent 会持续积累用户消息、模型输出、Tool Call 和 Tool Result。一个多轮 Agent 如果没有上下文管理，成本、延迟和窗口限制都会很快失控。工程上通常先从历史消息裁剪和 Tool Result 截断做第一版，再逐步升级到上下文压缩和摘要策略。
