# Lesson29：多 Agent 中的共享状态、局部状态与状态主权初版 - 面试题整理

## 1. 为什么多 Agent 一到状态层就特别容易乱？

### 参考答案

因为在单 Agent 中，虽然状态也复杂，但基本还集中在一个运行体里。

而到了多 Agent，状态开始分布到多个角色身上，这会立刻带来：

- 每个角色只看到局部状态
- 多个角色对当前进展理解不一致
- 系统难以判断谁持有最新真相

所以多 Agent 的难点不只是协作，而是协作中的状态一致性与裁决问题。

---

## 2. 什么叫共享状态？

### 参考答案

共享状态指的是：

> **多个角色都必须基于同一份事实来协作的状态。**

例如：

- 任务总目标
- 当前阶段
- 已完成关键步骤
- 待完成关键步骤

这类状态如果不共享，角色之间就无法建立共同现实。

---

## 3. 什么叫局部状态？

### 参考答案

局部状态指的是：

> **只对某个角色当前工作有意义，不需要强制同步给所有角色的状态。**

例如：

- Executor 的临时执行日志
- 某个角色的中间推理草稿
- 未确认的局部怀疑点

这类状态过早全局共享，通常只会增加噪音和同步成本。

---

## 4. 为什么不是所有状态都应该共享？

### 参考答案

因为“全部共享”会带来明显副作用：

1. 状态噪音增加
2. 同步成本上升
3. 角色被无关细节淹没
4. 状态主权更容易模糊

所以更合理的多 Agent 状态设计原则是：

> **只共享协作必需的骨架状态，而不是共享一切。**

---

## 5. 第一版多 Agent 系统里，哪些状态通常更适合优先共享？

### 参考答案

第一版通常优先共享：

1. `task_goal`
2. `phase`
3. `completed_steps`
4. `pending_steps`
5. `final_artifacts`

这些状态构成了多角色协作的共同骨架，能帮助不同角色围绕同一任务现实协同推进。

---

## 6. 哪些状态通常更适合局部持有而不是全局共享？

### 参考答案

更适合局部持有的通常包括：

1. 临时执行细节
2. 中间推理草稿
3. 局部探索分支
4. 未确认的 review 怀疑点

这些内容对局部工作可能重要，但未必应该成为全局事实。

所以可以总结为：

> **共享状态偏结论与进展，局部状态偏过程与草稿。**

---

## 7. 什么叫“状态主权”？

### 参考答案

状态主权是指：

> **某一类状态最终由谁拥有解释权和更新权。**

也就是说，当多个角色对同一状态出现不同理解时，系统最终听谁的。

这和“共享状态”不同，共享只是可见性，而主权是裁决权。

---

## 8. 为什么说“共享状态”和“状态主权”不是一回事？

### 参考答案

因为：

### 共享状态

解决的是：

> 谁都能看到什么

### 状态主权

解决的是：

> 最终谁说了算

例如 `phase` 可以被所有角色看到，但不代表所有角色都能修改或裁定它。

所以必须严格区分：

> **共享是可见性问题，主权是裁决权问题。**

---

## 9. 为什么状态主权不清，多 Agent 系统几乎一定会乱？

### 参考答案

因为一旦没有明确主权，多个角色就可能同时更新或解释同一状态。

例如：

- Planner 改 phase
- Executor 也改 phase
- Reviewer 又基于自己理解改 phase

这会导致：

- 状态来回覆盖
- tracing 难以解释
- 决策责任不清
- handoff 语义混乱

所以状态主权清晰，是多 Agent 稳定运行的基础条件之一。

---

## 10. 第一版状态主权通常可以怎么分配？

### 参考答案

当前阶段可以先采用一个很实用的默认思路：

### Planner / Coordinator

更适合拥有：

- `phase`
- `task_goal`
- `next_major_step`

### Executor

更适合拥有：

- `execution_result`
- `artifacts_generated`

### Reviewer

更适合拥有：

- `review_passed`
- `review_issues`
- `release_ready`

这不是唯一方案，但很适合作为第一版默认结构。

---

## 11. 为什么冲突处理规则在多 Agent 状态系统里必须显式存在？

### 参考答案

因为多角色系统几乎必然会发生冲突。

例如：

- phase 冲突
- 完成状态冲突
- review 结论冲突

如果没有明确规则，模型只能自己猜，系统会变得非常不稳定。

所以第一版至少应明确：

- 哪类状态冲突听谁的
- 当前观察与旧记忆冲突时谁优先
- review 不通过时回退到哪里

这就是最小状态治理规则。

---

## 12. 为什么说多 Agent 状态设计，本质上是前面状态治理主线的升级版？

### 参考答案

因为你前面已经学过很多状态治理内容：

- Session
- summary
- completed / pending
- checkpoint
- Memory
- RAG

到了多 Agent，并不是这些问题消失了，而是：

> **状态开始分布在多个角色之间。**

所以本质上还是状态治理，只是从单体运行时升级成了协作型运行时。

---

## 13. 如果让你总结这一课的工程意义，你会怎么说？

### 参考答案

我会这样总结：

> 多 Agent 协作最核心的问题之一不是“怎么多几个角色”，而是“如何定义共同现实和最终裁决权”。工程上要先区分共享状态和局部状态，再为关键共享状态定义主权归属与冲突规则。只有这样，多角色系统才不会因为状态混乱而失控。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 在多 Agent 系统里，不是所有状态都应该共享。更合理的方式是只共享协作必需的骨架状态，例如目标、阶段、完成进度和关键结果，而把中间草稿、临时日志等保留为局部状态。同时必须显式定义状态主权，也就是每类状态最终由谁拥有解释权和更新权。共享状态回答“谁都该知道什么”，状态主权回答“最终谁说了算”，这两者必须严格分开。
