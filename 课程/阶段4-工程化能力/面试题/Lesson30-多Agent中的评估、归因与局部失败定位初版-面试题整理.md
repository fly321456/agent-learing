# Lesson30：多 Agent 中的评估、归因与局部失败定位初版 - 面试题整理

## 1. 为什么多 Agent 系统不能只看“最终答案对不对”？

### 参考答案

因为多 Agent 的失败可能发生在多个层次：

- Planner 规划失败
- Executor 执行失败
- Reviewer 审查失败
- handoff 协作失败
- 共享状态同步失败

如果只看最终答案，所有失败都会被压缩成一句“结果不对”，这几乎没有足够的工程诊断价值。

所以多 Agent 评估必须从结果评估升级为过程评估和角色级评估。

---

## 2. 为什么说多 Agent 系统最怕的不是失败，而是失败以后无法归因？

### 参考答案

因为多 Agent 一旦没有归因能力，就会进入一种很糟糕的状态：

- 结果不好
- 每个角色都“看起来做了点事”
- tracing 很多
- 但没人能说清楚第一个错误发生在哪

这会导致系统越来越难维护。

所以真正成熟的多 Agent 系统，不只是能协作，还必须在失败后能拆得开、看得清、定位得到。

---

## 3. 什么叫“局部失败定位”？

### 参考答案

局部失败定位是指：

> **把一次整体失败拆解成具体哪个角色、哪次 handoff、哪类状态先偏了。**

因为多 Agent 的失败往往不是一瞬间全错，而是某个局部先偏，然后偏差逐步传染和放大，最后演化成整体错误。

所以成熟调试的目标，是尽量找到：

> **第一个把系统带偏的局部节点。**

---

## 4. 为什么多 Agent 系统更像“链路系统”而不是“单点系统”？

### 参考答案

因为多 Agent 是一条角色协作链，例如：

- Planner -> Executor
- Executor -> Reviewer
- Reviewer -> pass / revise

只要链路中某一段出现偏差，后面所有角色都可能在错误前提上继续工作。

所以问题不应该只按单点看，而要按：

> **协作链路上的偏差传播**

来理解。

---

## 5. 第一类多 Agent 评估为什么应该是“角色输出质量评估”？

### 参考答案

因为在多 Agent 中，每个角色本身就是一个独立输出节点。

例如：

- Planner 输出计划
- Executor 输出执行结果
- Reviewer 输出质量判断

如果不分别评估这些角色输出，就无法区分：

- 是规划本身不好
- 还是执行没跟上
- 还是审查标准不稳

所以角色输出质量评估是第一层必要拆分。

---

## 6. 为什么 handoff 质量必须作为独立评估对象？

### 参考答案

因为很多系统的问题并不出在角色内部，而出在角色之间的交接。

handoff 常见问题包括：

- 信息不完整
- 重点不清楚
- 责任边界不清
- 带太多噪音

如果 handoff 不被单独评估，就会误以为是角色本身出了问题，而忽略真正的协作断点。

---

## 7. 为什么状态一致性也是多 Agent 评估的重要一层？

### 参考答案

因为多个角色可能基于不同状态版本在协作。

例如：

- Planner 以为还在探索阶段
- Executor 以为已经进入执行阶段
- Reviewer 审查的不是最新结果

这类问题即使角色本身能力没问题，也会让系统整体表现不稳定。

所以状态一致性必须被纳入评估和定位框架。

---

## 8. 什么叫“链路传染评估”？

### 参考答案

链路传染评估关注的是：

> **一个局部小偏差如何在角色链路中被不断放大。**

例如：

- Planner 给了模糊计划
- Executor 因此执行偏了一点
- Reviewer 又在不完整结果上做了宽松判断

最终导致整体失败。

所以多 Agent 不仅要评某一层是否出错，还要评：

> **局部偏差如何向下游传染。**

---

## 9. 为什么“最终失败表现”不一定等于“第一错误发生点”？

### 参考答案

因为最后暴露的问题往往只是症状，而不是最早的根因。

例如：

- Reviewer 最终放过了错误结果

表面上看像 Reviewer 问题。

但继续往前追，可能是：

- Executor 上交的结果就不完整
- 甚至更早，Planner 给的计划就模糊

所以成熟归因必须尽量往前追，找到最早把系统带偏的节点，而不是只看最后爆点。

---

## 10. 多 Agent tracing 为什么需要比单 Agent 更多维度？

### 参考答案

因为多 Agent 不只是一个运行循环，还包含：

- 角色维度
- handoff 维度
- 状态快照维度
- 决策流转维度

你至少需要知道：

- 当前事件属于哪个角色
- 当前 handoff 从谁到谁
- 交接时的状态是什么
- 最终动作是通过、打回还是升级

所以多 Agent tracing 本质上是多角色交互链路 tracing。

---

## 11. 为什么多 Agent 评估体系必须从单 Agent 指标继续细化？

### 参考答案

因为单 Agent 常见指标例如：

- task success rate
- tool accuracy
- average turns

到了多 Agent 已经不够用了。

还必须增加：

- 角色输出质量
- handoff 质量
- 状态一致性
- 返工效率

否则你只能看到系统总体表现，却看不到具体哪个协作层在掉链子。

---

## 12. 为什么说多 Agent 的归因能力本质上是一种治理能力？

### 参考答案

因为只要系统复杂，就必须能回答：

- 问题在哪里出现
- 谁该负责修
- 是局部缺陷还是结构缺陷
- 是角色问题还是协议问题

如果没有这种能力，系统就无法稳定迭代。

所以归因能力不是调试小技巧，而是多 Agent 是否能长期维护和演化的关键治理能力。

---

## 13. 如果让你总结第一版多 Agent 评估与归因框架，你会怎么说？

### 参考答案

我会这样总结：

> 第一版多 Agent 评估不能只看最终答案，而应该分层观察角色输出质量、handoff 质量、状态一致性和链路偏差传播。归因时要尽量往前找第一个局部失败点，而不是只盯着最终失败表现。这样系统才能从“会协作”进一步升级到“出了问题也能定位和迭代”。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> 多 Agent 系统的评估不能只看最终结果，因为失败可能来自规划、执行、审查、handoff 或状态协同中的任意一层。工程上需要分别评估角色输出质量、handoff 质量和状态一致性，并结合 tracing 做链路归因。真正成熟的归因，不是看最后哪里爆了，而是尽量找到第一个把系统带偏的局部节点。
