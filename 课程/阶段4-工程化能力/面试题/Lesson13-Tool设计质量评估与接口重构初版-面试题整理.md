# Lesson13：Tool 设计质量评估与接口重构初版 - 面试题整理

## 1. 为什么说很多 Agent 的表现问题，本质上是 Tool 接口设计问题？

### 参考答案

因为模型不是直接理解你的 Python 实现，而是通过 Tool 的：

- 名字
- 描述
- 参数结构
- 返回结果

来判断：

- 什么时候该用它
- 怎么调用它
- 如何使用调用结果

如果这些接口设计得不清晰，模型就容易：

- 不调用该调用的 Tool
- 调错参数
- 调了 Tool 但拿不到可用结果

所以很多表面上的“模型不聪明”，实际上是 Tool 接口不友好。

---

## 2. 为什么 Tool 不能只用“能不能执行成功”来判断质量？

### 参考答案

因为 Tool 执行成功只说明：

> **底层函数运行了。**

但 Tool 质量还涉及更多问题：

- 模型是否容易发现它
- 模型是否容易正确调用它
- 返回结果是否真的有助于下一步决策

也就是说，Tool 的成功不只是代码成功，还要看：

> **Agent 是否能稳定、正确、有效地使用它。**

所以“执行成功”只是最低层标准，不是完整质量标准。

---

## 3. Tool 在 Agent 系统中本质上是什么？

### 参考答案

从工程视角看，Tool 本质上是：

> **LLM 与外部能力之间的接口层。**

也就是说，它不是单纯的业务函数，而是面向模型的接口产品。

既然是接口层，它就要满足典型接口设计要求：

- 命名清晰
- 职责明确
- 参数稳定
- 返回结构可用

所以 Tool 设计本质上属于 API / Interface Design 问题。

---

## 4. 一个低质量 Tool 往往有哪些典型特征？

### 参考答案

常见特征包括：

1. 名字抽象，模型不知道它到底做什么
2. Description 太空，无法判断什么时候该用
3. 参数太多太复杂，模型不容易构造正确调用
4. 返回结果太乱，不利于后续推理
5. 职责过多，边界不清

这些问题都会直接降低 Tool 在 Agent 中的可用性。

---

## 5. 一个高质量 Tool 通常具备哪些特点？

### 参考答案

高质量 Tool 通常具备：

1. 名字直接表达用途
2. Description 清楚说明“什么时候使用”
3. 参数少且语义明确
4. 返回值结构化、利于下一步决策
5. 职责单一、边界清晰

一句话总结：

> **好 Tool 不是暴露最多能力，而是暴露最容易被模型正确使用的能力。**

---

## 6. 为什么单一职责原则对 Tool 特别重要？

### 参考答案

因为模型不像人类程序员那样能灵活读文档、理解复杂语义。

如果一个 Tool 同时负责：

- 读文件
- 写文件
- 列目录
- 搜索内容

那么模型就更难判断：

- 什么时候该调用它
- 该走哪条参数路径
- 失败时问题出在哪

所以对于 Agent 来说，很多时候更适合把超级 Tool 拆成多个职责明确的小 Tool。

---

## 7. 为什么 Tool 参数设计会直接影响调用正确率？

### 参考答案

因为模型在调用 Tool 时，本质上是在生成参数。

如果参数设计不好，例如：

- 参数名不直观
- 多个参数语义重叠
- 参数嵌套过深

模型就更容易调用出错。

所以参数不是为“人类程序员手写调用”设计的，而是为“模型自动生成调用”设计的。

这是 Agent Tool 设计和普通函数设计很不同的一点。

---

## 8. 为什么返回值设计同样决定 Tool 的质量？

### 参考答案

因为 Tool 返回值会直接成为模型下一轮推理的输入之一。

如果返回值：

- 太短，没有关键信息
- 太长，重点被淹没
- 太乱，没有结构

那么即使 Tool 调用成功，模型也不容易从结果中提取下一步行动。

所以返回值设计应该关注：

- 是否结构化
- 是否突出关键信息
- 是否有利于模型继续决策

---

## 9. 如果让你评估一个 Tool 的质量，第一版可以从哪些维度看？

### 参考答案

当前阶段可以先从五个维度看：

1. 可发现性
2. 可调用性
3. 可消费性
4. 边界清晰度
5. 稳定性

这五个维度分别对应：

- 模型是否容易知道该不该用
- 模型是否容易正确传参
- 模型是否容易利用返回结果
- Tool 和其他 Tool 是否职责清楚
- Tool 在同类任务中是否表现稳定

---

## 10. Tool 重构通常优先从哪些动作开始？

### 参考答案

常见优先动作包括：

1. 改名字
2. 重写 Description
3. 简化参数
4. 拆分职责
5. 优化返回值结构

这些动作不一定要一次全做，第一版更适合每次只做一个小改动，再配合评测集回归。

---

## 11. 为什么 Tool 重构也应该走“评估 -> 改动 -> 回归”的流程？

### 参考答案

因为 Tool 改动也会引入副作用。

例如：

- 参数更简单了，但和别的 Tool 更像了
- Description 更强了，但模型变得过度保守
- 拆 Tool 后边界更清晰了，但调用选择更犹豫了

所以 Tool 不是“只要改了就是更好”，而是也需要和 Prompt 一样：

> **先识别问题，再做小改动，再通过固定样例验证效果。**

---

## 12. 为什么“模型不会用 Tool”不一定说明模型差？

### 参考答案

因为模型是否会用 Tool，很大程度上依赖接口是否友好。

如果 Tool 存在这些问题：

- 名字模糊
- 描述弱
- 参数复杂
- 返回值难用

那么模型失败并不奇怪。

这和人类程序员面对糟糕 API 时也容易调用错误是同一逻辑。

所以不能简单把问题归因给模型，很多时候应先检查 Tool 设计。

---

## 13. 如果让你简洁总结高质量 Tool 的核心标准，你会怎么说？

### 参考答案

我会这样总结：

> 高质量 Tool 的核心不是“功能多”，而是“模型容易理解、容易选择、容易正确调用、容易继续使用结果”。这意味着名字要清晰、Description 要说明使用时机、参数要简单明确、返回值要结构化且利于下一轮推理。

---

## 14. 面试时如何简洁总结这一课？

### 参考答案

可以这样回答：

> Tool 在 Agent 系统里本质上是面向模型的接口层，所以不能只看底层函数能不能执行成功，还要看模型是否容易发现、容易调用、容易利用结果。工程上可以从可发现性、可调用性、可消费性、边界清晰度和稳定性五个维度评估 Tool 质量，并通过小步重构和固定样例回归持续优化。
