# 阶段4 - Lesson 1 面试题整理

## 题目 1

**问题：** 为什么 Agent 项目进入工程化阶段后，Logging 应该优先于继续加新功能？

**参考答案：** 因为当系统已经具备 Runner、ToolManager、Session、LLM 抽象等运行时对象后，如果还没有最小可观测性，后续每增加一层能力都会显著提高排查成本。Logging 的作用不是锦上添花，而是让系统从“黑盒能跑”变成“出了问题至少知道发生了什么”。在工程化阶段，这种可观察能力往往比继续堆一个新功能更基础。

**追问方向：** 在什么节点上，一个项目应该判断“先补日志比继续加功能更重要”？

**易错点：** 把日志理解成调试时可有可无的辅助输出。

## 题目 2

**问题：** 为什么说 Logging 不是“多打印几行 print”？

**参考答案：** 因为工程日志不仅是把信息输出出来，还要让这些信息具备语义、层次和后续可控性。真正的 Logging 至少要解决日志级别、模块边界、错误与正常路径区分，以及未来是否能过滤和追踪的问题。`print()` 虽然能看到内容，但无法稳定承担这些工程职责，因此 Logging 的本质是结构化运行信息，而不是简单输出文本。

**追问方向：** 从工程能力上看，`print` 和 `logging` 最大的差别是什么？

**易错点：** 认为把所有关键变量 `print` 出来就等于做了日志。

## 题目 3

**问题：** 当前阶段为什么应该优先在系统边界上打日志，而不是 everywhere？

**参考答案：** 因为第一版日志的核心目标是看清主流程，而不是把系统淹没在噪音中。当前最值得优先打日志的地方是 Runner 入口、LLM 调用前后、Tool 调度前后以及错误边界，这些位置最能反映运行路径。如果一开始就把所有细节都打满，不仅难以定位真正重要的信息，还会让后续维护日志本身变成负担。

**追问方向：** 什么叫“边界日志”，为什么它比细节日志更适合作为第一版？

**易错点：** 误以为日志越多，系统就越专业。

## 题目 4

**问题：** 为什么说 Logging 的本质是给“未来的你”留线索？

**参考答案：** 因为日志真正发挥价值的场景，往往不是写代码的当下，而是系统已经变复杂、问题已经出现、开发者需要回头定位时。尤其在 Agent 项目中，一次运行可能涉及多次 Tool 调用、多轮消息和运行时状态变化，如果当初没有留下清晰的日志线索，后续排查成本会急剧上升。所以 Logging 本质上是一种面向未来调试与演进的工程准备。

**追问方向：** 为什么 Agent 项目里“未来排查”会比普通脚本更复杂？

**易错点：** 认为只要当前自己看得懂代码，就暂时不需要日志。

## 题目 5

**问题：** 在当前最小 Agent Framework 里，最适合优先打日志的三个模块是哪几个，为什么？

**参考答案：** 最适合优先打日志的通常是 Runner、ToolManager 和 LLM 层。Runner 是主流程中枢，适合记录运行开始、进入哪个分支、何时结束；ToolManager 适合记录执行了哪个 Tool、参数是什么、是否成功；LLM 层适合记录调用开始、失败和返回类型。这三层刚好覆盖主运行路径最关键的边界，因此最能帮助开发者快速理解一次运行到底发生了什么。

**追问方向：** 为什么 Session 在这一阶段通常不是第一批重点打细日志的地方？

**易错点：** 不分优先级地在所有模块里同时加日志。

## 题目 6

**问题：** 为什么说“一个工程级 Agent，不只是要能运行，还要能被观察”？

**参考答案：** 因为运行只是系统能力的下限，而可观察性决定了系统是否能被持续维护和演进。对于 Agent 这类带有循环、Tool 调度和运行时上下文的系统来说，如果不能观察它的关键路径，就很难定位问题、优化行为或安全扩展新能力。因此工程级 Agent 不只是功能集合，还必须具备最小日志、后续 tracing 和调试边界，这样它才真正具备工程可用性。

**追问方向：** Logging、Tracing 和 Debugging 在工程级 Agent 中分别扮演什么角色？

**易错点：** 把“能跑通一次”误认为“已经具备工程可用性”。
