# Lesson7：Memory 分层设计初版

## 1. 本课目标

前面两课我们已经连续解决了两个非常关键的问题：

### Lesson5

我们解决了：

> **上下文不能无限增长**

所以我们引入了：

- 历史消息裁剪
- Tool Result 截断

---

### Lesson6

我们进一步解决了：

> **有些历史不能直接删**

所以我们引入了：

- summary message
- 上下文压缩
- “裁剪 + 压缩”的组合策略

---

到这里，一个新的问题会自然出现：

> **如果这些信息不仅当前会话有用，而且下次会话还要继续用，怎么办？**

这时候你就不能只靠 Session 了。

因为 Session 解决的是：

> **当前会话里的上下文组织问题**

而不是：

> **长期信息跨会话保存问题**

所以这一课我们正式进入：

> **Memory 分层设计**

---

## 2. 为什么 Session 不等于 Memory

这是很多初学者最容易混淆的地方。

很多人会觉得：

```text
Session 里不是已经有 messages 吗？

那不就是 memory 吗？
```

这只能算一部分，而且只是最表层的一部分。

更准确地说：

### Session

管理的是：

> **当前这一轮或这一段对话过程中的运行状态**

它强调的是：

- 当前会话
- 当前消息
- 当前上下文
- 当前压缩状态

---

### Memory

管理的是：

> **超出单个会话范围、仍然值得保留和复用的信息**

它强调的是：

- 跨轮次
- 跨阶段
- 跨会话
- 稳定复用

所以你要先建立一个非常关键的认知：

> **Session 是短期工作记忆容器，Memory 是更长期的信息保留机制。**

---

## 3. 一个最典型的例子

假设你在做一个 Coding Agent。

用户第一天说：

> 帮我分析这个 SpringBoot 项目

Agent 经过多轮分析后得出：

- 这是 SpringBoot + Redis + MySQL 项目
- 订单主流程在 `OrderService`
- 权限逻辑集中在 `AuthService`

这些内容有两种不同的“保留价值”：

### 第一种

对当前会话后续 10 轮有用。

这属于：

> Session / Context 管理问题

---

### 第二种

下次用户再来问：

> 帮我继续分析支付模块

这些信息依然有用。

这就属于：

> Memory 问题

所以：

> **不是所有应该保留的信息都应该继续塞在 Session 里。**

有些内容应该从会话上下文中“毕业”，进入更长期的 Memory 层。

---

## 4. 这一课最重要的一句话

请你记住下面这句话：

> **Memory 的本质不是“存更多”，而是“分层存储不同生命周期的信息”。**

这句话非常重要。

很多人一提 Memory，就想到：

```text
加数据库

加向量库

加知识库
```

这些当然都可能是实现手段。

但在工程设计层面，先要回答的不是“存哪里”，而是：

> **什么信息该活多久？**

只有先回答这个问题，Memory 设计才会清晰。

---

## 5. 先建立三层记忆模型

在你当前阶段，最适合先建立一个非常实用的三层模型：

### 第一层：当前轮上下文

也就是：

- 当前输入
- 当前输出
- 当前正在使用的最近几条消息

特点：

- 生命周期最短
- 最贴近当前推理
- 对即时响应最敏感

---

### 第二层：当前会话压缩记忆

也就是：

- summary
- 已完成事项
- 当前任务阶段性状态

特点：

- 生命周期中等
- 服务于本次会话的连续性
- 重点是“本次任务还能接着干”

---

### 第三层：长期记忆

也就是：

- 用户偏好
- 稳定项目信息
- 可复用结论
- 下次任务仍然有价值的信息

特点：

- 生命周期最长
- 不依赖某一次具体上下文窗口
- 可以跨会话复用

你会发现：

> **Memory 一旦开始分层，很多设计问题就会立刻变清楚。**

---

## 6. 为什么要分层，而不是全部放一起

因为不同信息的访问频率和价值完全不同。

例如：

### 当前轮上下文

需要每轮都发给模型。

---

### 当前会话 summary

通常也要经常参与构建 prompt。

---

### 长期记忆

不一定每轮都要注入。

很多时候只需要在“相关时刻”检索出来使用。

如果你把这三类东西全部混在一起，就会出现两个问题：

1. 上下文很快膨胀
2. 重要信息与低价值信息混在一起，检索和组织都变差

所以分层的本质是：

> **让不同生命周期的信息走不同的数据路径。**

---

## 7. 第一版长期记忆应该存什么

这一点非常关键。

初学者最容易犯的错误就是：

> **什么都想存。**

这会让 Memory 很快变成垃圾堆。

在第一版里，更适合进入长期记忆的通常是：

### 用户级稳定偏好

例如：

- 用户喜欢中文回答
- 用户偏好分步骤解释
- 用户希望代码示例尽量简洁

---

### 项目级稳定事实

例如：

- 当前项目是 SpringBoot 单体架构
- 使用 Redis 做缓存
- 使用 MySQL 做主库

---

### 已验证的关键结论

例如：

- 订单主流程位于 `OrderService`
- 认证逻辑主要在 `AuthService`

这些信息的共同点是：

> **在后续任务中仍然高概率有用，而且不依赖具体某一轮原始消息。**

---

## 8. 什么不适合直接存入长期记忆

同样重要的是，你要知道哪些内容不该乱存。

例如：

- 临时中间推理
- 尚未验证的猜测
- 大段原始日志
- 过时的执行细节
- 一次性 Tool 输出全文

为什么？

因为长期记忆如果塞入太多低质量信息，会导致：

- 检索噪音变大
- 后续推理被误导
- Memory 价值迅速下降

所以 Memory 不是越多越好，而是：

> **越稳定、越高价值、越可复用的信息，越值得存。**

---

## 9. 第一版 Memory 不需要很复杂

你现在千万不要一上来就把 Memory 想成：

```text
向量数据库

embedding 检索

多路召回

rerank
```

这些当然是后续会学的内容，但不是第一版要解决的问题。

当前阶段，我们先建立一个最小有用模型：

> **先把长期记忆当成结构化存储层。**

例如可以先设计成：

```python
class MemoryStore:
    def __init__(self):
        self.user_preferences = {}
        self.project_facts = []
        self.key_findings = []
```

第一版的核心目标不是“检索最聪明”，而是：

> **先把长期记忆作为独立层引入系统。**

---

## 10. 推荐的职责划分

这一课最重要的工程设计点，就是职责边界。

### `Session`

负责：

- 当前会话消息
- 当前 summary
- 当前上下文构建

---

### `MemoryStore`

负责：

- 长期信息存储
- 长期信息读取
- 信息分类

---

### `Runner`

负责：

- 在合适时机把信息写入 Memory
- 在合适时机读取 Memory 注入上下文

---

### `Agent`

负责：

- 声明自己是否使用 Memory
- 决定有哪些记忆策略配置

这样你会得到一个非常清晰的系统：

```text
Session 解决“这次对话怎么继续”

Memory 解决“下次还能不能接着干”
```

---

## 11. Memory 应该什么时候写入

这是一个非常好的工程问题。

不是每一轮都写 Memory。

因为如果每一轮都写，通常会导致大量噪音进入长期存储。

第一版比较合理的写入时机通常有三类：

### 第一类：任务阶段结束时

例如分析完一个模块后，把结论写入 Memory。

---

### 第二类：明确发现稳定事实时

例如确认项目架构、数据库类型、核心模块归属时。

---

### 第三类：用户偏好明确暴露时

例如用户反复表达：

- 希望中文回答
- 偏好简洁代码
- 喜欢分步骤解释

所以第一版规则可以理解为：

> **不要实时乱写，要在“稳定结论出现时”写入。**

---

## 12. Memory 应该什么时候读出

和写入一样，也不是每一轮都应该无脑全部读出。

更合理的方式是：

> **按任务相关性读出。**

例如：

### 用户再次分析同一个项目

可以读出：

- 项目级事实
- 已验证模块归属

---

### 用户继续让你写代码

可以读出：

- 编码风格偏好
- 之前确认的项目结构

所以从设计上你要知道：

> **Memory 最好是“选择性注入”，而不是“全量回灌”。**

---

## 13. 这一课背后的核心思想

这一课表面在讲 Memory。

但它真正训练的是一种非常重要的系统设计能力：

> **把不同生命周期的信息放进不同层次的容器。**

这和很多成熟系统本质上是一样的：

- CPU 有寄存器、缓存、内存、磁盘分层
- Web 系统有请求态、会话态、数据库持久化
- Agent 也要有当前上下文、当前会话压缩、长期记忆分层

所以：

> **Memory 不是一个“附加功能”，而是 Agent 走向长期运行能力的必经架构升级。**

---

## 14. 和后面的 RAG、向量检索是什么关系

这一点你现在也要先建立认知。

很多人会误以为：

```text
Memory = RAG
```

其实不是。

更准确地说：

### Memory

更偏向：

> **系统应该记住什么**

---

### RAG

更偏向：

> **系统如何从外部知识中检索相关内容**

两者会有交集，但不是同一个层次的问题。

你可以先这样理解：

- Memory 更像“Agent 自己沉淀下来的可复用信息”
- RAG 更像“需要时去外部知识库拿信息”

后面这两条线会逐渐融合。

---

## 15. 当前阶段建议怎么落地

这节课不要一次做太多。

建议只完成下面三件事：

### 第一件

定义一个最小版 `MemoryStore`。

至少支持：

- `save_preference()`
- `save_fact()`
- `save_finding()`
- `get_relevant_memory()`

---

### 第二件

在 `Runner` 中增加两个钩子思维：

- 什么时候写 Memory
- 什么时候读 Memory

哪怕先只写成简单调用点，也可以。

---

### 第三件

先只存“高价值、稳定、可复用”的信息。

不要急着做全量记忆。

---

## 16. 本课小结

今天最重要的三句话：

### 第一

> **Session 不等于 Memory。**

### 第二

> **Memory 的本质不是存更多，而是分层保存不同生命周期的信息。**

### 第三

> **长期记忆应该优先存稳定、高价值、可复用的信息，而不是所有原始过程。**
