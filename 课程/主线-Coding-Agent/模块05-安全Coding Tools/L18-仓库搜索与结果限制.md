# L18 仓库搜索与结果限制：让 Agent 找得到，也让上下文装得下

> 建议学习时间：60–90 分钟。本课从单文件读取扩展到仓库检索，仍保持完全离线。

## 1. 本节要解决的真实问题

面对陌生仓库，Agent 不知道目标在哪。把所有文件一次读完既慢又会挤掉 Task 与关键 Observation；只凭模型猜文件名又容易走错。搜索 Tool 应提供“文件:行号:片段”的定位线索，但必须限制目录、glob、结果数并跳过二进制文件。

问题链是：搜索为什么也是 Context 工程？零结果与搜索失败有何区别？为什么结果越多不一定越好？`.git` 和二进制文件为何默认跳过？搜索返回完整文件还是定位摘要？

## 2. 前置回顾与 Observe 漏斗

L17 能定点读取，却要求先知道路径。合理流程像漏斗：先搜少量候选，再精读局部，最后修改。

```text
Task
  → search_files(query, glob, max_results)
  → candidate file:line snippets
  → read_file(candidate, line range)
  → precise evidence
```

搜索不是替代读取，而是降低下一步选择的不确定性。

## 3. 类比与两个案例

搜索像图书馆目录，不是把整座图书馆搬到桌上。目录告诉你书架和页码，随后再取具体书。

案例一：查找 `Runner(` 且 glob=`*.py`，返回三处调用，Agent 选择测试与实现分别阅读。案例二：查询常见词 `error`，仓库有数千处；若无限返回，真正相关项被噪声淹没，API 上下文和延迟同步增长。设置 `max_results=20` 并标记截断，让下一轮模型改用更具体 query。

二进制文件包含偶然字节序列，解码失败不应让整个搜索崩溃；`.git` 内容也不是当前工作树源码，默认跳过。

## 4. 搜索结果协议

```text
src/runner.py:42:class Runner:
tests/test_runner.py:18:def test_runner_completes():
... [result limit reached]
```

相对路径避免泄露机器目录；行号支持后续范围读取；原始行提供判断线索；截断标记告诉模型结果并不完整。零匹配返回空字符串，和 error Result 区分：前者是成功搜索但没有证据，后者是工具未完成。

## 5. 本课唯一代码增量：受限遍历

```python
for candidate in sorted(root.rglob(glob)):
    if not candidate.is_file() or ".git" in candidate.parts:
        continue
    try:
        lines = candidate.read_text(encoding="utf-8", errors="strict").splitlines()
    except (UnicodeDecodeError, OSError):
        continue
```

排序使离线测试稳定；严格 UTF-8 加捕获让二进制文件跳过；root 仍由 `workspace_path()` 验证。`max_results` 小于 1 时立即拒绝，避免“0 是无限还是无结果”的歧义。

## 6. 两个错误直觉与纠正

### 误区一：搜索结果越全，模型越聪明

上下文注意力和预算有限。重复、无关结果会降低决策质量。Tool 应支持逐步收窄，而不是一次倾倒仓库。

### 误区二：解码失败就使用 errors=ignore 搜下去

二进制内容可能产生伪匹配，行号也没有可靠意义。跳过并保持结果可信，比制造噪声更好。

另一个误区是返回绝对路径。它既浪费 token，也把本机目录写入 Trace，跨机器复现困难。

## 7. 完整运行轨迹

```text
workspace contains app.py with 3 TODO lines and binary.bin
search(query=TODO, glob=*.py, max_results=2)
  → app.py:1:TODO one
  → app.py:2:TODO two
  → stop and append result-limit marker
binary.bin does not match glob and is not decoded
next decision: narrow query or read app.py lines 1-5
```

这是 Observe 改变下一步的具体例子：截断不是失败，而是提示搜索策略需要收窄。

## 8. 修改前后差异

错误方式是把所有文件拼接：

```python
context = "\n".join(path.read_text() for path in workspace.rglob("*"))
```

受控方式：

```python
output = search_files(
    context=context, query="ToolManager", path="src", glob="*.py", max_results=20
)
```

调用参数本身进入 Event 后可审计：我们知道模型搜了什么、范围多大以及为何没有找到。

## 9. 搜索质量与后续设计

本课实现确定性子串搜索，不急着加入向量数据库。代码定位常常依赖精确标识符，简单搜索容易测试、解释和复现。未来可替换为 ripgrep 适配器，但返回协议仍应保持受限定位结果。

当结果被截断时，Runtime 不应自动把 `max_results` 翻倍。更合理的下一步由模型基于已有线索选择：增加目录限制、改用更完整的符号名、缩小 glob，或者先读取最可能的候选。这样每一步扩大上下文都有理由，Trace 也能解释为何继续搜索。若连续多次使用宽泛 query，模块 7 的评测还可以把它计为低效工具调用，而不是把问题归咎于模型“不会找代码”。

```python
relative = candidate.relative_to(context.workspace).as_posix()
matches.append(f"{relative}:{line_number}:{line}")
```

统一 `/` 让 Observation 跨平台稳定。若行本身极长，正式实现还应增加单行截断，本课可作为挑战。
