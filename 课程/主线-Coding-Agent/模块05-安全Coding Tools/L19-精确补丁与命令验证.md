# L19 精确补丁与命令验证：修改不是完成，证据才是闭环

> 建议学习时间：60–90 分钟。本课首次引入写入和进程副作用，所有示例只在临时工作区执行。

## 1. 本节要解决的真实问题

Agent 能定位代码后，需要修改并运行测试。直接让模型重写整个文件会破坏无关格式、覆盖用户改动；用普通 `replace()` 又可能同时改掉多个相同片段。命令若只返回 stdout，不保留退出码和 stderr，模型可能把失败误当成功。

本课建立 Coding Loop 的工程闭环：精读证据 → 唯一精确补丁 → 运行验证 → 根据结构化结果继续。问题链是：为什么 old_text 必须唯一？找不到目标时为何不能自动模糊匹配？命令输出“看起来正常”能代替退出码吗？验证失败后应回滚还是继续诊断？

## 2. 前置回顾与最小变更原则

L17、L18 负责 Observe；本课加入 Act 与 Verify：

```text
search → read exact region → apply_patch(old, new) → run_command(argv) → observe
```

补丁参数携带修改前证据。若文件在读取后被用户改变，old_text 可能不再匹配，工具应停止，而非把补丁猜到相似位置。这是简化的乐观并发控制。

## 3. 两个案例

案例一：文件只有一处 `value = 1`，替换为 `value = 2`，返回一处更新。随后运行 Python 断言，exit_code=0，形成可验证完成。

案例二：文件两处相同文本。模型没有足够上下文说明要改哪处，工具返回 `old_text is not unique`，文件保持原样。正确下一步是读取更多上下文，构造包含函数名或邻近行的唯一 old_text，而不是默认全量替换。

命令案例中，stdout 打印 `bad` 并 exit 3。ToolResult 必须同时保留 output、status=error 和 exit_code=3。

## 4. 精确补丁的契约

```python
occurrences = text.count(old_text)
if occurrences == 0:
    raise ValueError("old_text was not found")
if occurrences != 1:
    raise ValueError("old_text is not unique")
updated = text.replace(old_text, new_text, 1)
```

零次说明观察已过期或文本构造错误；多次说明定位不足；恰好一次才允许修改。工具不自动 trim、不做正则猜测、不静默 replace_all，因为这些便利会扩大副作用。

## 5. 本课唯一代码增量：Patch 后验证

```python
patch = manager.execute(ToolCall("p1", "apply_patch", {...}), context)
verify = manager.execute(ToolCall("v1", "run_command", {
    "command": [sys.executable, "-c", "from app import value; assert value == 2"]
}), context)
```

补丁成功只证明文本被改，不证明需求正确。验证命令成功才提供行为证据。两次 ToolResult 都应进入 RunResult，最终回答要区分“已修改并验证”和“已修改但测试失败”。

## 6. argv 命令与 shell 边界

```python
subprocess.run(
    command, cwd=workspace_path(context, cwd), shell=False,
    capture_output=True, text=True, encoding="utf-8", errors="replace",
)
```

命令使用字符串列表而非整段 shell 文本，避免 `&&`、重定向和插值带来的额外解析层。`cwd` 也必须在 Workspace 内。`shell=False` 不代表命令天然安全，它仍能执行危险程序，所以 L20 必须审批。

## 7. 两个错误直觉与纠正

### 误区一：模型很确定时可以重写整文件

模型的确定感不是版本控制。整文件重写扩大 diff，容易丢换行、注释和并发改动。优先最小唯一补丁，无法唯一定位时先补观察。

### 误区二：有 stdout 就算命令成功

失败程序也会打印 stdout，成功程序也可能没有输出。退出码是主控制信号，stdout/stderr 是诊断证据，三者不能互相替代。

另一个误区是验证失败立即宣称任务失败。失败 Observation 可能指出缺依赖或断言不符，Agent 应在剩余预算内诊断，但不能伪装已完成。

## 8. 完整运行轨迹

```text
read app.py → value = 1
apply_patch(call=p1) → status=success, one replacement
run_command(call=v1, python assertion)
  → exit_code=0
  → status=success
final answer: changed value and verification passed
```

反例轨迹：两处匹配 → patch status=error → 文件未变 → 不执行验证 → 重新读取上下文。这种停止比“也许改对了”更安全。

## 9. 结构化命令结果

成功 output 同时记录退出码、stdout、stderr：

```text
exit_code=0
stdout:
...
stderr:
...
```

非零时抛出内部 `CommandFailed`，ToolManager 将其转为 `ToolResult(status="error", exit_code=3, output=...)`。异常只用于层内控制，跨边界返回统一 Result，调用者无需认识内部异常类。

验证失败后还存在一个重要状态：文件已经改变，但任务尚未完成。Runner 不能丢弃 Patch Result，也不能把最终 content 写成“修改成功”。下一轮应同时看到已执行补丁和失败命令，决定修复代码、调整测试或停止并向用户报告。自动回滚也不是默认答案，因为测试失败可能来自原有问题，机械回滚会抹掉仍然正确的局部修改。是否回滚必须有事务策略和证据，本课选择保留现场、明确报告。

## 10. 运行、预期输出与故障实验

```powershell
python agent-from-scratch/course-checkpoints/05-coding-tools/steps/l19_patch_and_verify.py
```

```text
patch=success verify=success exit_code=0
```

故障实验：制造两处 old_text；使用不存在 old_text；让测试 exit 3；把 cwd 指向 `../`；把 argv 改成单个含 `&&` 的字符串，观察 shell=False 不会替你解析。每次检查文件是否保持预期状态。
