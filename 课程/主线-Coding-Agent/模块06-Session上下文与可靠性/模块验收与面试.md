## 功能检查

- Session UTF-8 保存/加载，Message 保留 turn_id。
- Context 按预算保留最近完整消息，裁剪时显式标记。
- 原 Session 不因 Context 构造被删除。
- Checkpoint 原子写入，恢复复用 run_id、next_step 和 completed call。
- 同一副作用 call_id 在恢复后实际执行次数为 1。
- Retryable 可有限重试；Deterministic 只调用一次；非法 Config 启动即失败。

## 代码讲解与故障注入

请手绘 Session→Turn→Run 关系，并讲解一次“Patch 后中断再恢复”。依次注入：未知 turn_id、Context 超预算、Checkpoint 未保存、恢复换 call_id、两次暂时性失败、一次确定性失败、`max_steps=0`。

## 设计取舍与面试题

1. Session 与 Context 为什么不是同一列表？
2. Turn id 与 Run id 分别服务谁？
3. 摘要为什么不能替代原历史？
4. Checkpoint 如何避免重复副作用，又有哪些失败窗口？
5. 什么是幂等键？
6. Retryable 与 Deterministic 如何分类？
7. Timeout、Retry、max_steps、deadline 有何不同？
8. 为什么 Retry 必须产生 Event？

## 通过标准

专项测试全部通过；能够解释至少一次崩溃窗口；能够证明副作用没有重复；能够指出 JSON Store 的工程边界。只会“保存 messages 并重试三次”不算通过。
