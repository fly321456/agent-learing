# L22 上下文预算与压缩：Session 可以很长，模型输入必须有边界

> 建议学习时间：60–90 分钟。本课实现确定性字符预算，并明确摘要不是事实数据库。

## 1. 本节要解决的真实问题

Session 保存越久，messages 越多。每次把全部历史发给模型会增加延迟和费用，还可能让旧错误、过期路径和无关讨论干扰当前任务。简单取最后 N 条也不可靠：一条消息可能是十万字符，N 条短消息又可能很小。

本课建立 Context Window（上下文窗口）边界：按预算保留最近的完整消息；发生裁剪时显式插入摘要或截断标记；不切半条消息，不把裁剪伪装成完整历史。问题链是：预算按 token 还是字符？System Instructions 是否参与？摘要由谁生成？最新消息超过预算怎么办？

## 2. Session 与 Context 的区别

```text
Session Store: 完整持久历史，面向恢复与产品体验
Context Build: 本次模型调用选择的有限输入，面向推理
```

裁剪 Context 不应删除 Session。把两者混为一谈会导致为了省 token 永久丢失用户记录，或者为了保留记录无限扩大模型输入。

教学版使用字符数，是因为完全离线、确定且不绑定 tokenizer。正式系统应使用模型对应 token 估算，但“预算选择算法”和“计量单位”仍可分离。

## 3. 类比与两个案例

Session 像完整病历，Context 像医生本次问诊前拿到的摘要和最近检查。病历不能全塞进桌面，摘要也不能冒充原始报告。

案例一：三条消息长度为 34、27、6，预算 25。只能保留最新 6 字符消息，并加入“Earlier”摘要。案例二：最新用户 Task 本身超过预算。教学实现仍完整保留它，因为切掉任务尾部可能改变意图，同时记录 used_chars 超预算；生产系统应在进入模型前拒绝、分块或要求用户缩小输入。

## 4. 从后向前选择完整消息

```python
used = 0
kept = []
for message in reversed(messages):
    size = len(message.content)
    if kept and used + size > max_chars:
        break
    kept.append(message)
    used += size
kept.reverse()
```

从最近向过去选择符合对话任务的时间局部性。遇到第一条放不下就停止，避免跳过大消息后又捡更老的小消息，造成时间顺序断层。消息作为原子单元，不截取半段 JSON 或半条 Tool Observation。

## 5. 本课唯一代码增量：ContextResult

```python
@dataclass(frozen=True)
class ContextResult:
    messages: list[Message]
    truncated: bool
    used_chars: int
```

调用者不应通过比较列表长度猜是否裁剪，因此显式返回 truncated。used_chars 让 Trace 和评测观察预算。构建结果与原 Session 分开，不原地删除 messages。

当裁剪发生时：

```python
marker = summary or "Earlier session messages were truncated."
kept.insert(0, Message("system", f"[Context summary] {marker}", "context"))
```

摘要带明确标签，防止模型把它误认为用户原话。

## 6. 摘要边界：压缩不是无损存储

摘要可能遗漏路径、数字和失败细节，也可能由模型生成错误事实。因此摘要适合保存“已做什么、当前目标、关键决定”，不应替代审批记录、Tool Result 或 Checkpoint。

好的摘要例子：已确认配置位于 `src/config.py`；测试 `test_load` 失败；尚未修改文件。差的摘要例子：项目差不多修好了。前者可验证，后者让下一轮产生虚假完成感。

摘要生成也需要预算与来源引用。教学版由调用者传入确定文本，不引入额外 LLM 调用。

## 7. 两个错误直觉与纠正

### 误区一：只保留最后五条消息就够

条数不等于大小，且可能把一个 Turn 的 user 留下、assistant 丢掉。预算至少应按字符或 token，进阶实现还应按 Turn 分组。

### 误区二：摘要后可以删除原 Session

摘要有损且可能错误。Session 是源记录，摘要是本次 Context 的派生物。删除源记录会让审计和重新摘要都失去依据。

另一个误区是把最新消息粗暴截断到 max_chars。对于代码和命令，缺失尾部可能反转语义。超大最新输入应成为明确产品错误或分块任务。

## 8. 完整裁剪轨迹

```text
max_chars=25
messages:
  old: 34 chars
  middle: 27 chars
  latest: 6 chars
reverse scan:
  keep latest → used=6
  middle would make 33 > 25 → stop
insert [Context summary] Earlier: inspected config
ContextResult(truncated=true, used_chars=6)
```

摘要本身是否计入预算？教学版不计入 used_chars，表示历史消息预算。正式系统必须为 Instructions、摘要、Tool Schema 和输出预留分别建账。

## 9. Context 预算账本

更完整的预算不是一个数字：

```text
total model window
- system instructions
- tool schemas
- summary
- selected messages
- reserved output
= safety margin
```

本课只实现 selected messages，避免假装字符数等于真实 token。重要的是形成“每部分都占预算”的意识，模块 7 才用指标观察裁剪频率和任务成功率。

预算还应在请求构造之前生效，而不是等供应商返回“上下文过长”后才补救。前置建账能让行为离线测试，也避免一次必然失败的在线调用。若工具 Schema 突然增大，预留区随之缩小，Runtime 应主动减少历史或拒绝请求，并在 Event 中说明原因。

## 最终实现校准

正式 `ContextWindow.build` 返回 `ContextResult(messages, truncated, used_chars)`，调用者无需从内容猜测是否发生裁剪。它保留最近完整消息且不修改原 Session；发生裁剪时插入显式 system marker。若最新单条消息已经超过总预算则明确报错，避免返回一个看似有效却丢失当前任务的上下文。
