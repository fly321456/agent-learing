# L32 打包发布与最终挑战：作品不是代码目录，而是可重复验证的工程

> 建议学习时间：60–90 分钟。本课完成 32 节主线，将所有能力收束为安装、运行、验证和答辩标准。

## 1. 本节要解决的真实问题

项目在开发者机器上 `python demo.py` 能运行，不代表别人可以使用。缺少 pyproject、依赖范围、入口命令、README、离线测试和发布检查时，作品只能靠作者现场解释。Coding Agent 的最终交付应让评审者克隆后明确知道：如何安装？默认是否联网？怎样运行 CLI？MCP 暴露什么？失败如何验证？

本课把“功能完成”升级为“可重复交付”。问题链是：editable 与 wheel 分别证明什么？为什么 wheel 测试不能只构建不安装？入口脚本从哪里生成？版本号表达什么？最终挑战如何避免只演示 Happy Path？

## 2. 最小标准包结构

```text
agent-from-scratch/
  pyproject.toml
  README.md
  src/agent_from_scratch/
  tests/
  evals/cases.json
  examples/
  course-checkpoints/
```

`src/` 布局防止测试意外从仓库根导入未安装源码；pyproject 声明构建系统、项目元数据、依赖和 console scripts；README 是唯一运行入口；tests 与 evals 分别证明协议正确和固定任务回归。

模块 8 检查点自身也具有 pyproject，可独立构建，不依赖最终项目“碰巧已安装”。

## 3. editable 与 wheel 的差异

Editable install 将环境指向当前源码，适合开发，修改后无需重装。Wheel 是发布制品，包含构建时收集的文件，更接近用户安装。

```powershell
python -m pip install -e . --no-deps
python -m pip wheel . --no-deps --no-build-isolation -w dist
```

Editable 成功但 wheel 缺 `data/cases.json` 很常见；因此两种安装都要验证 import、CLI 和资源。课程测试把 wheel 输出到临时目录，避免提交构建产物。

## 4. pyproject 的公共契约

```toml
[project]
name = "course-product"
version = "0.1.0"
requires-python = ">=3.11"

[project.optional-dependencies]
mcp = ["mcp>=1.27,<2"]

[project.scripts]
course-product-mcp = "course_product.__main__:main"
```

核心包无网络依赖，MCP 作为可选 extra；正式项目则声明 OpenAI 和 MCP extra。console script 把命令映射到 Python 函数，不复制脚本逻辑。

依赖既要下限保证所用 API，也要合理上限防止未验证的大版本自动升级。

## 5. 本课唯一代码增量：构建与安装验收

```python
built = subprocess.run([
    sys.executable, "-m", "pip", "wheel", ".",
    "--no-deps", "--no-build-isolation", "-w", wheel_dir,
])
assert built.returncode == 0
assert len(list(wheel_dir.glob("course_product-*.whl"))) == 1
```

随后使用临时 target 做 editable install，并检查 `__editable__` 元数据。测试不访问包索引，避免网络和费用；构建依赖必须已在开发环境准备。

正式发布还应在干净虚拟环境安装 wheel 后运行 smoke test，本课将其列入最终挑战。

## 6. 作品 README 应回答什么

```text
项目解决的问题与边界
Python 和依赖要求
离线安装与测试命令
在线调用所需显式环境变量
CLI 示例、审批语义和退出码
MCP Server 启动方式与只读 Tool 列表
架构图与关键协议
已知限制、安全说明和评测口径
```

不要只写“这是一个强大的 AI Agent”。可复现命令、预期输出和限制比宣传语更能展示工程能力。

## 7. 两个错误直觉与纠正

### 误区一：测试通过就不必构建 wheel

测试从源码运行，可能掩盖包发现、资源文件和入口配置错误。Wheel 是另一条交付边界，必须单独验证。

### 误区二：最终 Demo 只展示一次成功回答

作品价值还在失败路径：越界拒绝、审批拒绝、max_steps、Retry、Checkpoint 和 Trace。只演示 Happy Path 无法证明 Agent 可控。

另一个误区是把 API Key 写入示例配置。README 只说明环境变量名，密钥不进入仓库、Trace 或截图。

## 8. 最终作品运行轨迹

```text
clone repository
create environment
editable install for development
run offline pytest → green
run 20-case offline eval → 20 protocol cases
run CLI with explicit model/API key → optional online
deny one command → safe non-zero finish
run read-only MCP Server → list two tools
build wheel → install in clean environment
```

每一步都有预期结果和失败说明。在线实验不进入默认验收，因为它依赖密钥、网络、模型和费用。

## 9. 最终架构复盘

```text
CLI / MCP Adapters
        ↓
Runner → BaseLLM → LLMResponse
  ↓         ↑
ToolManager → ToolResult
  ↓
RunResult + Event + Trace
  ↓
Session / Context / Checkpoint / Eval
```

Agent 配置不拥有运行状态；外部 SDK 在 Adapter 结束；副作用经 Workspace、审批和 Timeout；结果分单次模型、单次 Tool 和整次 Run；每层都有离线测试。

这张图比背诵框架 API 更重要，因为它能迁移到其他 SDK 和模型供应商。

## 10. 运行、预期输出与故障实验

```powershell
cd agent-from-scratch

```

```text
package=course-product version=0.1.0 python=>=3.11
release_checks=tests,wheel,editable,cli,mcp,readme
```

故障实验：删除 package discovery；改错 console script；遗漏 MCP 依赖上限；从 wheel 中检查包文件；在无 API Key 情况运行默认离线验收；把 write Tool 注册到 MCP，确认安全测试失败。

## 11. 最终挑战与答辩任务

最终挑战：在新的临时 Git 仓库中让 Agent 读取需求、搜索实现、提出精确补丁、等待审批、运行测试、保存 Trace、总结结果；中断一次并恢复；最后用固定 Eval Case 记录 steps、Tool calls、耗时和 finish reason。

答辩必须解释一个没有采用的设计，例如为什么 Web 工作台不进入主线、为什么 MCP 只读、为什么多 Agent 不是默认、为什么 Runner 不读 raw response。答案应基于边界和测试证据。

答案与评分参考见 [模块练习参考答案](模块练习参考答案.md)。
