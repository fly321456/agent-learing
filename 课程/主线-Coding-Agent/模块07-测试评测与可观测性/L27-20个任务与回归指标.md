# L27 20 个任务与回归指标：从“案例能跑”到“退化可见”

> 建议学习时间：60–90 分钟。本课建立离线协议评测，不把脚本回放宣传为真实模型成功率。

## 1. 本节要解决的真实问题

单元测试按开发者想到的分支编写，无法回答一次重构是否让 Agent 更爱调用无关 Tool、步骤变多或安全任务退化。我们需要固定任务集和统一指标，比较不同版本，而不是凭几次聊天感觉“好像更聪明”。

但评测也容易造假：创建 20 个 `{passed: true}` 再打印 100%，或者把 expected sequence 同时当 actual sequence，指标永远不会失败。本课要求 executor 真正产生 actual tools；故意让一条返回错误序列时，passed 必须从 20 降到 19。

问题链是：case 包含哪些字段？成功标准如何可执行？为什么成功率不够？协议回放和模型评测有何边界？任务集自身如何防止重复与漂移？

## 2. 固定任务集的组成

20 条任务覆盖 read、search、edit、execute、safety 五类，每类四条。Case 包含稳定 id、category、prompt 和 expected_tools。

```json
{
  "id": "edit-01",
  "category": "edit",
  "prompt": "Fix README typo.",
  "expected_tools": ["read_file", "apply_patch"]
}
```

id 用于跨版本对比；category 用于发现某类能力退化；prompt 是输入；expected_tools 是本离线协议评测的判定标准。真实 Coding Agent 评测还需要文件最终状态和测试结果，不能只看 Tool 序列。

## 3. 类比与两个评测案例

任务集像驾照固定路线：每次换车都走相同路，才能比较刹车与转向。路线不是全部真实道路，但比随意兜一圈更能发现回归。

案例一：20 条 actual sequence 全等于 expected，得到 20/20、25 次 Tool、40 steps。案例二：read-01 实际返回空列表，得到 19/20、失败分类 tool_sequence=1。若代码仍打印 20，说明指标是写死的，不是计算结果。

另一个案例是成功率相同但效率不同：两个版本都 20/20，A 用 25 次 Tool，B 用 70 次。B 可能出现无效搜索或循环，成功率单指标看不出来。

## 4. 本课核心数据模型

```python
@dataclass(frozen=True)
class EvalMetrics:
    total: int
    passed: int
    success_rate: float
    tool_calls: int
    steps: int
    duration_ms: float
    failures: dict[str, int]
```

total/passed 描述覆盖与成功；tool_calls/steps 描述效率；duration 描述执行成本；failures 汇总原因。未来可加 token 和费用，但只有真实在线执行才能产生可信模型成本。

指标必须由每个 Case 的结果汇总，不从常量复制。

## 5. 本课唯一代码增量：evaluate_cases

```python
for case in cases:
    actual_tools = executor(case)
    tool_calls += len(actual_tools)
    steps += 2 if actual_tools else 1
    if actual_tools == case.expected_tools:
        passed += 1
    else:
        failures["tool_sequence"] = failures.get("tool_sequence", 0) + 1
```

executor 是可替换边界：教学 Demo 使用确定性脚本；正式离线协议评测可运行 FakeLLM+Runner；在线评测可调用真实模型并记录模型、Prompt、日期和费用。

`duration_ms` 使用 perf_counter 从真实执行计时，即使很小也不是写死值。

## 6. 协议评测不等于智能评测

本课 executor 返回预期序列，证明评测管线、Case 加载、指标和失败注入正确。它不证明真实模型会从 prompt 推导出序列。

```text
offline protocol eval: Runtime 在给定剧本下是否正确
online model eval: 模型面对任务是否选择正确行动
repository outcome eval: 文件最终状态和测试是否满足需求
```

三者必须分别命名。把 offline 20/20 写成“Agent 成功率 100%”会误导作品展示。

## 7. 两个错误直觉与纠正

### 误区一：Case 越多越好

重复 100 条 read_file 只增加数字，不增加行为覆盖。任务集应覆盖边界、失败和安全类别，并定期分析失败簇。

### 误区二：只看总体成功率

总体 90% 可能掩盖 safety 0%。至少按 category 分组，并同时观察 Tool 次数、steps、延迟和失败分类。

另一个误区是每次失败就修改 expected 让测试变绿。Expected 代表任务契约，变化需要评审和版本记录，而不是迎合当前实现。

## 8. 完整评测轨迹

```text
load cases.json → validate 20 unique ids
for each case:
  executor(case) → actual_tools
  compare ordered list
  record calls, steps, duration, failure
aggregate:
  total=20 passed=20 rate=1.0 calls=25 steps=40
inject one empty actual list:
  passed=19 rate=0.95 failures={tool_sequence:1}
```

顺序重要，因为 read→patch 与 patch→read 的风险完全不同。某些任务可接受多条合法路径时，应使用 outcome 判定或允许集合，而不是硬塞单一序列。

## 9. 指标解释与基线比较

评测结果只有与基线比较才有意义。记录 commit、配置、模型、Prompt 版本和 Case 版本。离线管线应在 CI 固定运行；在线模型评测可以按需运行，避免默认费用和波动。

```text
baseline: passed 20, calls 25, steps 40
candidate: passed 20, calls 31, steps 46
decision: correctness unchanged, efficiency regressed
```

阈值应基于项目目标。安全类别通常要求零退化，平均延迟可能允许小幅波动。

## 最终实现校准

正式包把两种证据拆成不同入口：`run_protocol_replay` 用 expected 工具序列生成 Scripted LLM，只验证传输、Runner 和指标管线，因此报告名明确为 protocol replay；`run_offline_protocol_eval` 必须接收独立 executor 产生的 actual tools、finish reason 与 outcome，再分别对照冻结的工具和结果 oracle。预期值生成自己的实际值只能证明管线自洽，不能宣称 Agent 质量。
