# L26 契约、集成与 E2E：每一层测试回答不同问题

> 建议学习时间：60–90 分钟。本课在临时 Git 仓库完成读、搜、改、验，不访问真实项目。

## 1. 本节要解决的真实问题

单元测试能证明函数局部行为，却可能遗漏连接错误：Event 字段改名后 TraceWriter 仍按旧格式；Patch 单测成功，但 Runner 没把审批 Context 传入；Command 在当前仓库通过，换工作目录后导入失败。

本课区分 Contract Test（契约测试）、Integration Test（集成测试）和 End-to-End Test（端到端测试），并用一个临时 Git 仓库贯穿。问题链是：契约测试与类型检查有何区别？集成测试应使用多少真实组件？E2E 为什么不能大量堆积？如何证明测试没有修改学习者真实仓库？

## 2. 测试层级与证据强度

```text
Unit: 一个稳定边界，快，定位精准
Contract: 两侧共同遵守的数据不变量
Integration: 多个真实组件协作
E2E: 从用户任务到最终可验证结果
```

层级越高覆盖越广，失败定位和运行成本也越高。不是 E2E 越多越好；大多数错误应由小测试快速捕获，少量关键路径由 E2E 证明整链路。

## 3. Event 契约案例

Event 消费者依赖 sequence、run_id、step、type。契约测试不关心 Runner 私有实现，只验证输出流：

```python
def validate_event_contract(events):
    assert sequences == [1, 2, ..., n]
    assert len({event.run_id for event in events}) == 1
```

若第二个 Event sequence=3 或 run_id 改变，契约立即失败。类型注解只能说明字段类型，无法保证“整次 Run 连续递增”这种跨对象不变量。

## 4. 临时 Git 仓库为何重要

Coding Tool 的行为依赖文件系统、cwd、Python 导入和 Git 边界。`tmp_path` 创建隔离目录，`git init` 让场景与真实仓库相似，测试结束自动清理。

```python
subprocess.run(["git", "init", "-q"], cwd=tmp_path, check=True)
(tmp_path / "app.py").write_text("value = 1\n", encoding="utf-8")
```

不要在仓库根运行写入 E2E 后再“尽量清理”；测试失败时清理代码可能不执行，污染用户文件。隔离是设计，不是善后。

测试失败后是否立即删除临时仓库也有取舍。默认自动测试应清理，保持可重复；调试模式可以通过显式参数保留目录并打印绝对路径，方便检查 Git diff 和失败输出。不能偷偷永久保留每次运行，因为源码副本与日志会持续占用磁盘，也可能含敏感测试数据。保留策略应由测试入口控制，而不是写死在 Tool 中。

## 5. 本课唯一代码增量：真实 E2E Helper

```text
read app.py
search unique "value = 1"
patch to "value = 2"
run python -m pytest -q
return passed + actions + test_output
```

源码见 [testing.py](../../../agent-from-scratch/course-checkpoints/07-testing-evaluation/src/course_observability/testing.py)。这里不调用真实模型，Tool 决策是确定的；目标是测试文件与进程集成，不混入模型选择噪声。

## 6. 为什么 E2E 仍然需要结构化结果

```python
@dataclass(frozen=True)
class E2EResult:
    passed: bool
    actions: list[str]
    test_output: str
```

只返回 True 无法解释失败发生在 search、patch 还是 test。actions 提供粗粒度轨迹，test_output 保留诊断。正式 Runner 由 Event 和 RunResult 提供更完整结构，教学 helper 保持最小。

成功要求退出码为 0，不搜索 `passed` 文本。不同 pytest 版本输出可变，退出码契约更稳定。

## 7. 两个错误直觉与纠正

### 误区一：全部用 Mock，测试更快

Mock 掉 Path、subprocess 和编码后，最容易出错的工作区/cwd/UTF-8 连接反而没测。集成测试应在安全临时目录使用真实文件和进程。

### 误区二：一个超大 E2E 可以替代所有小测试

超大测试失败只告诉“任务没完成”，无法快速定位；还会重复初始化进程。E2E 证明主链，小测试证明边界和失败分支。

另一个误区是用真实模型让 E2E 更“真实”。这会把 Runtime、Tool、Prompt、模型和网络五种变量混在一起，默认回归不再确定。

## 8. 完整 E2E 轨迹

```text
create temp directory
git init
write app.py value=1
write test_app.py expecting value=2
read → actions=[read]
search exactly one match → +search
patch exact text → +patch
python -m pytest -q → exit 0 → +test
E2EResult(passed=true, actions=[read,search,patch,test])
temp directory removed
```

若搜索有两处匹配，Helper 在 Patch 前停止，证明非唯一边界继续有效。

## 9. 契约、集成、E2E 如何组合

契约测试验证 Event 和 Result；集成测试验证 ToolManager + 文件系统；E2E 验证完整用户价值路径。发现 Bug 时先在最低可复现层增加测试：路径解析 Bug 用单元测试，不必每次启动整套 E2E。

```text
失败越靠底层捕获 → 定位越快
关键路径再由上层测试 → 防止组件连接退化
```

测试金字塔是资源分配原则，不是死板百分比。

## 10. 运行、预期输出与故障实验

```powershell
python agent-from-scratch/course-checkpoints/07-testing-evaluation/steps/l26_contract_e2e.py
```

```text
passed=true actions=read,search,patch,test
```

故障实验：不执行 git init；制造两处 `value = 1`；让测试期望 3；把 cwd 改为仓库外；故意破坏 Event sequence。确认每个失败都给出可定位证据，并检查真实项目无文件变化。
