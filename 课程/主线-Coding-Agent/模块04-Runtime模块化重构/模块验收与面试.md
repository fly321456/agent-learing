# 模块 4 验收与面试：Runtime 模块化重构

```powershell
cd agent-from-scratch
```

验收必须证明：四个步骤脚本离线运行；纯文本与 Tool Loop 都有明确结果；未知 Tool 被标准化；事件 sequence 连续；`max_steps` 不伪装 completed；Runner 不读取供应商 raw response。

## 二、功能检查

- `Agent` 只有配置，没有 `run()` 和运行中事件。
- `BaseLLM.generate()` 返回 `LLMResponse`。
- `ToolManager.execute()` 返回 `ToolResult`。
- `Runner.run()` 返回 `RunResult`。
- `continuation_items` 原样进入下一轮，Tool Result 使用相同 call_id 回传。
- 两次运行拥有独立 run_id 与事件列表。

## 三、代码讲解

请在 10 分钟内从 Task 开始，沿 `Runner → BaseLLM → ToolManager → BaseLLM → RunResult` 讲完数据流。讲解时必须指出三种 Result 的生命周期，以及 Event 中 sequence、step、run_id 各自解决的问题。

## 四、故障注入

1. 删除 continuation_items 追加，解释第二轮为何协议不完整。
2. 注册两个同名 Tool，说明为什么应在启动时拒绝。
3. 让 ScriptedLLM 永远返回 Tool Call，证明 max_steps 生效。
4. 让 handler 抛异常，说明为何 Run 仍有机会恢复。
5. 连续运行两次，检查状态是否串线。

## 五、设计取舍

请答辩：为什么本模块不直接复制最终 Runtime？为什么 ToolManager 当前不含 Workspace？为何保留 Event 与聚合 Tool Results 两种视图？什么时候给 BaseLLM 增加 streaming 才合理？

## 六、精选面试题

1. 什么是依赖倒置，BaseLLM 如何体现它？
2. 抽象供应商协议时，最小共同语义如何确定？
3. `LLMResponse` 与 `RunResult` 为什么不能合并？
4. 未知 Tool 应在哪一层处理？
5. Tool error 与 Run error 有什么不同？
6. 为什么 Event 需要全局 sequence？
7. 如何证明 Runner 没有供应商依赖？
8. Fake LLM 能发现哪些集成问题？
