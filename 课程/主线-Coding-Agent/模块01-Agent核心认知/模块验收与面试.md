# 模块 01 验收与面试：Agent 核心认知

## 验收目标

本模块不是以“看完四篇文档”为完成，而是以你能解释、手绘、运行、破坏和修复最小 Agent 为完成。请在不查看正文的情况下先做原理验收，再打开代码做项目验收。

## 一、原理复述

用 3 分钟回答：普通 LLM 为什么还不是 Agent？回答必须包含目标、环境、行动、观察、持续决策和停止，不得只说“Agent 会调用工具”。

再说明 `LLM + Tool + Loop + Environment` 每个部分负责什么、不能负责什么，并举出缺少任意一个后系统退化的具体例子。

## 二、轨迹手绘

给定任务“README 缺失时找到项目入口”，在纸上画出至少三轮状态：

```text
Task → Decision → Action → Observation(error)
     → Decision → Action → Observation(success)
     → Decision → Finish
```

要求写出每个 Decision 和 Observation 的实际字典内容，并指出哪个观察改变了下一步。

## 三、项目功能检查

在仓库根目录执行：

```powershell
python agent-from-scratch/course-checkpoints/01-agent-concepts/steps/l01_single_shot_vs_agent.py
python agent-from-scratch/course-checkpoints/01-agent-concepts/steps/l02_four_elements.py
python agent-from-scratch/course-checkpoints/01-agent-concepts/steps/l03_workflow_vs_agent.py
python agent-from-scratch/course-checkpoints/01-agent-concepts/steps/l04_think_act_observe.py
python agent-from-scratch/course-checkpoints/01-agent-concepts/demo.py
```

五个脚本必须完全离线运行，L04 与 `demo.py` 最后一行应为：

```text
finish_reason: completed
```

## 四、自动验证

```powershell
cd agent-from-scratch
python -m pytest -q tests/test_course_module1.py
```

测试必须覆盖直接完成、一次 Tool、工具失败后重新决策、未知 Tool、`max_steps` 和四课脚本。不能为了通过测试而删除错误状态或写死统一答案。

## 五、代码讲解

用 8–10 分钟讲解 `agent_core.py`，顺序必须从 `run_agent` 的输入开始，到返回结果结束。至少说明：

1. `ScriptedLLM.decide(task, observations)` 为什么保存观察快照。
2. `TOOLS` 注册表如何把工具名称映射到 Python 函数。
3. 工具异常为什么进入 Observation，而未知工具为什么明确停止。
4. `observations` 与 `trace` 的服务对象有何不同。
5. `max_steps` 为什么是宿主程序边界，而不是 Prompt 建议。

## 六、故障注入

依次完成三项，保留命令、输出和结论：

1. 将 `read_file` 改成未知名称，验证 `finish_reason="unknown_tool"`。
2. 将 `max_steps` 改为 1，验证已执行步骤仍保留在 Trace 中。
3. 让 `read_file` 抛错后再调用 `list_files`，验证错误没有阻止下一轮恢复。

故障注入后必须恢复代码，并重新运行测试。

## 七、设计取舍

比较固定 Workflow 与 Agent，分别从可预测性、成本、审计、安全和任务不确定性说明选择。至少举一个“应使用 Workflow”的场景和一个“值得使用 Agent”的场景。答案不能使用“Agent 更高级”作为理由。

说明为什么模块 1 使用字典、`ScriptedLLM` 和单文件代码，而没有提前使用正式 `BaseLLM`、`Runner`、`RunResult`、`ToolManager`。正确重点是学习顺序和可观察性，不是说正式抽象没有价值。

## 八、精选面试题

1. Tool Calling 与 Agent Loop 的本质区别是什么？
2. 为什么工具错误应标准化为 Observation，而不是全部抛到最外层？
3. Agent 执行成功与工具执行成功有什么区别？
4. 如何证明后续 Decision 确实使用了先前 Observation？
5. 为什么生产级 Agent 仍需要大量确定性的 `if/else`？
6. 什么情况下应采用 Workflow 包围局部 Agent 的混合架构？
7. `max_steps` 解决了什么问题，又不能保证什么？
8. 如果 Agent 最终答案正确，但 Trace 中工具结果与答案矛盾，应如何判断？

## 通过标准

以下六项必须同时通过：原理复述无概念混淆；轨迹手绘数据流正确；五个脚本可运行；自动测试通过；能定位三种故障；能说明 Workflow 与 Agent 的取舍。通过后再进入模块 2，避免把未理解的闭环藏进 API 调用细节。
