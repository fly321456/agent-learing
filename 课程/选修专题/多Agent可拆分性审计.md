# 选修：多 Agent 可拆分性审计

## 定位

多 Agent 是高成本架构选择，不是课程升级标志。默认结论是继续使用单 Agent，除非审计证明拆分后的并行性、权限隔离或专业化收益大于通信与治理成本。

## 审计问题

1. 任务是否能拆成输入输出明确、低耦合的子任务？
2. 每个角色是否拥有独立工具、权限或上下文边界？
3. 单 Agent 基线失败在哪里，拆分如何直接解决？
4. 是否能分别评测 Planner、Executor、Reviewer？
5. 共享状态由谁拥有，冲突如何解决？
6. 局部失败如何重试，如何避免重复副作用？
7. 通信 token、延迟和调试成本是否可接受？

## 进入实现的硬条件

- 单 Agent 已有 M07 评测基线。
- 至少一个角色可以被独立测试。
- 协作协议具有稳定 Schema 和超时语义。
- 能追踪每个角色的输入、输出、成本和失败原因。
- 有明确回退到单 Agent 的方案。

## 最小实验

如果审计通过，只实现一个可替换 Reviewer：Executor 先产生候选变更，Reviewer 使用独立规则或模型给出结构化结论。不要第一版就加入共享 Memory、自治角色网络或无限委派。

## 验收

```powershell
cd agent-from-scratch
python -m pytest -q
coding-agent-eval
```

实验必须与单 Agent 基线比较成功率、步骤、延迟、调用次数和失败归因。无法局部评测时，不实施多 Agent。当前状态：完成审计模板，未引入多 Agent Runtime。
