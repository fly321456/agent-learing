# R04 检索评测与三层边界：先测“找没找到”，再测“答没答对”

> 建议学习时间：60–90 分钟。本课完成 RAG 选修，建立 Recall@K 和 RAG/Session/Memory 边界。

## 1. 本节要解决的真实问题

用户得到错误答案时，问题可能在三层：Retriever 没找到正确文档；Context Builder 找到了却裁掉或混入噪声；Generator 看到了证据仍回答错误。若只测最终答案，我们不知道该调 chunk_size、Top-K、Prompt 还是模型。

本课先评测检索层：对每个 Query 标注 relevant sources，计算正确来源是否出现在前 K。然后再讨论答案层的引用与事实。问题链是：Recall@K 如何计算？为什么 K=1 与 K=5 都要看？检索命中是否等于答案正确？无答案问题怎样评测？RAG、Session 和 Memory 分别保存什么？

## 2. 分层评测漏斗

```text
Retrieval: relevant source in Top-K?
  → Context: source preserved, bounded, marked untrusted?
  → Generation: answer supported and cited?
  → Task: user goal actually satisfied?
```

越靠前的层越确定、便宜。Retriever 漏文档时，不应首先改生成 Prompt。生成引用错误时，也不一定要更换索引。

固定 Query 集应包含正常命中、无答案、来源冲突和注入文档。

## 3. Recall@K 的定义

对每个 Query，若前 K 个返回 source 与相关来源集合有交集，记为 hit；所有 Query 的 hit 比例就是 Recall@K。

```text
rankings = [[a,b], [x,c], [z]]
relevant = [{a}, {c}, {missing}]
K=1 hits: query1 only → 1/3
K=2 hits: query1 + query2 → 2/3
```

这是“每题是否至少找回一个相关来源”的 hit recall，适合入门。若一题需要多个来源，应使用更细的 source-level recall。

## 4. 本课唯一代码增量：recall_at_k

```python
def recall_at_k(rankings, expected, k):
    if len(rankings) != len(expected):
        raise ValueError(...)
    hits = sum(
        bool(set(ranking[:k]) & relevant)
        for ranking, relevant in zip(rankings, expected)
    )
    return hits / len(expected) if expected else 0.0
```

K 必须正数，rankings 与 expected 数量一致，空数据返回 0。指标由实际排名计算，不写静态分数。

测试同时断言 K=1 和 K=2，证明排名位置会改变结果。

## 5. Precision、MRR 与答案指标

Recall 高可能返回大量无关文档。Precision@K 衡量前 K 中相关比例；MRR（Mean Reciprocal Rank）奖励第一个相关结果更靠前。课程先实现 Recall，再根据失败证据扩展。

```text
Recall@5 high, Precision@5 low → 找得到但噪声多
MRR low → 正确来源经常排在后面
Answer citation rate low → 生成层未引用来源
```

最终答案还要检查事实准确、引用支持和合理拒答，不能用检索指标替代。

## 6. 无答案与冲突案例

无答案问题的正确行为是检索结果为空或低于阈值，并最终 abstain。若 Retriever 总返回最相似片段，模型容易把弱相关内容编成答案。

来源冲突时，例如旧文档写 3000、新文档写 4312，评测应包含版本和权威性规则。单纯 Recall 两份都命中并不说明应选哪份。

```json
{
  "question": "current port?",
  "relevant_sources": ["server-v2.md"],
  "deprecated_sources": ["server-v1.md"]
}
```

这迫使索引保留 metadata，而不是只有 text。

## 7. RAG、Session 与 Memory 边界

```text
RAG：外部文档知识，可重建索引，按 Query 检索
Session：当前会话历史，按时间和 Turn 组织
Memory：跨会话保存的用户/任务长期事实，需要写入治理
```

用户刚说的“把端口改成 5000”属于 Session；官方手册中的默认端口属于 RAG；用户长期偏好“总用简体中文”可能进入 Memory，但应有明确同意、更新和删除机制。

把三者都存进向量库会掩盖生命周期、权限和新鲜度差异。

## 8. 两个错误直觉与纠正

### 误区一：最终回答错了，说明 Retriever 不好

正确来源可能已在 Top-1，错误发生在生成或 Prompt。必须保存 rankings 与 Context 才能定位。

### 误区二：Recall@K 越高，系统一定越好

把所有文档都返回可以提高 Recall，却摧毁 Precision、延迟和 Context。指标必须组合，并关注安全来源。

另一个误区是把 Session 摘要长期写入 RAG 作为事实。摘要有损且可能过期，不应无治理地变成跨用户知识。

## 9. 完整评测轨迹

```text
load fixed queries + relevant sources
run retriever → ordered source ids
compute Recall@1 and Recall@2
inspect failed query:
  tokenization issue? chunk boundary? wrong source metadata?
build untrusted Context from retrieved chunks
run answer evaluation separately
record index version and parameters
```

调整 chunk_size、overlap 或评分后重跑同一集合，才有可比较证据。
