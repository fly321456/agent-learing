# A01 多 Agent 可拆分性审计：先证明需要拆，再增加角色

> 建议学习时间：60–90 分钟。本课不创建多个 Agent，先建立单 Agent 基线和可拆分性检查。

## 1. 本节要解决的真实问题

多 Agent Demo 很容易显得高级：Planner 写计划、Executor 工作、Reviewer 点评，终端里出现三种角色。但同一个任务若由单 Agent 加一条验证步骤就能完成，多 Agent 只增加模型调用、上下文复制、通信延迟和失败点。

本课把默认答案反过来：**先使用单 Agent，只有任务可拆、角色有不同能力、共享状态可控，并且存在固定评测能证明收益时，才考虑多 Agent。**

问题链是：任务能否分成独立子目标？子目标需要不同工具或权限吗？可以并行吗？每个角色需要复制多少 Context？没有评测时如何知道 Reviewer 真有用？

## 2. 单 Agent 基线为什么必须先存在

```text
Task → one Agent → Tools → Result → Tests/Eval
```

基线记录成功率、Tool 次数、steps、延迟、费用和失败分类。加入多 Agent 后比较同一任务集，才能把变化归因于架构，而不是 Prompt、模型或数据同时改变。

如果没有基线，“多人讨论后答对一次”不能证明增益。多 Agent 也可能让三个角色共同确认同一个错误。

## 3. 类比与两个任务案例

把多 Agent 想成组建项目小组。一个人能在十分钟完成的配置修改，开三场会议反而更慢；大型迁移若能分为数据库、API、前端并有独立验收，专业分工才可能回本。

案例一：修复一个明确的拼写错误。目标单一、上下文小、补丁可由测试验证，不应拆。案例二：审计大型仓库的安全、性能和兼容性，每个维度可独立分析，最后汇总，可能适合并行 Specialist。

案例三：连续修改同一个函数的三行代码。虽然能写三个子任务，但共享状态高度耦合，并发执行会产生冲突，不适合拆。

## 4. 五维审计表

```text
independent_subtasks：子任务结果能否独立产生？
distinct_expertise：是否需要不同工具、权限或专业判断？
parallelizable：并行是否真正缩短关键路径？
low_shared_state：角色是否只交换小型明确产物？
evaluation_available：能否测量质量增益？
```

前四项描述潜在收益与成本，第五项是上线前提。没有评测，即使任务看起来可拆，也无法判断复杂度是否值得。

## 5. 本课唯一代码增量：TaskAudit

```python
@dataclass(frozen=True)
class TaskAudit:
    independent_subtasks: bool
    distinct_expertise: bool
    parallelizable: bool
    low_shared_state: bool
    evaluation_available: bool
```

教学决策要求 evaluation_available 为真，并且前四项至少三项成立。这个阈值不是普遍公式，而是把“为什么拆”从直觉变为可讨论输入。

审计结果同时返回 reasons，避免只有一个无法解释的布尔值。

## 6. 成本账本

多 Agent 的成本不仅是模型调用次数：

```text
每个角色的 Instructions 和 Context tokens
角色间消息与序列化
计划、执行、审查的额外等待
共享状态与冲突处理
局部失败恢复
Trace、权限和审批复杂度
```

并行可能降低墙钟时间，却增加总 token 和协调成本。作品应同时报告质量与成本，不只展示角色数量。

可以先写一张最小收益账：`净收益 = 质量增益 + 时间收益 - 通信成本 - 恢复成本`。这不是要求把所有维度强行换算成人民币，而是防止只挑有利指标。比如三个角色把运行时间从 10 分钟降到 6 分钟，却让错误接受增加一倍，那么“更快”不能证明方案更好；反过来，Reviewer 多花 20% 时间但稳定阻止高风险错误，可能仍值得保留。审计阶段要先声明哪个指标优先、最低改善多少才算成功，不能看到结果后再修改标准。

## 7. 两个错误直觉与纠正

### 误区一：任务复杂就应该多 Agent

复杂任务可能高度串行，一个 Agent 保持完整 Context 更容易。可拆分性比主观“复杂”更重要。

### 误区二：Reviewer 一定提高质量

Reviewer 可能使用同一模型、同一错误 Context，产生一致性偏见；也可能只复述 Executor。必须用缺陷发现率或 false acceptance 测量。

另一个误区是角色名称本身代表专业能力。若三个角色拥有相同 Prompt、工具和 Context，只是名字不同，就没有真实职责边界。

## 8. 审计运行轨迹

```text
Task: modify one tightly coupled function
independent_subtasks=false
distinct_expertise=false
parallelizable=false
low_shared_state=true
evaluation_available=false
Decision: use_multi_agent=false
Reasons: no evaluation; subtasks tightly coupled
```

另一任务四项收益成立且有评测，Decision 才为 true。决策仍是实验许可，不是永久架构承诺。

## 9. 从审计到实验假设

好的多 Agent 提案应写成可证伪假设：

```text
“独立 Reviewer 将把测试缺失的 false acceptance 从 20% 降到 5%，
同时通信 token 增幅不超过 30%。”
```

若结果没有达到阈值，回到单 Agent 或给单 Agent 增加确定性验证。不能因为已经写了 Planner 就不断修改评测迎合架构。

## 10. 运行、预期输出与故障实验

```powershell
python agent-from-scratch/course-labs/multi-agent/steps/a01_decomposability_audit.py
```

```text
use_multi_agent=true reasons=1
```

故障实验：关闭 evaluation_available；把共享状态改为高耦合；只有 parallelizable 一项成立；为单行拼写修复强行分三个角色；比较审计理由是否足够解释决策。

## 11. 基础练习与进阶挑战

基础练习：对“修拼写”“跨模块安全审计”“迁移数据库”分别填写五维表。进阶挑战：为自己的任务定义质量收益、通信成本和停止实验阈值，先写评测再实现角色。

1. 为什么单 Agent 基线必须先存在？
2. 任务复杂与任务可拆有什么区别？
3. low_shared_state 为什么重要？
4. 没有 evaluation 为什么不应实施多 Agent？
5. 怎样写一个可证伪的多 Agent 收益假设？

下一课 [A02 Planner–Executor–Reviewer 协议](A02-Planner-Executor-Reviewer协议.md) 将定义角色之间真正交换的数据，而不是只写三段角色 Prompt。

在进入下一课前，再做一次反向检查：如果把审计表中的五个布尔字段全部改成 `True`，是否就自动证明应该采用多 Agent？仍然不能。审计表只说明任务具备实验条件，不说明具体实现一定获得收益；最终还要用 A04 的同任务、同标准对照评测来决定保留或回退。

反过来，如果审计拒绝拆分，也不表示永远禁止实验。它要求先补齐评测、降低共享状态或重新划分任务边界，而不是用更多角色掩盖原问题。建议把每次审计保存为一段可复查记录：任务是什么、单 Agent 基线是什么、哪些维度支持拆分、哪个维度仍有风险、什么指标出现时立即回退。团队讨论的对象由此从“多 Agent 看起来更高级”变成“这个假设能否被同一组数据推翻”。
