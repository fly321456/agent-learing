# 多 Agent 工程选修模块导学

## 为什么把多 Agent 放在最后

多 Agent（Multi-Agent）不是单 Agent 的自动升级版，而是用更多角色、消息和失败边界换取专业分工或独立审查。学习者如果还不能测试单 Agent，就无法判断多 Agent 到底解决了问题，还是只让终端输出更热闹。

进入本模块前，应完成 32 节主线，能解释 `Runner`、`ToolManager`、`RunResult` 和 `Event` 的职责，并保存一份单 Agent 离线评测基线。所有实验均使用确定性 Scripted Agent，不调用真实模型，也不把选修概念耦合进正式 Runtime。

## 模块问题链

~~~text
任务真的需要多个角色吗？
  -> 能否拆成低耦合、可分别验收的子任务？
  -> 角色之间交换什么结构化数据？
  -> 共享状态由谁写，局部失败如何保留？
  -> Reviewer 是否带来可测质量增益？
  -> 收益不足时能否回退单 Agent？
~~~

## 四课路线

| 课程 | 只新增的核心概念 | 课程产物 |
| --- | --- | --- |
| [A01 可拆分性审计](A01-可拆分性审计.md) | 先审计任务，再批准实验 | `TaskAudit` 与可解释架构决策 |
| [A02 Planner-Executor-Reviewer 协议](A02-Planner-Executor-Reviewer协议.md) | 角色靠数据契约协作 | `PlanItem`、`WorkResult`、`Review` |
| [A03 共享状态、成本与局部失败](A03-共享状态、成本与局部失败.md) | 状态所有权与失败隔离 | `SharedState`、消息成本、局部结果 |
| [A04 最小 Reviewer 实验](A04-最小Reviewer实验.md) | 用同任务对照评测架构 | 错误接受与通信成本比较 |

四课不是四种独立技巧，而是一条决策链。A01 不通过时应停在单 Agent；A02 无法写清协议时不应增加角色；A03 无法说明状态所有权时不应并发；A04 没有质量增益时应删除 Reviewer。

## 代码实验

离线实验位于 `agent-from-scratch/course-labs/multi-agent/`，四个步骤脚本逐课递进，`demo.py` 展示最终状态。先手工预测输出，再运行：

~~~powershell
cd agent-from-scratch
python course-labs/multi-agent/steps/a01_decomposability_audit.py
python course-labs/multi-agent/steps/a02_protocols.py
python course-labs/multi-agent/steps/a03_shared_state_failures.py
python course-labs/multi-agent/steps/a04_reviewer_comparison.py
python course-labs/multi-agent/demo.py
~~~

专项测试：

~~~powershell
python -m pytest -q tests/test_course_multi_agent.py
~~~

## 推荐学习方式

每课按“先写判断、再看轨迹、最后运行代码”的顺序学习。不要先复制最终结论。A01 为自己的真实任务填写审计表；A02 手绘角色输入输出；A03 标出每项状态的写入者；A04 先定义失败指标和回退阈值。

完成练习后再阅读 [模块练习参考答案](模块练习参考答案.md)。答案册提供一种可验证思路，不代表所有项目都应采用同一阈值。最终通过 [模块验收与面试](模块验收与面试.md) 检查原理、代码、故障分析和设计取舍。

## 完成标准

学完后，你不只应能实现 Planner、Executor 和 Reviewer，还要能坚定地拒绝不必要的多 Agent。合格结果包括两种：数据证明 Reviewer 值得保留；或者数据证明没有增益，因此保留更简单的单 Agent。二者都比没有基线的成功 Demo 更可靠。
