# 多 Agent 工程选修模块验收与面试

## 一、项目功能验收

- 能用 `TaskAudit` 解释一个任务为什么适合或不适合多 Agent，而不是只给布尔结论。
- Planner 产生带稳定 ID 的 `PlanItem`，Executor 对每项产生独立 `WorkResult`。
- 一个子任务失败后，其他独立任务的成功结果不会丢失。
- `SharedState` 能根据实际消息计算消息数和通信字符数。
- Reviewer 使用显式验收标准，审查时不直接修改 Executor 候选结果。
- 同一组案例能比较单 Agent 与 Reviewer 的错误接受；无增益时回退单 Agent。

## 二、自动验证

在项目目录执行：

~~~powershell
cd agent-from-scratch
python course-labs/multi-agent/demo.py
python -m pytest -q tests/test_course_multi_agent.py tests/test_course_structure.py
~~~

预期：Demo 输出可拆分性与 Reviewer 比较指标；四个步骤脚本完全离线运行；行为测试、教材质量门和课程链接检查全部通过。验收者应修改一个案例文本，确认通信字符数随真实数据变化，而不是静态打印。

## 三、原理复述

请在不看教材的情况下画出以下链路：

~~~text
TaskAudit
  -> PlanItem[]
  -> WorkResult[]
  -> SharedState messages
  -> Review
  -> Comparison
  -> keep Reviewer or revert
~~~

复述时必须说明每个对象的创建者、不可承担的职责、失败表现和可观测指标。只说“Planner 规划、Executor 执行、Reviewer 审核”不算通过，因为这仍停留在角色名称层面。

## 四、代码讲解

随机选择以下两段现场讲解：

1. `audit_task` 为什么把 `evaluation_available` 设为硬条件？
2. `execute_plan` 为什么逐项捕获异常，什么情况下又不该继续？
3. `Message` 为什么不可变，`SharedState` 为什么只追加？
4. `review_candidate` 为什么返回问题列表而不修改候选？
5. `decide_from_comparison` 为什么在 `gain <= 0` 时默认单 Agent？

讲解需要联系一个 Coding Agent 真实场景，而不只是逐行翻译代码。

## 五、故障注入

验收者从以下故障中随机选择两项：

- 关闭 `evaluation_available`，解释为什么即使其余四项为真仍不批准实验。
- 让第二个 Executor 子任务抛异常，证明第一、第三项结果仍存在。
- 删除 `WorkResult.item_id`，说明恢复与重试为什么失去关联依据。
- 增加十条重复角色消息，观察成本增长而质量不变。
- 构造 `Comparison(0, 0, 100)`，证明 Reviewer 无收益时会回退。
- 构造 Reviewer 全部拒绝的反例，指出仅统计错误接受的局限。

## 六、设计取舍答辩

答辩题一：大型仓库安全审计看起来可并行，但多个角色需要读取同一套配置和依赖图。你如何判断共享状态是否仍足够低？

答辩题二：Reviewer 减少一次错误接受，却增加三倍延迟。你会保留吗？请先说明错误接受的业务代价，再给阈值，不接受“视情况而定”作为完整答案。

答辩题三：为何不直接让单 Agent 在结束前运行确定性测试？什么证据出现时，独立 Reviewer 才比新增一个验证 Tool 更合理？

## 七、精选面试题

1. Multi-Agent 与 Workflow 的主要区别是什么？
2. 任务复杂度和可拆分性为什么不是同一件事？
3. 多 Agent 系统中共享状态最常见的风险有哪些？
4. 如何设计 Planner 与 Executor 之间的稳定协议？
5. 什么是局部失败？它与吞掉异常有什么区别？
6. 如何避免子任务重试造成重复副作用？
7. 为什么 Reviewer 与 Executor 使用同一上下文可能产生一致性偏见？
8. 评测多 Agent 时为什么必须固定任务集和单 Agent 基线？
9. 除质量外，还应记录哪些成本指标？
10. 哪些结果出现时应该主动删除多 Agent 实现？

## 八、评分标准

| 维度 | 通过标准 |
| --- | --- |
| 心智模型 | 不默认多 Agent 更高级，能先给出单 Agent 基线 |
| 协议 | 角色输入输出结构化，状态所有权明确 |
| 可靠性 | 能区分成功、错误、阻塞和副作用风险 |
| 评测 | 使用同任务对照，质量与成本同时报告 |
| 取舍 | 能根据数据保留或回退，不为 Demo 复杂度辩护 |

任一硬性失败均不通过：无评测就宣称收益；角色共享并任意改写全部状态；Reviewer 没有验收标准；只展示成功案例；默认测试依赖网络。
