# A03 共享状态、成本与局部失败

> 选修课｜建议时长：60–90 分钟｜前置课程：A01、A02

## 1. 本节要解决的真实问题

A02 把 Planner、Executor、Reviewer 的输入输出写成了明确协议，但“有协议”不等于“协作就免费”。当一个任务从单 Agent 变成三个角色后，至少会多出三个问题：中间结果放在哪里？谁有权修改它？其中一个角色失败时，哪些已经完成的工作还能保留？

假设 Planner 拆出“检查配置、运行测试、补充文档”三项工作。Executor 已经成功检查配置，运行测试时却发现环境缺少依赖。如果系统只保存一个不断改写的自然语言大字符串，我们很难回答：检查配置的结果还在吗？测试失败属于任务失败还是环境失败？补充文档是否还能继续？失败后重跑会不会重复修改文件？

本课只引入一个核心概念：**显式共享状态（explicit shared state）**。它不是让所有角色随意读写同一份内存，而是把计划、结果、消息和失败分别记录，使每项数据都能找到来源与所有者。

## 2. 从 A02 继续追问

A02 的结构化协议解决了“角色之间传什么”，本课继续追问“传递以后由谁保管”。问题链如下：

~~~text
角色增加
  -> 边界之间需要传递信息
  -> 传递会产生消息和上下文成本
  -> 中途失败时不能丢掉全部进度
  -> 因此状态必须可追踪，失败必须局部化
~~~

先区分三个容易混淆的对象：`PlanItem` 是尚待完成的工作；`WorkResult` 是一次执行的事实；`Message` 是角色之间发生过的一次通信。它们不能合并成同一个“万能消息”。计划会被执行，结果应当只追加不篡改，消息则用于审计成本。对象职责越清楚，恢复和排障越简单。

## 3. 用接力赛理解共享状态

可以把多 Agent 协作理解为接力赛。接力棒不是“所有运动员的共同思想”，而是一份经过约定的交接物。上一棒必须把可验证的结果交出来，下一棒才能继续。裁判记录每次交接，但不会替运动员跑步。

在代码任务中：Planner 像教练，只创建赛段；Executor 像运动员，只提交每段结果；Reviewer 像裁判，只判断结果是否满足标准；`ExecutionState` 像成绩表，保存计划与逐项结果。若所有角色都可以重写成绩表，失败后便无法判断谁改了什么。

案例一：三个子任务互相独立，第二项失败。系统应该保留第一项成功结果，并继续尝试第三项。这叫**局部失败（local failure）**，不是把整次运行抹成失败。

案例二：第二项会修改第一项依赖的同一文件，并且第三项必须读取第二项输出。此时任务高度耦合，简单的局部继续可能制造错误状态。正确做法不是强行并行，而是显式描述依赖，或者退回单 Agent 顺序执行。

## 4. 核心概念：状态必须有所有权

共享状态最危险的误解，是把“共享”理解成“谁都能改”。工程上更可靠的规则是：**可以共同读取，但写入权限按对象划分**。

| 状态 | 创建者 | 更新方式 | 失败后用途 |
| --- | --- | --- | --- |
| `plan` | Planner | 本实验创建后不改 | 确认原任务边界 |
| `results` | Executor 调度器 | 每个子任务追加一条 | 保留成功与失败事实 |
| `messages` | 协作边界 | 每次交接追加一条 | 计算通信成本与追踪来源 |
| `review` | Reviewer | 对候选结果生成新结论 | 不覆盖原始候选内容 |

这是一种**追加式状态（append-only state）**思路。追加并不自动解决所有并发问题，但比“每个角色都重写整份状态”更容易审计。正式系统还要增加版本号、持久化和幂等键；本实验先把最小边界看清，不提前堆叠工程抽象。

## 5. 从全局失败推导局部失败

最简单的错误实现会把循环包在一个总 `try/except` 里：

~~~python
try:
    for item in plan:
        outputs.append(executor(item))
except Exception as exc:
    return {"status": "error", "error": str(exc)}
~~~

第二个任务抛错后，循环直接结束，第三个任务没有机会执行；返回值还丢失了第一个任务成功的结构化事实。改进方向不是“吞掉异常”，而是把异常转换成属于当前 `PlanItem` 的 `WorkResult`：

~~~python
for item in plan:
    try:
        result = WorkResult(item.id, "success", executor(item))
    except Exception as exc:
        result = WorkResult(item.id, "error", error=str(exc))
    state.results.append(result)
~~~

这样，错误被隔离在一个子任务内。注意：只有彼此独立的任务才适合继续。如果失败会破坏共享文件或数据库状态，系统必须先执行补偿、回滚或停止后续依赖项。局部捕获异常不等于盲目忽略异常。

## 6. 最小实现逐段解释

实验中的 `SharedState` 只记录通信，不承担业务真相：

~~~python
@dataclass(frozen=True)
class Message:
    sender: str
    receiver: str
    content: str

@dataclass
class SharedState:
    messages: list[Message] = field(default_factory=list)

    def record(self, sender: str, receiver: str, content: str) -> None:
        self.messages.append(Message(sender, receiver, content))

    @property
    def message_count(self) -> int:
        return len(self.messages)

    @property
    def communication_chars(self) -> int:
        return sum(len(message.content) for message in self.messages)
~~~

`Message` 使用不可变数据类，避免记录后又被悄悄修改；`SharedState.record` 是唯一写入口；两个属性分别记录消息次数和字符数。字符数不是 Token、费用或延迟的精确替代，但它是稳定、离线、可比较的通信代理指标。后续接入真实模型时，可以换成 Token 和耗时统计，比较思想不变。

## 7. 手工走一遍失败轨迹

输入计划为 `inspect`、`test`、`document`。脚本让 `test` 故意抛出 `RuntimeError("unavailable")`：

~~~text
PlanItem task-01 inspect
  -> WorkResult(status="success", output="done")
PlanItem task-02 test
  -> RuntimeError("unavailable")
  -> WorkResult(status="error", error="unavailable")
PlanItem task-03 document
  -> WorkResult(status="success", output="done")
Planner -> Executor: "three tasks"
  -> messages=1
  -> communication_chars=11
~~~

这里最重要的不是“程序没有崩”，而是三条事实都被保留。系统可以准确报告两项成功、一项失败，也可以只重试 `task-02`。若只有一个总错误字符串，就做不到这种精确恢复。

## 9. 两个错误直觉与故障实验

**错误直觉一：共享状态越多，角色协作越聪明。** 实际上，每多共享一段内容，就多一份同步、权限和上下文成本。把整个会话、全部文件和所有中间推理广播给每个角色，会让错误来源更难定位。实验：连续记录十条重复消息，观察 `message_count` 和 `communication_chars` 如何增长，但任务质量完全不变。

**错误直觉二：捕获子任务异常后总能继续。** 若 `test` 失败只是环境缺依赖，可以继续独立的文档任务；若 `apply_patch` 写到一半失败，后续任务读取的可能是损坏文件。实验：把两个任务设计为写同一个临时文件，思考第二项失败后第三项是否仍安全。答案取决于副作用边界，而不是 `try/except` 是否存在。

还可以故意删除每个结果的 `item_id`。测试仍可能显示“两个成功一个失败”，但你无法知道该重试哪项，这说明可关联标识也是恢复协议的一部分。

## 10. 基础练习与进阶挑战

基础练习：给 `ExecutionState` 写一个 `failed_items()` 函数，只返回状态为 `error` 的结果；再写测试证明成功项保持原顺序。不要修改正式 Runtime。

进阶挑战：为 `PlanItem` 增加 `depends_on` 教学字段。当依赖项失败时，把后续项记录为 `blocked`，而不是执行或伪装成 `error`。比较 `error` 与 `blocked` 对排障含义的区别，并说明为什么“默认并行所有任务”是不安全的。

故障注入：让 Executor 对某项先产生副作用再抛错，设计一个幂等键或补偿动作。你需要回答：重试由谁发起？怎样识别这是不是同一次子任务？怎样避免重复写入？

## 11. 自测问题

1. 为什么共享状态不等于让所有角色随意修改同一个字典？
2. `PlanItem`、`WorkResult` 和 `Message` 分别描述什么事实？
3. 为什么把异常转成局部 `WorkResult` 比返回一个全局错误字符串更利于恢复？
4. `communication_chars` 能证明真实费用下降吗？它适合比较什么？
5. 哪些副作用场景下不应该在子任务失败后继续执行？

## 12. 本节总结与下一课衔接

本课把多 Agent 的隐藏成本变成了可以观察的数据：计划属于 Planner，结果由执行边界逐项追加，消息只记录协作，失败绑定到具体子任务。真正可靠的多 Agent 系统不是“角色更多”，而是状态所有权更清楚、局部失败更可恢复、通信成本可测量。

下一课只增加一个 Reviewer，并用同一组任务比较单 Agent 自审与独立审查。重点不再是“能否运行”，而是 Reviewer 防止了多少错误接受，以及这点收益是否值得新增通信成本。
