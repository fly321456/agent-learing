# 多 Agent 工程模块练习参考答案

> 请先独立完成 A01–A04 的基础练习与故障实验。这里提供的是可验证的参考思路，不是要求照抄的唯一架构。

## A01 可拆分性审计

### 基础练习参考

“修复单处拼写”通常应填为：独立子任务 `False`、不同专业能力 `False`、可并行 `False`、低共享状态 `True`、存在评测 `True`。虽然有测试，但前三个收益维度不成立，保持单 Agent。

“跨模块安全审计”可能是：独立子任务 `True`、不同专业能力 `True`、可并行 `True`、低共享状态取决于模块边界、存在评测必须由固定漏洞样本证明。只有“看起来很大”不能把字段都写成真。

“迁移数据库”往往高度依赖顺序和共享 Schema。即使可以让角色分别分析，也不代表迁移动作适合并行。可以采用多个只读 Specialist 提建议，再由单一 Executor 执行有副作用步骤。

~~~python
audit = TaskAudit(
    independent_subtasks=True,
    distinct_expertise=True,
    parallelizable=True,
    low_shared_state=False,
    evaluation_available=True,
)
decision = audit_task(audit)
assert decision.use_multi_agent is True  # 教学阈值允许实验，不代表直接上线
~~~

### 常见错误

不要把 `parallelizable=True` 理解为“实现时立刻并发”，它只说明存在潜在收益；不要为了通过阈值而改审计字段；不要省略回退条件。更好的实验假设是：“固定 20 个任务上，Reviewer 将错误接受从 4 降至 1，额外通信字符不超过基线输出的 40%。”

## A02 角色协议

### 为 PlanItem 增加验收条件

一种最小扩展如下：

~~~python
@dataclass(frozen=True)
class PlanItem:
    id: str
    objective: str
    acceptance: tuple[str, ...]

item = PlanItem(
    "task-01",
    "run unit tests",
    ("exit code is zero", "output is recorded"),
)
~~~

验收条件描述可观察结果，不应写成“调用 pytest Tool 三次”之类的内部步骤。Executor 可以选择实现方式，Reviewer 只按结果判断。

### 依赖与循环检查思路

可给 `PlanItem` 增加 `depends_on: tuple[str, ...]`。执行前先验证所有依赖 ID 存在，再用拓扑排序检查循环。依赖失败时，后续项应记录 `blocked`，而不是伪装成执行错误。

~~~text
task-01 success
task-02 error
task-03 depends_on task-02 -> blocked
~~~

常见错误是让列表顺序隐含依赖。顺序一旦被并行调度或重新排序，语义就消失；稳定 ID 和显式依赖才可恢复。

## A03 共享状态与局部失败

### failed_items 参考实现

~~~python
def failed_items(state: ExecutionState) -> list[WorkResult]:
    return [result for result in state.results if result.status == "error"]

def test_failed_items_preserves_identity() -> None:
    state = execute_plan(create_plan(["inspect", "test", "document"]), executor)
    failed = failed_items(state)
    assert [result.item_id for result in failed] == ["task-02"]
    assert state.results[0].status == "success"
    assert state.results[2].status == "success"
~~~

测试重点不是列表推导式，而是失败仍与原计划 ID 关联，成功结果没有因中间异常被覆盖。

### blocked 与 error 的边界

`error` 表示任务实际执行并失败；`blocked` 表示因依赖未满足而没有执行。二者若合并，重试系统可能错误地执行本不该开始的任务，也无法区分根因和连带影响。

对于有副作用的任务，应增加幂等键，例如 `run_id + item_id + operation_version`。重试前查询该键是否已经成功写入；若操作无法幂等，则需要补偿动作或人工审批。简单捕获异常绝不能替代事务设计。

### 通信成本实验

~~~python
shared = SharedState()
for _ in range(10):
    shared.record("planner", "executor", "same context")

assert shared.message_count == 10
assert shared.communication_chars == 10 * len("same context")
~~~

消息增多不代表结果更正确。这项实验用于建立“协调也是成本”的直觉。

## A04 Reviewer 对照实验

### 增加第三个反例

~~~python
cases = [
    ReviewCase("good", "code plus tests", ("code", "tests")),
    ReviewCase("missing-tests", "code only", ("code", "tests")),
    ReviewCase("missing-code", "tests only", ("code", "tests")),
]
comparison = compare_single_and_reviewer(cases)
assert comparison.single_false_accepts == 2
assert comparison.reviewer_false_accepts == 0
assert decide_from_comparison(comparison).use_multi_agent is True
~~~

通信字符数应根据新增文本重新计算，不要复制 A04 的 83。测试只断言它大于零还不够；可以先记录旧值，再验证新增案例后成本确实增长。

### 加入误拒绝指标

要统计误拒绝，首先需要独立真值 `expected_valid`，不能再用同一个 Reviewer 推导“实际是否合格”，否则评测者和被评测者是同一套规则。

~~~python
@dataclass(frozen=True)
class LabeledReviewCase:
    candidate: str
    required_fragments: tuple[str, ...]
    expected_valid: bool
~~~

然后分别统计：实际不合格却批准为错误接受；实际合格却拒绝为误拒绝。架构决策应结合业务代价。例如自动合并代码时错误接受代价很高，可以更保守；只提供建议时，过多误拒绝可能让用户停止使用。

## 模块最终实验参考框架

1. 冻结同一批任务和单 Agent 输出。
2. 写出机器可判定或人工双盲标注的验收真值。
3. 只增加 Reviewer，不同时更换模型与 Prompt。
4. 比较错误接受、误拒绝、完成率、调用、延迟和通信量。
5. 预先写明保留阈值与回退条件。
6. 结果不达标时删除 Reviewer，并保留实验记录。

最成熟的结论不一定是“多 Agent 胜出”。如果确定性测试 Tool 能以更低成本发现相同缺陷，应该优先增强单 Agent。多 Agent 只有在角色边界带来可重复、可归因的净收益时才值得进入作品架构。
