# Sprint 1 - Lesson 9 学习整理

## 本节定位

到上一节为止，我们已经完成了 Sprint 1 里非常关键的一步：

> 最小测试

现在项目已经不再只是“能跑一次”的 demo，而是开始具备：

- 运行时对象
- 多 Tool
- 最小测试

这时候，下一个最自然、也最工程化的问题就来了：

> 如果失败了怎么办？

也就是说，这一节要补上的不是新功能，而是：

> 错误处理初版

从这一节开始，项目会第一次从“快乐路径可运行”升级到“出现异常时仍有边界”的阶段。

---

## 本节目标

这一节不追求一步把所有容错系统做全。

真正目标只有一个：

> 给当前最小 Agent 加上第一层失败边界

这一节建议优先覆盖三类失败：

1. Tool 执行失败
2. LLM 调用失败
3. 未知 Tool / 参数异常

也就是说，要让系统从：

```text
出错就直接崩
```

变成：

```text
出错后知道在哪一层拦住，并给出最小可解释反馈
```

---

## 本节核心知识点

### 1. Agent 系统比普通脚本更容易出现“链式失败”

普通脚本出错，通常是某个函数报错就结束。

但 Agent 不一样，因为它是一个链路系统：

```text
Runner
↓
LLM
↓
ToolManager
↓
Session
↓
LLM
```

所以一旦某一层出问题，很容易导致：

- Tool 没执行成功
- Tool Result 没写回
- Runner 不知道该不该继续
- LLM 下一轮上下文断裂

也就是说，Agent 系统的失败往往不是单点失败，而是：

> 链式失败

所以错误处理必须尽早建立边界。

---

### 2. 当前阶段最重要的不是 Retry，而是“先知道在哪拦”

很多人一提到错误处理，第一反应就是：

- 自动重试
- fallback
- 重跑

这些以后都重要，但在当前阶段，优先级更高的是：

> 先知道错误应该在哪一层被拦住

例如：

#### Tool 相关错误

应该优先在：

```text
ToolManager
```

这一层处理。

#### 模型调用错误

应该优先在：

```text
OpenAILLM / Runner
```

这一层处理。

#### 上下文状态错误

应该优先在：

```text
Session / Runner
```

这一层处理。

所以这一节真正训练的是：

> 错误边界意识

而不是“把异常都 try/except 一把包掉”。

---

### 3. 错误处理的第一版目标不是隐藏错误，而是让错误可解释

初学者常见误区是：

> 只要程序别报错就行

于是开始写一堆：

```python
try:
    ...
except:
    pass
```

这其实是非常糟糕的方向。

因为对于 Agent 项目来说，当前阶段更重要的是：

- 知道是哪里失败了
- 知道失败时上下文停在什么位置
- 知道是 Tool 问题、LLM 问题还是消息问题

所以第一版错误处理的目标不应该是“静默吞掉异常”，而应该是：

> 让失败变得可解释

这会直接影响你后面做：

- 日志
- tracing
- retry
- checkpoint

---

## 本节推荐的最小错误边界

这一节建议先明确三层边界。

### 边界 1：ToolManager.execute

这里应该拦住：

- Tool 不存在
- 参数不匹配
- Tool 本身执行报错

这一层建议至少做两件事：

1. 抛出明确异常或返回明确错误结果
2. 不让 Runner 直接面对杂乱的底层函数错误

### 边界 2：OpenAILLM.generate

这里应该拦住：

- API Key 缺失
- 请求失败
- provider 调用异常

这一层的作用是：

> 把模型供应商错误留在模型抽象层附近

不要让底层 SDK 细节直接泄漏到 Agent 层。

### 边界 3：Runner.run

这里不应该吞掉所有错误，但应该负责：

- 决定当前运行是否终止
- 决定用户看到什么最小反馈
- 保证主循环不会在未知状态下继续乱跑

Runner 更像是：

> 最终运行边界控制层

---

## 本节推荐的最小策略

当前阶段不需要上复杂恢复策略。

最小正确策略就够了：

### 1. Tool 执行失败时

- 记录失败原因
- 停止当前轮次
- 返回清晰错误信息

### 2. LLM 调用失败时

- 终止当前运行
- 返回“模型调用失败”的清晰反馈

### 3. 未知 Tool 时

- 不继续盲目 Loop
- 明确提示“工具不存在或未注册”

这一版先建立：

> 错误不能 silently continue

就已经足够有价值。

## 这一节和测试的关系

上一节我们刚刚引入了最小测试。

这一节其实是测试思路的自然延伸，因为：

一旦有错误处理，就意味着你应该开始测试：

- 错误能不能被正确抛出
- 错误会不会被错误吞掉
- Runner 出错时会不会继续进入错误状态

所以这一节结束后，下一轮测试通常会开始增加：

- Tool 失败测试
- 未知 Tool 测试
- FakeLLM 抛异常测试

这就是工程系统逐步成熟的路径。

## Code Review 视角

### 不推荐的写法

```python
try:
    ...
except:
    pass
```

问题在于：

- 吃掉了错误
- 丢失了问题定位信息
- 让系统在未知状态下继续运行

这会让后续调试非常痛苦。

### 更推荐的写法

```python
try:
    ...
except SpecificError as e:
    return clear_error_message
```

或者：

```python
raise ToolExecutionError(...)
```

重点不是语法，而是：

> 失败要被边界化、语义化，而不是被静默吞掉

## 官方框架怎么做

成熟框架在错误处理上一般都会逐层做：

- Tool 层：统一 Tool 执行异常
- Model 层：统一 Provider 异常
- Runner 层：统一运行时终止策略
- Tracing / Logging 层：统一记录错误轨迹

这和前面一直讲的架构思想是一致的：

> 错误处理也必须按职责分层

而不是在某个顶层大 `try/except` 里一把全吃掉。

---

## 本节最重要的一句话

> 错误处理的第一步不是“让错误消失”，而是“让错误在正确的边界上被看见”。

这就是这一节最重要的工程意识。
