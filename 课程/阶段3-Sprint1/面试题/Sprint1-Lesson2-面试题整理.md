# Sprint 1 - Lesson 2 面试题整理

## 题目 1

**问题：** 为什么要先定义 `BaseLLM` 抽象类，而不是直接在 Runner 里写 OpenAI 调用？

**参考答案：** 因为 Runner 需要依赖的是“生成响应”这项稳定能力，而不是某家具体供应商的 SDK 细节。先定义 `BaseLLM`，可以把 OpenAI、Claude、Gemini、Qwen 等实现都放在统一接口之后，让上层系统只依赖抽象，不依赖具体实现。这既符合依赖倒置原则，也为后续模型替换、多模型支持和测试 Mock 提供了良好边界。

**追问方向：** 如果未来要同时支持多家模型，这种抽象会如何降低重构成本？

**易错点：** 觉得现在只用 OpenAI，所以暂时不需要抽象层。

## 题目 2

**问题：** 为什么 `OpenAILLM` 应该实现 `BaseLLM.generate()`，而不是让 Runner 直接知道 `responses.create()`？

**参考答案：** 因为 `responses.create()` 属于 OpenAI SDK 的底层实现细节，而 Runner 的职责是组织运行流程，不应该感知某家模型 SDK 的具体调用方式。把这些细节收敛到 `OpenAILLM.generate()` 中，可以让 Runner 保持稳定，只依赖统一接口，避免运行时层和供应商实现层耦合在一起。

**追问方向：** 如果把 OpenAI 细节暴露给 Runner，后续在代码维护上会有什么问题？

**易错点：** 把“能跑”当成唯一标准，忽略模块边界。

## 题目 3

**问题：** 为什么这一节要把 `Agent` 从保存 `model` 改成保存 `llm`？

**参考答案：** 因为字符串形式的 `model` 只能表示某个模型名称，但不能表达完整的模型能力抽象。保存 `llm` 对象意味着 Agent 依赖的是一个真正可调用的 LLM 能力接口，而不是某个写死的供应商配置。这样 Agent 就可以持有 `OpenAILLM`、`ClaudeLLM` 等不同实现，而无需改动自身结构，扩展性更强。

**追问方向：** 如果 Agent 继续只保存 `model="gpt-5"`，后续会在哪些地方受限？

**易错点：** 以为把字符串模型名换成对象只是语法变化，没有看到抽象层升级。

## 题目 4

**问题：** 为什么这一节虽然还没接 Tool，却依然是整个项目的重要里程碑？

**参考答案：** 因为在接 Tool 之前，必须先确认最基本的“Runner -> LLM -> Responses API”调用链路是正确的。如果这一层没有稳定打通，后面无论 Tool Calling、Loop、Memory 还是 Session 都没有可靠基础。这一节完成的是整个 Agent 系统最底层的运行依赖验证，所以它是后续所有能力扩展的前提。

**追问方向：** 为什么先分层打通链路，比一开始把 Tool 也一起塞进来更稳？

**易错点：** 低估“先只跑通最小链路”的工程价值。

## 题目 5

**问题：** 从 Code Review 角度看，为什么 `Agent.run()` 里直接 new `OpenAI()` 是一个坏味道？

**参考答案：** 因为这样会让 Agent 直接依赖某个具体 SDK，实现层次混乱。Agent 本应是配置层，却同时承担了运行逻辑和模型访问职责，导致高耦合、低内聚。一旦底层模型供应商变化，Agent 本体就必须跟着改，破坏了可维护性和扩展性。这是典型的职责边界失守。

**追问方向：** 如果看到这种代码，你作为 Reviewer 会建议怎样重构？

**易错点：** 只看结果能不能跑通，不看设计是否可演进。

## 题目 6

**问题：** 为什么这一节可以看作“第一个真正运行的 Agent 雏形”？

**参考答案：** 因为从这一节开始，项目已经具备了最基本的真实运行链路：创建 LLM 实例、注入 Agent、由 Runner 驱动调用模型，并拿到真实 `response.output_text` 输出。这说明系统已经不是纯骨架或伪代码，而是开始拥有真实运行能力。虽然还没有 Tool Loop，但最小运行时已经成立，因此可以视为第一个真正可运行的 Agent 雏形。

**追问方向：** 从“能调模型”到“能做 Tool Calling”，中间还差哪一层关键能力？

**易错点：** 认为只有接上 Tool 才算真正进入开发阶段。
