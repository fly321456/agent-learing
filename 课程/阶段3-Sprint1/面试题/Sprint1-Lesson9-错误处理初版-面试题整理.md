# Sprint 1 - Lesson 9 面试题整理

## 题目 1

**问题：** 为什么 Agent 系统比普通脚本更早需要系统化的错误处理？

**参考答案：** 因为 Agent 系统不是单函数执行，而是由 Runner、LLM、ToolManager、Session 等多个运行时对象协同组成的链路。一旦某一层失败，影响往往会向后传播，形成链式失败，例如 Tool 没执行成功、结果没回填、Loop 状态混乱等。所以 Agent 系统的错误处理不能只靠末端报错，而需要尽早建立分层边界。

**追问方向：** 什么叫链式失败，它在 Agent 项目里最常见的表现是什么？

**易错点：** 把 Agent 出错理解成和普通脚本一样的“单点异常”。

## 题目 2

**问题：** 为什么当前阶段错误处理的重点不是 Retry，而是先明确错误边界？

**参考答案：** 因为在系统还没有稳定之前，最重要的是知道错误应该在哪一层被发现、被解释和被终止。如果连错误边界都不清楚，就急着做重试，只会把问题重复执行多次，甚至隐藏真正原因。当前阶段更重要的是让 Tool 错误留在 ToolManager、模型调用错误留在 LLM 抽象层、运行终止策略留在 Runner，这样系统才具备清晰的分层控制。

**追问方向：** 如果错误边界不清，直接上 Retry，后果通常是什么？

**易错点：** 觉得“自动重试”天然就是更高级的错误处理。

## 题目 3

**问题：** 为什么 Tool 相关错误应该优先在 ToolManager 层处理？

**参考答案：** 因为 ToolManager 本身就负责工具注册、查找和执行，它最了解工具相关失败属于什么类型，例如未注册 Tool、参数不匹配或工具函数内部执行异常。如果把这些错误直接泄漏到 Runner，Runner 就会被迫知道工具系统细节，职责边界被破坏。把 Tool 错误留在 ToolManager 处理，更符合单一职责和低耦合设计。

**追问方向：** ToolManager 处理错误时，最少应该向上层暴露哪些信息？

**易错点：** 认为只要最终能报错，在哪层处理都无所谓。

## 题目 4

**问题：** 为什么 `except: pass` 在 Agent 项目里是非常危险的写法？

**参考答案：** 因为它会直接吞掉异常，导致错误来源、运行位置和当前状态全部丢失。对于 Agent 这种运行时链路系统来说，一旦错误被静默吞掉，系统可能继续在坏状态下 Loop，结果比直接崩溃更难排查。Agent 项目的第一版错误处理应该追求“让错误可解释”，而不是“让错误看起来没发生”。

**追问方向：** 如果真的不想让程序直接崩溃，正确做法应该是什么？

**易错点：** 把“程序没崩”误解成“错误处理做得好”。

## 题目 5

**问题：** Runner 在错误处理里更合适承担什么职责？

**参考答案：** Runner 不应该负责理解所有底层错误细节，但应该负责最终的运行边界控制，例如遇到错误时是否停止、返回什么最小反馈、是否允许继续下一轮 Loop。也就是说，ToolManager 和 LLM 层负责就近解释错误，Runner 负责决定“这次运行还能不能继续”。它更像运行时终止策略的控制层。

**追问方向：** 如果 Runner 同时负责所有错误细节解释，会出现什么架构问题？

**易错点：** 把 Runner 理解成“异常总收口处”，结果把所有错误逻辑都堆进去。

## 题目 6

**问题：** 为什么说错误处理的第一步不是“让错误消失”，而是“让错误在正确边界上被看见”？

**参考答案：** 因为工程系统中的错误本来就是系统行为的一部分，不能靠掩盖来解决。只有先让错误在正确层级被识别、记录和语义化，后面才有可能做重试、恢复、Tracing、日志分析和 Checkpoint 设计。如果一开始就把错误吞掉，系统会失去可观察性，也失去后续工程演进的基础。因此第一步必须是让错误清晰、可见、可定位。

**追问方向：** 这个原则会如何影响后续日志与 tracing 系统设计？

**易错点：** 把错误处理理解成“尽量别让用户看到报错”，而不是“让系统保留足够的错误信息”。
